Sharding reference

Where to look a thing up: the routes of a tenant node and of the router, the router's flags, what each quota bounds, the tokens, a lease's timings, the statuses a client meets, and what the deploy kit holds. The steps are in the tutorial and the guides it lists.

The node: fenec-server --dir

A node is one fenec-server serving a directory of tenant files instead of one file. The path names the tenant: /t/acme/ is acme.fenec.

fenec-server --dir /data/n1 --http 127.0.0.1:8081 --admin-token a1
curl -X POST 127.0.0.1:8081/t/acme/query -d '{"query": "get notes limit 5"}'
  • Opened on first use, closed when idle (--idle-close, 300 s by default).
  • Unknown tenants are 404. A request never creates one.
  • /_admin/ is how the router drives the node; it needs --admin-token.
  • A user's token is bound to its tenant. A JSON Web Token reaches /t/acme/ only when its tenant claim names acme (Tokens).
  • Archived as a whole by fenec archive --tenants, one connection for every tenant (Archiving a node).
Details

--dir serves a directory of <tenant>.fenec files instead of one file. It is still one process per directory — the single-writer rule is per file, and one process owning all of them is what keeps it. --http is required. The tenant is looked up for every request — so one created a moment ago is there, one closed as idle reopens, one deleted meanwhile answers 404, and one frozen for a move refuses writes while its reads go on.

  • Opened on first use. Open cost is proportional to the file, so a node does not spend its start-up on tenants nobody asks for. A tenant that has not been created is 404 — a request never brings one into being, or a typo would make an empty database.
  • Closed when idle. --idle-close <s> (default 300) syncs, checkpoints when there is a vector index, and closes a tenant nothing has touched for that long. One with an open request or subscription is never closed.
  • --max-memory covers the open tenants together. Opening one more over the ceiling first closes idle tenants, least recently used first. With everything busy the open goes ahead anyway: refusing a read because other tenants are busy would turn a memory warning into an outage. A write that grows a tenant is refused once that tenant alone is past the ceiling, over either listener.
  • Shutdown syncs every open tenant and checkpoints the ones with a graph, holding their write locks until exit.

The router drives the node through /_admin/, which answers only to --admin-token and is off (404) without it — a client allowed to read and write a tenant must not be able to delete it or take another tenant's image:

An image is replayed in memory before it is written, so a truncated transfer is refused rather than installed, and the file appears by rename, never half-written. Tenant names are [a-z0-9_-], 1 to 64 characters: they become file names, and that set means the same thing on every file system.

The router: fenec-shard

The router looks up which node holds a tenant and passes the request there unchanged. Its only state is a small directory of nodes and tenants, managed under /_shard/.

  • New tenants go to the node with the least data on disk — in the region you name, if you name one (Regions) — unless you name the node.
  • A page on another origin needs --http-cors on the router, as it would on a node: fenec-shard --http-cors https://app.example.
Details

Its only state is the directory: two collections in a fenecdb file of its own, nodes and tenants. Every change is written and synced before it takes effect, and a tenant's node and state change in one statement, so there is no moment on disk where a tenant belongs to both nodes or to neither. The node admin tokens stay in it; GET /_shard/nodes does not return them.

RouteDoes
GET /_shard/nodesname, address, region and zone of each node
PUT /_shard/nodes/<n>{addr, token, region, zone}; checked against the node before it is recorded; a region or zone left out is the one recorded
DELETE /_shard/nodes/<n>refused while the node holds a tenant
GET /_shard/tenantsname, node, state and region of each tenant; with ?bytes, its bytes on disk, asked of each node; with ?region=<r>, one region's
GET /_shard/tenants/<t>one tenant: its node, state, region and zone, and the node holding its copy
PUT /_shard/tenants/<t>place and create; {region} to place it in a region, {node} to choose the node, otherwise the node with the fewest bytes on disk; {schema}, FenecQL create collection text, applied there before the tenant is answered (A tenant with its schema)
DELETE /_shard/tenants/<t>delete on the node, then forget
POST /_shard/tenants/<t>/move{to}, {region} or both; see Moving a tenant and Regions
POST /_shard/queryone read on every tenant, or those named, the answers merged as the request says (A query across tenants)
GET /_metricswhat the router answered and forwarded, the nodes' time and the ones it could not reach, and its moves, in Prometheus's text format (Monitoring)

Placement goes by disk rather than memory: memory counts only the open tenants, and which ones are open depends on who asked last.

A page on another origin — an app, the sync layer, FenecHttp.live, the studio served by a node — reaches its tenants through the router once the router has --http-cors <origin>, read as fenec-server reads it (Security): * or one origin. The router answers a browser's preflight itself, before it looks the tenant up, and puts the CORS headers on every answer it gives. Its own — an unknown tenant's 404, a standby's 503, an unreachable node's 502, the 503 past --max-connections or at its thread limit (marked Fenec-Unserved: the request never ran, so the global entry and a relaying router ask the region's next router), the 401 of /_shard/ without its token — reach the page as the refusals they are; without the headers a browser hands the page a network error for each, and the sync layer backs off from what was an answer. On a node's answer the router's headers take the place of the node's, so the page is told the rule the router's preflight told it, and never two Access-Control-Allow-Origins, which a browser refuses whole. The 503s carry their wait as Retry-After and as retry_after in the body, as a quota's refusal does. Without the flag the router sends none of its own and passes a node's through as the node wrote them, and a preflight goes to the node.

Quotas: what each bounds and what a refusal says

The quotas of a tenant: what each one bounds, and what a write past it is answered.

QuotaBoundsPast it
bytesthe tenant's file, as written507, the write put back whole
rowsthe documents of its collections, together507, the write put back whole
streamssubscriptions, /_changes waits and Fenec-After waits while they wait: a read after a write the node holds takes none429, Retry-After: 1
heldwrites held until they can write (Fenec-Wait): workers waiting for jobs429, Retry-After: 1
requestsrequests in flight429, Retry-After: 1
writesrows written a second, charged as each write lands429, retry_after_ms until a row's worth is back
write_bytesbytes written a second, charged as each lands429, Retry-After until the debt is paid

A refusal names its quota in the body and in a header, and every SDK's error carries it typed (quota, retryAfter). A 429 says its wait twice: in whole seconds, rounded up, in Retry-After and retry_after, as HTTP has it, and to the millisecond in retry_after_ms, which every SDK and a replica's sync read first -- a bucket of 600 rows a second refills a row in 1.7 ms, and fifty couriers told to come back in a second waited fifty seconds between them:

HTTP/1.1 429 Too Many Requests
Fenec-Quota: writes
Retry-After: 1

{"error":"the tenant writes past its quota of 600 rows a second","quota":"writes","retry_after":1,"retry_after_ms":2}
HTTP/1.1 507 Insufficient Storage
Fenec-Quota: rows

{"error":"the write would take the tenant past its quota of 50000 rows: delete rows, or raise the quota","quota":"rows"}
  • A write that writes nothing costs nothing. writes counts the rows of the tenant's collections a write landed -- a put of ten rows ten, a claim that took no job, a require unmet or a held claim looking none -- and lets a write through while the bucket holds a row's worth, so one of many rows goes through and the next waits out the debt. Charged as a write started, 45 claims held at once by a fleet on a small plan were refused for writes before any for being held. A held claim the rate refuses as it is to run stays held, and runs once a row's worth is back. The node's own landings -- the sweep of rows past their @ttl, a compact -- are not the tenant's rate.
  • A tenant waits in a share of the node. Every stream and every held write is a connection and its thread, and a node's --max-connections is what all its tenants share: --http-max-streams counts each tenant's own subscriptions, and nothing counted a tenant's held writes, so a hundred workers of one tenant waiting for jobs took every connection of a default node and its neighbours were answered 503. Where the node sets neither --tenant-max-streams nor --tenant-max-held, each is a quarter of --max-connections -- 25 of a default node's 100 -- so no one tenant's dashboards and workers hold more than half; a node serving a fleet raises --max-connections (each is about 50 KB of memory) and sets its plans' quotas.
  • Deletes always land. A write that only takes away — a del, a drop — is never refused, and neither is a compact, which gives bytes back. A tenant at its quota deletes its way under it.
  • A replica's sync knows them. A synced write a 507 refuses is put back on the replica and the app told, the quota named, and the writes behind it -- a delete that makes the room among them -- go on; a 429 is waited out for its Retry-After, as a move's 503 is (Sync).
  • A full file is compacted by the node once an eighth of its quota is dead, where a file of its own waits for 64 MB: deleted rows become room without the tenant running compact itself.
  • Never passed by a write that adds. Bytes and rows are asked as the write lands, its record built, under the write lock: writers at once cannot take the file a byte past its quota, nor the rows one past theirs.
  • It goes with the tenant. The router keeps each tenant's quota in its directory and sends it to the tenant's node, its standby and its replica; a move sends it to the target before the directory points there, and a failover finds it on the copy it promotes.
  • Seen by quota, not by tenant: /_metrics counts refusals as fenec_quota_refused_total{quota="rows"}, the audit log writes each as a quota event naming the tenant, and GET /_admin/quotas on a node — or /_shard/tenants?quota on the router, which the studio's admin view shows — lists every tenant's usage against its quota.

Tokens

There are three tokens: one for data, one per node for the router, and one for managing the router. A user's JSON Web Token is bound to the tenant its tenant claim names:

fenec-server --dir /data/n1 --http 127.0.0.1:8081 --admin-token a1 \
         --jwt-secret-file jwt.secret --policy policy.txt
fenec-server --jwt-secret-file jwt.secret --mint-token '{"sub":"alice","tenant":"acme"}'
Details

Three, each for a different job. Data requests carry whatever the nodes' --http-token expects, and the router passes Authorization through untouched. Each node has its own --admin-token, which only the router holds. The router's --token guards /_shard/; like the nodes, it refuses to listen on a non-loopback address without one unless given --insecure.

With --jwt-secret or --jwt-keys a node also takes JSON Web Tokens held to its --policy, and the policy is the node's, not a tenant's: notes read,write where owner = $jwt.sub matches alice's rows in every tenant's file alike. So on a --dir node a token reaches /t/<t>/ only when its tenant claim names <t>, a text or a list holding it, and is refused with 403 elsewhere: on every route under the prefix, the statements, REST, /batch, a subscription, /_changes, /_schema and the statement counts. The check comes before the tenant is looked up, so a refused token learns nothing of which tenants exist. A token naming no tenant is refused on a --dir node unless it is started with --jwt-unbound-tenants, which takes such a token for every tenant it serves; --jwt-tenant-claim <name> reads another claim than tenant. The node's own --http-token and --admin-token are not bound. The router forwards Authorization as it came and holds no keys, so the node is what enforces it, behind the router or reached directly. What a scoped token writes to a tenant is checked against its rules as on a single file (Scoped access).

Every token is also read from the environment, which keeps it off a command line every user of the machine reads with ps: a node's from FENEC_HTTP_TOKEN, FENEC_ADMIN_TOKEN and FENEC_REPLICATION_TOKEN, a router's from FENEC_SHARD_TOKEN, FENEC_SHARD_REPLICATION_TOKEN and FENEC_SHARD_ENTRY_TOKEN, an archiver's from FENEC_REPLICATION_TOKEN. A variable set and empty, as an environment file leaves a line it does not use, is no token; a token given empty as a flag is refused at the start. A request carrying no Authorization reads as the empty token, so an empty FENEC_SHARD_TOKEN, taken for one, let anyone into /_shard/ -- and past the check that keeps a router with no token off a public address. The kit's systemd units hand every one over from an environment file (Deploying it).

Lease timings

What happens when, in fractions of the lease (--auto-failover <s>), and what a lease of 5 seconds comes to. How a lease holds, and why, is under Leases in the design.

WhatWhen
The router renews a node's leaseas it starts, then every third of the lease while the node answers (The lease and the failover)
The router fails a node overonce the node has gone a tenth past its lease unrenewed
A node cut off from the router, whose clients still reach it, stops writingtwo thirds of a lease after its last renewal at the most: its lease runs from the grant before that one (Automatic failover)
A lost node's tenants cannot be writtenfor 5.5 to 7.2 s, with a 5-second lease
What the router has out to a node it failed over is answeredat the failover, not at --upstream-timeout (Requests out to a node failed over)
A write a standby router sent on before the leading router's grant reached the new primary is asked againfor two thirds of a lease or --upstream-timeout, whichever is sooner, and only while its client is still there
A write sent with no Idempotency-Key and answered 500 with "outcome": "unknown" is read backa lease and a tenth (--auto-failover × 1.1) after the answer, and not before; one sent with a key is sent again with the same key, which the node refuses while its lease has lapsed and answers once the tenant settles (A write answered after the lease lapsed)

Refusals and their statuses

The statuses a client meets from the router and the nodes, and where each is explained. A refusal's body says why; a 503 or a 429 says when to come back, as Retry-After and as retry_after in the body.

401A request to the router's /_shard/ without its --token, a user's token or a node's data token included (A query across tenants); a node's /_admin/ asked without its --admin-token; where the node was started with none, /_admin/ is off and answers 404 (The node)
403A token whose tenant claim does not name the tenant under /t/<tenant>/ (Tokens); a statement that writes, in a query across tenants, which every node refuses before it runs; a write sent marked as a read, Fenec-Read: replica (Read replicas)
404A tenant the router's directory, or a node, does not hold: a request never creates one (The node); at the global entry, every path but /t/<tenant>/... and, where the entry is told to, /_shard/ (One URL for every region); a node named as another's standby that the router does not know (Get started)

Deploying it

The repository's deploy/ is a kit for running everything on these pages on machines of your own: systemd units, their environment files, alert rules, and the operator's runbook. make drill breaks a deployment of two regions on purpose, in Docker, and holds it to losing no acknowledged write.

make deploy-check   # the units under a real systemd, the alert rules under promtool
make drill          # two regions: a node killed and back, a router killed, the global router cut off, a restore
  • A unit for each part: a tenant node, a region's router and its standby, the global router and its standby, a node's archiver and its copy to a bucket (rclone), and the Cloudflare Tunnel the global entry reaches a router through. Each runs sandboxed as its role's user -- a node, the routers, the archiver and the bucket copy each their own, so none reads another's tokens -- its tokens in an environment file only root reads. The tunnel lets a tenant's paths alone through, and Cloudflare Access with a service token the entry holds says who; the entry passes no cookie Access sets on to its clients, and the routers no Access header on to a node. The bucket copy refuses a new disk's first copy over the bucket's archive.
  • Alerts for Prometheus and for Grafana: nodes and routers down, a region's primary router told from a standby, failovers and late leases, tenants without a replica, copies in their primary's zone, read replicas given up, connections near their ceiling, the bucket copy gone stale or unreadable by node_exporter, quota refusals, the entry's marks not believed, refusals and errors.
  • The drill's figures, lease 2 s, three runs on one laptop -- what they saw, not bounds: a node cut off the network and killed, as a machine lost, was failed over 1.9 to 2.6 s after the kill, the other tenants of its region never more than 18 ms between two answered writes, none of 41 577 acknowledged writes was lost, and a tenant restored from its node's archive held exactly the rows acknowledged by the moment it was restored to.
Details

make deploy-check boots systemd in two privileged containers, installs every unit and environment file as the runbook installs them, and runs them: systemd-analyze verify on each, a region, two nodes and a tenant made through the global router, rows written through the router and its standby, no token on any process's command line or in an environment another role's user can read, the limits and the sandbox in force (systemd-analyze security puts each unit at 1.2), a node's stop syncing within its timeout, a sealed archive verified with the key the unit hands its archiver and copied to a bucket by real rclone while its tenant is written, a real node_exporter scraped for the copy's success, a new disk's archive refused over the bucket's and copied once the bucket is copied back, and a standby router promoted and its unit switched as the runbook does it. cloudflared's own matcher is asked where the tunnel sends 28 paths, every spelling of a tenant's replication stream among them. promtool checks the alert rules and runs their tests, and a test of fenec-shard holds every metric and label value they read to a real scrape of every kind of process.

make drill runs each process in a container of its own on one Docker network -- two regions, each a router keeping its own directory and that router's standby, two nodes in two zones under --lease and --replicas, an archiver for each node, and the global router and its standby -- every token in the processes' environments and no port fixed. A writer a tenant puts rows by id, the next only once the one before was answered, while the drill cuts the global routers off the network (each region writes on), cuts the node holding the most primaries off the network and kills it, as a machine lost, and starts it again, kills a region's router and promotes its standby as an operator would, and marks a moment it later restores a tenant to from its node's archive. Then every acknowledged write is read back from each tenant's primary and its replica, and the times are printed. The router fails a killed node over a lease and a tenth after its last renewal and the promotions after: 1.92, 2.56 and 1.90 s after the kill in three runs at a lease of 2 s. Its tenants' writers write again once the request each had in flight to the dead node is let go of, at the router's upstream timeout -- 4 s in the drill, twice its lease, as the kit's routers run at twice theirs: 3.90, 3.97 and 3.93 s. The tenants whose replica it held went 17, 18 and 17 ms between two answered writes at most, the rest 16, 18 and 17; a reviewer's runs on another machine saw 28-30 ms, so these are what three runs saw, not bounds. The runbook says what each alert means, the order to bring a deployment up in, how to rotate each token and upgrade with no downtime, and what is not measured yet.
