Serverless and Cloudflare

Run fenecdb inside a Cloudflare Worker, with one small database for each Durable Object.

Two ways to use it

Either the engine runs inside the function, one database per Durable Object, or the function sends its queries to a fenec-server server. Inside is faster; a server holds more data and more writers.

Details

The browser module runs wherever V8 runs a WebAssembly module, a Cloudflare Worker among them. A Durable Object gives it what a file gives a server: one writer, and storage that outlives the process. So one object holds one database, as a tenant is one file on a fenec-server node.

The second needs nothing new: Fenec.connect(url), the Python Client or fetch, and a function's connections are HTTP requests, so there is no pool to exhaust. The rest of this page is the first.

A database a Durable Object

The object opens the engine on its first request, restores its database from storage, and saves after every write, before it answers.

import { DurableObject } from 'cloudflare:workers';
import { Fenec } from '@fenecdb/web';
import { checkpoint, persist, restore } from '@fenecdb/cloudflare';
import wasm from '@fenecdb/web/fenec.wasm';

interface Env {
  TENANT: DurableObjectNamespace<Tenant>;
}

export class Tenant extends DurableObject<Env> {
  #db: Promise<Fenec> | null = null;
  #alarm = false;

  #open(): Promise<Fenec> {
    // Once, with every other event held back while it restores.
    return (this.#db ??= this.ctx.blockConcurrencyWhile(async () => {
      const db = await Fenec.open(wasm);         // the module as the Worker imports it
      await restore(db, this.ctx.storage);
      return db;
    }));
  }

  async query(sql: string, params: unknown[]): Promise<unknown> {
    const opened = this.#open();
    const db = await opened;
    try {
      return db.run(sql, params);
    } finally {
      let wrote = 0;
      try {
        wrote = await persist(db, this.ctx.storage); // durable before the answer goes
      } catch (e) {
        if (this.#db === opened) this.#db = null;   // the next request restores
        throw e;
      }
      if (wrote > 0 && !this.#alarm) {
        this.#alarm = true;                          // an alarm is a row written too
        await this.ctx.storage.setAlarm(Date.now() + 5_000);
      }
    }
  }

  async alarm() {
    this.#alarm = false;
    await checkpoint(await this.#open(), this.ctx.storage);
  }
}

export default {
  async fetch(req, env) {
    const tenant = env.TENANT.get(env.TENANT.idFromName('acme'));
    const { sql, params } = await req.json<{ sql: string; params: unknown[] }>();
    return Response.json(await tenant.query(sql, params));
  },
} satisfies ExportedHandler<Env>;
Details

A Worker imports a .wasm file compiled, and cannot compile bytes at run time; Fenec.open takes the module so. The open and the restore run inside blockConcurrencyWhile, once: opened by whichever request found the object cold, two requests could each restore an engine of their own and append to the storage as if alone. persist runs in a finally, since a statement that failed may follow ones in the same text that wrote. A persist that fails leaves the database in memory holding writes its storage never took, so the object lets it go and the next request restores what storage holds, rather than answer from writes nobody kept. integrations/cloudflare/example is this Worker with a tenant from the path, POST /t/<tenant>/query, and its test runs it under wrangler dev — workerd, as Cloudflare runs it — then stops and starts it over the same storage and reads the rows, a near's answer and each tenant's own database back, and sends a cold object 32 writes at once.

What the storage holds

persist saves a full image once, then only the new writes: one row each in a SQLite-backed object's storage, which bills by the row written. If storage stops part way through, the last whole database is still there.

Details

persist keeps what a file would hold: an image the first time, then only the writes since the last call — the engine's journal, as persist in the browser takes it for IndexedDB — until they outgrow half the image and 64 KiB, and a new image replaces them.

A SQLite-backed object — the only kind a new account makes — has ctx.storage.sql, and the database is a table a generation, fenec:1, fenec:2 and on (the key, then the generation): the image's rows, cut under the 2 MB a row takes, then a row each time writes are stored. Nothing names where the database stands beside the rows: the table there is says it, so a write is the one row. A new image is written, and the table before it dropped, in one transactionSync: workerd counts a table made as two rows written and a table dropped as none, where a DELETE of the rows before counts each, and storage that stops part way holds the generation before, whole. The rows are an INTEGER PRIMARY KEY table with no other index, since an index is a row written more.

A write goes out at once, unless the one before it is still on its way to being durable (storage.sync()): then it waits for that, and every request whose writes land meanwhile — a Durable Object takes the next request in while one waits — goes out with it, in one row. Each persist resolves only once its own writes are durable, and a read that may have seen writes on their way waits for them, so no answer leaves before what it shows is kept, and a lone write answers as soon as before: 2.0 to 2.3 ms p50 against 2.4 to 3.1. Waiting a turn of the event loop instead, for requests to land, cost a lone write 1.7 to 2.4 ms more. The figures above are make cloudflare-bench's, under wrangler dev with every storage call counted: a write before was a value, a record naming it and an alarm set again, and a checkpoint a value each 128 KiB of the image and a delete each of the values before.

A key-value backed object, made before SQLite with new_classes, has no sql; there the image and the writes are cut into values under its 128 KiB, every image goes under a generation of its own, and the record naming the whole one is written last. A test stops either kind of storage after every number of operations, an image's, an append's and a compact's, and restores the last whole database each time; and a write that fails fails every write that went out with it.

A database kept by an earlier version on a SQLite-backed object is in values, which restore no longer reads there. To move one, restore it through the key-value methods alone — an object holding get, put, delete and list of ctx.storage and no sql — and persist through ctx.storage.

A cold start

After an eviction or a deploy, the first request has to load the database again: tens of milliseconds for 10 000 rows, under 200 for 50 000. A checkpoint from an alarm after the writes folds them into a new image, for fewer rows to read and no vectors to link.

Details

An object evicted, or a deploy, starts the next request with no database in memory: the module instantiated, the image and the writes after it read out of storage and loaded. The graphs the image holds are restored as they were; the writes after it are applied as the write path would, their vectors linked into the graph one after another — the browser module has one thread. The first near after a restart, against the ones after it, under wrangler dev on an M1 (make cloudflare-bench, median of five restarts; rows of a text, an int and a 128-dim vector, 1 000 a request, each kept before it was answered, no alarm) are in the table above; a second run was within 2 ms of each.

Linking the writes after the image is no longer what a start waits for: when this page was first written it took the first near over 10 000 rows to 792 ms and over 50 000 to 1 455, and the same measurement on today's module gives 39 and 175, so a checkpoint takes 50 000 rows from 175 ms to 157, 10 000 none quicker, and is mostly worth the rows it folds. The rows are read into the module a row at a time rather than joined first: 50 000 rows as written started in 175 ms against 186 to 196, after a checkpoint 157 against 168 to 171. A request's round trip through wrangler dev is in every figure. The rows went in at 5 200 to 15 000 a second, a request of 1 000 at a time with its vectors linked and kept before the answer.

The alarm is set once a write lands and none is set, not again by each write: setAlarm is a row written too, which made every write before this change cost three. It checkpoints only once the writes since the image reach 64 KiB ({min}): written again for a few writes, a 27.6 MB image was 16 rows for one.

Limits

An object holds about 60 000 rows of 128 dimensions, or 12 000 of 768. For more, use a fenec-server server or spread a tenant over more objects.

  • One writer an object. Writes to one tenant go one after another, as on a server; tenants write side by side.
  • Bundle collation data. Collation data for scripts the module does not carry is fetched from a URL by default; in a Worker, pass {collation: name => ...} to Fenec.open and hand the chunks from your bundle.
  • Install it from npm. npm install @fenecdb/cloudflare @fenecdb/web; both are published with each release.

A WebAssembly memory grows and never gives back, so an object holds the most it ever held. The module keeps an index's vectors in chunks of about a mebibyte and lets a segment of documents grow no further than the record that seals it: grown by doubling, old and new side by side, 5 000 rows of 768 written 1 000 a request held 100 MB, 58 now, and 10 000 of them 150, 84 now. A restore keeps the image it reads and the documents in it, rather than copy each out: 10 000 rows of 768 restored held 97 MB, 66 now; and it copies the rows into that image as it reads them, one at a time (loadParts): read whole, joined, then copied in, a 27.6 MB image — 50 000 rows of 128 — held 60 MB of JavaScript beside the module's 42 at its peak, and holds 4, the process 105 MB more resident against 49 to 55 (make cloudflare-bench, in Node). A checkpoint takes the image a mebibyte at a time (snapshotChunks), each chunk made as it is taken out of the documents the stores hold, not a copy of them, and let go once it is in storage: made all at once, the image stood beside the rows, and 50 000 rows of 128 went from 73 to 109 MB at it, 83 now. So an object holds about 60 000 rows of 128 dimensions and 12 000 of 768, however many a request brings; past that, a fenec-server node and Fenec.connect, or a tenant's data spread over more objects.
