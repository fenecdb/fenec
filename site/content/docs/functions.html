Functions and webhooks

There are no triggers and no stored functions in the server. Code that reacts to a write runs beside the database, and the database gives it three things to stand on: an endpoint to sit behind, a queue with leases, and a stream of every write.

That is a choice, and a plain one: the code is yours, in the language and the runtime you already deploy, and it fails and retries where you can see it. (A Rust program that embeds the engine can register write hooks and functions of its own: Embedded Rust. A fenec-server loads none.) What follows is the three ways to react, when each fits, and each one run against a real server (node functions-demo.mjs in examples/recipes, after npm install; the Worker part runs when wrangler is on the path or WRANGLER names it).

A function: a Worker that is an endpoint

A Cloudflare Worker, a Lambda or a small server in front of the database, holding a token of its own as a secret, never a person's. The Worker below takes a signup, checks what the database's rules do not, and writes the signup and the job that welcomes it in one /batch: the two land together or not at all, so no worker finds a job with no signup, and no signup goes unwelcomed.

// A function beside the data, docs/functions: a Cloudflare Worker that is an
// endpoint of its own. POST /signup checks what the database's rules cannot
// (an address that looks like one), then writes the signup and the job that
// welcomes it in ONE batch, so a worker never finds a job with no signup nor
// a signup that will never be welcomed. The Worker holds a token of its own
// (a secret: `wrangler secret put FENEC_TOKEN`), never a person's.
//
// The client's Idempotency-Key goes on to fenec-server as it is: a request
// sent again after a timeout is answered what the first was, and writes
// nothing twice.
export default {
  async fetch(request, env) {
    const { pathname } = new URL(request.url);
    if (request.method !== 'POST' || pathname !== '/signup') return new Response('not found', { status: 404 });

    const { email, name } = await request.json().catch(() => ({}));
    if (!/^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(email ?? '') || !name) {
      return Response.json({ error: 'a name and an email address' }, { status: 400 });
    }

    const lines = [
      { query: 'put signups {email: $1, name: $2}', params: [email, name] },
      // An object goes in as a parameter: inside an object literal only constants do.
      { query: 'put jobs {kind: "welcome", payload: $1, run_at: now(), attempts: 0}', params: [{ email, name }] },
    ];
    const headers = { authorization: `Bearer ${env.FENEC_TOKEN}`, 'content-type': 'application/x-ndjson' };
    const key = request.headers.get('idempotency-key');
    if (key) headers['idempotency-key'] = key;
    const res = await fetch(`${env.FENEC_URL}/batch`, { method: 'POST', headers, body: lines.map((l) => JSON.stringify(l)).join('\n') });

    if (res.status === 409) return Response.json({ error: 'already signed up' }, { status: 409 }); // @unique(email)
    if (!res.ok) return Response.json({ error: 'the database refused', status: res.status }, { status: 502 });
    return Response.json({ ok: true, replayed: res.headers.get('idempotent-replayed') === 'true' }, { status: 201 });
  },
};

  • Run under wrangler dev (workerd, as Cloudflare runs it) against a real server. The token is a line of .dev.vars there and wrangler secret put FENEC_TOKEN deployed; fenec-server is reached over HTTP like any other service, so a function holds no pool of connections to exhaust.
  • The same request, sent again (a timeout, a retry) is answered the first one's answer, replayed: true, and writes nothing twice; the key is the client's, passed on. A different request for an address already signed up reaches the @unique on email and is 409, and the batch, jobs and all, is put back.
  • An object goes in as a parameter. Inside an object literal a FenecQL statement takes constants only, so the job's payload is $1, and the parameter is the object.
  • A Worker is also where a provider's webhook is verified before anything is written, and where a token that arrives in another header (a Cloudflare Access one) can be moved into the one the server reads (Auth with your identity provider). Servers in several regions take one URL through a Worker at the front, the global entry.

Work after a write: a job queue

The job is a row, and a worker claims it with one statement that picks the oldest ready jobs and writes a lease on them; held at the server with Fenec-Wait until there is one. The queue is Job queues; the function here is the worker.

// A worker of the `jobs` collection, docs/functions: it claims the oldest
// ready jobs, each its own for a lease; the claim is held at the server until
// there is one (`wait`), so an idle worker costs nothing and a new job reaches
// it in under a millisecond. A job done is deleted; a job that fails is put
// back after a back-off; a worker that dies holds its jobs only until the
// lease lapses. Each step names the owner it was claimed by and requires its
// row, so a worker whose lease lapsed finds out (412) instead of acking
// another worker's job. (The queue itself is docs/queues.)
import { connect, expr, inc, raw } from '@fenecdb/web/client';

export async function work({ fenec, token, handlers, name = 'worker', lease = 30_000, wait = 30_000, signal, log = console.log }) {
  const jobs = connect(fenec, { token }).from('jobs');
  const me = `${name}-${Math.random().toString(36).slice(2, 6)}`;
  while (!signal?.aborted) {
    const owner = `${me}:${Date.now()}`; // a claim, not the worker: two claims of one job tell apart
    let claimed;
    try {
      claimed = await jobs.where(raw('run_at <= now()')).order('run_at').limit(10)
        .update({ owner, run_at: expr('now() + ?', lease), attempts: inc(1) }, { returning: true, wait, signal });
    } catch (e) {
      if (signal?.aborted) return;
      throw e;
    }
    for (const job of claimed) {
      log(`${me}: job ${job.id} ${job.kind}, attempt ${job.attempts}`);
      try {
        await handlers[job.kind](job.payload);
        await jobs.where('id', job.id).where('owner', owner).delete({ require: 1 });
      } catch (e) {
        log(`${me}: job ${job.id} failed (${e.message}); back in ${2 ** job.attempts} s`);
        await jobs.where('id', job.id).where('owner', owner)
          .update({ owner: null, run_at: expr('now() + ?', 1000 * 2 ** job.attempts) }, { require: 1 }).catch(() => {});
      }
    }
  }
}

  • A worker that dies holds nothing for long. The job the first worker took and never acked was ready again once its two-second lease lapsed, and the next claim took it, attempt 2. (The worker claims for 30 seconds; the dead one's claim was made for two, to keep the run short.)
  • It is at least once. A job can run twice, once by a worker that was only slow. The handler is built to be run twice: key what it does by the job's id or the row it is about, or send it under an Idempotency-Key of that.
  • An idle worker costs nothing: the claim is held at the server (30 seconds at most) and answered when it takes a job, which a new one does in 0.38 ms at the median (Waiting for a job).
  • Retries, back-off, priorities and dead letters are statements on the same collection (Fail, back off, dead-letter, Priorities).

A webhook for a table: a consumer

To tell something else that a row changed, read the change stream. With --cdc the server hands every write over once it is on disk, in order, documents and all, and keeps a consumer's place for it. The consumer below POSTs the writes to the collections it is asked for to a URL, as signed JSON, and moves on only when the URL has answered.

webhook.mjs 
// A webhook for a table, docs/functions: a consumer of the change stream
// (`fenec-server --cdc`) that POSTs each write it is asked for to a URL as
// signed JSON, and moves on only when the URL has said yes. The server keeps
// the consumer's place, so the relay can be stopped, killed or run on another
// machine and carry on from the last delivery that was answered.
//
//   FENEC_URL=... ADMIN_TOKEN=... HOOK_URL=https://... HOOK_SECRET=... node webhook.mjs orders
//
// What a receiver can rely on:
//   X-Signature-256: sha256=<HMAC-SHA256 of the body, with the shared secret>
//   Idempotency-Key: <seq>, the change's number in this database: a delivery
//   sent again (the relay died between the answer and the commit) carries the
//   same key, and a receiver that has seen it answers 200 and does nothing.
import { createHmac } from 'node:crypto';

const sleep = (ms, signal) => new Promise((resolve) => {
  const t = setTimeout(resolve, ms);
  signal?.addEventListener('abort', () => (clearTimeout(t), resolve()), { once: true });
});

export const sign = (secret, body) => `sha256=${createHmac('sha256', secret).update(body).digest('hex')}`;

/** Deliver the writes to `collections` (ops: put, del) at `url`, forever. */
export async function relay({
  fenec, adminToken, url, secret, collections, ops = ['put', 'del'], name = 'webhook',
  tries = 5, backoff = 500, wait = 10_000, signal, log = console.log,
}) {
  const headers = { authorization: `Bearer ${adminToken}`, 'content-type': 'application/json' };
  const server = (path, init) => fetch(`${fenec}${path}`, { headers, ...init });
  await server(`/_changes/consumers/${name}`, { method: 'POST' }); // made once; a second ask says it exists

  async function deliver(change) {
    const body = JSON.stringify(change);
    for (let attempt = 1; attempt <= tries; attempt++) {
      const res = await fetch(url, {
        method: 'POST',
        headers: { 'content-type': 'application/json', 'x-signature-256': sign(secret, body), 'idempotency-key': String(change.seq) },
        body,
        signal,
      }).catch(() => null);
      if (res?.ok) return true;
      if (signal?.aborted) throw new Error('stopped'); // not delivered, not committed: the next run sends it again
      // 4xx other than 408 and 429 is the receiver saying "never": trying
      // again would only hold up every change behind this one.
      if (res && res.status >= 400 && res.status < 500 && ![408, 429].includes(res.status)) {
        log(`relay: seq ${change.seq} refused (${res.status})`);
        break;
      }
      log(`relay: seq ${change.seq} try ${attempt} of ${tries}: ${res ? res.status : 'no answer'}`);
      await sleep(backoff * 2 ** (attempt - 1), signal);
    }
    // Kept where a person will look, and the stream goes on.
    await server('/query', {
      method: 'POST',
      body: JSON.stringify({ query: 'put dead_letters {seq: $1, collection: $2, op: $3, change: $4, at: now()}',
        params: [change.seq, change.collection, change.op, change] }),
    });
    log(`relay: seq ${change.seq} kept in dead_letters`);
    return false;
  }

  while (!signal?.aborted) {
    const page = await server(`/_changes?consumer=${name}&wait=${wait}`, { signal }).catch(() => null);
    if (!page) break;
    if (!page.ok) throw new Error(`/_changes: ${page.status} ${await page.text()}`);
    const next = Number(page.headers.get('fenec-next'));
    for (const line of (await page.text()).split('\n').filter(Boolean)) {
      const change = JSON.parse(line);
      if (collections.includes(change.collection) && ops.includes(change.op)) {
        try {
          await deliver(change);
        } catch (e) {
          if (signal?.aborted) return;
          throw e;
        }
      }
    }
    // After every delivery of the page was answered, not before.
    await server(`/_changes/consumers/${name}`, { method: 'POST', body: JSON.stringify({ since: next }) });
  }
}

  • What a receiver checks. X-Signature-256 is an HMAC-SHA-256 of the body with the secret the two share; recomputed over the body as received, and compared in constant time, it says the sender holds the secret. Idempotency-Key is the change's seq, its number in this database: a delivery repeated after the relay died between the answer and the commit carries the same one, and a receiver that has seen it answers 200 and does nothing. (seq counts every write of the database, the jobs and the signups among them, so the numbers above are not consecutive.)
  • Retry, then give up in a place you will look. A 500 is tried again after a back-off. A 4xx (but a 408 or a 429) is the receiver saying never, and trying again would only hold up every change behind it: the change is kept in dead_letters and the stream goes on. Without that, one poisoned row would stop the webhook for everything after it.
  • The server remembers the place. The relay was stopped, an order written, and a new relay started: it delivered the new order alone. A crash between a delivery and the commit repeats that delivery, which is why the key is there.
  • Everything is seen, whoever wrote it. A change by the backend, by a person's own token from a page and by a sweep are the same to a consumer, which is the point; and the reason it takes the server's token and no scoped one, which could not hold back a deletion of a row it never saw (Change data capture).
  • It is one lane. A slow receiver holds up what is behind it. For parallel work let the consumer do no work of its own: have it write a job per change (a put jobs), and let workers take them.
  • Already built. python -m fenecdb.relay http://127.0.0.1:8080 --consumer search --to https://indexer.internal/hook does the same from a package (Services and events), and a consumer in Python or Go is a loop of the same shape.

Choosing

  • A function when a request is the event: something arrives and must be answered, validated or paid for before it is written. It is the only one of the three in the request's path.
  • A queue when the work is the event: it can be split among workers, outlive the request that asked for it, and be tried again.
  • A consumer when the change is the event: you want to know about every write to a table, whichever program made it, in order, and you do not own all the writers.
  • The queue and the consumer combine. A consumer that turns a change into a job gets a lane that is parallel and a history that is ordered.

What this does not do

  • No exactly once. A delivery, a job and a request can each be repeated, and each carries a key so that a repeat does nothing.
  • No order across tenants. The stream is one database's, in the order its writes landed.
  • A buffer, not an archive. The server keeps the stream in a buffer of 64 MiB unless told otherwise (--replication-buffer); a consumer further behind is answered 410 and starts over from a read of the collections (Delivery and replay).
  • No schedule of its own. A cron job, an object's alarm or a @ttl is the clock.
