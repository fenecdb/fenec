Functions and webhooks

There are no triggers and no stored functions in the server. Code that reacts to a write runs beside the database, and the database gives it three things to stand on: an endpoint to sit behind, a queue with leases, and a stream of every write.

That is a choice, and a plain one: the code is yours, in the language and the runtime you already deploy, and it fails and retries where you can see it. (A Rust program that embeds the engine can register write hooks and functions of its own: Embedded Rust. A fenec-server loads none.) What follows is the three ways to react, when each fits, and each one run against a real server (node functions-demo.mjs in examples/recipes, after npm install; the Worker part runs when wrangler is on the path or WRANGLER names it, and make recipes-test holds this page's outputs to what the demo prints).

A token for each service

Each service here is its own caller with the least the server will give it, and the policy says so in a file a person can read. A service is its sub, which a provider assigns and a person does not choose, not a role (a role claim in the provider's namespace would be one the provider's settings might fill); it signs a five-minute token with a key of its own, whose public half is in the server's keys file beside the provider's. Why not --mint-token, and how the file is made, are in Auth with your identity provider.

A function: a Worker that is an endpoint

A Cloudflare Worker, a Lambda or a small server in front of the database, holding a key of its own as a secret, never a person's token. The Worker below takes a signup, checks what the database's rules do not, and writes the signup and the job that welcomes it in one /batch: the two land together or not at all, so no worker finds a job with no signup, and no signup goes unwelcomed.

// A function beside the data, docs/functions: a Cloudflare Worker that is an
// endpoint of its own. POST /signup checks what the database's rules cannot
// (an address that looks like one), then writes the signup and the job that
// welcomes it in ONE batch, so a worker never finds a job with no signup nor
// a signup that will never be welcomed.
//
// The Worker is a service of its own to fenec-server: a key (the secret
// SERVICE_KEY, PKCS#8 in base64) whose public half is in the server's keys
// file, and a token signed with it for five minutes, `sub` signup-function.
// functions-policy.txt lets that sub insert into two collections and nothing
// else, so a Worker that leaked its secret could add rows, not read them. Not a
// person's token, and not the server's own.
//
// The client's Idempotency-Key goes on to fenec-server, with the caller's name
// in front of it. The server keeps a key under this token's subject, which is
// every caller's alike: left as it came, one caller's key could collide with
// another's (a 422, or a replayed answer that was not theirs).
const b64url = (bytes) => btoa(String.fromCharCode(...bytes)).replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
const text = (s) => new TextEncoder().encode(s);

let kept = null; // the token, per isolate, until a minute before it lapses

async function serviceToken(env) {
  const now = Math.floor(Date.now() / 1000);
  if (kept && kept.exp - 60 > now) return kept.token;
  const key = await crypto.subtle.importKey('pkcs8', Uint8Array.from(atob(env.SERVICE_KEY), (c) => c.charCodeAt(0)),
    { name: 'RSASSA-PKCS1-v1_5', hash: 'SHA-256' }, false, ['sign']);
  const head = b64url(text(JSON.stringify({ alg: 'RS256', typ: 'JWT', kid: 'svc-1' })));
  const body = b64url(text(JSON.stringify({ sub: 'signup-function', iat: now, exp: now + 300 })));
  const sig = new Uint8Array(await crypto.subtle.sign('RSASSA-PKCS1-v1_5', key, text(`${head}.${body}`)));
  kept = { token: `${head}.${body}.${b64url(sig)}`, exp: now + 300 };
  return kept.token;
}

export default {
  async fetch(request, env) {
    const { pathname } = new URL(request.url);
    if (request.method !== 'POST' || pathname !== '/signup') return new Response('not found', { status: 404 });

    const { email, name } = await request.json().catch(() => ({}));
    if (typeof email !== 'string' || email.length > 254 || !/^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(email)
      || typeof name !== 'string' || !name || name.length > 100) {
      return Response.json({ error: 'a name and an email address' }, { status: 400 });
    }

    const lines = [
      { query: 'put signups {email: $1, name: $2}', params: [email, name] },
      // An object goes in as a parameter: inside an object literal only constants do.
      { query: 'put jobs {kind: "welcome", payload: $1, run_at: now(), attempts: 0}', params: [{ email, name }] },
    ];
    const headers = { authorization: `Bearer ${await serviceToken(env)}`, 'content-type': 'application/x-ndjson' };
    const key = request.headers.get('idempotency-key');
    if (key) {
      // The caller: who signed in, where there is a sign-in; the address otherwise.
      const caller = request.headers.get('cf-connecting-ip') ?? 'unknown';
      headers['idempotency-key'] = `${caller}:${key.slice(0, 100)}`;
    }
    const res = await fetch(`${env.FENEC_URL}/batch`, { method: 'POST', headers, body: lines.map((l) => JSON.stringify(l)).join('\n') });

    if (res.status === 409) return Response.json({ error: 'already signed up' }, { status: 409 }); // @unique(email)
    if (!res.ok) return Response.json({ error: 'try again later' }, { status: 502 }); // not the server's words
    return Response.json({ ok: true, replayed: res.headers.get('idempotent-replayed') === 'true' }, { status: 201 });
  },
};

  • Run under wrangler dev (workerd, as Cloudflare runs it) against a real server. The key is a line of .dev.vars there (PKCS#8 in base64, openssl pkcs8 -topk8 -nocrypt -outform DER | base64) and wrangler secret put SERVICE_KEY deployed; fenec-server is reached over HTTP like any other service, so a function holds no pool of connections to exhaust.
  • A leaked key adds rows and reads none. The last three lines are what the Worker's own token is answered: its reads are refused, its del finds no row it may delete, and its insert is the one thing it was given.
  • The same request, sent again (a timeout, a retry) is answered the first one's answer, replayed: true, and writes nothing twice. A different request for an address already signed up reaches the @unique on email and is 409, and the batch, jobs and all, is put back.
  • The client's key is scoped to the caller. The server keeps an Idempotency-Key under the token's subject, which here is every caller's alike, so the Worker puts the caller (a sign-in where there is one, the address where there is not) in front of it: left as it came, one caller's key could collide with another's, or replay an answer that was not theirs.
  • An object goes in as a parameter. Inside an object literal a FenecQL statement takes constants only, so the job's payload is $1, and the parameter is the object.
  • The server's words are not the Worker's. A refusal is "try again later" to the caller, and a body or an address is checked before it is sent.
  • A Worker is also where a provider's webhook is verified before anything is written, and where a token that arrives in another header (a Cloudflare Access one) can be moved into the one the server reads (Auth with your identity provider). Servers in several regions take one URL through a Worker at the front, the global entry.

Work after a write: a job queue

The job is a row, and a worker claims it with one statement that picks the oldest ready job and writes a lease on it; held at the server with Fenec-Wait until there is one. The queue is Job queues; the function here is the worker.

// A worker of the `jobs` collection, docs/functions: it claims one ready job
// at a time, its own for a lease; the claim is held at the server until there
// is one (`wait`), so an idle worker costs nothing and a new job reaches it in
// under a millisecond. A job done is deleted. A job that fails is put back
// after a back-off, and after `maxAttempts` tries is kept with its error and no
// time to run (a dead letter: no claim takes a job without one) for a person
// to look at. A worker that dies holds its job only until the lease lapses.
// Each step names the owner it was claimed by and requires its row, so a
// worker whose lease lapsed finds out (412) instead of acking another worker's
// job. (The queue itself is docs/queues.)
//
// One job to a claim, because a claim's lease is the job's: ten claimed
// together under one 30 s lease, and run one after the other, would lapse on
// the ninth while the first was still being done. A handler is also given the
// time the lease has left, and a signal that fires then.
import { connect, expr, inc, raw } from '@fenecdb/web/client';

/**
 * `token` is `() => Promise<token>`: the worker's own (service-token.mjs),
 * asked for again on each claim since a claim can wait half a minute.
 */
export async function work({
  fenec, token, handlers, id = Math.random().toString(36).slice(2, 6), lease = 30_000, wait = 30_000,
  maxAttempts = 3, backoff = 1000, signal, log = console.log,
}) {
  while (!signal?.aborted) {
    const jobs = connect(fenec, { token: await token() }).from('jobs');
    const owner = `${id}:${Date.now()}`; // a claim, not the worker: two claims of one job tell apart
    let claimed;
    try {
      claimed = await jobs.where(raw('run_at <= now()')).order('run_at').limit(1)
        .update({ owner, run_at: expr('now() + ?', lease), attempts: inc(1) }, { returning: true, wait, signal });
    } catch (e) {
      if (signal?.aborted) return;
      throw e;
    }
    for (const job of claimed) {
      log(`${id}: job ${job.id} ${job.kind}, attempt ${job.attempts}`);
      const mine = () => jobs.where('id', job.id).where('owner', owner);
      try {
        const left = AbortSignal.timeout(lease - 5000); // stop short of the lease
        await Promise.race([
          handlers[job.kind](job.payload, { signal: left }),
          new Promise((_, no) => left.addEventListener('abort', () => no(new Error('out of time')))),
        ]);
        await mine().delete({ require: 1 });
      } catch (e) {
        if (job.attempts >= maxAttempts) {
          log(`${id}: job ${job.id} failed (${e.message}); ${job.attempts} attempts, kept as dead`);
          await mine().update({ owner: null, run_at: null, error: e.message }, { require: 1 }).catch(() => {});
        } else {
          const ms = backoff * 2 ** job.attempts;
          log(`${id}: job ${job.id} failed (${e.message}); again in ${ms / 1000} s`);
          await mine().update({ owner: null, run_at: expr('now() + ?', ms), error: e.message }, { require: 1 }).catch(() => {});
        }
      }
    }
  }
}

  • A worker that dies holds nothing for long. The job the first worker took and never acked was ready again once its three-second lease lapsed, and the next claim took it, attempt 2. (The worker claims for 30 seconds; the dead one's claim was made for three, to keep the run short.)
  • One job to a claim, a lease to a job. Ten claimed together under one 30-second lease and done one after another would lapse on the ninth while the first was still being done, and another worker would take them. The handler is also given the time the lease has left, as a signal.
  • Bounded. A job that fails is tried again after a back-off (0.6 s, then 1.2 s here; the worker's default base is a second, so 2 s and then 4 s) and, after three attempts, is kept with its error and no time to run: a dead letter, which no claim takes and a person can read (get jobs where run_at is null). Without the bound one bad job would be tried for ever.
  • It is at least once. A job can run twice, once by a worker that was only slow. The handler is built to be run twice: key what it does by the job's id or the row it is about, or send it under an Idempotency-Key of that.
  • An idle worker costs nothing: the claim is held at the server (30 seconds at most) and answered when it takes a job, which a new one does in 0.38 ms at the median (Waiting for a job).
  • Retries, priorities and dead letters are statements on the same collection (Fail, back off, dead-letter, Priorities).

A webhook for a table: a consumer

To let something else know that a row changed, read the change stream. With --cdc the server hands every write over once it is on disk, in order, documents and all, and keeps a consumer's place for it. The consumer below POSTs the writes to the collections it is asked for to a URL, as signed JSON, and moves on only when the URL has answered. It sends the document (every field of it, as the stream has it) to the receiver, unless it is told shape: 'ids', which sends the change's number, collection, kind and id: use that where the receiver has no business with the rest and can read the row itself.

webhook.mjs 
// A webhook for a table, docs/functions: a consumer of the change stream
// (`fenec-server --cdc`) that POSTs each write it is asked for to a URL as
// signed JSON, and moves on only when the URL has said yes. The server keeps
// the consumer's place, so the relay can be stopped, killed or run on another
// machine and carry on from the last delivery that was answered.
//
//   FENEC_URL=... ADMIN_TOKEN=... HOOK_URL=https://... HOOK_SECRET=... node webhook.mjs orders
//
// What goes out is the change as the stream has it: `put` carries the whole
// document, every field of it. A receiver is told as much as the stream says,
// so send ids (`shape: 'ids'`) where the receiver has no business with the
// rest and can read the row itself.
//
// What a delivery is answered decides what happens to the stream:
//   2xx           done; the next change.
//   408, 429, 5xx, no answer
//                 tried again with a back-off, `tries` times; then the relay
//                 stops (below), for a receiver that is down is not a reason
//                 to put every change it missed away.
//   400, 413, 422 and the other 4xx
//                 the receiver refuses this change, and would refuse it again:
//                 it is kept in `dead_letters` and the stream goes on.
//   401, 403, 404, 405, 410, and any redirect
//                 stop, and say so. The receiver does not trust this sender
//                 (a secret that was rotated, a URL that moved), and every
//                 change behind this one would be put away for the same reason.
//                 A redirect is never followed: the body is signed for the
//                 address it was sent to.
// Stopping is throwing an Alert, with nothing committed: the process exits
// non-zero, whoever watches it is told, and a restart sends this change again.
import { signatures } from './webhook-verify.mjs';
import { isMain } from './main.mjs';

export class Alert extends Error {}

const sleep = (ms, signal) => new Promise((resolve) => {
  const t = setTimeout(resolve, ms);
  signal?.addEventListener('abort', () => (clearTimeout(t), resolve()), { once: true });
});

const STOP = new Set([401, 403, 404, 405, 410]);
const RETRY = (status) => status === 408 || status === 429 || status >= 500;

/**
 * Deliver the writes to `collections` (ops: put, del) at `url`, forever.
 * `secrets` is one secret, or two while one is being rotated out.
 */
export async function relay({
  fenec, adminToken, url, secrets, collections, ops = ['put', 'del'], shape = 'full', name = 'webhook',
  tries = 5, backoff = 500, wait = 10_000, signal, log = console.log,
}) {
  const headers = { authorization: `Bearer ${adminToken}`, 'content-type': 'application/json' };
  const server = (path, init) => fetch(`${fenec}${path}`, { headers, ...init });
  // Made once, where there is none. A POST to a consumer that exists moves it
  // to the last write on disk, and every change since it was stopped is lost.
  const listed = await (await server('/_changes/consumers')).json();
  if (!listed.some((c) => c.name === name)) await server(`/_changes/consumers/${name}`, { method: 'POST' });

  async function deliver(change) {
    const sent = shape === 'ids' ? { seq: change.seq, collection: change.collection, op: change.op, id: change.id ?? change.doc?.id } : change;
    const body = JSON.stringify(sent);
    for (let attempt = 1; attempt <= tries; attempt++) {
      const timestamp = Math.floor(Date.now() / 1000);
      const res = await fetch(url, {
        method: 'POST',
        headers: {
          'content-type': 'application/json',
          'x-webhook-timestamp': String(timestamp),
          'x-webhook-signature': signatures([].concat(secrets), timestamp, body),
        },
        body,
        redirect: 'manual',
        signal,
      }).catch(() => null);
      if (res?.ok) return;
      if (signal?.aborted) throw new Error('stopped'); // not delivered, not committed: the next run sends it again
      const status = res ? res.status : 0;
      if (status >= 300 && status < 400) throw new Alert(`seq ${change.seq}: ${url} redirects (${status}), and a signed body is not sent on`);
      if (STOP.has(status)) throw new Alert(`seq ${change.seq}: ${url} answers ${status}; stopped, nothing committed`);
      if (res && !RETRY(status)) {
        log(`relay: seq ${change.seq} refused (${status})`);
        await server('/query', {
          method: 'POST',
          body: JSON.stringify({ query: 'put dead_letters {seq: $1, collection: $2, op: $3, status: $4, change: $5, at: now()}',
            params: [change.seq, change.collection, change.op, status, sent] }),
        });
        log(`relay: seq ${change.seq} kept in dead_letters`);
        return;
      }
      log(`relay: seq ${change.seq} try ${attempt} of ${tries}: ${status || 'no answer'}`);
      if (attempt < tries) await sleep(Math.min(backoff * 2 ** (attempt - 1), 60_000), signal);
    }
    throw new Alert(`seq ${change.seq}: ${url} did not answer ${tries} times; stopped, nothing committed`);
  }

  while (!signal?.aborted) {
    const page = await server(`/_changes?consumer=${name}&wait=${wait}`, { signal }).catch(() => null);
    if (!page) break;
    if (!page.ok) throw new Error(`/_changes: ${page.status} ${await page.text()}`);
    const next = Number(page.headers.get('fenec-next'));
    for (const line of (await page.text()).split('\n').filter(Boolean)) {
      const change = JSON.parse(line);
      if (!collections.includes(change.collection) || !ops.includes(change.op)) continue;
      try {
        await deliver(change);
      } catch (e) {
        if (signal?.aborted) return;
        throw e;
      }
    }
    // After every delivery of the page was answered, not before.
    await server(`/_changes/consumers/${name}`, { method: 'POST', body: JSON.stringify({ since: next }) });
  }
}

if (isMain(import.meta.url)) {

What the receiver does with a delivery, in the order it does it:

webhook-verify.mjs, the receiver's checks 
// What a receiver of webhook.mjs's deliveries does, docs/functions. Three
// checks, in this order, before the body is trusted:
//
//   1. The signature: HMAC-SHA-256 over `<timestamp>.<body>` with the secret
//      the two share, compared in constant time. The timestamp is part of
//      what is signed, so it cannot be moved to make an old body new.
//   2. The timestamp: within a few minutes of now. A body someone captured and
//      sends again an hour later has a good signature and a stale time.
//   3. The `seq` inside the body, which the signature covers: a change already
//      done is answered 200 and not done again. A header outside the signature
//      (an Idempotency-Key, say) is whatever the sender of this request wrote.
//
// A secret is rotated by the sender signing with the new and the old (two
// `v1=` values) while the receiver learns the new: it accepts a body one of
// whose signatures one of its secrets makes.
import { createHmac, timingSafeEqual } from 'node:crypto';

export const sign = (secret, timestamp, body) => createHmac('sha256', secret).update(`${timestamp}.${body}`).digest('hex');

/** The header a sender sets: one `v1=` for each secret it signs with. */
export const signatures = (secrets, timestamp, body) => secrets.map((s) => `v1=${sign(s, timestamp, body)}`).join(',');

const same = (a, b) => a.length === b.length && timingSafeEqual(Buffer.from(a), Buffer.from(b));

/** `{ok: true}` or `{ok: false, why}`; `now` is seconds, a parameter so that a test can move it. */
export function verify({ secrets, headers, body, tolerance = 300, now = () => Date.now() / 1000 }) {
  const timestamp = headers['x-webhook-timestamp'];
  if (!/^\d{1,12}$/.test(timestamp ?? '')) return { ok: false, why: 'no timestamp' };
  const given = (headers['x-webhook-signature'] ?? '').split(',').map((p) => p.trim().replace(/^v1=/, ''));
  const good = secrets.some((secret) => given.some((g) => same(g, sign(secret, timestamp, body))));
  if (!good) return { ok: false, why: 'bad signature' };
  if (Math.abs(now() - Number(timestamp)) > tolerance) return { ok: false, why: 'stale' };
  return { ok: true };
}

/**
 * A request handler for node:http. `secrets` is a list, or a function that
 * answers one (read at each delivery, so that a secret can be rotated). `done`
 * is the set of `seq`s already done
 * (a table, in a receiver that is run twice), `act(change)` what the receiver
 * is for.
 */
export function receiver({ secrets, act, done = new Set(), tolerance, now, log = () => {}, captured }) {
  return async (req, res) => {
    let body = '';
    for await (const chunk of req) {
      body += chunk;
      if (body.length > 1 << 20) return void res.writeHead(413).end();
    }
    const checked = verify({ secrets: typeof secrets === 'function' ? secrets() : secrets, headers: req.headers, body, tolerance, now });
    if (!checked.ok) {
      log(`rejected: ${checked.why}`);
      return void res.writeHead(401).end();
    }
    captured?.push({ headers: req.headers, body }); // for a demonstration of a replay
    const change = JSON.parse(body);
    if (done.has(change.seq)) {
      log(`seq ${change.seq} seen: nothing done`);
      return void res.writeHead(200).end();
    }
    try {
      await act(change);
    } catch (e) {
      log(`seq ${change.seq}: answered ${e.status ?? 500}`);
      return void res.writeHead(e.status ?? 500).end();
    }
    done.add(change.seq);
    log(`seq ${change.seq} ${change.collection} ${change.op}: done`);
    res.writeHead(200).end();
  };
}

  • What is signed is <timestamp>.<body>. The receiver checks the signature in constant time, then that the timestamp is within five minutes of its own clock. A delivery someone captured and sends again an hour later has a good signature and a stale time: 401 above. (The run moves the receiver's clock to show it.)
  • It deduplicates on the signed seq, not on a header. seq is the change's number in this database and is inside the body the signature covers. A delivery repeated at once, or after the relay died between the answer and the commit, carries the same seq, and a receiver that has seen it answers 200 and does nothing (seen above). A header outside the signature, an Idempotency-Key for one, is whatever the sender of that request wrote. (seq counts every write of the database, so the numbers are not consecutive, and a run's differ.)
  • What the receiver answers decides the stream. 2xx is done. A 500 is tried again after a back-off; after tries of them the relay stops and says so, since a receiver that is down is no reason to put away every change it missed. A 400, 413 or 422 is the receiver refusing this change, which it would refuse again: it goes to dead_letters and the stream goes on, where one poisoned row would otherwise stop the webhook for everything after it. A 401, 403, 404, 405 or 410 stops the relay: the receiver does not trust this sender or has moved, and every change behind would be put away for the same reason. It exits with an ALERT and nothing committed, and a restart sends that change again.
  • A redirect is not followed. The body is signed for the address it was sent to, and a 3xx would hand it on to another: the relay stops, as for a 401.
  • A secret is rotated with both. The receiver learns the new one while the relay signs with the new and the old (two v1= values); once every receiver has the new, the old goes. The run: the receiver rotated before the relay heard (ALERT, stopped), then the relay was given both and the same change went out.
  • The server remembers the place. The relay was stopped, an order written, and a new relay started: it delivered the new order alone. A crash between a delivery and the commit repeats that delivery, which is why seq is there. A consumer is made once: a POST to one that exists moves it to the last write on disk.
  • Everything is seen, whoever wrote it. A change by the backend, by a person's own token from a page and by a sweep are the same to a consumer, which is the point; and the reason it takes the server's token and no scoped one, which could not hold back a deletion of a row it never saw (Change data capture).
  • It is one lane. A slow receiver holds up what is behind it. For parallel work let the consumer do no work of its own: have it write a job per change (a put jobs), and let workers take them.
  • Already built. python -m fenecdb.relay http://127.0.0.1:8080 --consumer search --to https://indexer.internal/hook does the plain version of this from a package (Services and events), without the signature and the stop; a consumer in Python or Go is a loop of the same shape.

Choosing

  • A function when a request is the event: something arrives and must be answered, validated or paid for before it is written. It is the only one of the three in the request's path.
  • A queue when the work is the event: it can be split among workers, outlive the request that asked for it, and be tried again.
  • A consumer when the change is the event: you want to know about every write to a table, whichever program made it, in order, and you do not own all the writers.
  • The queue and the consumer combine. A consumer that turns a change into a job gets a lane that is parallel and a history that is ordered.

What this does not do

  • No exactly once. A delivery, a job and a request can each be repeated, and each carries something a repeat is known by.
  • No order across tenants. The stream is one database's, in the order its writes landed.
  • A buffer, not an archive. The server keeps the stream in a buffer of 64 MiB unless told otherwise (--replication-buffer); a consumer further behind is answered 410. What that means for one that must see every change is in Files (a reconcile, not a read of the collections, for deletions) and Delivery and replay.
  • No schedule of its own. A cron job, an object's alarm or a @ttl is the clock.
