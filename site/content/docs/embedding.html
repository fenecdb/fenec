Embedded Rust

fenec-core is a plain Rust library with no dependencies. Parsing is fenec-ql; everything else is the engine.

use fenec_core::prelude::*;
use fenec_ql::parse;

let mut db = fenec_core::fs::open("data.fenec")?;
for stmt in parse("get docs near embed $1 limit 5")? {
    let r = db.execute_with(&stmt, &[Value::Vector(embedding)])?;
}

Reads and writes take different locks

Database::query takes a shared lock and execute_with the exclusive one. Every write is a block: what a statement writes lands in the file as one record, or — a hook's refusal, a document the schema refuses half way through a put of many — none of it does, and the database is as it was. Several statements are one block with execute_block, or between begin and commit, with rollback to put them back; whoever opens one holds the exclusive lock until it ends. A create, a drop, a create index or a compact runs on its own, outside a block. FenecQL has no BEGIN or COMMIT: fenec-pg runs a transaction as a block held open (Transactions).

let stmts: Vec<Statement> = parse("put orders {total: 12}; set stock {n: 4} where id = 7")?;
let block: Vec<(&Statement, &[Value])> = stmts.iter().map(|s| (s, &[][..])).collect();
match db.execute_block(&block) {
    Ok(answers) => { /* both landed, as one record */ }
    Err((at, e)) => { /* statement `at` failed: neither landed */ }
}

One process per file. Two processes opening the same file and writing it corrupt it. There is no lock file and no advisory locking — the single-writer rule is yours to keep.

Durability is the caller's job

File writes are buffered. If the process crashes before sync is called, the last writes are lost. In embedded use nothing calls it for you — fenec-pg has the --sync policy and a shutdown hook precisely because the library does not.

A storage error stops writes. Once the sink refuses an append, a sync or a rewrite, every later write — and every later sync — returns Error::Io until the file is reopened, and Database::failure() says what failed. A failed fsync is not retried: the kernel may already have dropped the pages, so a retry that succeeds would prove nothing. Reads go on, from memory.

The same applies to the HNSW graph. It is derived data and is written only during snapshot, compact and checkpoint, never on the write path. Without a graph in the file it is rebuilt on open: 10.2 s at 100 000 × 128, against 110 ms with it. A crash does not cost the graph: the next open restores the one the last checkpoint wrote and applies the writes since — 0.19 s for 1 000 of them at 100 000 × 128, where the rebuild took 8.8 s. A process that has to answer before those are linked opens with fs::open_serving: the vectors written since go in unlinked, near measures each of them until Database::link_pending(n) has linked them, and the process calls it under its write lock a few at a time, as fenec-pg does. Database::unlinked() says how many are left.

Measuring the footprint

Database::memory_bytes() sums the segment bytes, offset indexes, vector arenas, graph links and every other index from counters they keep as they change, so it costs nothing to ask. It is not RSS — allocator slack, HNSW build buffers, upper-level neighbour allocations and the 2–3× transient peaks all sit outside it. Measured ratios are in Limits.

Errors

Error in fenec-core/src/error.rs is the single error type across the whole engine: allocation-free variants, no Box. fenec-pg maps it onto PostgreSQL SQLSTATE codes.

Plugins

The registry takes after PostgreSQL's extension model. Scalar functions, write hooks in the shape of triggers, and transport adapters can all be registered.

db.install_plugin(&PgPlugin)?;   // pg_version(), pg_typeof(), to_pgvector()
