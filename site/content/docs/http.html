HTTP endpoint

Talk to fenecdb with fetch, curl or any standard library — no driver needed.

Start it

Add --http to fenec-server. Every collection gets REST routes from its schema.

fenec-server --file data.fenec --http 127.0.0.1:8080

curl 'http://127.0.0.1:8080/articles?select=title,year&year=gte.2024&tags=has.rust&order=year.desc&limit=10'
# [{"title":"the rust book","year":2024}]

curl 'http://127.0.0.1:8080/articles?year=gte.2024&count'
# {"count":1}

curl -X POST http://127.0.0.1:8080/articles -d '{"title":"new","year":2025}'
# {"inserted":1}

curl -X POST 'http://127.0.0.1:8080/articles?returning=id' -d '{"title":"newer","year":2026}'
# [{"id":3}]
Details

For clients that want no driver at all: fetch, curl, or any language's standard library. The schema is already in the database, so the surface is derived from it.

Not a separate binary. The HTTP endpoint is a second listener in the same process as fenec-server. fenecdb has a single writer, and two processes writing one file corrupt it. Being in the same process also keeps the sync policy, the checkpoint, the memory ceiling and the shutdown signal in one place — --sync always covers HTTP writes too.

Details

With --replication-token, /_replication is taken as well: the stream a replica is fed, its status, and a replica's promotion — see Replication. It asks for that token rather than --http-token, and a collection named _replication is then out of HTTP's reach.

/_schema compares a schema declared in code with the server's, in the engine every SDK's check goes through — see Schema in code. Its body is the description, {"format": 1, "fenecql": "create collection ...", "migrations": [...]} or its collections as JSON. A plan answers {"applied", "ran", "migrations", "statements", "refusals"}, and writes nothing; with ?mode=follow it says only what the code declares and the server lacks, which a scoped token may ask of the collections it reads. An apply takes the server's token, runs the migrations not yet recorded and the additions under the write lock as one block, and answers 409 with the refusals when anything is refused, having written nothing.

With --mcp, /_mcp is the Model Context Protocol's endpoint: an agent's schema, search, query and get tools, and write and a memory where asked for, each a statement held to the request's token as /query is — see Agents and MCP. Without the flag it answers 404.

/_metrics is the server's statements, latency and data in Prometheus's text format, readable with --http-token or the admin token — see Monitoring. The underscore keeps it out of the way of a collection called metrics; a collection called _metrics cannot be read over GET.

Values are parsed by the field's type: ?year=gte.2024 is an int, ?published=gte.2024-01-01 is a timestamp. An unknown field returns 404. where= exists for what the pattern cannot hold — or groups and function calls.

Vector search

Send the vector in a POST body to /<name>/near, with an optional filter. Add "match" to mix in keyword search.

curl -X POST http://127.0.0.1:8080/articles/near -d '{
  "vector": [0.1, 0.2, 0.3],
  "ef": 128, "limit": 5,
  "select": ["title"],
  "where": "year >= 2024"
}'
# [{"title":"the rust book","_score":0.97}]
  • field can be left out when the collection has one vector field.
  • Query-string filters are combined with the body's where.
Details

near is a POST rather than a query parameter because a 768-dimension embedding does not fit in a query string. Squeezing it into the URL — base64, truncation — is unreadable and runs into proxy and server URL ceilings. PostgREST's model does not cover fenecdb's headline feature, so near gets its own endpoint, and it takes a filter in the body.

If the collection has a single vector field, field can be left out. Filters in the query string are anded with the where in the body.

A vector in an answer, and a _score, is its f32s written as the shortest decimals that read back as them — 0.1 as it was written, the text pgvector gives — rather than the 0.10000000149011612 of the f64 each widens to. A reader that takes a number as an f64 and rounds it to f32, as a Float32Array does, gets every one back: the one f32 an f64 would round away, 7.038531e-26, is written as its f64.

A "match" makes it hybrid: BM25 over the collection's @text field ranks the same request, and the two rankings are fused by reciprocal rank (fuse). match_field names the text field when there are several; match_fuzzy (true, or 0 to 2 edits) and match_prefix read its words as match ... fuzzy and prefix do; fuse_k and candidates are the rank offset and how many candidates each side ranks.

curl -X POST http://127.0.0.1:8080/articles/near -d '{
  "vector": [0.1, 0.2, 0.3],
  "match": "borrow checker lifetimes",
  "limit": 10
}'

Raw FenecQL

When the REST routes do not fit, send FenecQL to /query. Parameters stay parameters.

curl -X POST http://127.0.0.1:8080/query \
  -H 'content-type: application/json' \
  -d '{"query":"get articles where year >= $1 limit $2","params":[2024, 10]}'
  • A text is parsed once. /query keeps what it parsed by the text, so the values go as parameters — a page's limit and offset too (Pages by parameters): written into the text, every page was a statement of its own.
  • The answer is the rows, a JSON array — or, when the query asks for facets, {"rows": [...], "facets": {"brand": [{"value": "acme", "count": 12}, ...]}}. A write answers {"affected": n}, and one with returning the rows it wrote, as a read does, with its Fenec-Seq: a job queue's claim (Job queues).
  • From Python: pip install fenecdb gives a client with no dependencies.
Details

The counts answer for the whole set the query matched, not for a row, so they go beside the rows rather than into one, and a query that asks for none keeps the bare array every client reads. The same holds for a line of a /batch ({"rows": [...], "facets": {...}}), for GET /<name>?facet=..., whose list is FenecQL's (facet=brand top 5,color), and beside a count ({"count": 3, "facets": {...}}). A subscription keeps a shape's rows and carries no facets; a live query over the server (live on connect(), useLiveQuery) runs its query again after each write, facets and all. A highlight() is a column like any other, under its label.

From Python, pip install fenecdb — the standard library alone — makes the same calls, blocking or in an event loop:

from fenecdb import AsyncClient, Client

db = Client("http://127.0.0.1:8080", token="...")
db.query("get articles where year >= $1 limit 10", [2024])

async with AsyncClient("http://127.0.0.1:8080", token="...") as db:
    await db.query("get articles where year >= $1 limit 10", [2024])

AsyncClient keeps one connection alive and opens it again when the server has closed it; calls made at once over one client go one after another over it, so requests side by side take a client each. Client.follow reads the change stream as a consumer, and python -m fenecdb.relay hands it on to another program or a webhook: see Services and events.

Embedding a collection

Use lookup to nest matching rows of another collection under each row, such as each product's latest reviews.

curl 'http://127.0.0.1:8080/products?limit=20&select=name\
&lookup=reviews&reviews.on=product_id&reviews.stars=gte.4\
&reviews.order=created.desc&reviews.limit=3'
# [{"name":"Kahve","reviews":[{...},{...},{...}]}, ...]
  • Prefix the child's options with its name: reviews.on, reviews.limit.
  • Chain levels with a comma: lookup=orders,lines.
  • A key over several fields lists a field of each side: lines.on=org,order&lines.parent=org,id, FenecQL's on (org, order) = (org, id).
  • A level that folds aggregates in its select, as the query's own does: orders.select=count(*),sum(total), each parent's children folded, and orders.group=status a row a group, its order naming columns (orders.order=count(*).desc). Off a query's groups, <name>.parent names a column of its list: /orders?select=courier,count(*)&group=courier&lookup=couriers&couriers.on=user&couriers.parent=courier.
Details

lookup=<name> names the collection once; every key prefixed with it configures the clause — on (required, the child's field holding the key), parent, select, order, limit, offset, required, where, and any field name as a condition, in the same op.value form the parent's filters use. Prefixing is what keeps the two sides apart in a query string, the way the clause's position does in FenecQL.

curl 'http://127.0.0.1:8080/shops?limit=20&select=name\
&lookup=orders,lines&orders.on=shop_id&orders.limit=3\
&lines.on=order_id&lines.limit=5'
# [{"name":"Merkez","orders":[{"code":"A","lines":[{...}]}, ...]}, ...]

A comma-separated list chains, read left to right, each name binding to the one before it and each level keeping its own prefix. A query string has no position to scope by, so the order is written out; the meaning is the same one FenecQL gets from position, up to the same 8 levels.

lookup is a reserved key here, so a field named lookup cannot be filtered over the REST path — the FenecQL and fenec-server paths are unaffected, as with the other reserved names.

A query with a lookup answers with the children nested under the collection's name — one object per parent, with an empty array where nothing matched, and a chain nests all the way down.

curl -X POST http://127.0.0.1:8080/query \
  -H 'content-type: application/json' \
  -d '{"query":"get products limit 20 lookup reviews on product_id limit 3"}'
# [{"id":1,"name":"Kahve","reviews":[{"id":1,"stars":5,"body":"guzel"}]}, ...]

Batches

POST /batch runs several statements, one per line, as a single all-or-nothing write. If one fails, the ones before it are undone and the answer says so.

{"error":"collection `tasks` has no field `nofield`","completed":0,"at":1}

A statement that matches no row is no error, and the batch goes on. To make a count a condition, end the write with require N: unless it wrote exactly N rows the batch stops with 412 and is put back, a transfer's debit and its credit together (Transfers).

{"error":"unmet: `set accounts` wrote 0 rows, and requires 1","completed":0,"at":1}

Every client sends one: db.batch([...], { idempotencyKey }) in JavaScript, batch(...) in Python, Batch in Go, BatchAsync in .NET, and the remote clients of Swift, Kotlin and Dart; a batch that stops throws the client's error with the statement's at and the status.

Details

POST /batch takes one query body per line as NDJSON. The statements run in order under a single write lock, as one block: their writes land in the file as one record, or none of them do. The first error puts back what the statements before it did, and the answer says so: at is the statement that stopped it, counted from 0, and completed how many stay applied — none of a block.

A batch whose every statement only reads — a get, with or without require — is a snapshot instead: every read at the one change Fenec-Seq names, no write landing between the first and the last. When it is long — an aggregate, a scan, a filtered count over 10 000 rows or more — the server pins what it reads under the read lock and reads it with no lock held, so writes land beside it; otherwise, and where an index answers a statement, it runs under one read lock, and writes wait for it as they wait for any read. A reconciliation over a million journal entries took 140 to 200 ms, and a transfer arriving meanwhile waited up to 187–512 ms; pinned, 5.4–29 ms (make recon-bench). A long POST /query read is pinned the same way.

No other writer slips in between, a read in the batch sees the writes before it, and a subscriber is woken once, for all of them. A create, a drop or a create index in it is put back with the rest. A compact rewrites the file, which cannot be put back, so a batch holding one runs each statement on its own: it stops at the first error, and completed says how many were applied. Either way a failed batch says what it left behind, because a silent error would permanently separate a client's optimistic local state from the server's.

The body is NDJSON rather than a JSON array because fenecdb's JSON parser deliberately does not accept nested objects, so {"statements":[{...}]} could not be parsed anyway. Instead of writing a second parser, the boundary was put at the end of a line — by the escaping rules no JSON encoder can write a bare newline into the body.

Retrying a write

Send an Idempotency-Key header with a write, and retrying it after a timeout cannot write it twice: a repeat gets the first answer back.

curl -X POST http://127.0.0.1:8080/query \
  -H 'Idempotency-Key: 5f0c2d6e-order-1142' \
  -d '{"query":"put orders {customer: $1, total: $2}","params":[7, 129.5]}'
  • One key per write. The same key with a different request is refused (422).
  • A failed write keeps no key, so a retry runs it again.
Details

A put with no id makes a row each time it runs, so a client that sends a write again after a timeout or a dropped connection — not knowing whether the first landed — may write it twice. Send an Idempotency-Key with it, one per write, and a request sent again with the key is answered as the first was, with Idempotent-Replayed: true, and not made again. Its Fenec-Seq is where the database stands as it replays, which holds the write, so a read sent to a replica with Fenec-After waits for it as after the first answer.

  • The key and the answer are kept in the same block as the write, under the write lock: they land together, so a crash cannot leave a write whose retry makes it again, and a second request with the key waits for the first and is handed its answer.
  • A write that failed keeps no key: sent again, it runs again.
  • A key is for one request: the same key with another method, path or body is refused (422).
  • Under a scoped token the keys are its subject's (sub), so no user is handed another's answer; a token with no subject is refused a key (400).
  • REST writes, /query and /batch take one, a compact — which cannot be put back — does not; a read ignores it. An answer over 64 KB is kept as its status and a note.
  • Keys are kept for --idempotency-ttl seconds, a day unless given, in a _idempotency collection the change stream leaves out. Its at is @ttl: a key past its time is gone at once, and the sweeper deletes it.

A write without a key costs what it did; with one, 16 200 single puts a second over HTTP against 18 300 without.

Holding a write until it can write

Send Fenec-Wait: <ms> with a set or a del on /query or /batch, and while it would write nothing the server holds it, answering the moment it writes — or at the end of the wait, 30 seconds at most, as it would have answered at once. A job queue's claim waits for a job that way (Waiting for a job).

curl -X POST http://127.0.0.1:8080/query -H 'Fenec-Wait: 30000' \
  -d '{"query":"del tasks where run_at <= now() order run_at limit 1 returning *"}'
  • What wakes it: a write to a collection it reads, and the time reaching a row's moment — a field compared with now(), a @ttl. A filter that reads the time any other way is refused (400), as is a request holding a put.
  • Wrote nothing means no row written, or a require not met; any other refusal is answered at once.
  • With Fenec-After the header is that wait's, as below, and holds no write.

Marking a read

Send Fenec-Read: replica with a request that only reads, and a router standing in a region where the tenant has a read replica answers it there rather than from the tenant's home (Read replicas); with Fenec-After and Fenec-History, as an answer from home named them, it is answered from nothing older than that change of that history (Reading your own writes), a subscription and a /_changes page as much as a read: each waits for it before its head. Every server runs a marked request read-only on every route — home, a replica, a single file; a statement, REST, /batch, an MCP tool, a change-stream consumer's commit — so a write sent with the mark is refused with 403 and words that say why, never landed; a value but replica is a 400. A copy that has not caught up with its primary yet answers it 503.

curl -X POST https://ap.example.com/t/acme/query -H 'Fenec-Read: replica' \
  -H 'Fenec-After: 1043' -H 'Fenec-History: 2-6c1f0a9e44d7b2c8' \
  -d '{"query":"get orders where customer = $1","params":["c-7"]}'

The data ceiling

With --max-memory, writes that would grow the data past the limit are refused with 507. Reads, deletes and compact still work.

Details

Inside fenec-server started with --max-memory, the listener holds its writes to that ceiling: above it, a statement that grows the data — a put, a patch, a create index — is refused with 507, a batch stops there as at an error, and reads, deletes and compact go on, since they are the way out. The rule and why it is there are under Server.

Refusals and their statuses

A refusal is a status and {"error": "..."}. The status says what to do about it; a /batch that stopped adds where (at) and what stayed applied (completed), a tenant's quota names itself (quota, and the Fenec-Quota header), and one to come back from says when (retry_after, the seconds of its Retry-After header: a page on another origin, or an app's replica, reads the body; a quota's 429 says it to the millisecond as well, retry_after_ms, which is the one to wait). A write whose outcome the server cannot know says so ("outcome": "unknown", a 500), with where it left the database in the body (seq, history) rather than in Fenec-Seq, which a client takes as its own position. Every SDK's error carries the rest; the outcome and its position are the Go, .NET, JavaScript and Python clients' (Go's and .NET's code outcome_unknown, JavaScript's and Python's outcome).

Subscriptions

GET /<name>/changes is a server-sent events stream: first the rows matching your filter, then each change to them as it happens.

curl -N 'http://127.0.0.1:8080/articles/changes?year=gte.2024'
# event: seed
# data: {"seq":12,"rows":[...]}
  • Limited separately from ordinary requests: --http-max-streams, 64 by default, a database's -- on a tenant node each tenant's own -- and each one of --max-connections too, which a node's tenants share (a tenant's share).
  • A row reaching its @ttl is told as a deletion at its time, as a write would be, not when the sweep deletes it a minute and its grace later.
  • Sent after a write (Fenec-After, and Fenec-History as the write's answer named it), a stream waits for it before its head, as a read does: its seed holds the write, or it is answered 504 with where the server stands (Reading your own writes). One resumed with since waits the same way: since is where the stream left off, not a write it must see.
  • Its head says where the server stood as it opened: Fenec-Seq, the change its seed is at or after, and Fenec-History, the history that change and every event's seq are of, as a write's answer names it (none on a database that never had a replica). A read sent after an event's seq to another copy goes with both (Reading your own writes): a number alone names no write across a failover. FenecHttp.live on a client reading near sends its runs so.
  • In the browser, Sync builds on this stream.
Details

GET /<name>/changes is a server-sent events stream: a seed carrying the current shape, then incremental diffs. No driver needed.

A subscription does not poll. fenec-core has no waiting primitive at all — there are no threads in wasm — it only reports that the change counter has reached a point, and fenec-http ties that to a Condvar. A 50 ms polling loop would take 20 read locks per second per subscriber and still add 50 ms of latency.

Every subscription is a connection and a thread, so they are counted separately from ordinary requests as well (--http-max-streams, default 64, a database's: on a tenant node each tenant's). Sharing one ceiling would let 100 subscribers shut the server to plain requests. A stream is also one of the node's --max-connections, the bound every tenant of a node shares, of which each tenant's streams take a quarter at most unless its quota says otherwise. The client-side layer built on this stream is Sync.

A row past its @ttl leaves every read at once and the file at the sweep, a minute and its grace later; a stream of its collection is told of it at its time. It works out when the next row of the collection reaches its time -- a step of the field's ordered index, again after each write to the collection -- sleeps until then if no write comes first, and reads the rows that reached it since it last looked, the shape ANDed in, telling each as a deletion as the sweep's delete would be told: a scoped stream of the rows it was sent alone, a shape that holds nothing (what FenecHttp.live opens) that something changed. Heard at the sweep, a courier whose phone went quiet stayed on a dispatcher's map 73 s after it had gone from every read; at its time, it is told about 10 ms after it. The sweep's delete comes after, a deletion of what is gone already.

What a stream costs, measured on an M1 with streams of a shape that holds nothing (what FenecHttp.live opens): 45 to 57 KB of resident memory and a thread each, and every write wakes every stream, which reads what it changed: a write's p50 went from 0.26 ms with none to 0.94 with 60 and 3.1 with 500. A page thousands view should not hold one a viewer; it polls (below).

Under a scoped token, a stream of a shape that holds nothing (where=false) is told of the writes to rows the token may read, and of nothing else: the server follows the token's own filter, keeps the ids it selects and sends none, and a write to one of them, or one of them leaving the token's rows, is a change holding no rows. ANDed with the token's filter, the shape matched nothing and FenecHttp.live never ran again; told of every write, the stream would hand the token the moments of other users' writes.

Polling a read

Send If-None-Match with a /query read and the answer carries an ETag: the change the database stood at. Sent back, the tag is answered 304, with no body and the query not run, while no write has touched a collection the read reads.

curl -si http://127.0.0.1:8080/query -H 'If-None-Match: "0"' \
  -d '{"query":"get inventory select available where sku = $1","params":["TENT-1"]}'
# HTTP/1.1 200 OK
# ETag: "48211"
curl -si http://127.0.0.1:8080/query -H 'If-None-Match: "48211"' -d '...the same...'
# HTTP/1.1 304 Not Modified
  • Nothing is held between polls: no stream, no thread, no wake-up at a write. FenecHttp.live(query, cb, { poll: 5000 }) polls so.
  • Untagged, and run each time: a read of a collection whose rows expire (@ttl), one calling now(), one holding an inner get — answers that move with no write.
  • A scoped token's tag is its answer's ("c…", a digest of the rows): its query runs every time and is answered 304 when the rows are the ones it had. Tagged by the change counter, 304 against 200 -- and a 304's speed -- told it when anyone wrote to what it reads, other users' rows among them, and the tag how many writes the database had taken.
Details

Whether a collection was written since a tag is the change ring's answer (Database::changed_collections_since): a tag older than the ring reaches, or a collection dropped since, counts as a change and the query runs. A read without the header is answered as before, no tag worked out. Over one keep-alive connection a 304 took 54 us at the median, against 55 for a read by key and 95 for a page of 24 run; the round trip is most of either. A browser keeps its connection between polls, so a public page polls through the site's own server or a proxy, which keeps few connections to fenec-server however many viewers it has.

A tag is a change of the copy that answered. A read replica holding that change of its history (Fenec-After) judges it as home does, but only up to where it stands: behind home it answers 304 to a write home holds, so FenecHttp.live polls home on a client reading near (Read replicas).

Change data capture

To see every write exactly as it happened — to feed a search index, Kafka or a read model — start the server with --cdc and read GET /_changes: one JSON line per write.

fenec-server --file data.fenec --http 127.0.0.1:8080 --sync 250 --cdc

curl -i 'http://127.0.0.1:8080/_changes?since=0&limit=1000&wait=10000'
# Content-Type: application/x-ndjson
# Fenec-Next: 5
# Fenec-Seq: 5
#
# {"seq":1,"at":1790784252138,"collection":"a","op":"create"}
# {"seq":2,"at":1790784252158,"collection":"a","op":"put","id":1,"doc":{"id":1,"n":1,"t":"x"}}
# {"seq":3,"at":1790784252158,"collection":"a","op":"put","id":2,"doc":{"id":2,"n":2,"t":"y"}}
# {"seq":4,"at":1790784252173,"collection":"a","op":"put","id":1,"doc":{"id":1,"n":1,"t":"z"}}
# {"seq":5,"at":1790784252187,"collection":"a","op":"del","id":2}
  • Send Fenec-Next back as the next since and nothing is missed or seen twice.
  • Only writes already on disk are handed out.
  • Fenec-Seq is the last write the database holds: when Fenec-Next has reached it, you have every write.
  • Sent with Fenec-After, a page waits until the server holds that change, as a read does, and its Fenec-Seq is never behind it; a write not yet on the server's disk comes on a later page.
Details

A subscription keeps a query's rows up to date, and a client that falls behind its ring of ids is sent the rows again. A service that must see every write — to index it elsewhere, send it on to Kafka, or keep a read model — reads GET /_changes instead: the writes on disk, documents and all, one JSON object a line, from any write the server still keeps.

  • seq is the change counter's number for the write, and Fenec-Next the last one in the answer: sent back as the next since, nothing is missed or had twice. Keep it where your consumer keeps its own state, and commit the two together.
  • Fenec-Seq on every answer is the last write the database holds, on disk or not yet, the writes the stream leaves out (a consumer's cursor, an idempotency key) among them. An answer whose Fenec-Next is that has every write there is: a worker that catches up before it serves knows it at once, where an empty page alone could not tell it from one whose writes are not on disk yet under --sync 250, and waited out pages to be sure. A Fenec-Next behind it has writes to come: read again with wait. A client that notes Fenec-Seq for Fenec-After reads a replica from there on.
  • A batch's writes are one record on disk and come together, numbered one by one; a cursor inside one goes on after the write it names.
  • Only what an fsync has covered is handed over, as a replica is fed: a write the server lost in a crash never reached a consumer.
  • since left out is the last write on disk: what is written from now on. limit is 1 000 unless given, 10 000 at most; wait is how long an answer with nothing in it waits for a write first, in milliseconds, 30 000 at most.
  • The server keeps as many writes as --replication-buffer holds (64 MiB unless given). A cursor further back is answered 410 with the first since it does serve, never with writes missing from the middle; one past the last write — another database's cursor, or this one restored — 409. The feed starts at the change counter when the server starts.
  • op is put, del, create, alter or drop; a put carries the document as it was written, as JSON writes a row.
  • It needs --http-token or no token at all: a scoped token's filter could not hold back the deletion of a row it never saw, and is refused (403).

--cdc keeps the feed a primary keeps for its replicas and feeds none; with --replication-token it is kept already, and a tenant node's tenants have theirs at /t/<tenant>/_changes. It needs --file and a --sync other than off. Keeping it cost nothing measurable: 16 400 single puts a second over HTTP either way, and 9 000 rows of 128 dimensions read back at 283 000 a second.

Consumers

A consumer with no storage of its own can let the server remember its place, like a Kafka consumer group: create it, read from it, then commit how far it got.

curl -X POST http://127.0.0.1:8080/_changes/consumers/search-index
curl -i 'http://127.0.0.1:8080/_changes?consumer=search-index&wait=10000'
# Fenec-Next: 42 -- index the lines, then:
curl -X POST http://127.0.0.1:8080/_changes/consumers/search-index -d '{"since": 42}'
  • At least once: a crash between reading and committing means those writes come again.
Details

A consumer that keeps no state of its own can have the server keep where it is, as a Kafka consumer group keeps its committed offset. Made with a POST — at the last write on disk unless the body names a since — it reads with ?consumer= from where it stands, and moves once it has done with what it read.

So a consumer has each write at least once, and a write again after a crash between reading it and committing. The cursors are rows of a _consumers collection, written as any write is — on disk before the answer under --sync always, and on the replicas — and their own writes are left out of the stream, the cursor going past them. A read with wait waits on past them too, so a consumer's own commit does not wake its next read, and a commit past nothing but cursors writes nothing: a consumer that commits after every answer, an empty one too, sits idle while nothing else is written. An unknown consumer is 404 rather than read from "now" each time, which would miss what is written between two reads; a commit past the last write on disk is 409. GET /_changes/consumers lists each consumer's since and how many writes it is behind.

Security

Protect the endpoint with a bearer token, and put a TLS terminator in front of it on an open network.

fenec-server --file data.fenec --http 127.0.0.1:8080 \
         --http-cors 'http://localhost:8787' \
         --http-token "$TOKEN" \
         --http-read-only
--http-token <value>every request needs Authorization: Bearer <value>, compared in constant time
--http-cors <origin>sets Access-Control-Allow-Origin; without it no CORS header is sent at all. A browser’s preflight (OPTIONS) from that origin, or any with *, is answered 204 before a token is asked for -- the browser sends none with it -- on a single database and under /t/<tenant>/. Every answer exposes Fenec-Seq, X-Request-Id and Retry-After and lets Idempotency-Key in. Through fenec-shard, give the router the flag: it answers the preflight itself and puts its headers on its own answers and in place of the node's (Tenants and sharding)
--http-read-onlywrite endpoints return 403; fenec-server's own path is unaffected
a replicaevery write returns 403, whatever the flags: its writes come from its primary
non-loopback addressrefuses to bind without a token, unless --insecure is given
Details

There is no TLS, the same rule as fenec-server: on an open network it needs a TLS terminator in front. A PATCH or DELETE without a filter is refused, and covering a whole collection needs a separate path rather than a flag — a key like ?all=true would collide with a field named all.

Limits are shared with fenec-server (--max-connections, --idle-timeout: a connection silent that long between requests is closed with nothing written, and one that went silent part way through a request is answered 408); the body ceiling is 64 MiB and the header block 64 KiB. Transfer-Encoding: chunked is unsupported and refused with 411, which beats reading half a body. A field whose name matches a clause name (select, order, limit, offset, count, where, group) cannot be filtered over HTTP; the FenecQL and fenec-server paths are unaffected.

A shape alone is not a security boundary. Under the server's own token, which ids changed is visible to a subscriber even when the rows are not. Rows are hidden by a scoped token, below.

Scoped access

Give each user a JSON Web Token, and a policy file decides which collections and which rows that token can read or write. A browser can then talk to the database directly.

# collection   access         rows                                role
notes          read,write     where owner = $jwt.sub
posts          read           where published = true or author = $jwt.sub
posts          write          where author = $jwt.sub
messages       read,insert    where room in $jwt.rooms
journal        read,insert    where owner = $jwt.sub
journal        append-only
accounts       update(balance, held)                              for app
orders         update(status, run_at)  where customer = $jwt.sub and status = "ready" and new.status = "cancelled"
orders         read(pickup, run_at)    where run_at <= now()                    for courier
positions      read           where courier in (get orders select courier where customer = $jwt.sub)
*              read                                               for dashboard
  • Reads only see the rows the rule allows.
  • Fields. read(pickup, run_at) shows the rows it admits with those fields alone, and id: a row shows the fields of every read rule admitting it, the rest null. A courier sees a ready order's pickup, and the customer's door once the order is theirs.
  • Writes must stay inside the rule, or get 403. write grants insert, update and delete, and each can be granted alone; update(balance, held) grants an update of those fields and no other.
  • Transitions. new.status reads a row as the write leaves it, and a bare name as it stands: the orders rule above lets a customer cancel a ready order, and not take a cancelled one back.
  • returning answers rows the token may read as the write leaves them: a courier who reads the orders they carry claims a ready one and is answered it, claimed.
  • append-only collections take inserts from scoped tokens, and refuse every update and delete with 403.
  • A list claim, such as "rooms": ["r1", "r2"], goes after in.
  • Another collection. in (get …) reads a rule's list from rows: the positions rule above lets a customer read where the courier carrying their order is, and nothing of the others.
  • The server's own --http-token still has full access.

A whole product built on these rules is examples/saas: sign-up and sessions owned by the app, a tenant per organisation behind fenec-shard, roles and teams as grants and list claims, live boards and search under each person's token, with its threat model and the attacks its tests try.

Details

--http-token is everything or nothing. With --jwt-secret the endpoint also takes HS256 JSON Web Tokens, each held to the rules of a --policy file, collection by collection and down to the rows, so a browser can talk to the database directly with a token per user:

fenec-server --file data.fenec --http 0.0.0.0:8080 --http-token "$ROOT" \
         --jwt-secret-file jwt.secret --policy policy.txt

fenec-server --jwt-secret-file jwt.secret --mint-token '{"sub":"alice","exp":1893456000}'
  • Reads get the rule's filter ANDed in at every level: the collection's where, each lookup below it, a subscription's shape, a count. A collection no rule grants a token anything on does not exist for it: 404, and absent from the list.
  • Writes get it twice, as PostgreSQL's USING and WITH CHECK: a set or del touches only the rows the filter matches, and every document written — a put, or a row a set rewrote — has to match it afterwards, or the write is refused with 403. A put that leaves out a field the filter pins to a claim gets the claim's value, so {"title":"a"} is alice's. A scoped put names no id, which could overwrite a row the token cannot see, and a scoped token changes no schema and runs no maintenance.
  • returning answers what the write wrote, so the rows it answers are held to the read rules: a set's as it wrote them, a del's as they were. A row the read rules leave out by a field the write does not change is passed over, as a get passes it over; a set that would leave a row the token may not read is refused with 403 and writes nothing. PostgreSQL asks its SELECT policies of the row before an UPDATE … RETURNING as well as after, which is why a courier who reads the orders they carry, claiming a ready order, would take nothing there and be told nothing; here the terms over the fields the set writes are asked of the row it leaves, and the claim answers the order, claimed. Without returning a write's rows are those its own rules reach, read rules or not.
  • Grants are read, insert, update and delete, joined by commas, and write is the three writes. An insert is a put of new documents, held to the filters of the rules granting insert; an update is a set and a delete a del, of rows the token may read and the filters of the rules granting them, a set's rows checked again after. update(balance, held, status) names the fields an update may change: a write over a row — a set, a REST PATCH or PUT, a line of a /batch — is judged by the fields it changes, and each of them must be one rule's whose filter admits the row before and after, or it is refused with 403 naming a field (a batch holding it is put back whole). A field written with the value it holds is not changed. Rules widen each other, each with its fields and its rows: notes update where owner = $jwt.sub beside notes update(title) changes every field of the token's notes and the title of anyone's. A token may insert into a collection it cannot read, such as an event stream: its reads of it are refused with 403 and it is not listed. expired grants the rows past their @ttl, which expired() reads (the reaper): a statement asking it is held to the filters of the rules granting expired beside the ones its operation needs, and neither write nor * grants it — a lapsed hold is the reaper's, not a user's to see again.
  • Fields a read shows. read(pickup, run_at) grants the rows its filter admits with those fields and id; read grants every field. A row shows the fields of every read rule admitting it, and the rest answer null — in /query, /batch, REST, each lookup level by its own collection's rules, a write's returning, a subscription's seed and changes, and the MCP tools. Beside orders read where courier = $jwt.sub for courier, the rule above shows a courier every ready order's pickup and the whole of the orders they carry. A field no read rule grants is not there: select * leaves it out, describe, /collections and /_schema do not list it, and naming it is refused (403) as a name the collection lacks is. 
    get orders where dropoff = $1                 -- no ready order matches, whatever its door
get orders where not (dropoff = $1)           -- every ready order does: no door told from another
get orders order dropoff                      -- 403: the order would tell the doors
get orders where courier = $1 order dropoff   -- $1 their sub: every order reached shows it
    A field withheld from a row must not show through what a statement does with it either. A where term reading it holds only where the row shows it — dropoff = $1 is asked as (courier = $jwt.sub and dropoff = $1), the or of the filters of the rules granting dropoff — in a get, a set or del, a lookup level, a facet's and an inner get's; and stops at the first false, so the term is never worked out over a value it may not see. order, group, having, a facet, an aggregate, match, near, a highlight, a lookup key and a set's values read a field only where every row they reach shows it, and are refused with 403 naming it otherwise: when every read rule of the collection grants it, or when one rule granting it has no filter or one whose and terms are each a term of the statement's own where, parameters bound — as the last line above. A computed column over such a field is null where the row does not show it and never worked out there, and an inner get's column of one is listed from the rows showing it. A write reaches the rows it reached before; its returning is masked as a read's rows are. PostgreSQL's column privileges are a role's and the same on every row, and refuse a statement naming a column the role lacks, SELECT * included; a column shown on some rows is a view of CASE WHEN … THEN col END there, whose WHERE reads NULL on the rest where this reads the term as false. A token whose rules name no fields reads as before; one whose do loses the stored-bytes path of a plain get where a column is masked, and pays each rule that could show a row more, per row: over HTTP on loopback a row by id took 28.0 µs against 26.0 under the same two rules naming no fields, a page of twenty 39.5 against 34.4, about 0.13 µs a row of it in process (make policy-bench).
  • Transitions. A rule's filter reads the row as it stands, and new.<field> reads it as the write leaves it, as new. names the document in an upsert's else set. One filter asked of the row before and after cannot say which way a row may go: status = "ready" or status = "cancelled" lets a customer cancel an order and take a cancelled one back, and run_at granted lets them move it to the head of the queue. A rule naming new. is a transition, asked of the two rows together: 
    # a customer cancels a ready order, out of the queue for good
orders  update(status, run_at)  where customer = $jwt.sub and courier is null and status = "ready" and new.status = "cancelled" and new.run_at is null  for customer
# a courier claims an order whose lease is out, for themselves, counting the attempt
orders  update(status, run_at, courier, claim, attempts)  where run_at <= now() and new.status = "assigned" and new.courier = $jwt.sub and new.attempts = attempts + 1  for courier
# and delivers only what they carry
orders  update(status, delivered_at, run_at, claim)  where courier = $jwt.sub and (status = "assigned" or status = "picked") and new.status = "delivered" and new.run_at is null  for courier
    A write over a row is the token's when one rule granting update names every field it changes (or names none) and admits the change: a transition by being true of the row before and after together, any other rule by admitting each. Rules naming no fields and no new. widen each other as before, the row before one rule's and the row after another's, as PostgreSQL's permissive policies do; a transition lends neither half. A set picks the rows a transition reaches by what the row before can answer of it — status = "ready" of the first rule above — and each row it writes is then asked the whole rule, a refusal 403 and the statement (or the batch) put back. The row after is held to what the rule says of new. and nothing more: the field list keeps the rest where it was, so a transition with none should pin what must not move (new.customer = customer). A rule naming new. grants update alone — a read, an insert or a delete has no row after, or none before — and one granting more stops the server at startup. A scoped set of one row over HTTP on loopback took 5.0 µs more than the server token's 45 µs under a plain rule, 5.7–5.9 under a field list and 6.1–6.8 under a transition (make policy-bench).
  • append-only is a line of its own, journal append-only, with no filter and no role. No scoped token updates or deletes there, by any route — /query, REST, /batch — whatever its rules grant: write and * mean insert there, and a rule naming update or delete for the collection stops the server at startup. It binds JSON Web Tokens and not the server's own token: corrections, erasure and @ttl's sweep stay with whoever holds that, and an app server that should only append is given a scoped token of its own, a role for instance.
  • List claims. A claim that is a JSON array goes after in: room in $jwt.rooms matches the rooms it lists, room in [$jwt.rooms, "lobby"] those and one more, and a text claim there is a list of one. It holds reads, writes (WITH CHECK: a post into a room the list does not hold is 403) and subscriptions alike. A token whose list claim holds more than 1 000 values is refused (401). A role claim may be a list too, and a rule for a role applies when the list holds it. Membership kept in another collection is a rule's in (get …) (below).
  • Rules that read another collection. A rule's filter takes in (get …), its claims bound inside as anywhere else: 
    # a customer follows the courier carrying their order
positions  read  where courier in (get orders select courier where customer = $jwt.sub and (status = "assigned" or status = "picked"))  for customer
# a member reads and posts in the rooms they belong to
messages   read,insert  where room in (get members select room where user = $jwt.sub)
    The inner get reads the rows of its collection the token's own get would, held to the token's rules there; one no rule lets the token read gives none of its rows, as PostgreSQL's row security gives a policy's subquery none of a table no policy grants. The fields it reads are the policy's own: its list is never shown, only what it admits. It is answered before each statement, under the lock that runs it, as the in list it is: reads, a lookup level, a facet, a match and an agent's MCP tools see the list as it stands, and a write's WITH CHECK — an insert's document, an update's row before and after, a transition's pair, an upsert's row written over, returning's rows — is tested by it where no query could run. A rule naming the fields it shows may read another collection too, positions read(courier, at, loc) where courier in (get orders …): each row is shown the fields of the rules admitting it as their lists stand, in a read, a lookup level and a stream (Fields a read shows). A /batch answers it again for each statement: a courier's claim, then a read of the customer's door the claim lets them read, is one round trip. The list is held to a list claim's bound, 1 000 values, and a statement whose list would hold more is refused (400) rather than answered with a list cut short; a value held by many rows counts once. Rules that read each other's collections — positions reading orders whose rules read positions, at any depth, whatever their roles — stop the server at startup, since none of them could be answered first; so do a rule on * that reads a collection, a claim anywhere in the inner get but its where, and what an inner get may not say anyway. A scoped subscription whose rules read another collection is bound again when that collection is written: the courier enters a customer's stream of positions as the order is claimed and leaves it, a deletion of the row it was sent, as it is delivered, with no write to positions between. It costs one inner get a statement — a @hash bucket's read, 1.8 to 2.1 µs in process and 4.3 to 4.7 µs over HTTP on loopback above a rule naming a claim — and a stream one at each write to the collection its rules read: beside 100 scoped streams a write took 1.89 ms of the server's CPU against 1.65 under a rule naming the courier as a claim, every scoped stream looking at every write either way. A token with no such rule runs as it did (make policy-bench, ARGS=streams).
  • match scores over the rows the token may read. BM25's statistics — how many documents, their mean length, how many hold each word — are taken over the rows the query's filter selects, the token's rules among them, not over the collection: there a user's own memo scored 9.87, then 4.79 once another user wrote 200 private memos holding the same word, which told the first how many of the second's held it. A score is what a collection holding the user's rows alone would give, and so is the order of match, rerank's candidates and fuse's text side. It costs the token's query its rows' lengths and each word's count among them: over 100 000 documents, a filter keeping 2.5% took 0.16 ms and takes 0.24, one keeping half 5.4 and 6.2. The server's own token scores over the collection, as before.
  • Subscriptions are told only of rows they were sent: a scoped subscriber hears of a row leaving its shape only if the row was in it, so the ids other users write never reach it — rows leaving as a rule that reads another collection moves among them. Where a rule names the fields it shows, a row written again that shows what it showed is not sent: a write to a field the subscriber does not see would tell it when.
  • Tokens are HS256, or RS256 with --jwt-keys (below). The algorithm is the key's, not the token's, so alg: none is refused. Every token is checked against exp and nbf, and one with no exp is refused (401): it would be good for ever, and a token that leaked could only be outlived by rotating every key. --jwt-require-exp off takes such tokens again, and --jwt-max-age <s> also refuses one whose exp lies further ahead than that. --mint-token gives claims naming no exp one an hour away. A rule with for applies to tokens whose role claim names that role, or lists it; rules on one collection widen each other; a rule whose filter names a claim the token lacks does not apply. A subscription is checked when it opens, and ended at its token's exp with event: error and {"error":"the token has expired","status":401}: the client takes it as a refused request, fetches a fresh token and opens the stream again (FenecHttp.live, subscribe, the sync layer, Go's *Error and .NET's Event.Status). Without it a stream outlived its token, and a member taken off a team heard the team until the client went away. No other request is held open past its token, nor before it: a read, a subscription or a /_changes page sent with Fenec-After waits only once its token is taken — one the server refuses is answered 401 at once, never after the wait — and is checked again once its wait ends, a write held by Fenec-Wait asks its token again each time it runs, and /_changes takes no scoped token.
  • Refusals tell a scoped token only what it may read: a @unique clash (409) names the field, not the document holding the value nor the value, since that row is another user's.
  • Tenants. On a --dir node a token reaches /t/<t>/ only when its tenant claim names <t> (a text, or a list holding it), and is refused with 403 under every other tenant's prefix; one naming no tenant is refused there unless the node runs with --jwt-unbound-tenants (Tokens).

The server's own --http-token keeps full access alongside.

Keys, rotation and identity providers

To accept tokens from Auth0, Clerk, Firebase or another identity provider, give --jwt-keys its published key file. Edit the file to rotate keys; no restart is needed.

# the provider's public keys, as it publishes them
curl -s https://example.auth0.com/.well-known/jwks.json > jwks.json
fenec-server --file data.fenec --http 0.0.0.0:8080 --jwt-keys jwks.json --policy policy.txt
Details

--jwt-keys takes a JWKS file, {"keys": [...]}, in place of a secret. An oct key verifies HS256 tokens and needs at least 32 bytes. An RSA key of at least 2048 bits verifies RS256 tokens, which is what Auth0, Clerk, Firebase and most identity providers sign with. A token issued by one of them is taken with its public keys alone. Keys of any other kind (EC, OKP) are skipped. A key is only used for its own algorithm: an RSA modulus is public, and taken as an HS256 secret it would let anyone sign. A token that names a kid is checked against that key only. A token without one is checked against each key of its algorithm.

The server looks at the file at most once a second and reads it again when it has changed, so keys rotate without a restart. To rotate:

  1. Add the new key to the file.
  2. Start signing with it.
  3. Once the tokens signed with the old key have expired, remove the old key.

If the file can no longer be read, the server keeps the keys it read last and logs why. --mint-token signs with the first oct key and names its kid.

A token that has already been verified is kept by its text, so that later requests with it skip the check. The server keeps up to 4 096 tokens, and the kept tokens are dropped whenever the keys change. Checking a token from that cache takes 0.3 µs for HS256 and 0.5 µs for RS256. Checking a new one takes 2.9 µs for HS256 and 38 µs for RS256 over 2048 bits (Apple M1).
