HTTP endpoint

For clients that want no driver at all: fetch, curl, or any language's standard library. The schema is already in the database, so the surface is derived from it.

fenec-pg --file data.fenec --http 127.0.0.1:8080

curl 'http://127.0.0.1:8080/articles?select=title,year&year=gte.2024&tags=has.rust&order=year.desc&limit=10'
# [{"title":"the rust book","year":2024}]

curl 'http://127.0.0.1:8080/articles?year=gte.2024&count'
# {"count":1}

curl -X POST http://127.0.0.1:8080/articles -d '{"title":"new","year":2025}'
# {"inserted":1}

Not a separate binary. The HTTP endpoint is a second listener in the same process as fenec-pg. fenecdb has a single writer, and two processes writing one file corrupt it. Being in the same process also keeps the sync policy, the checkpoint, the memory ceiling and the shutdown signal in one place — --sync always covers HTTP writes too.

With --replication-token, /_replication is taken as well: the stream a replica is fed, its status, and a replica's promotion — see Replication. It asks for that token rather than --http-token, and a collection named _replication is then out of HTTP's reach.

/_metrics is the server's statements, latency and data in Prometheus's text format, readable with --http-token or the admin token — see Monitoring. The underscore keeps it out of the way of a collection called metrics; a collection called _metrics cannot be read over GET.

Values are parsed by the field's type: ?year=gte.2024 is an int, ?published=gte.2024-01-01 is a timestamp. An unknown field returns 404. where= exists for what the pattern cannot hold — or groups and function calls.

Vector search

near is a POST rather than a query parameter because a 768-dimension embedding does not fit in a query string. Squeezing it into the URL — base64, truncation — is unreadable and runs into proxy and server URL ceilings. PostgREST's model does not cover fenecdb's headline feature, so near gets its own endpoint, and it takes a filter in the body.

curl -X POST http://127.0.0.1:8080/articles/near -d '{
  "vector": [0.1, 0.2, 0.3],
  "ef": 128, "limit": 5,
  "select": ["title"],
  "where": "year >= 2024"
}'
# [{"title":"the rust book","_score":0.97}]

If the collection has a single vector field, field can be left out. Filters in the query string are anded with the where in the body.

A vector in an answer, and a _score, is its f32s written as the shortest decimals that read back as them — 0.1 as it was written, the text pgvector and the pg wire give — rather than the 0.10000000149011612 of the f64 each widens to. A reader that takes a number as an f64 and rounds it to f32, as a Float32Array does, gets every one back: the one f32 an f64 would round away, 7.038531e-26, is written as its f64.

A "match" makes it hybrid: BM25 over the collection's @text field ranks the same request, and the two rankings are fused by reciprocal rank (fuse). match_field names the text field when there are several; fuse_k and candidates are the rank offset and how many candidates each side ranks.

curl -X POST http://127.0.0.1:8080/articles/near -d '{
  "vector": [0.1, 0.2, 0.3],
  "match": "borrow checker lifetimes",
  "limit": 10
}'

Raw FenecQL

When the REST shape does not fit, send the language itself. Parameters stay parameters.

curl -X POST http://127.0.0.1:8080/query \
  -H 'content-type: application/json' \
  -d '{"query":"get articles where year >= $1 limit 10","params":[2024]}'

From Python, pip install fenecdb — the standard library alone — makes the same calls, blocking or in an event loop:

from fenecdb import AsyncClient, Client

db = Client("http://127.0.0.1:8080", token="...")
db.query("get articles where year >= $1 limit 10", [2024])

async with AsyncClient("http://127.0.0.1:8080", token="...") as db:
    await db.query("get articles where year >= $1 limit 10", [2024])

AsyncClient keeps one connection alive and opens it again when the server has closed it; calls made at once over one client go one after another over it, so requests side by side take a client each.

Embedding a collection

curl 'http://127.0.0.1:8080/products?limit=20&select=name\
&lookup=reviews&reviews.on=product_id&reviews.stars=gte.4\
&reviews.order=created.desc&reviews.limit=3'
# [{"name":"Kahve","reviews":[{...},{...},{...}]}, ...]

lookup=<name> names the collection once; every key prefixed with it configures the clause — on (required, the child's field holding the key), parent, select, order, limit, offset, required, where, and any field name as a condition, in the same op.value form the parent's filters use. Prefixing is what keeps the two sides apart in a query string, the way the clause's position does in FenecQL.

curl 'http://127.0.0.1:8080/shops?limit=20&select=name\
&lookup=orders,lines&orders.on=shop_id&orders.limit=3\
&lines.on=order_id&lines.limit=5'
# [{"name":"Merkez","orders":[{"code":"A","lines":[{...}]}, ...]}, ...]

A comma-separated list chains, read left to right, each name binding to the one before it and each level keeping its own prefix. A query string has no position to scope by, so the order is written out; the meaning is the same one FenecQL gets from position, up to the same 8 levels.

lookup is a reserved key here, so a field named lookup cannot be filtered over the REST path — the FenecQL and fenec-pg paths are unaffected, as with the other reserved names.

A query with a lookup answers with the children nested under the collection's name — one object per parent, with an empty array where nothing matched, and a chain nests all the way down. The fenec-pg side of the same query flattens them into the parent row instead, because a PostgreSQL row cannot nest: one row per root-to-leaf path, with nulls below the first level that ran out.

curl -X POST http://127.0.0.1:8080/query \
  -H 'content-type: application/json' \
  -d '{"query":"get products limit 20 lookup reviews on product_id limit 3"}'
# [{"id":1,"name":"Kahve","reviews":[{"id":1,"stars":5,"body":"guzel"}]}, ...]

Batches

POST /batch takes one query body per line as NDJSON. The statements run in order under a single write lock, as one block: their writes land in the file as one record, or none of them do. The first error puts back what the statements before it did, and the answer says so:

{"error":"collection `tasks` has no field `nofield`","completed":0}

No other writer slips in between, a read in the batch sees the writes before it, and a subscriber is woken once, for all of them. A create, a drop or a create index in it is put back with the rest. A compact rewrites the file, which cannot be put back, so a batch holding one runs each statement on its own, as the pg wire runs a text holding one: it stops at the first error, and completed says how many were applied. Either way a failed batch says what it left behind, because a silent error would permanently separate a client's optimistic local state from the server's.

The body is NDJSON rather than a JSON array because fenecdb's JSON parser deliberately does not accept nested objects, so {"statements":[{...}]} could not be parsed anyway. Instead of writing a second parser, the boundary was put at the end of a line — by the escaping rules no JSON encoder can write a bare newline into the body.

The data ceiling

Inside fenec-pg started with --max-memory, the listener holds its writes to the ceiling the pg wire holds its own to: above it, a statement that grows the data — a put, a patch, a create index — is refused with 507, a batch stops there as at an error, and reads, deletes and compact go on, since they are the way out. The rule and why it is there are under PostgreSQL server.

Subscriptions

GET /<name>/changes is a server-sent events stream: a seed carrying the current shape, then incremental diffs. No driver needed.

curl -N 'http://127.0.0.1:8080/articles/changes?year=gte.2024'
# event: seed
# data: {"seq":12,"rows":[...]}

A subscription does not poll. fenec-core has no waiting primitive at all — there are no threads in wasm — it only reports that the change counter has reached a point, and fenec-http ties that to a Condvar. A 50 ms polling loop would take 20 read locks per second per subscriber and still add 50 ms of latency.

Every subscription is a connection and a thread, so they are counted separately from ordinary requests (--http-max-streams, default 64). Sharing one ceiling would let 100 subscribers shut the server to plain requests. The client-side layer built on this stream is Sync.

Change data capture

A subscription keeps a query's rows up to date, and a client that falls behind its ring of ids is sent the rows again. A service that must see every write — to index it elsewhere, send it on to Kafka, or keep a read model — reads GET /_changes instead: the writes on disk, documents and all, one JSON object a line, from any write the server still keeps.

fenec-pg --file data.fenec --http 127.0.0.1:8080 --sync 250 --cdc

curl -i 'http://127.0.0.1:8080/_changes?since=0&limit=1000&wait=10000'
# Content-Type: application/x-ndjson
# Fenec-Next: 5
#
# {"seq":1,"at":1790784252138,"collection":"a","op":"create"}
# {"seq":2,"at":1790784252158,"collection":"a","op":"put","id":1,"doc":{"id":1,"n":1,"t":"x"}}
# {"seq":3,"at":1790784252158,"collection":"a","op":"put","id":2,"doc":{"id":2,"n":2,"t":"y"}}
# {"seq":4,"at":1790784252173,"collection":"a","op":"put","id":1,"doc":{"id":1,"n":1,"t":"z"}}
# {"seq":5,"at":1790784252187,"collection":"a","op":"del","id":2}
  • seq is the change counter's number for the write, and Fenec-Next the last one in the answer: sent back as the next since, nothing is missed or had twice. Keep it where your consumer keeps its own state, and commit the two together.
  • A transaction's writes are one record on disk and come together, numbered one by one; a cursor inside one goes on after the write it names.
  • Only what an fsync has covered is handed over, as a replica is fed: a write the server lost in a crash never reached a consumer.
  • since left out is the last write on disk: what is written from now on. limit is 1 000 unless given, 10 000 at most; wait is how long an answer with nothing in it waits for a write first, in milliseconds, 30 000 at most.
  • The server keeps as many writes as --replication-buffer holds (64 MiB unless given). A cursor further back is answered 410 with the first since it does serve, never with writes missing from the middle; one past the last write — another database's cursor, or this one restored — 409. The feed starts at the change counter when the server starts.
  • op is put, del, create, alter or drop; a put carries the document as it was written, as JSON writes a row.
  • It needs --http-token or no token at all: a scoped token's filter could not hold back the deletion of a row it never saw, and is refused (403).

Consumers

A consumer that keeps no state of its own can have the server keep where it is, as a Kafka consumer group keeps its committed offset. Made with a POST — at the last write on disk unless the body names a since — it reads with ?consumer= from where it stands, and moves once it has done with what it read:

curl -X POST http://127.0.0.1:8080/_changes/consumers/search-index
curl -i 'http://127.0.0.1:8080/_changes?consumer=search-index&wait=10000'
# Fenec-Next: 42 -- index the lines, then:
curl -X POST http://127.0.0.1:8080/_changes/consumers/search-index -d '{"since": 42}'

So a consumer has each write at least once, and a write again after a crash between reading it and committing. The cursors are rows of a _consumers collection, written as any write is — on disk before the answer under --sync always, and on the replicas — and their own writes are left out of the stream, the cursor going past them. An unknown consumer is 404 rather than read from "now" each time, which would miss what is written between two reads; a commit past the last write on disk is 409. GET /_changes/consumers lists each consumer's since and how many writes it is behind.

--cdc keeps the feed a primary keeps for its replicas and feeds none; with --replication-token it is kept already, and a tenant node's tenants have theirs at /t/<tenant>/_changes. It needs --file and a --sync other than off. Keeping it cost nothing measurable: 16 400 single puts a second over HTTP either way, and 9 000 rows of 128 dimensions read back at 283 000 a second.

Security

--http-token <value>every request needs Authorization: Bearer <value>, compared in constant time
--http-cors <origin>sets Access-Control-Allow-Origin; without it no CORS header is sent at all
--http-read-onlywrite endpoints return 403; fenec-pg's own path is unaffected
a replicaevery write returns 403, whatever the flags: its writes come from its primary
non-loopback addressrefuses to bind without a token, unless --insecure is given

There is no TLS, the same rule as fenec-pg: on an open network it needs a TLS terminator in front. A PATCH or DELETE without a filter is refused, and covering a whole collection needs a separate path rather than a flag — a key like ?all=true would collide with a field named all.

Limits are shared with fenec-pg (--max-connections, --idle-timeout); the body ceiling is 64 MiB and the header block 64 KiB. Transfer-Encoding: chunked is unsupported and refused with 411, which beats reading half a body. A field whose name matches a clause name (select, order, limit, offset, count, where, group) cannot be filtered over HTTP; the FenecQL and fenec-pg paths are unaffected.

A shape alone is not a security boundary. Under the server's own token, which ids changed is visible to a subscriber even when the rows are not. Rows are hidden by a scoped token, below.

fenec-pg --file data.fenec --http 127.0.0.1:8080 \
         --http-cors 'http://localhost:8787' \
         --http-token "$TOKEN" \
         --http-read-only

Scoped access

--http-token is everything or nothing. With --jwt-secret the endpoint also takes HS256 JSON Web Tokens, each held to the rules of a --policy file, collection by collection and down to the rows, so a browser can talk to the database directly with a token per user:

# collection   access       rows                                role
notes          read,write   where owner = $jwt.sub
posts          read         where published = true or author = $jwt.sub
posts          write        where author = $jwt.sub
*              read                                             for dashboard

fenec-pg --file data.fenec --http 0.0.0.0:8080 --http-token "$ROOT" \
         --jwt-secret-file jwt.secret --policy policy.txt

fenec-pg --jwt-secret-file jwt.secret --mint-token '{"sub":"alice","exp":1893456000}'
  • Reads get the rule's filter ANDed in at every level: the collection's where, each lookup below it, a subscription's shape, a count. A collection no rule lets a token read does not exist for it: 404, and absent from the list.
  • Writes get it twice, as PostgreSQL's USING and WITH CHECK: a set or del touches only the rows the filter matches, and every document written — a put, or a row a set rewrote — has to match it afterwards, or the write is refused with 403. A put that leaves out a field the filter pins to a claim gets the claim's value, so {"title":"a"} is alice's. A scoped put names no id, which could overwrite a row the token cannot see, and a scoped token changes no schema and runs no maintenance.
  • Subscriptions are told only of rows they were sent: a scoped subscriber hears of a row leaving its shape only if the row was in it, so the ids other users write never reach it.
  • Tokens are HS256 only — the algorithm is the server's, not the token's, so alg: none is refused — and checked against exp and nbf. A rule with for applies to tokens whose role claim names that role; rules on one collection widen each other; a rule whose filter names a claim the token lacks does not apply. A subscription is checked when it opens.

The server's own --http-token keeps full access alongside, and the PostgreSQL listener is not affected: it has its own password.
