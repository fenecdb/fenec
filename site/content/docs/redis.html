Instead of Redis

The jobs an app adds Redis for — counters, rate limits, locks, sessions — done by the database it already has, each a statement or two.

Three things make these work. A set can read the row it writes ({n: n + 1}), and the read and the write happen under the one writer's lock, so an increment is atomic. Every write answers how many rows it changed, so a write that names what it expects says whether it found it. And @ttl lets a row expire, and a write take its place the moment it does. See Writes that read the row for the rules.

Every FenecQL block on this page is run, statement by statement, by a test (crates/fenec-core/tests/redis_docs.rs), and each -- → n is the answer it checks. The costs are make counters-bench on an M1 Air, in process unless said otherwise; over HTTP a request adds its round trip.

Counter

An increment is a set that reads the field it writes.

create collection counters (name text @unique, n int)
put counters {name: "visits", n: 0}
set counters {n: n + 1} where name = "visits"     -- → 1
get counters select n where name = "visits"       -- → 1
  • None is lost. Sixteen HTTP clients each incrementing one key 10 000 times ended at 160 000, 102 000 increments a second against fenec-server; sixteen threads in process, 320 000 a second.
  • An increment costs 1.36 us in process.
  • From nothing: coalesce(n, 0) + 1 counts a row with no n yet; n + 1 over a null is null.

In JavaScript, inc() writes the coalesce for you:

import { connect, inc } from '@fenecdb/web/client';

const db = connect('http://127.0.0.1:8080');
await db.from('counters').where('name', 'visits').update({ n: inc(1) });

Python's inc(1), Go's fenecdb.Inc(1), .NET's Computed.Inc(1), and Swift's, Kotlin's and Dart's builders render the same text.

Fixed-window rate limit

A row a client and window, made if absent and expiring after the window; the increment names the limit, so its answer is the decision.

create collection hits (key text @unique, n int, at timestamp @ttl(2m))
put hits {key: "ip1:29630000", n: 0, at: now()} if absent    -- → 1: the window's row
put hits {key: "ip1:29630000", n: 0, at: now()} if absent    -- → 0: there already
set hits {n: n + 1} where key = "ip1:29630000" and n < 2     -- → 1: allowed
set hits {n: n + 1} where key = "ip1:29630000" and n < 2     -- → 1: allowed
set hits {n: n + 1} where key = "ip1:29630000" and n < 2     -- → 0: over the limit
  • The window is in the key — here the minute, floor(now / 60000), which the client works out — so a new window is a new row, and @ttl lets the old ones go.
  • A request costs its two statements, 3.5 us; send them as one /batch for one round trip.

Lock with expiry

A lock is a row: taken by the write that makes it, held while it lives, and free again once its time passes, so a holder that dies cannot keep it.

create collection locks (name text @unique, owner text, at timestamp @ttl(30s))
put locks {name: "nightly", owner: "w1", at: now()} if absent      -- → 1: w1 holds it
put locks {name: "nightly", owner: "w2", at: now()} if absent      -- → 0: w2 does not
set locks {at: now()} where name = "nightly" and owner = "w1"      -- → 1: renewed
set locks {at: now()} where name = "nightly" and owner = "w2"      -- → 0: not w2's
del locks where name = "nightly" and owner = "w1"                  -- → 1: released
  • Exactly one wins. The write lock decides: of any number of clients racing, one is answered 1 and the rest 0 — sixteen threads are raced for it in crates/fenec-core/tests/writes.rs, and again once its time has passed.
  • Thirty seconds after its last renewal the row is out of every read, the renewal's answer is 0 — the holder has lost it — and the next put … if absent takes it, the old row deleted in the same statement. The sweeper need not have come by.
  • Costs: refused while held 0.91 us, renewed 2.34, released and taken again 2.67.
Details

if absent passes over a document whose @unique value or id a live row holds, and counts what it wrote: Redis's SET NX. insert refuses the same document with a 409 instead, which serves too, but makes losing the race an error to catch and aborts a /batch it is part of. A lock named by a number can be its id: put locks {id: 1, owner: $1, at: now()} if absent.

Time is the server's clock, and a lock lasts its ttl from its last renewal: renew well within it. As with any lock that expires, a holder paused past its ttl may still believe it holds the lock; give the work it guards a check of its own — the version below — where that matters.

Optimistic concurrency

Read a row with its version; write it back only where the version is still the one read, and move the version on in the same statement.

create collection docs (body text, version int)
put docs {id: 7, body: "draft", version: 1}
get docs select body, version where id = 7                                   -- → "draft"
set docs {body: "final", version: version + 1} where id = 7 and version = 1   -- → 1: written
set docs {body: "other", version: version + 1} where id = 7 and version = 1   -- → 0: read again
set docs {body: "other", version: version + 1} where id = 7 and version = 1 require 1   -- → refused: 412, and its batch put back
  • 0 means someone wrote first: read the row again and retry, or tell the user.
  • In a /batch, add require 1: a 0 would let the statements after it go on, where a lost race should stop them. With it the write that found another version is refused (412) and the batch is put back whole (Writes that must find their rows).
  • Costs: a write that wins 1.13 us, one that loses 0.66.

Session store

A session is a row that lives while it is used: @ttl on the time it was last seen, a @unique token to find it by.

create collection sessions (token text @unique, user text, data json, seen timestamp @ttl(30m))
put sessions {token: "s-81f2", user: "ada", data: {"cart": 2}, seen: now()}
get sessions select user where token = "s-81f2"            -- → "ada"
set sessions {seen: now()} where token = "s-81f2"           -- → 1: seen again
del sessions where token = "s-81f2"                         -- → 1: signed out
  • An idle session is gone at once for every read, thirty minutes after it was last seen, and the server deletes it within a minute (Rows that expire).
  • Costs, over 10 000 sessions: a read 1.32 us, seen again 2.26.

Leaderboard

A score field with @sorted: the top of the board is a walk of the index from its end, and a player's rank is a count.

create collection scores (player text @unique, score int @sorted)
put scores [{player: "ada", score: 0}, {player: "bo", score: 90}]
set scores {score: score + 120} where player = "ada"            -- → 1
get scores select player, score order score desc limit 10       -- → "ada"
get scores where score > 120 count                              -- → 0: ada is first
  • Costs, over 100 000 players: a score added 1.79 us, the top ten 1.52. A player's rank is a count of the scores above it, the index's range gathered: 1.5 ms at the median of the board.

Job queue

A job is a row. A worker claims a batch with one statement, which finds the oldest ready jobs and makes each its own for a lease, and acks a job by deleting it.

create collection jobs (payload json, run_at timestamp @sorted, owner text, attempts int)
put jobs [{payload: {"to": "ada"}, run_at: now(), attempts: 0}, {payload: {"to": "bo"}, run_at: now(), attempts: 0}]
set jobs {owner: "w1", run_at: now() + 30000, attempts: attempts + 1} where run_at <= now() order run_at limit 10 returning id   -- → 1: both, w1's for 30 s
del jobs where id = 1 and owner = "w1" require 1                       -- → 1: done
  • None is taken twice: the claim finds its jobs and writes them under the write lock. A job whose worker died is ready again once its lease lapses, and the next claim takes it.
  • Costs, over a million jobs: a claim of ten 18.7 us; sixteen threads claimed and acked them all in 5.4 s, 185 800 jobs a second, and sixteen HTTP clients at 138 500.
  • Retries with a backoff, dead letters, delays and priorities are on their own page, Job queues.

Change notification

A client that wants to hear of a change subscribes to the rows it cares about; a service that must see every write reads the change stream.

# the rows of a shape, then each change to them as it lands
curl -N 'http://127.0.0.1:8080/jobs/changes?state=eq.ready'

# every write on disk, from where a named consumer left off
curl 'http://127.0.0.1:8080/_changes?consumer=mailer&wait=10000'
  • A subscription (Subscriptions) is woken by the write, not by polling: from a write sent to its event read by a subscriber took 0.037 ms at the median and 0.103 at p99 over HTTP on one machine.
  • The change stream (Change data capture) hands out every write on disk exactly once to a consumer that sends back where it is, which a subscription — a shape's rows kept up to date — does not promise.

Places near a point

GEOADD and GEOSEARCH are a geo field with @geo: the metres between two points, the rows within a radius or a box, the nearest first — see Points and distances.

create collection sicily (name text, loc geo @geo)
put sicily [{name: "Palermo", loc: [13.361389, 38.115556]}, {name: "Catania", loc: [15.087269, 37.502669]}]   -- → 2
get sicily select name where distance(loc, [15, 37]) <= 200000 near loc [15, 37] limit 10   -- → "Catania"

What this does not cover

  • A cache in front of another database. There is no eviction by memory or by use, no LRU: a row lives until its @ttl, and the file is not a cache that can lose what it holds.
  • HyperLogLog and Redis's other probabilistic structures. A count of distinct values is exact, and costs a scan or a @hash index's buckets.
  • Pub/sub without storage. Every message is a write that lands in the file and moves the change counter; there is no fire-and-forget channel. For messages that need not be kept, a row with a short @ttl and a subscription is the nearest.
  • A blocking claim — BLPOP, a worker waiting on an empty list and handed the next job. A claim of an empty queue answers no rows at once; a worker sleeps, or holds a subscription to the queue and claims when it hears a write (Job queues).
  • Sub-millisecond latency across a network as Redis's design goal: a write here is durable by the server's --sync policy, and a request is HTTP.
