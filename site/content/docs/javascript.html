JavaScript

One dependency-free ES module runs fenecdb in the page: open a database, query it, and keep it between visits.

Opening a database

Copy fenec.js and fenec.wasm next to your page, open the module, and run FenecQL or the query builder. persist keeps the database in IndexedDB and restore reads it back.

import { Fenec, persist, restore } from './fenec.js';

const db = await Fenec.open('./fenec.wasm');

db.run('create collection docs (title text, embed vector<384> @hnsw(cosine))');
db.run('put docs {title: $1, embed: $2}', ['hello', embedding]);

const { rows } = db.run('get docs near embed $1 limit 5', [queryVector]);
const titles = await db.from('docs').select('title').limit(10).rows();   // the builder

await persist(db);     // into IndexedDB: the image once, then only the writes since
await restore(db);     // read it back
  • db.run() is synchronous; the builder's endpoints return promises.
  • Text in a collation also needs the collate/ directory beside the module (below).
Details

web/fenec.js is one dependency-free ES module: the WebAssembly glue, the query builder, the HTTP client and the sync layer. Copy two files — and the collate/ directory beside the module, for text in a collation — and you are done.

db.run() is synchronous because raw FenecQL is a single wasm call. The builder's endpoints return promises, because a builder has to pick its transport first.

Keeping a database

In a dedicated worker, openFile keeps the database in a file of the origin private file system — the same file fenec-server keeps — and each write is flushed before run returns. persist and restore keep the same bytes in IndexedDB, and work anywhere a page runs.

// in a dedicated worker
import { Fenec, openFile } from './fenec.js';

const db = await Fenec.open('./fenec.wasm');
const file = await openFile(db, 'notes.fenec');   // loads what it holds, or takes the database's image
db.run('put notes {text: $1}', ['in the file before run returns']);
const bytes = file.bytes();                        // what fenec and fenec-server open
  • The file is portable: download it and fenec notes.fenec opens it, and a server's file loads in a page.
  • One owner at a time: a second worker or tab that opens the file is refused.
  • A crash leaves a whole file: the next openFile holds every write run answered.
Details

openFile keeps the database in a file of the origin private file system, byte for byte the file fenec-server keeps on disk: download it and fenec notes.fenec opens it, and a server's file handed to a page loads there. run appends each statement's writes to it and flushes the file before it answers. It needs a dedicated worker, the one place a page gets synchronous access to a file, and it takes the file for itself: a second worker or tab that opens the file is refused, where a second process over a server's file would corrupt it.

A compact, and writes appended past half the image (and past 64 KB), put a new image in the file. It is written into a copy beside the file (notes.fenec~) and flushed before the file is touched, so a crash at any point leaves one of the two whole, and the next openFile takes whichever holds every write run answered. A write a crash cut short is cut off. What updates and deletes leave behind stays in the image until a compact, as it does in a server's checkpoint. Once the file refuses a write, every later write is refused too; the database has to be opened from the file again.

persist and restore keep the same bytes in IndexedDB, wherever a page runs: the image once, then only the writes since the last call, as chunks. persist stores what was written when it is called, and IndexedDB decides when that reaches the disk; the file is flushed before every answer. Over 32.4 MB (61 000 rows with a vector<128>), in a worker (make file-bench):

Sealed in IndexedDB

Pass a WebCrypto AES-GCM key and persist encrypts what it stores; restore then needs the same key. Where the key comes from is up to the page — never keep it in IndexedDB beside the data.

// A key from a passphrase, never stored: the page asks for it again.
const salt = new TextEncoder().encode('myapp:' + userId);
const base = await crypto.subtle.importKey('raw', new TextEncoder().encode(passphrase), 'PBKDF2', false, ['deriveKey']);
const cryptoKey = await crypto.subtle.deriveKey(
  { name: 'PBKDF2', salt, iterations: 600000, hash: 'SHA-256' },
  base, { name: 'AES-GCM', length: 256 }, false, ['encrypt', 'decrypt']);

await persist(db, 'notes', { cryptoKey });   // the image and each chunk sealed
await restore(db, 'notes', { cryptoKey });   // another key, or none, is refused
Details

With a cryptoKey (AES-GCM, from WebCrypto) the image and every chunk are sealed before they reach IndexedDB, each with a random nonce and a tag over the key it is stored under and its place. A chunk moved, dropped from the middle, or left from an image before is refused, as is one byte changed. A restore without the key refuses a sealed record, and a restore with one refuses a record stored in the clear. Where the key comes from is the page's decision: derived from a passphrase, as above, or handed over by the server after a login, so that what IndexedDB holds on the disk reads as nothing without it. A key kept in IndexedDB beside the data protects nothing. The sync layer takes it as sync({ persist, cryptoKey }). Its cursors, which are only numbers, are stored in the clear. The same 32.4 MB in Chrome 154: the first image 129 ms against 76, a new row 0.16 ms p50 either way, a restore 37 ms against 29. Only the image pays: it is 32 MB to seal. The file of openFile stays plain, since it is the file fenec-server opens. The disk's own encryption covers it.

State in the page

A database in the page can hold an app's whole state, with no server. db.live(query, fn) hands fn the query's rows now, and again after every write to a collection the query reads. Event handlers write, and persist keeps the state between visits.

import { Fenec, persist, restore } from './fenec.js';

const db = await Fenec.open('./fenec.wasm');
if (!(await restore(db, 'todos'))) {
  db.run('create collection todos (key text @hash, title text, done bool @hash, at timestamp @sorted)');
}

// the rows now, and again after every write to todos
const stop = db.live(db.from('todos').where('done', false).order('at'), draw);

async function add(title) {
  await db.from('todos').insert({ title, done: false, at: new Date() });
  await persist(db, 'todos');            // only this write, not the whole image
}
async function finish(id) {
  await db.from('todos').where('id', id).update({ done: true });
  await persist(db, 'todos');
}

In React, useLiveQuery from @fenecdb/react takes the same database:

import { FenecProvider, useFenec, useLiveQuery } from '@fenecdb/react';

function Todos() {
  const db = useFenec();
  const todos = useLiveQuery(db.from('todos').where('done', false).order('at'));
  if (todos === undefined) return null;
  return todos.map((t) => (
    <li key={t.id} onClick={() => db.from('todos').where('id', t.id).update({ done: true })}>{t.title}</li>
  ));
}

root.render(<FenecProvider db={db}><Todos /></FenecProvider>);

To share the todos through a server later, open a synced replica instead. The components stay as they are: a replica has the same from and live, and its writes reach the server.

const db = await sync({
  url: 'https://todos.example.com',
  shapes: [{ collection: 'todos', key: 'key' }],
});
root.render(<FenecProvider db={db}><Todos /></FenecProvider>);
  • One run per task: the writes made in one task, such as a run of several statements or a loop, run each live query once.
  • Only what it reads: a query built with db.from knows its collections, including each lookup's. A text names them: db.live('get todos count', fn, { collections: ['todos'] }).
  • A restore runs them all: restore, openFile and load hand every live query the loaded rows.
  • live returns its stop function. An error goes to { onError }, or db.onError.
Details

The engine notes every write in its change ring, a collection id and a document id each, and fenec_changes(since) names the collections written since a cursor. A block's writes are noted as it lands, so a text of several statements that fails names nothing. A create, an alter and a create index name their collection. A drop answers null, which means every collection: a dropped collection has no name left to give. Its live query runs again and gets the error that the collection is gone. Queries over other collections also run again for nothing, which is harmless.

The notice costs a write nothing. A statement's answer does not carry it. A page with a live query asks once, in a microtask after the task that wrote: a write to a collection no live query reads costs that one call, about 2 µs in Node. Running a query again is the query itself: a page of 50 open todos out of 1 000 to 3 000, ordered by an @sorted field, took 0.19 ms. No incremental maintenance is needed (Sync says why). The module did not grow, and make wasm-speed's put did not move.

A synced replica runs its live queries at the next frame instead, so that a seed landing in chunks is not shown half done. Both share one implementation. A load runs every live query whatever the ring says, since the image's counter may stand where the cursor did.

With openFile, the database and its live queries live in the dedicated worker that holds the file. The worker runs them, and posts the rows to the page that draws them. The page holds no database to subscribe to.

The key field in the example is what a replica reconciles an optimistic insert by. It fills the field in for you. Without a key, the row shows up once the server has it, not at once.

Collation data

Text ordered with collate und or collate tr needs each script's sorting data. The module carries Latin and fetches the rest from collate/ beside it the first time a page needs them.

const db = await Fenec.open('./fenec.wasm');            // collate/ beside it
db.run('create collection people (name text collate und @sorted)');

await db.from('people').insert([{ name: 'Ζωή' }, { name: '山田' }]);   // fetches greek, han
const rows = await db.query('get people order name');                  // the same, raw

await db.collation('cyrillic', 'arabic');   // ahead of the first statement that needs them
await db.collation('all');                  // every script's: 145 KB, 67 KB gzip, 61 KB brotli
  • db.query() and the builder fetch what is missing and run the statement again.
  • db.run() cannot wait, so it throws a FenecError naming the chunks to load.
Details

collate und and collate tr need the weights of the scripts they compare (Collation). The module carries the Latin ones and is handed the others as a page first needs them, a chunk a group of scripts, from collate/ beside the module — or from where Fenec.open(src, { collation }) says: a URL, or a function handed the chunk's name that returns its bytes. make wasm writes the chunks next to fenec.wasm.

A statement that would compare text of a script whose chunk the module has not got is refused rather than answered in another order: db.run(), which is synchronous, throws a FenecError whose collation names the chunks, and db.query() and the builder fetch them and run the statement again. A write is refused before it changes anything, so running it again is safe; of several statements in one text only the first is run again by itself. restore and db.loadAsync() fetch what an image's collated text needs — its @sorted indexes would be out of order without it — and the sync layer fetches what its seed, the changes it is sent and its optimistic writes need (sync({ collation }) says where from). A chunk of another version's tables is refused: its ranks would mean something else.

A smaller module

A page that does not use every index can load a module built without the rest. The release ships fenec-lite.wasm, built without any, beside fenec.wasm.

make wasm                          # every index: 142 KB brotli
make wasm FEATURES="text sorted"   # no vector or sparse search: 120 KB
make wasm FEATURES=none            # none of the four: 107 KB
FeatureWhat needs it
vectornear over a vector field, and fuse
textmatch, and the rerank after it, which reads the vectors themselves
sparsenear over a sparse<N> field

Details

The module carries four indexes, and a page that uses fewer can load one built without the rest. The release's fenec-web bundle carries fenec-lite.wasm, built without any, beside fenec.wasm; another set is a make wasm away. What each set weighs is in Benchmarks.

Everything else is in every build: documents, filters, order, aggregates, lookup, collations, the change feed, persistence and the sync layer.

The file does not change with the build. A collection that declares an index the module lacks is made and loaded all the same, and its documents are read and written. A statement that needs the index, or a create index of its kind, throws a FenecError naming the feature. A module that has the index builds it when it loads what the other wrote, so a page can hand a store to the other module and take it back.

The query builder

The builder writes FenecQL for you, with every value passed as a parameter. Each call returns a new query, so a base query can be shared and extended with optional filters.

const rows = await db.from('articles')
  .select('title', 'year')
  .where('year', '>=', 2024)
  .where('tags', 'has', 'rust')
  .near('embed', queryVector, { ef: 128 })
  .limit(10)
  .rows();
  • Each where is anded with the ones before it.
  • Queries are immutable, so if (year) q = q.where(...) branches safely.
  • No npm, no build step, and no second schema definition.
Details

FenecQL reads well, but on the application side the job is still building a string — and every interface with conditional filters ends up here:

let q = 'get articles where 1=1';
if (year) q += ` and year >= ${year}`;    // quote escaping and $n by hand

What usually drives people to an ORM is not the ORM but two things: dynamic queries and type safety. The builder gives both, without npm, a build step, or a second schema definition.

Every where is anded with the previous one, and the query object is immutable — so a body can be shared and branched:

let q = db.from('articles').select('title');
if (year) q = q.where('year', '>=', year);
if (tag)  q = q.where('tags', 'has', tag);
const rows = await q.limit(20).rows();

Filters

A filter can be written three ways, which all build the same query. The table lists everything else a query can carry.

.where('year', '>=', 2024)                   // field, operator, value
.where('category', 'book')                   // two arguments means equality
.where({ year: { gte: 2024 }, tags: { has: 'rust' } })
.where('meta.lang', '=', 'tr')               // a path into a json field

A path into a json field goes wherever a field does — where, select, order, and the keys of update, which sets one key inside the field — and a plain object is a json field's value: insert({ meta: { lang: 'tr' } }). fenec types writes a json field as Json, and the builder's types take 'meta.lang' as a path of it.

Details: lookup, or, not and raw

Use whichever spelling reads better at the call site.

lookup hangs another collection's matching documents off each row. Everything in its options object binds to that collection, so limit there counts children per parent — twenty products with three reviews each, in one query:

const rows = await db.from('products')
  .where('price', '>=', 10000)
  .limit(20)
  .lookup('reviews', {
    on: 'product_id',
    where: { stars: { gte: 4 } },
    order: [['created', 'desc']],
    limit: 3,
  })
  .rows();

// [{ id: 1, name: 'Kahve', price: 12000, reviews: [ {...}, {...} ] }, ...]

Calling it again chains rather than replaces: the second call binds to the collection the first one named, the way position scopes it in FenecQL.

const rows = await db.from('shops')
  .limit(20)
  .lookup('orders', { on: 'shop_id', limit: 3 })
  .lookup('lines',  { on: 'order_id', limit: 5 })
  .rows();

// [{ name: 'Merkez', orders: [{ code: 'A', lines: [ {...} ] }, ...] }, ...]

The row type follows the nesting, so rows[0].orders[0].lines[0] is typed without a cast. required keeps meaning what it means at its own level: on lines it drops the orders that have none, and the shops stay unless orders asks for it too.

The child's field names cannot be reached from a builder that carries one collection's types, so in TypeScript they default to a loose row; naming them tightens it: .lookup<'reviews', FenecSchema['reviews']>('reviews', {...}).

or and not are separate functions because the where chain is an and. A nested group is written explicitly and the parenthesising is left to the builder:

db.from('articles')
  .where('year', '>=', 2024)
  .where(or({ tags: { has: 'rust' } }, { title: { like: 'rust' } }))
// get articles where year >= $1 and (tags has $2 or title ~ $3)

raw covers what the builder cannot express, which in practice today means function calls. Its ? placeholders bind to parameters in order, so the escape hatch does not become string concatenation either.

Seeing what it produces

toFenecQL() returns exactly the text and parameters that will run, so you can log it, test it or run it by hand.

db.from('articles').where('year', '>=', 2024).limit(10).toFenecQL()
// ['get articles where year >= $1 limit 10', [2024]]
  • Values are always parameters, never pasted into the text.
  • Collection and field names are checked against FenecQL's identifier rule; anything else throws.
Details

Nothing is hidden. Every leaf value is bound to a parameter and text is never embedded into the query, which leaves a single injection boundary: names. Collection and field names cannot be parameterised, so they are validated against FenecQL's identifier rule and anything that does not fit errors out.

db.from('articles').where('title', '"; del articles; --')
// get articles where title = $1     ← a value, not text

A parameter that is a vector — a Float32Array, or any array of finite numbers, which the module reads as a vector either way — goes into the module as its f32s beside the JSON rather than as text: 200 768-dim vectors are put in 4.4 ms, against 21.9 written out as digits and read back. The vector stored is the same, -0 as 0 as JSON writes it; over HTTP a parameter is JSON. Where such a parameter is given a json field, or compared with a path into one, the module names it before running anything and run sends it again as JSON, so a plain array keeps its numbers as written and a Float32Array goes as the numbers it holds.

Independent of the transport

The same query code runs against the module in the page, a fenec-server server or an HTTP endpoint: build it with from(), then bind() it to where it should run.

import { from, connect } from './fenec.js';

const q = from('articles').where('year', '>=', 2024);

await q.bind(db).rows();                                // wasm, local
await q.bind(connect('http://localhost:8080')).rows();  // remote server
q.toFenecQL();                                          // or just the text
Details

connect() returns the same builder; the FenecQL it produces goes to POST /query as is. See HTTP endpoint.

TypeScript

Generate types from your database file, and queries are checked against its real schema: unknown fields, wrong value types and unselected fields are compile errors.

fenec types data.fenec > web/fenec-schema.d.ts     # or: make types FILE=data.fenec

import { Fenec } from './fenec.js';
import type { FenecSchema } from './fenec-schema.js';

const db = await Fenec.open<FenecSchema>('./fenec.wasm');

const rows = await db.from('articles').select('title', 'year').rows();
//    rows: { title: string; year: number | null }[]
Details

The schema is not written a second time — it is generated from the live file, so the two cannot drift apart.

vector<N> / bytesVector / Bytes — number[] on read, each component the shortest decimal that reads back as its f32 (0.1 as written, not 0.10000000149011612); Float32Array also accepted on write

What the types catch: a collection or field that does not exist, a wrong value type, access to an unselected field, near applied to a non-vector field, and a type mismatch inside insert. Objects inside or, and and not are checked against the query's collection rather than the first argument. A query using near or match gains _score: number.

A standalone from() cannot know the collection name, since the schema lives in the call rather than in db. In TypeScript it binds through TypedFrom; at runtime it is the same function and the only difference is name completion.

import { from as fenecFrom, type TypedFrom } from './fenec.js';
import type { FenecSchema } from './fenec-schema.js';

const from: TypedFrom<FenecSchema> = fenecFrom;
from('articles').where('year', '>=', 2024);   // completes like db.from

fenec.d.ts is hand-written — it is the client's own surface — and fenec-schema.d.ts is generated. There is no link between them: the Timestamp, Vector and Bytes brands are structural, so the generated file stands alone and imports nothing.

What the builder will not do

The builder adds nothing FenecQL lacks, and refuses a few things that are easy to get wrong.

  • No aggregate FenecQL lacks. Aggregates go in select spelled as FenecQL spells them — .select('status', 'count(*)', 'sum(total)').group('status') — and each row answers under those names; a median or a distinct count is not there to compile to.
  • An update or delete without a filter is refused. Covering a whole collection by accident is far too easy and impossible to undo; when it is deliberate you write delete({ all: true }). PostgREST decides the same.
  • near, order, limit and lookup error out on write statements. FenecQL does not support them on set or del, and ignoring them silently would breed the illusion that limit(1) deletes a single row, or that a required lookup spares the parents with no children.
  • No JOIN, no returning. The builder adds no capability on top of FenecQL — it only builds it safely. lookup is the exception FenecQL itself makes, and .lookup(name, opts) builds it like any other clause; a query given as an in's value is FenecQL's in (get …), its parameters bound with the outer one's.
