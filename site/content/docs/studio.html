Studio

fenec studio is the server's own admin page: its collections, their rows and their schema in a browser, and the edits you make there. Start the server with --studio and open /_studio/.

Turn it on

Add --studio to fenec-server, open /_studio/ on the same address, and paste a token.

fenec-server --file data.fenec --http 127.0.0.1:8080 \
         --http-token "$TOKEN" --studio

open http://127.0.0.1:8080/_studio/
  • Off by default. Without --studio, /_studio/ answers 404, as an unknown path does.
  • No new authority. The page reads and writes with the token you paste, over the same HTTP surface every client uses.
  • A tool for operators: keep it on a private network or behind your own sign-in (Security).
Details

The studio is plain ES modules and CSS from the repository's studio/ folder, with the HTTP client and query builder of @fenecdb/web/client beside them — no framework and no build step. The server embeds the files, so the binary is all you deploy. Its first load is 56 KB of JavaScript and CSS, gzipped, its modules preloaded together from the page. The server sends the files as they are, uncompressed; a proxy in front may compress them.

A router serves it too: fenec-shard --studio puts the same pages on the router's address, where each tenant is reached through the router (Tenants).

Connect

The server is the page's own address unless you name another, and the token is the one the server takes: its --http-token, or a JSON Web Token its policy holds to its rows. The top bar says who the server takes it for.

  • Your token stays in the tab. It is kept in session storage and forgotten when the tab closes: never in local storage, a cookie or a URL.
  • Who you are: the token's subject, role and tenant, the rules that apply to it, and how long until its exp. The line under the top bar shortens as the token's life runs out, and the page warns you five minutes before it does.
Details

The identity comes from GET /_whoami, which any client may ask: open on a server that asks for no token, full for the server's token, and scoped for a JSON Web Token, with each rule of the policy that applies to it — the collection, the grants, the fields an update may change and the rows, as the policy writes the filter. A token is shown its own rules and no other's: a rule for a role it does not hold is not among them. It grants nothing; a token the server refuses gets the same 401 here as anywhere.

curl -H "Authorization: Bearer $ALICE" http://127.0.0.1:8080/_whoami
# {"node":"single","tenant":null,"read_only":false,"kind":"scoped","sub":"alice",
#  "tenants":null,"unbound":false,"append_only":[],
#  "rules":[{"collection":"orders","grants":["read","insert","update","delete"],
#            "fields":null,"rows":"owner = $jwt.sub"}]}

The token's claims — its subject, role and exp — are read in the page to show them, and decide nothing: the server checks the token on every request.

Collections and rows

The sidebar lists the collections the token can read, each with its rows and its fields' types and indexes. The grid shows a collection's rows, as many as it holds, read a page at a time as you scroll.

  • Sort by id, or by a field an index orders: @sorted or @ttl.
  • Filter with a where clause in FenecQL and its parameters, or a box under each column: abc, =v, >=v, a..b, null.
  • Counts by value for each @hash field, over what the filter selects; pick one to filter by it.
  • A row unfolded (Space): a json field as a tree, a vector as its dimension, its length and its first components.
  • File size and what a compact would give back, where the token may read /_metrics.
Details

A page is 100 rows. In id order the page after one already read is asked for by its last id — get orders where id > $1 limit 100 — which walks the id index from there; a page reached by a jump, or under an order, by its offset. Only the rows in view are drawn, so 100 000 rows cost what 40 do: a scroll down the whole collection and back in Chrome took no task over 50 ms (make studio-test). Past 8 million pixels of rows the scroll bar stands for the rows in proportion, since browsers cap an element's height.

The count and the counts by value are one /batch of reads, under one read lock, so they are of one moment. A vector is never written out whole: 768 numbers in a cell are noise.

Edit

Enter writes a cell, N opens a form for a new row, and Delete removes one after you confirm the statement it will send.

set orders {note: $1} where id = $2 require 1
insert orders {customer: $1, total: $2}
del orders where id = $1 require 1
  • Every value is a parameter. A text shaped as FenecQL is stored as it reads.
  • Every write is a /batch with an Idempotency-Key, so a retry cannot write it twice.
  • A refusal says why: 403 names the field the policy refused, and 412 says the row changed — deleted, or no longer the token's — since it was read.
Details

require 1 makes a write that found no row a refusal (412) rather than a quiet affected 0, so an edit of a row someone deleted meanwhile is told so. The form is built from the schema: a box a field, typed as the field is, the statement written out below it as you fill it. A name FenecQL cannot write is refused rather than spliced into the text, and the where clause you type is held inside parentheses it cannot close, so it stays one condition among the page's.

Tenants

On a tenant node or a router, the top bar picks the tenant: those the token's tenant claim names, or the node's or router's list where the token may read it. Otherwise type the tenant when you connect.

fenec-server --dir tenants --http 127.0.0.1:8081 --admin-token "$ADMIN" --studio
fenec-shard --listen 127.0.0.1:8090 --directory shard.fenec --studio
Details

A token is bound to the tenants it names on a node, so the picker offers nothing it would be refused. Through a router the studio is on the router's address and every tenant is that same origin; a page served by a node would be another origin to the router. --studio-connect <origin> lets the pages a server serves send requests to one more origin, which its content security policy names.

Security

The studio is a new surface, not a new authority. Treat it as you would the server's own port: keep it on a private network, or behind your own sign-in and TLS.

authoritynone of its own: every statement carries the pasted token, so a scoped token sees its rows alone — in the grid, the counts and the facets
the tokensession storage of one tab; sent only as Authorization: Bearer
headersContent-Security-Policy with default-src 'self', no inline script, connect-src 'self' and the --studio-connect origin; X-Frame-Options: DENY; nosniff; no referrer
valuesshown as text, never as markup; sent as parameters, never spliced
cachingthe page is never kept; its modules are asked about again each load (ETag, 304)
offwithout --studio, 404
