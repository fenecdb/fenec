Quickstart

Go from a fresh clone to a collection you write rows into, read back and search, in the browser, on a server or in the shell.

Build

  1. Clone the repository.

    git clone https://github.com/fenecdb/fenec
cd fenec

  2. Build and run the tests.

    make test      # 705 Rust tests, 103 JS tests

The wasm32 target comes from rustup. Homebrew's cargo ships no wasm32 standard library. The Makefile prefers ~/.cargo/bin/cargo; building by hand needs rustup target add wasm32-unknown-unknown first.

Details

That produces target/release/fenec (the shell) and target/release/fenec-server (the server). The Rust suite runs first on purpose: cargo test builds fenec-server, and the JS sync tests run against that binary.

In the browser

  1. Build the module and open the console at http://localhost:8787.

    make serve                    # or: make serve PORT=3000

  2. For your own page, take the files it needs.

    cp web/fenec.js web/builder.js web/http.js web/fenec.wasm my-page/

  3. Open a database, make a collection and write two rows.

    import { Fenec } from './fenec.js';

const db = await Fenec.open('./fenec.wasm');
db.run('create collection notes (title text @text, year int @sorted)');
db.run('put notes {title: $1, year: $2}', ['Dunes', 2021]);
db.run('put notes {title: $1, year: $2}', ['Night at the oasis', 2024]);

  4. Read them back by a filter and an order, and search the words, a typo and all.

    const { rows } = db.run('get notes where year >= $1 order year desc', [2020]);
// [{ id: 2, title: 'Night at the oasis', year: 2024 }, { id: 1, title: 'Dunes', year: 2021 }]

const hits = db.rows('get notes select title match title $1 fuzzy', ['oasys']);
// [{ title: 'Night at the oasis', _score: 0.62... }]

  5. Keep the rows in step as they change: a live query hands its function the rows now, and again after every write to what it reads.

    db.live(db.from('notes').where('year', '>=', 2020).order('year', 'desc'), (rows) => {
  console.log(rows.map((n) => n.title));   // draw the list here
});
db.run('put notes {title: $1, year: $2}', ['Sand and stars', 2023]);   // logged again, the new row in it

  6. Serve the page over HTTP — it does not open from file://.

    python3 -m http.server
Details

make serve builds the wasm and serves http://localhost:8787. web/index.html is a full console: a FenecQL editor, a sample data generator, live statistics and IndexedDB persistence.

For your own page you need four files: fenec.js, the builder.js and http.js it imports, and fenec.wasm. No npm, no bundler, no build step. A page whose queries run on a server needs only client.js and those two (Which package).

import { Fenec, persist, restore } from './fenec.js';

const db = await Fenec.open('./fenec.wasm');

db.run('create collection notes (title text @text, year int @sorted)');
db.run('put notes {title: $1, year: $2}', ['Night at the oasis', 2024]);

const { rows } = db.run('get notes where year >= $1 order year desc limit 10', [2020]);

// or with the builder, for dynamic filters and bound parameters
const recent = await db.from('notes').where('year', '>=', 2020).order('year', 'desc').limit(10).rows();

await persist(db);      // write the snapshot to IndexedDB
await restore(db);      // read it back next session
// or, in a worker: a file every statement is flushed into, which fenec-server opens too
// const file = await openFile(db, 'notes.fenec');

A page can declare its collections in code instead, and the open makes them (State in the page).

It does not open over file://. WebAssembly.instantiateStreaming and module imports both need an HTTP origin. Any static server works: python3 -m http.server, npx serve, nginx.

The same module runs in Node, where fetch cannot resolve a relative path — so hand it the bytes:

import { readFile } from 'node:fs/promises';
const db = await Fenec.open(await readFile('./fenec.wasm'));

As a server

  1. Start the server on a file.

    ./target/release/fenec-server --file data.fenec --http 127.0.0.1:8080

  2. Make a collection and write a row. The language is FenecQL, and the values go as parameters.

    curl -X POST http://127.0.0.1:8080/query \
  -d '{"query": "create collection notes (title text @text, year int @sorted)"}'
curl -X POST http://127.0.0.1:8080/query \
  -d '{"query": "put notes {title: $1, year: $2}", "params": ["Night at the oasis", 2024]}'

  3. Read it back by a filter and an order, or search the words.

    curl -X POST http://127.0.0.1:8080/query \
  -d '{"query": "get notes where year >= $1 order year desc limit 10", "params": [2020]}'
curl -X POST http://127.0.0.1:8080/query \
  -d '{"query": "get notes select title match title $1 fuzzy", "params": ["oasys"]}'

  4. Or use the REST routes, and follow the rows as they change.

    curl 'http://127.0.0.1:8080/notes?select=title,year&year=gte.2020&order=year.desc&limit=10'
curl -N 'http://127.0.0.1:8080/notes/changes?year=gte.2020'
Details

Every language reaches the server over HTTP: Your language has the same requests in each, and every route is on HTTP endpoint. A write's answer is {"affected": 1}, a read's an array of rows, and the stream of /notes/changes sends the rows its filter holds, then each change to them (Subscriptions).

./target/release/fenec-server --ping        # 0 means up — a health check

Tokens, durability, limits and containers are on Server. Past one machine, a read replica and archives are on Replication, a file per tenant behind a router, in one region or several, on Tenants and sharding, and the systemd units, alert rules and runbook to run them on machines of your own in Deploying it.

In the shell

  1. Open a file of its own in the shell — not the server's data.fenec, which two processes would corrupt.

    ./target/release/fenec notes.fenec

  2. Create a collection, each field typed and the ones you filter, order and search by indexed.

    create collection notes (
  body   text @text,
  topic  int @hash,
  posted timestamp @sorted
)

  3. Write your rows. A write runs at the empty line after it, or at a ;.

    put notes {body: "a night at the oasis, under the stars", topic: 3, posted: now()}
put notes [ ... 100 000 more ... ]

  4. Read them back, newest first.

    get notes select body, posted where topic = 3 order posted desc limit 10

  5. Search the words. fuzzy finds them typed wrong.

    get notes select body match body "oasys stars" fuzzy limit 10
Details 
./target/release/fenec notes.fenec              # interactive
./target/release/fenec notes.fenec -c 'get notes limit 5'
echo 'get notes' | ./target/release/fenec notes.fenec
./target/release/fenec notes.fenec < seed.fenecql   # a script

Inside the shell: .help .tables .stats .functions .save <path> .checkpoint .quit.

A statement may run over several lines, and the shell runs it only once nothing after it can go on with it. Typed, a read or a schema change written on one line runs at Enter. A write, and a read written over several lines, wait for the next line: one that goes on with them — where, order, and — joins them, and an empty line or another statement runs them first. A ; after a statement runs it at once. So del notes with where id = 3 on the line under it deletes one row. A . command leaves a waiting statement waiting — .tables to look a name up before the where — and .quit leaves it unrun.

Piped from a file, a statement runs once the next one begins, and a paste is read the same way, its lines all there at once; -c reads its text whole, as POST /query does, so a text that does not parse runs nothing. A line that begins no statement — a where after a read that already ran at Enter, a wher mistyped — is refused, and so is a statement still waiting before it, which that line may have meant to go on with.

Fields and indexes can come later too, with no row rewritten: alter collection notes add field mood text, then create index on notes (mood) @hash over the rows already there (Changing a collection). prefix finds a word half typed (Typos and words begun), and highlight() and snippet() mark what matched (Highlights and snippets).

Search by meaning

A vector field adds search by meaning beside the words: near ranks the rows by how close their embedding is to a query's, and fuse puts that ranking together with match's. The vectors come from your embedding model. In the shell, on the notes above, each is written out as its list of 384 numbers, since the shell binds no parameters:

alter collection notes add field embed vector<384>
put notes {body: "hnsw is a navigable small world graph", topic: 3, posted: now(), embed: [0.12, -0.03, …]}
create index on notes (embed) @hnsw(cosine)
get notes select body where topic = 3 near embed [0.11, -0.02, …] limit 10

Over POST /query the statement says near embed $1 instead and the vector goes in params, as every value does there; in the page, through db.run, it is a Float32Array among the parameters.

Details

Load the vectors first and build the index after, not before: the graph is then built once over all of them, on every core, rather than a row at a time. The reason is in How it works.

When a file with a vector index is closed from an interactive or piped session, a checkpoint is written so the graph is not rebuilt on the next open. A one-shot -c call does not write one.

To serve the shell's notes, quit the shell and start fenec-server --file notes.fenec: one process holds a file at a time. In the page the builder writes the search too: db.from('notes').near('embed', queryVector).limit(5).rows(). Every clause is on FenecQL, and words and meaning together on Hybrid search.

Bring your own data

fenec import copies a SQLite file or a PostgreSQL table into a collection, its schema and indexes included.

./target/release/fenec import data.sqlite --table docs --into articles --index "category@hash"
Details

fenec import derives the schema from the table's columns and builds the indexes you name once the rows are in, into articles.fenec unless --file names another. --follow keeps a PostgreSQL table's copy in step, applying each change as it commits.

./target/release/fenec import postgres://user@host:5432/database --table docs \
    --into articles --index "category@hash" --follow

--dry-run prints the derived schema and any warnings without writing anything. A vector column comes across too, with --vector embed:384 for a SQLite blob and --index "embed@hnsw(cosine)" (Vector columns). Full flag list in Import.

Generate TypeScript from the file

Generate TypeScript types from the schema already in your file, so your code and the database cannot drift apart.

./target/release/fenec types articles.fenec > web/fenec-schema.d.ts
Details

The schema is already in the database, so it is not written a second time in TypeScript — it is generated, and the two cannot drift.

import { Fenec } from './fenec.js';
import type { FenecSchema } from './fenec-schema.js';

const db = await Fenec.open<FenecSchema>('./fenec.wasm');
const rows = await db.from('articles').select('title', 'category').rows();
//    rows: { title: string | null; category: string | null }[]
