PostgreSQL server

fenec-pg speaks the PostgreSQL v3 wire protocol, so psql, psycopg, asyncpg, pgx, tokio-postgres, node-postgres, JDBC and pgbouncer all connect. What is compatible is the transport, not the language.

fenec-pg --listen 127.0.0.1:5433 --file data.fenec

psql -h 127.0.0.1 -p 5433 -U fenec
# fenec=# get articles select title near embed '[0.1, 0.2]' limit 5;

fenecdb does not speak SQL. It does work with the connection tooling of the PostgreSQL ecosystem: vectors are pgvector's types, in its text representation ([1,2,3], and {1:0.5,3:0.25}/30522 for a sparse vector, indices from 1) and in its binary format where a driver asks for it, so pgvector's client libraries work unchanged; errors map to SQLSTATE codes (42P01, 42601, 42804, 57014, and 25006 for a write sent to a replica).

explain get ... answers the way PostgreSQL's EXPLAIN ANALYZE does on the wire: rows of text in one column, here plan, tagged EXPLAIN, so psql prints the plan and a driver reads it as rows. The steps are fenecdb's own — which index, how many rows each stage read — and are described under Explain.

With --replica-of the process follows another fenec-pg as a read replica: it serves every read, refuses every write with 25006 as a PostgreSQL standby does, and answers SHOW transaction_read_only and pg_is_in_recovery() accordingly, which is what libpq's target_session_attrs and JDBC's targetServerType go by. The flags, promotion and what a failover loses are on Replication.

With --dir <path> instead of --file the process serves a directory of tenant files, one per tenant under /t/<tenant>/ over HTTP and, when --listen names an address, over this protocol as well — there the database in the startup packet is the tenant, so psql postgres://host:5433/acme is a session on acme.fenec. That mode, its --admin-token and --idle-close, and the router in front of it are on Tenants and sharding.

Drivers

A driver is held to its own flows against a real fenec-pg — make drivers-test, and CI on every change: the queries it sends on its own, the formats it reads rows and sends parameters in, its transactions and its COPY — and with it pgvector's library for it (pgvector's clients).

Two limits are the drivers': node-postgres has no binary mode — with binary: true it reads a binary cell as UTF-8, from PostgreSQL too — and pgx's QueryExecModeSimpleProtocol writes every parameter into the text as a quoted literal, so n = '2' compares an int field with the text 2, which FenecQL does not resolve to the field's type as PostgreSQL resolves an untyped literal: use pgx's default mode.

Sessions

One thread per connection. Read-only statements run at the same time under a shared lock; writes take the exclusive one. HNSW search buffers are thread-local, so the same index can be searched in parallel — eight concurrent full scans on eight cores measured 4.3×.

Transactions

Between BEGIN and COMMIT a session's writes are one block: COMMIT lands them in the file as one record, and ROLLBACK puts them back — as do a statement that fails, a client that goes away and a server going down. A crash holds none of an open transaction, whose writes reach the file only when it lands, and cuts off none of a landed one. A replica applies a transaction whole, and a subscriber is woken once for all of it.

A transaction lands with one fsync where its statements alone would take one each: under --sync always a write in a transaction of a hundred costs 90 µs against 3.97 ms on its own, and a lone statement costs what it did (make tx-bench). Its vectors are linked into the graph together as well, 512 at a time on every core and the rest at COMMIT: a driver's executemany of 100 000 rows of 128-dim vectors goes in at 17 200 rows/s with the HNSW graph kept, where linked a row at a time it went in at 5 400 (Loading rows).

There is one writer, so a transaction holds the database against every other write from its first write until it ends: nothing may write after its writes. It takes the write lock for each of its statements alone, and between them other sessions read what has landed: a reader puts the transaction's writes aside while it waits for its next statement, and they are written again when it comes. A transaction that changed a graph — a vector written or deleted — or the schema is not put aside, and readers wait for it. Until its first write it reads what others have committed, statement by statement — PostgreSQL's read committed — and holds nobody up. BEGIN ISOLATION LEVEL SERIALIZABLE, or REPEATABLE READ, takes the lock at its first statement instead, so nothing it read changes before it ends; BEGIN READ ONLY refuses a write with 25006.

A transaction that has written holds every other session's writes, and the reads beside one that changed a graph. Keep it short, and have the client send COMMIT rather than work between statements. One whose client stays silent for --idle-in-transaction-timeout seconds — 10 by default, 0 for never — is put back and its session closed with 25P03, as PostgreSQL's idle_in_transaction_session_timeout closes one.

As in PostgreSQL:

  • A statement that fails fails the transaction. ReadyForQuery reports E, and every statement up to COMMIT, ROLLBACK or a ROLLBACK TO is refused with 25P02; the COMMIT of a failed transaction answers ROLLBACK. Its writes are put back at once, and the lock let go — unless a savepoint after one of them is there to go back to.
  • SAVEPOINT, ROLLBACK TO and RELEASE: ROLLBACK TO puts back the writes after the savepoint and the transaction goes on, a failed one included; the savepoint stays, and the ones after it are over. RELEASE forgets a savepoint and the ones after it, and keeps their writes. The newest of a name is the one meant, and names fold to lower case unless quoted. psycopg's nested transaction() blocks, SQLAlchemy's begin_nested() and psql's ON_ERROR_ROLLBACK run on them. Outside a transaction they are refused with 25P01, and a savepoint the transaction does not have with 3B001. Taken back to a savepoint before its first write, a transaction lets the lock go, and reads what others commit again until its next write.
  • A pipeline of the extended protocol is one block up to its Sync: JDBC's executeBatch, pgx's batches and libpq's pipeline mode land whole or not at all. A text of several statements sent as one query is one block as well.
  • A text holding BEGIN, COMMIT, ROLLBACK or a savepoint — psql -c "BEGIN; …; COMMIT" — runs a statement at a time, each answered: the statements outside a transaction are one implicit block, which a COMMIT or a ROLLBACK in the text closes, a BEGIN takes into the transaction it opens, and the text's end lands. The first error ends the text, and a transaction the text opened is left failed; a statement that cannot be read runs none of it. A savepoint needs a transaction, not an implicit block (25P01), and the extended protocol takes one command at a time (42601).
  • COMMIT AND CHAIN begins the next transaction in the same mode; SET TRANSACTION sets a transaction's before its first statement, and SET SESSION CHARACTERISTICS AS TRANSACTION every later one's.
  • Outside a transaction COMMIT and ROLLBACK warn with 25P01 and succeed, as the pools that send them on every check-in expect.

A create, a drop and a create index are writes of the transaction like any other, as in PostgreSQL: its ROLLBACK, or a ROLLBACK TO a savepoint before one, puts it back — the collection made goes, the one dropped comes back with its documents, the index goes — and nobody sees it before the COMMIT. In a transaction a create index is built under the lock the transaction holds; on its own it is built beside the database. A compact rewrites the file, which nothing can put back: before a transaction's first write it runs on its own, and after one it is refused (25001). Two-phase commit is refused (0A000): taken for the COMMIT or the ROLLBACK it begins with, it would end a transaction other than the one named.

Resource ceilings

One thread per connection means unlimited connections would leave the stack memory ceiling to the client.

FlagDefaultBehaviour above the ceiling
--max-connections10053300, PostgreSQL's sorry, too many clients already
--idle-timeout <s>off57P05 on a session that has gone quiet
--idle-in-transaction-timeout <s>1025P03, and the transaction put back, on a session gone quiet holding the database
--max-message <MiB>64the length is read before the body, so an oversized body is never allocated
startup packet10 000 Bthe same as PostgreSQL; the only allocation before authentication
--max-memory <MiB>off53200 on statements that grow the data, 507 over HTTP

--max-memory puts a ceiling on the data footprint. Above it, statements that grow the data are rejected — over this protocol and over the HTTP listener alike — while reads, del and compact keep working — hitting a ceiling with no way out would be no better than a cgroup OOM. The point is to bring the OOM forward: nobody warns you about a process felled by SIGKILL, and both the last sync and the checkpoint are lost with it. The measurement happens before the statement, so the overshoot is at most one statement, whose body --max-message bounds as well.

Durability

Writes accumulate in a 1 MB buffer. --sync decides when they reach the disk.

--syncMeaningCost
alwaysevery write statement waits for an fsync; writes arriving together share one~3.7 ms a write alone
250 (default)periodic; at most one interval is at risknegligible
offon shutdown onlynone

Under always the fsync runs after the write has let go of the exclusive lock, and the bytes reach the file there too. Readers therefore do not wait on the disk, and writes that arrive while one fsync runs are made durable together by the next. Over eight clients on macOS, where an fsync is a full cache flush of about 3.7 ms, that took durable writes from 268 to 1 156 a second, and a read's p99 under that load from 320 ms to 0.44 ms, against 0.15 ms idle. One client still gets one write per fsync. The HTTP listener's writes take the same path. So does the sync of 250, for a single database and for each tenant of a --dir node: held through the fsync, a tenant's lock had its reads and writes wait up to 27 ms once an interval.

SIGINT, SIGTERM and SIGHUP are caught and a final sync runs before exit. The exclusive lock is held until exit, so no write can be accepted between the sync and the exit and no write is left that looked successful to the client but never reached the disk. Sessions waiting on the lock do not wait for nothing — they come back with 57P01. Under kill -9 you get exactly what the chosen policy promised, and no more.

When the disk refuses a write or a sync, the statement fails with 58030 — under always, before the client is told it succeeded — and every later write is refused until the process restarts; reads go on answering from memory. The sync is not retried: after a failed fsync the kernel may already have dropped the pages, so a retry that succeeds would prove nothing.

The shutdown checkpoint

After the sync, if a vector index exists, a checkpoint is written: the HNSW graph lands in the file and the next open does not rebuild it — 9 ms instead of 3.4 s at 100 000 × 128. Vectors still waiting to be linked after a crash (below) are written as waiting, and linked after the next open.

The cost is that shutdown takes longer on a large database: the image is written into the new file as it is produced, so it is a copy on disk rather than one in memory. --no-checkpoint turns it off.

The order is deliberate. The sync comes first, so even if the process is killed while the checkpoint is being written, the data is already on disk and only the graph is lost. The rewrite goes to a side file and is renamed, so a half-written checkpoint cannot corrupt anything.

Health checks

fenec-pg --ping        # 0 means up

It connects, authenticates and exits — the same depth as pg_isready, and it deliberately runs no query. Every query takes the database lock first, so during a long compact the probe would wait too and a healthy server would look dead. Measured at roughly 100 ms.

Because the listener binds after the file is opened, "healthy" also means "the index is ready" — a start period has to be long enough to cover the graph build.

What the server is doing is at /_metrics, in Prometheus's text format: --metrics <address> opens a listener for it alone, for a server whose data goes over PostgreSQL only, and --slow-ms <ms> logs every statement at least that slow with its text. The metrics, a Grafana dashboard and the log are in Monitoring.

Query cancellation

CancelRequest is a real cancellation: the pending lock is released and the query returns 57014 at about 1 ms, with the connection still usable. A cancel arriving while idle, or one carrying the wrong secret key, is ignored.

Authentication

With --password, the default is SCRAM-SHA-256 (RFC 7677): the password never crosses the wire and the exchange cannot be replayed. --auth cleartext exists for clients that cannot speak it, and --user restricts the user name.

Pass the password with --password-file or the FENECPG_PASSWORD environment variable — argv shows up in ps output.

A reporting tool, a dashboard or a service that only reads can log in as a reader: --reader <name> with a password of its own (--reader-password, --reader-password-file or FENECPG_READER_PASSWORD), by the same method as the writer's. Every write of its session is refused with 25006 — out of a transaction or in one, by COPY FROM, as an index or a compact — whatever it sets, BEGIN READ WRITE and default_transaction_read_only included. It needs --password, since without one every user writes. Over HTTP the same is a JSON Web Token's policy granting read (Scoped access).

fenec-pg --file data.fenec --password-file writer.pw \
  --reader reporting --reader-password-file reader.pw
psql 'host=127.0.0.1 port=5433 user=reporting dbname=fenec'

There is no TLS. SSLRequest is refused with N, and a client connecting remotely gets a NoticeResponse saying the connection is unencrypted. Listening on a non-loopback address without authentication is refused outright; it can be opened deliberately with --insecure. On an open network, put it behind a TLS terminator such as stunnel or nginx stream.

Extended protocol

Describe is answered without running the query: the parameter count comes from the largest $n in the statement, and the columns and type OIDs from the schema — with near or match, _score is reported too. A parameter's type is the one its place names — the field it is given for or compared with, id's, the field's type for the vector of a near or a rerank, the text of a match — and text where nothing names one; a type the client names in Parse is kept. A driver told the types sends its values as them, tokio-postgres and asyncpg in binary, and they are read by them. A value sent as text is read as the field its place names, as COPY reads a cell of it — a text field's as the text it is, so "t" and "42" stay text — and by its look where no field is named: psycopg and node-postgres name no type for a string and ask for no Describe, and the places are found at the statement's first Bind. RowDescription goes exactly once, on Execute when Describe is skipped.

A column goes in the binary format when Bind asks for it — as tokio-postgres and asyncpg ask for every column, and pgx for every type it knows: bigint, double precision, boolean, bytea and timestamptz as their types send them, a vector as pgvector sends one, and a text as its text.

A list is PostgreSQL's array of its element's type — [text] is text[], [int] bigint[], [float] double precision[], and boolean[], bytea[] and timestamptz[] the same way — in array_out's text, an element quoted where it is empty, says NULL or holds a brace, a comma, a quote, a backslash or a space, and in array_send's binary form where a client asks for it; a parameter in its place is described as the array, and taken in either form. So psycopg and asyncpg read a list field as a Python list, pgx scans it into a slice, node-postgres into an array and tokio-postgres into a Vec, and each binds its own as a list — described as text, it was the string {a,b} to all of them. A list of lists or of vectors, which PostgreSQL has no array for, still goes as text. The catalog's columns go in binary as well, but for an array, which is refused (0A000) rather than sent in a form the client would misread.

An error drops every message after it up to the next Sync, as PostgreSQL does, and is sent at once rather than at the Sync. A pipelining client — libpq's pipeline mode, pgx's batches, JDBC's — writes off what it queued behind a failure, so none of it runs: run anyway, a write the client counted as aborted would be made, and psycopg 3, reading answers it did not expect, fails with cannot exit pipeline mode while busy. What ran before the error in the pipeline is put back as well: a pipeline is one block up to its Sync (Transactions).

Loading and reading rows out: COPY

COPY docs [(col, ...)] FROM STDIN loads rows the way a PostgreSQL client loads a table: psql's \copy, psycopg's cursor.copy, JDBC's CopyManager, the postgres crate's copy_in, asyncpg's copy_records_to_table and pgx's CopyFrom all work, in the text format, in CSV with its options (HEADER, DELIMITER, NULL, QUOTE, ESCAPE), and in PostgreSQL's binary format, each cell as its column's type sends it. asyncpg and pgx learn those types first by asking for SELECT the columns FROM the collection, which is read as the get it is — as is any plain SELECT of columns, or *, from one collection, with a LIMIT or none.

psql -h 127.0.0.1 -p 5433 -U fenec \
  -c "\copy docs (title, year, embed) from 'docs.csv' with (format csv, header)"
# COPY 30000

Without a column list the columns are id and then every field in the order the schema declares them, as \d lists them; a NULL or missing id is handed out as a put's would be. Each cell is read as its field's type: a vector as pgvector writes one, [1,2,3], or as an array, {1,2,3}; a list as an array, {a,b}, or JSON; a sparse vector as {1:0.5}/30522; bytes as \x and hexadecimal digits; a timestamp in any form a put takes.

A COPY is one command, as in PostgreSQL. Its rows go in as puts of 10 000 — each links its vectors on every core — into one block, so a bad row, a cancel or the client's CopyFail puts back every row, and in a transaction the rows are the transaction's writes. Past its first put the COPY holds the database as a transaction does, and a client that stops sending for longer than --idle-in-transaction-timeout has its rows put back. An error names the line and the column (COPY docs, line 3, column year: invalid input syntax for type bigint: "n/a", 22P02; a row of too few or too many cells, 22P04) and is sent at once; what the client still streams is dropped.

Refused with 0A000, before a row is sent: a file or a program on the server's side (\copy sends the file from the client), and a COPY among other statements in one query. In binary an int, a float, a timestamp and a vector are read without parsing text: pgx's CopyFrom of the same 100 000 rows loads at 600 000 rows/s without an index with pgvector-go's Vector, and at 243 000 with each vector written as text. 100 000 rows of a text, an int and a 128-dim vector load at 17 600 rows/s with the HNSW graph kept as they land and 171 000 without, against 17 200 and 152 000 sent a put a row in a transaction, as a driver's executemany sends them, and 434 and 62 000 into PostgreSQL with pgvector by its own COPY (Loading rows).

COPY docs [(col, ...)] TO STDOUT reads a collection out the way a client reads a table: psql's \copy ... to, psycopg's cursor.copy, asyncpg's copy_from_table, pgx's CopyTo and the postgres crate's copy_out. Every row goes, in id order, in the text format or CSV with the same options — each value as its PostgreSQL text, escaped or quoted so that COPY ... FROM reads the same row back — or in the binary format, each cell as a binary query's row sends it: a list as its element's array, a vector as pgvector's.

psql -h 127.0.0.1 -p 5433 -U fenec \
  -c "\copy docs (title, year) to 'docs.csv' with (format csv, header)"
# COPY 30000

The rows are read a page of 1 000 at a time, each page under a read lock of its own and written to the client with none held, so a slow client keeps no writer waiting and only a page is in memory. A row goes out once, as it stood when its page was read; a transaction that holds the database — one that wrote, or a serializable one — reads it as it stands throughout. COPY (get ...) TO STDOUT reads a FenecQL get's rows out instead, as the get answers them: its order and page, a near's _score, a lookup widened into the row, run whole as it would be on its own. Anything but one get in the parentheses is refused (0A000). The same 100 000 rows of a text, an int and a 128-dim vector read out at 157 000 rows/s in text and 1 540 000 in binary, against PostgreSQL's 156 000 and 747 000 (Loading rows).

DuckDB, and Parquet through it

INSTALL postgres; LOAD postgres;
ATTACH 'host=127.0.0.1 port=5433 user=fenec dbname=fenec' AS f (TYPE postgres, READ_ONLY);
SELECT g, count(*), avg(x) FROM f.public.docs WHERE year = 2024 GROUP BY g;
COPY (SELECT * FROM f.public.docs) TO 'docs.parquet' (FORMAT parquet);

DuckDB reads a collection as a table through its own postgres extension: the catalog lists it, and each read is COPY (SELECT "col", ... FROM "public"."docs" WHERE ...) TO STDOUT (FORMAT "binary"), which fenec-pg runs as the get it is. The conditions DuckDB pushes down — a column compared with a literal, IS [NOT] NULL, IN (...), joined by AND — are read as their columns' types, since DuckDB quotes an int's 100 as '100'; COLLATE "C" is the byte order fenecdb compares in anyway. It splits a table into tasks by ctid, and fenecdb has no row addresses: the range covering every row is taken, and part of a table named by them refused rather than read wrong. A vector, whose type DuckDB has no reader for, it asks cast to VARCHAR, and gets its text. 50 000 rows went into a Parquet file in 97 ms, and count, sum and a GROUP BY over them in 52 to 90 ms; from Parquet, pandas, Spark and the rest read them.

Spark, through JDBC

df = spark.read.jdbc("jdbc:postgresql://127.0.0.1:5433/fenec", "docs",
                     properties={"user": "fenec", "driver": "org.postgresql.Driver"})
df.filter("year >= 2024 and g = 'a'").groupBy("g").count().show()

Spark reads a collection through pgjdbc with plain SQL, which fenec-pg runs as the get it is: SELECT * FROM docs WHERE 1=0 for the columns, SELECT "n","g" FROM docs WHERE ("n" IS NOT NULL) AND ("n" < 10) AND ("g" = 'a') for the rows with the conditions it pushed down — each in parentheses, a number bare and text quoted, read so — and SELECT 1 FROM docs for count(), answered with as many rows of the constant as rows match, Describe naming the column first as pgjdbc asks it. The aggregation is Spark's. For a large table, DuckDB's Parquet (above) is the faster road in.

pgvector's clients

A vector field is pgvector's vector, a vector<N, f16> its halfvec and a sparse vector its sparsevec: the catalog names them so, in public where CREATE EXTENSION vector puts them, and a column and a parameter are described with their OIDs. pgvector's client libraries find the types by name and register their codecs, and read and write vectors in pgvector's binary format — the dimension, then each component's float4 or float2, and for a sparse vector its indices from 0 and its weights — as they do against PostgreSQL with pgvector:

libraryregistered withwhat goes
pgvector-python, psycopg 3register_vector(conn)NumPy arrays, HalfVector, SparseVector both ways, executemany, a binary COPY with set_types
pgvector-python, asyncpgawait register_vector(conn)NumPy arrays, HalfVector, SparseVector both ways, executemany, copy_records_to_table
pgvector-go, pgxpgxvec.RegisterTypesVector, HalfVector, SparseVector, batches, CopyFrom
pgvector-node, node-postgresregisterTypes(client)a vector read as an array, written with toSql

Each is held to these flows beside its driver (Drivers).

In binary a vector costs no text to write or parse: through tokio-postgres a page of 1 000 768-dimension vectors reads in 5.5 ms, against 31.4 ms as text. A client with no codec for the type reads a vector as its text, as before — psycopg, asyncpg, pgx and node-postgres give a string — and sends one as text. tokio-postgres does not: like any type it has no Rust type for, it refuses a &str for a vector parameter and a String for a vector column, as it does against pgvector, so it takes pgvector-rust's types. A vector holding a NaN or an infinity is refused (22000), as pgvector refuses it.

The catalog

psql's \d, JDBC's DatabaseMetaData and DBeaver's navigator do not ask which collections exist: they send SQL over pg_catalog and information_schema, with joins, CASE, casts to regclass, correlated subqueries, UNION and window functions. fenec-pg runs that SQL over a catalog it makes from the schemas each time, so the tools see the database as it is:

fenec=# \d docs
                        Table "public.docs"

--------+--------------------------+-----------+----------+---------

    "docs_pkey" PRIMARY KEY, btree (id)
    "docs_body_text" bm25 (body)
    "docs_embed_hnsw" hnsw (embed)
    "docs_n_sorted" btree (n)
    "docs_title_hash" hash (title)

A collection is a table in public, its id the first column and the primary key, each field a column of the type the wire already reports for it — a vector as vector(N), a sparse one as sparsevec(N), a list as an array. Each fenecdb index is an index with its own access method: hash, btree for @sorted, hnsw, bm25 for @text, and inverted for @inverted. It is checked against psql 17's own queries (\d, \d+, \dt, \di, \dn, \l), PgJDBC 42.7's getTables, getColumns, getPrimaryKeys and getIndexInfo, and the SQL DBeaver's PostgreSQL navigator runs for databases, schemas, tables, columns, constraints and indexes.

Over a thousand collections of ten fields, psql's \d answers in 11 ms and JDBC's column lookup for every table in 122 ms. Joins find their rows by key where the query names an equality; trying every pair took the same column lookup 18.1 s. A WITH is read, and a recursive one runs until a step adds no row, as PostgreSQL runs it — asyncpg looks up a type it has no codec for with one — for 1 000 steps at most. A query outside what the catalog reads, a right or full join, is answered empty, as every catalog query was before, so a client never stalls on one.

A catalog query's parameter is the type the query casts it to — $1::oid[], the array of type OIDs asyncpg looks up, arrives as the binary array it is told, $1::text as text — or else the type of the column it is compared with, as PostgreSQL infers the $1 of t.oid = $1 an oid, and text where neither names one. pgvector's clients find its types as they find them in PostgreSQL: psycopg's TypeInfo by to_regtype, which pgvector-python's register_vector calls for vector, halfvec, sparsevec and the bit every PostgreSQL has; pgvector-go by to_regtype('vector')::oid; pgx's LoadType by $1::text::regtype::oid; and tokio-postgres by its lookup of an OID it does not know.

Both directions

The same protocol code runs the other way round. fenec import connects to a real PostgreSQL server and streams COPY ... TO STDOUT, and with --follow reads a logical replication slot through pgoutput. The server half of SCRAM lives in scram.rs and the client half in fenec-wire's client.rs; both are hand-written, so they test each other. See Import.

fenec-pg --follow postgres://... runs that follower inside the server, over the file it serves: a table of PostgreSQL mirrored as it commits, and served over this protocol, HTTP and subscriptions at once. The mirrored collection refuses every write but the follower's with 25006. See Serving the mirror as it follows.

Plugins

The plugin system takes after PostgreSQL's extension model: scalar functions, write hooks and transport adapters can be registered.

db.install_plugin(&PgPlugin)?;   // pg_version(), pg_typeof(), to_pgvector()

Containers

The Dockerfile is two-stage: a static musl build copied into scratch. There are no dependencies and the binary runs its own health check, so the runtime image holds nothing but the binary — no shell, no package manager, no libc. The image is 2.88 MB on amd64 and 2.51 MB on arm64 — since no target is written in, both come out of the same file.

make docker                     # build the image
make docker-run PGPASS=secret   # 127.0.0.1:5433, named volume

FENECPG_PASSWORD=secret docker compose up -d

Three things behave differently in a container:

  • A password is mandatory. The default CMD listens on 0.0.0.0, and with authentication off a non-loopback bind errors out and exits. Give FENECPG_PASSWORD, a Docker secret works too, or add --insecure deliberately.
  • The memory limit comes from the data. With no page cache there is no knob to tune: the file is mapped and what the process holds is the indexes, which is what --max-memory counts. Below that the cgroup sends SIGKILL, the clean shutdown never runs and up to one sync interval is lost. Set --max-memory to a third of the container limit to bring that forward.
  • The restart cost depends on how it stopped. docker stop sends SIGTERM and a checkpoint is written, so the next open takes 9 ms. After kill -9 or a cgroup OOM the graph of the last checkpoint is restored, and the vectors written since it go in unlinked: the server answers once the documents are read, and links them on a thread beside its queries, near measuring each of them until then. The only checkpoint the server writes on its own is the one at shutdown, but it appends its graphs to the file as they change — a graph that changed in 10 000 nodes, once the file has grown by three times its record, logged as 1 graph written into the file, with writes held off for the 5 ms that takes at 100 000 × 768 — so what waits is what came after the last of them: at 100 000 × 768 at most 10 000 vectors, linked in 2.6 s with near at 1.56 ms p50 meanwhile. With no graph in the file every vector waits: at 100 000 × 768 never checkpointed the first near was answered 1.23 s after the start, against 67.7 s when the open linked them first, and linking takes 19 s, 30 s with two clients each sending a near every 20 ms, which take 11.2 ms p50 and 33 ms p99 meanwhile. fenec_vectors_unlinked counts down to 0.

Every default has to be written out by hand. Overriding CMD drops --file and the container comes up with an in-memory database.

docker run -d --name fenecdb -v fenecdata:/data \
  -p 127.0.0.1:5433:5433 -p 127.0.0.1:8080:8080 \
  -e FENECPG_PASSWORD=secret fenecdb \
  --listen 0.0.0.0:5433 --file /data/data.fenec --sync 250 \
  --http 0.0.0.0:8080 --http-token a-token

There is no shell in the image, so docker exec ... sh does not work; what is left is docker logs and docker run --rm fenecdb --help.

A single instance, always. Two containers loading the same file into memory and writing it corrupt it. On Kubernetes that means a StatefulSet rather than a Deployment, replicas: 1, strategy: Recreate and a ReadWriteOnce volume — a rolling update keeps two pods up together for a moment. There is a connection ceiling but no pool: an excess connection does not wait, it gets 53300. Put pgbouncer in front to queue.
