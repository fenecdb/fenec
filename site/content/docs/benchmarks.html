Benchmarks

Every number here comes from crates/fenec-bench and can be reproduced with a make target. The method is written out below the table, because a number without one is a claim, not a measurement.

Method

  • All three follow the same workflow: bulk load first, index after. That is already the recommended order for SQLite and PostgreSQL; in fenecdb create index exists for exactly this.
  • SQLite: WAL with synchronous=NORMAL, the bulk write in one transaction, the index built afterwards. fenecdb does not fsync per write.
  • PostgreSQL: in Docker, bulk load with COPY, then hnsw (m=16, ef_construction=200) — the same parameters as fenecdb — with max_parallel_maintenance_workers set so the build gets one process per core, as fenecdb's does: seven workers and the leader here. At query time hnsw.ef_search = 100, fenecdb's default.
  • fenecdb and SQLite compute vector distance with the same code: SQLite's rows are read back and scored by fenecdb's kernel, so what separates the two is the cost of fetching the data, not the arithmetic. PostgreSQL computes it inside pgvector.
  • SQLite's core has no ANN index, so a vector search there is a full scan. The comparison is therefore exact against exact first, with ANN on a separate row.
  • The write is split in two stages, rows and index. A single "total" would weigh an engine that builds an ANN index and one that does not on the same scale.
  • The PostgreSQL figures include a 0.41 ms TCP round trip, about 40% of its ANN time. That is not a measurement flaw, it is the client-server architecture.

How to read the numbers

fenecdb leads on raw write speed: 925 k rows/s, more than twice SQLite's. The append-only segment store reduces a write to appending to an arena — no B-tree rebalancing, no page splits.

pgvector builds the index faster: 8.7 s against fenecdb's 10.2 s, at the same m and ef_construction on the same cores. This page used to say the opposite, 10.2 s against 14.2 s — pgvector was then building with its default two workers while fenecdb used every core. SQLite's 0.03 s is not an ANN index but a single-column B-tree; that cost does not vanish, it is deferred to query time, where a vector search takes 31.1 ms — 174× slower than fenecdb's ANN.

The clearest loss is reopen. SQLite opens in 1 ms because it loads nothing, reading pages as it needs them. fenecdb pulls the vector arena into memory and validates the graph: 120 ms. That is not a shortcoming but the other side of the same coin — it is why queries are 3–174× faster. The measured break-even is four vector queries; after that fenecdb is ahead on the total.

fenecdb leads on disk as well, 2.5× smaller than pgvector — though not for the reason this page used to give. Of pgvector's 144.9 MB, 83.2 MB is the HNSW index, which keeps its own copy of every vector so a search reads no heap tuple. The heap is 58.7 MB, as large as fenecdb's whole file with its graph, and its MVCC headers are about 2.8 MB of that. fenecdb's graph stores links and nothing else; the vectors are read from the one arena. The WAL is in neither figure.

Without a persisted graph, reopening the same data takes 10.2 seconds — the index is rebuilt from scratch, which would make a page refresh in the browser unusable. The graph record makes that roughly 90× faster and costs 11% more space in the image, 52.1 MB to 57.9 MB.

The ef and recall trade-off

The default is 100: recall is complete and it is still roughly 7× faster than the engines compared above. It is tunable per query — get docs near embed $1 ef 200 limit 10 — and exact performs a full scan when you want ground truth.

--example sweep walks the same trade-off on both distributions, but its latency column is the mean over 50 cold queries, so the two tables are not directly comparable.

On uniformly random vectors — the pathological case for any ANN index, where in 128 dimensions all distances converge and no neighbourhood structure survives — recall at the same ef is around 82%. Real embedding models output clustered data. --uniform measures that worst case deliberately.

The compressed columns are filled in only where they mean something: the wasm module and the client are fetched over HTTP, so what the browser pays is 150 KB brotli for both together. A binary you execute and an image whose layers are already compressed are not served that way, hence the dashes.

The brotli column is -q 11, and the level matters. That is the right number for a file compressed once at build time and served as a static asset, which is how this site ships the module. A server compressing on the fly does not spend that: the same two files come out at 164 KB at -q 5, nginx's dynamic default, and 174 KB at -q 4. Quoting the best case without naming it would flatter the number by 12–18%.

The on-disk column is not the transfer size and is not trying to be. It is what gets decompressed, compiled and held: WebAssembly.compile and the module's memory footprint track that figure, not the compressed one, and so does reading the thing end to end.

fenec-pg stays on the release profile on purpose: a connection thread that panics unwinds and takes down only its own session, and the server stays up. The cli profile turns panic unwinding into abort, which is right for a single process with nothing to recover.
