The vectors are quant's: 64 centres spread along 32 directions, as embeddings vary along far fewer directions than they have, 1 000 held-out queries, and recall against the exact ten found by brute force. Each row also carries a tag from a hash of its own, which a filter keeps 1% or 25% of the rows by, with an index on it in both. Both HNSW indexes take m 16 and ef_construction 64, pgvector's defaults.

Each side gets its best way. fenec-pg keeps its index as the rows land from a binary COPY. pgvector builds after the COPY, as it advises, in memory and on every core of Docker's virtual machine (4 GB, 8 CPUs; its parallel_workers is set, since 768-dim vectors live in TOAST and PostgreSQL planned one process for them), reads its index into its buffers before the queries (pg_prewarm), and searches a filter with hnsw.iterative_scan = relaxed_order. PostgreSQL answers from inside that virtual machine, so an empty query's round trip is 0.21 ms against fenec-pg's 0.07 on the host: it accounts for 0.14 ms of each answer, not for the rest.

Each server was run on its own after four idle minutes, on an Apple M1 MacBook Air: fanless, it slows under minutes of load on every core, and a run straight after another took up to three times as long. pgvector's recall moves from build to build, since its workers insert in parallel: 95.3 to 98.3% at a beam of 100 over four builds of the million. The greedy descent through its upper layers leaves some queries in another cluster than their own, and 3 to 23 of the 1 000 found none of their ten. A million 768-dim vectors does not fit this machine: pgvector's build alone needs about 4 GB.

The memory a server holds is what the kernel cannot take back without swapping it out, on Linux for both: PostgreSQL's is its container's anonymous memory and the shared memory of its buffers, from the container's cgroup — mostly the buffers, 1 GB as configured here and full once the index is read into them — measured in a container started afresh for each run, since the buffers keep what an earlier run left. fenec-pg's is its vector arena, its graph and its indexes, and at most 16 MB of documents written since it last handed them over to its file (The file is mapped): what its engine counts (fenec_memory_bytes), which is what the same load held of anonymous memory in a Linux container, 716 and 820 MB. On this Mac its physical footprint was larger, 1 074 and 892 MB, since macOS's allocator keeps freed blocks in a cache of its own. The pages of their files each keeps besides are clean, and the kernel takes them back as it needs the memory: the pages of fenec-pg's mapped file that the queries read, and PostgreSQL's page cache of its table and index.

What a load holds at its peak is another matter, and a COPY of every row in one command shows it (make scale-bench SCALE_ARGS="--copy-rows 0"). A block holds its writes until it lands, and it used to hold them twice, in its record and in the stores: 250 000 768-dim rows in one block peaked at 2 389 MB of anonymous memory against the 820 they left, measured in process in a Linux container. A block now spills into the file every 16 MB before it lands (File format), and the same load peaks at 904 MB; in blocks of 50 000 rows, 888 against 1 144. On this Mac the peak footprint of that one COPY went from 2 577 to 1 396 MB, the rest of it blocks its allocator keeps.

Method

  • All three follow the same workflow: bulk load first, index after. That is already the recommended order for SQLite and PostgreSQL; in fenecdb create index exists for exactly this.
  • SQLite: WAL with synchronous=NORMAL, the bulk write in one transaction, the index built afterwards. fenecdb does not fsync per write.
  • PostgreSQL: in Docker, bulk load with COPY, then hnsw (m=16, ef_construction=200) — the same parameters as fenecdb — with max_parallel_maintenance_workers set so the build gets one process per core, as fenecdb's does: seven workers and the leader here. At query time hnsw.ef_search = 100, fenecdb's default.
  • fenecdb and SQLite compute vector distance with the same code: SQLite's rows are read back and scored by fenecdb's kernel, so what separates the two is the cost of fetching the data, not the arithmetic. PostgreSQL computes it inside pgvector.
  • SQLite's core has no ANN index, so a vector search there is a full scan. The comparison is therefore exact against exact first, with ANN on a separate row.
  • The write is split in two stages, rows and index. A single "total" would weigh an engine that builds an ANN index and one that does not on the same scale.
  • The PostgreSQL figures include a 0.41 ms TCP round trip, about 40% of its ANN time. That is not a measurement flaw, it is the client-server architecture.

How to read the numbers

fenecdb leads on raw write speed: 936 k rows/s, more than twice SQLite's. The append-only segment store reduces a write to appending to an arena — no B-tree rebalancing, no page splits.

fenecdb builds the index faster: 3.4 s against pgvector's 8.6 s, at the same m and ef_construction on the same cores. It was the other way round, 10.2 s against 8.7, while fenecdb linked each batch of new nodes on one core: pruning the neighbour lists they joined was 70% of its build, and the lists are now pruned in parallel, grouped by list, into the same graph. On aarch64 the distances are written out in NEON as well, a walk measures its neighbours four at a time, to the same bits, and it asks for the next neighbour list and the neighbours' vectors before it reads them, so that one cache miss is not waited out before the next. Before that, this page said fenecdb was faster, 10.2 s against 14.2 s — pgvector was then building with its default two workers while fenecdb used every core. SQLite's 0.03 s is not an ANN index but a single-column B-tree; that cost does not vanish, it is deferred to query time, where a vector search takes 30.2 ms — 330× slower than fenecdb's ANN.

The clearest loss is reopen. SQLite opens in 0.9 ms because it loads nothing, reading pages as it needs them. fenecdb pulls the vector arena into memory and validates the graph: 9 ms. That is not a shortcoming but the other side of the same coin — it is why queries are 10–330× faster. The measured break-even is one vector query: from the first, fenecdb is ahead on the total.

fenecdb leads on disk as well, 2.4× smaller than pgvector — though not for the reason this page used to give. Of pgvector's 145.0 MB, 83.2 MB is the HNSW index, which keeps its own copy of every vector so a search reads no heap tuple. The heap is 58.7 MB, as large as fenecdb's whole file with its graph, and its MVCC headers are about 2.8 MB of that. fenecdb's graph stores links and nothing else; the vectors are read from the one arena. The WAL is in neither figure.

Writers and readers at once

fenecdb and SQLite both take one writer at a time. What that costs when many want to write, and what readers wait meanwhile, measured in one process: fenecdb's threads share one database behind a lock, as fenec-pg does; SQLite's hold a connection each, WAL, with a 30 s busy timeout. A row a write, a row by id a read, median of three runs on an M1. Durable is an fsync per commit, F_FULLFSYNC for both (Rust's sync_data on macOS; PRAGMA fullfsync for SQLite, synchronous=FULL); without one, fenecdb's writes stay in its buffer and SQLite's reach the operating system (synchronous=NORMAL).

Durable writes scale with the writers. fenecdb's fsync runs after its lock is released, and a write an earlier fsync already covered waits for none, so sixteen writers share their fsyncs; SQLite syncs a commit while it holds the write lock. Without an fsync, one fenecdb writer is fourteen times SQLite's, and handing the lock between sixteen costs a third of that.

A transaction held open does not stop the readers. One writer is how fenecdb isolates a transaction: from its first write to its COMMIT no other session writes. Between its statements it lets go of the lock, though, and a reader that arrives puts the transaction's writes aside — the undo a rollback does, the writes kept for its next statement to write again — and reads what has landed. Here the reads went at the rate they go alone, and none waited more than 0.3 ms; held under the lock throughout, as it once was, the transaction cut them to a thirtieth and kept one waiting 34 ms. A transaction that changed a graph — a vector written or deleted — or the schema is not put aside, since undone and written again each of its nodes would be a tombstone and another node: readers wait for that one, where SQLite's WAL reads the last commit. A statement on its own holds the lock for microseconds, and --idle-in-transaction-timeout (10 s) bounds how long a transaction keeps the writers waiting.

Most of a round trip is the loopback. For a row by id the server's own work is a few microseconds of the twenty: one read and one write on the socket, and the statement. A prepared statement is parsed when it is prepared, and POST /query keeps the statement a text parsed to, so neither reads its text again for each request; an HTTP answer goes out in one write. The network, not the engine, is most of that difference, and the bench prints the empty query beside the rest so that it reads that way.

With the graph kept, the graph is the cost. Every way lands within a fifth of linking the vectors in process. A transaction's, a pipeline's, a /batch's and a COPY's vectors are linked together, 512 at a time on every core, whether they came a row a statement or 10 000 a put, so a driver's executemany goes as fast as a COPY: linked a row at a time, as they were before, the same rows went in at 5 400 rows/s. PostgreSQL's HNSW index takes each row on its own, on one core.

Without it, the vectors' text is. Each row's vector is 128 numbers written out, read straight into its f32s wherever it comes from — a JSON array, a pg parameter, a COPY cell — in one pass that finds each number's end: through a JSON value a number, the same rows went in over HTTP at 123 000 rows/s. The simple protocol reads them as FenecQL literals, with the rest of the statement's text, and is the slowest of the ways, still 1.7× PostgreSQL's COPY. In process the rows arrive parsed, which is what the rest can at most reach. PostgreSQL answers from inside Docker's virtual machine on the same Mac, whose network carries every byte.

The compressed columns are filled in only where they mean something: the wasm module and the client are fetched over HTTP, so what the browser pays is 166 KB brotli for both together. A binary you execute and an image whose layers are already compressed are not served that way, hence the dashes.

The brotli column is -q 11, and the level matters. That is the right number for a file compressed once at build time and served as a static asset, which is how this site ships the module. A server compressing on the fly does not spend that: the same two files come out at 180 KB at -q 5, nginx's dynamic default, and 190 KB at -q 4. Quoting the best case without naming it would flatter the number by 12–19%.

The on-disk column is not the transfer size and is not trying to be. It is what gets decompressed, compiled and held: WebAssembly.compile and the module's memory footprint track that figure, not the compressed one, and so does reading the thing end to end.

fenec-pg stays on the release profile on purpose: a connection thread that panics unwinds and takes down only its own session, and the server stays up. The cli profile turns panic unwinding into abort, which is right for a single process with nothing to recover.
