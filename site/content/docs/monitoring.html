Monitoring

fenec-pg counts every statement it answers — over PostgreSQL and over HTTP, reads and writes apart, with how long each took — and serves the counts at /_metrics in Prometheus's text format. A Grafana dashboard comes with it, and --slow-ms logs every statement over a threshold with its text.

# data over PostgreSQL alone: /_metrics on a listener of its own
fenec-pg --file data.fenec --listen 0.0.0.0:5433 \
         --metrics 0.0.0.0:9464 --admin-token "$SCRAPE" --slow-ms 100

curl -H "Authorization: Bearer $SCRAPE" http://127.0.0.1:9464/_metrics
# fenec_statements_total{transport="pg",kind="read"} 1834
# fenec_statement_duration_seconds_bucket{transport="pg",kind="read",le="0.001"} 1790
# fenec_documents{collection="people"} 90000
# ...

With --http the HTTP listener serves /_metrics as well, and a --dir node serves it there. The path carries an underscore, as /_admin and /_replication do: a collection may well be called metrics, and GET /metrics is how its rows are read. Prometheus takes the path as metrics_path.

A scrape needs the server's token (--http-token) or the admin token (--admin-token); with neither and no JSON Web Tokens the server is open, and so are its metrics. A JWT is not taken: a user held to a policy must not learn the other collections' names from a scrape. A --metrics address outside loopback wants one of the two tokens, as the HTTP listener does, or --insecure.

What is counted

A statement is timed from its arrival to its answer: the wait for the lock is in it, and under --sync always the wait for the disk, since that is the latency a client sees. Over PostgreSQL a statement is a query string; over HTTP it is a request, and /batch is one however many statements it carries. A statement that took the write lock is a write, so a get sent through POST /query is a read.

A tenant node counts its tenants and not what they hold: a tenant's collection names are not the node's to publish, and a label per tenant would be as many series as there are customers. The statement counters are one set per process, and start again at zero with it, which rate() takes in its stride.

The dashboard

monitoring/ in the repository holds a Grafana dashboard (grafana/fenecdb.json), a Prometheus configuration and a compose file that runs fenec-pg with both, the dashboard already loaded:

FENECPG_PASSWORD=secret FENEC_METRICS_TOKEN=scrape \
  docker compose -f monitoring/docker-compose.yml up -d
# Grafana: http://127.0.0.1:3000/d/fenecdb     Prometheus: http://127.0.0.1:9090

It opens on the figures that decide whether anything needs doing — the version and uptime, whether the disk has refused a write, statements and errors per second, the memory footprint — then statements by transport and kind with their p50 and p99, errors, and slow statements a minute; documents, writes a second and each collection's dead share, the one that says when to compact; replication; and tenants. The instance variable picks one server or all of them. Imported on its own, the dashboard asks for a Prometheus data source.

# the p99 of reads over PostgreSQL, over five minutes
histogram_quantile(0.99, sum by (le) (rate(fenec_statement_duration_seconds_bucket{transport="pg",kind="read"}[5m])))

# worth an alert
fenec_storage_failed == 1
fenec_replica_behind > 10000
fenec_dead_bytes / (fenec_data_bytes + fenec_dead_bytes) > 0.5

Slow statements

--slow-ms 100 writes every statement that took 100 ms or longer to the log, pg and HTTP alike, with the same timing the histogram has:

slow statement: 312.4 ms, pg read: get people select name order name collate tr
slow statement: 148.9 ms, http write: POST /batch {"query":"put orders {person: 7, total: 4200}"} {"query":...

A parameter's value is not logged, only how many there were: a value bound as $1 stays out of the log, a literal written into the text does not. Over HTTP the line is the method and the target, and for /query and /batch the body that holds the statements. A line is cut at 1 000 bytes, so a bulk put of a megabyte shows what it was without being all of it.

What each statement cost

curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8080/_stats/statements
psql -c "select query, calls, mean_exec_time, rows from pg_stat_statements order by total_exec_time desc limit 10"
curl -X DELETE -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8080/_stats/statements

Every statement is also counted by its shape — its text with each literal and parameter written $1, $2… and a list of literals alone, a vector's components, as one — so the same statement run with other values is one line: how often it ran, its total, mean, least and most time, the rows it returned or changed, and its failures. Over HTTP a /query or /batch is counted as its FenecQL, with the same statement over the pg wire; a call to a collection's path as its method and path. GET /_stats/statements answers JSON, most time first, and DELETE forgets it all; over the pg wire the counts are PostgreSQL's pg_stat_statements view, which psql and monitoring agents read as they read the extension's.

The server keeps at most 5 000 shapes, as the extension does by default, and forgets the least called when it is full. The counts need what reads the data without a JWT's scope, or the admin token: a shape names every collection. A tenant node keeps each tenant's apart — /t/<tenant>/_stats/statements and its own connection's view — and lists every tenant's, named, to its admin alone.

What it costs

Counting a statement is a handful of relaxed atomic adds, into counters a thread each: 6.7 ns a statement with eight threads counting at once. Into one shared set of counters the same eight cost 720 ns each, the cache line moving from core to core, which is why they are spread. A scrape reads the gauges under the database's shared lock, beside the readers and ahead of a writer for as long as a count would be.

Counting it by its shape is a pass over its text into a buffer the thread keeps, and an entry found in the thread's shard: 0.34 µs for a read of 87 bytes, 0.56 µs with eight threads counting at once — a sixth of the 2.2 µs parsing it takes. It grows with the text: 5.6 µs for a near with 768 components written into it, whose parse takes 85 (make statements-bench).
