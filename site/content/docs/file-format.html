File format

A fenecdb file is a header followed by records, and an open reads it from start to end in one pass.

Records

Every record is [kind][collection-id][length][body]. These are the kinds:

"FENECDB\x01"
  [6][u64 counter][u64 body length]        change counter (optional)
  [1][collection-id][length][schema]       create collection
  [7][collection-id][length][next-id]      id counter (optional),
                           [index]         an image's, and its data's index
  [5][collection-id][length][schema]       schema change (index)
  [12][collection-id][length][change]      a field added, dropped or renamed,
                           [field][name]   the field and its new name,
                           [schema]        and the schema after it
  [2][collection-id][length]               drop collection (empty body)
  [3][collection-id][length][records]      data
  [4][collection-id][length][field][graph] HNSW graph (optional)
  [8][0][length][history]                  replication history (optional)
  [9][0][length][records]                  a block of several records
  [10][0][length][records]                 a block's spill, before it lands
  [11][0][length][spills][records]         a block that spilled, landing

Inside a data record, each document is [op][doc-id][length][fields], each field a tagged value. A sparse<N> field is [10][N][count], then the indices, each as its distance from the one before, then the weights as f32.

A record cut short is cut off the file, not only skipped. Left in place, the first write appended after it is read back as the rest of it: the write was acknowledged, and the next open loses it.

The length is written even for an empty body — a drop record has one — and the reader must consume it. Otherwise the leftover byte is read as the next record kind and the file stops opening.

Details

The reasons for each exception to the plain layout are worth knowing before you touch the reader; the sections below give them.

A sparse vector's indices are written as gaps because a SPLADE vector's sit close together, and a small gap takes a byte.

A crash in the middle of an append leaves the last record cut short, in its header or its body: the open loads everything before it and cuts it off the file, so there is no separate recovery step after a crash.

The graph record

Kind 4 holds an HNSW graph's links, so an open does not have to build the graph again. It is derived data: if it does not match the documents, it is ignored and the graph rebuilt, so it can never lose data.

  • It stores links, not vectors — except a tombstone's vector.
  • The last one wins, and the writes after it are applied on top.
  • Versions 5 and 6 are a checkpoint with nodes waiting to be linked, and a server's record in the tail.
Details

It is derived data, not a cache. On open, the version, the dimension, the precision and the link bounds are validated, and the live nodes against the documents: every one's document has to hold a vector, and every document holding one has to have a node. If any of it does not hold, the record is ignored and the index is rebuilt from scratch. A corrupt or stale graph therefore cannot cause data loss.

It is written during snapshot, compact and checkpoint, and a server appends one to the file's tail now and then (below) — never on the normal write path. What it stores is the links, not the vectors: the vectors are already in the document records, and the expensive part is the build. The exception is a tombstone, the node a deleted or rewritten document leaves behind until compact: it still routes searches, but its document is gone or holds another vector, so the record carries the vector the node was linked with.

The graph is restored where its last record is, against the documents as they stood there: a checkpoint's image holds one after each collection's data. Everything after that point is applied to it the way the write path applied it: the node of each document written since is retired, and the vector the document holds now goes in. A crash therefore costs the writes after the last graph, not the graph. An earlier record of the same graph is passed over — the open walks the record heads to find the last one first — since restoring it would read every vector again for nothing.

A server keeps its graphs in the file as they change, since it writes a checkpoint only on its way down: once a graph has changed in 10 000 nodes since it last reached the file, has none waiting to be linked, and the file has grown by three times its record since, it is appended to the tail, the writes held off while it is written. The record holds the whole graph, which is why the growth counts too: a big graph written every few thousand writes would be written over and over for a little of it. It is written in version 6, whose layout is version 5's; a binary that does not know 6 rebuilds the graph rather than restore it against the documents the whole file left, which a vector rewritten after the record would not match. It is not a write: the change counter does not move, no replica is sent it, and a record cut short is cut off the file like any other. The next checkpoint leaves the ones before it out.

A server does not wait for the tail. It opens with the tail's vectors in the arena but in no neighbour list, measures each of them in every near, and links them on a thread beside its queries. A checkpoint written before that is done marks those nodes as waiting: a node's flag byte, 0 for a live node and 1 for a tombstone, is 2 for one, in a graph record of version 5, which is written only then. The next open leaves them waiting again, or links them there when it is not a server's. An older binary does not know version 5 and rebuilds the graph, as it does from any record it cannot read.

A graph over bit codes (quant=bit) also carries the centres its codes are taken from, since a restored graph has to code its vectors against the ones it was built with. Where the quantization's code goes, a bit graph writes 3; the number of centres follows, then each centre as dim little-endian f32s — none while the index still holds its vectors whole. A tombstone's vector is its code: the signs, the centre's number in a byte and two f32s. A bit graph written before the centres, with the vectors' own signs and code 2, is built again on open; a binary from before them does not know 3, and builds its own.

Indexes in the schema

A schema names each field's index by a kind byte. Only the graph is stored; every other index is built from the documents after an open.

kindindex
0none
1@hash
2@hnsw with its parameters
3@text with its parameters
4@sorted
5@hnsw over codes (quant=)
6@inverted
7@text indexing characters as well (chars), with the parameters kind 3 has
8@unique: a hash that refuses a value held twice

A field ordered in a collation (name text collate tr) is written with type tag 11 and the collation's code in front of its type: 1 for tr, 2 for und. A dropped field's place (alter collection ... drop field) is written where it stands as a field with no name and type tag 12: the documents written before the drop hold a value there, which a read passes over, and a document written after it a null. A document that ends before a field's place holds null there: it was written before the field was added.

Details

For every kind but the graph that byte is all the file holds: the hash, text, ordered and inverted indexes are built from the documents by the first statement that reads each after an open, so there is nothing of theirs to validate or to go stale — and a binary that splits text another way, as one before runs of characters did, builds its own text index from the same documents. An old binary cannot open a file whose schema uses a newer kind and reports unknown index kind 4, the same refusal as for a record kind it does not know.

An older binary meets a type tag it does not know, or a collation code, and refuses the file, rather than read the field and order it in another order. The collation's weights are not in the file: they are the binary's, and a @sorted index over the field is built from the documents on open.

The change counter, and why it is at the front

Kind 6 holds the change counter. It sits at the front of the file and is fixed width; its body length marks where the image's own records end.

Details

Record kind 6 sits at the front of the file and is fixed width. Both are deliberate.

At the front, because at the end a corrupt or half-written tail would break opening. The end of the file is exactly where the graph stops, and the graph is derived data — a record that errors out in that region would take that tolerance back.

Fixed width, because the body length is known only after the body is written. A placeholder can be filled in place, whereas a uvarint would mean shifting the whole image.

The body length means "this is where this image's own records end". Every record after it was written after the checkpoint and carries the counter forward. Old files without the record load fine — the counter is then counted from the records. The reverse does not hold: an old binary cannot open a new file and reports unknown record kind 6.

A statement's writes are one record

All the writes of one statement, /batch or transaction are appended as one record, so a crash keeps all of them or none. Within one collection that is a data record (kind 3); otherwise a block (kind 9).

Details

Every write is a block: the documents a put, a set or a del writes, the statements of a /batch, of a text sent over the pg wire or of a transaction. Their frames are held back until the block ends and are appended as one record, so a crash cuts all of them off the file or none; a block that fails is put back in memory instead, and nothing of it reaches the file. Within one collection the record is a data record of as many frames — the form an image's data records have always had, so a binary from before blocks reads it — and a lone schema change is the record it always was. Across collections, or with a schema change among other writes, it is record kind 9, holding each write's record: a data record, or a create's, a drop's or an index's. A binary from before blocks refuses it with unknown record kind 9, and one from before 10.4 a block holding a schema change as corrupt.

The change counter moves by the writes a record holds, not by one a record: a block of five writes is numbered by its last, and whatever counts records by their numbers — a replica, an archive — counts them that way. A restore to a change inside a block stops before it, since the database never stood there.

A large block spills before it lands

A block past 16 MB is written to the file in parts as it goes (kind 10, a spill), then landed by a record that names those parts (kind 11). A spill no land names is ignored.

Details

Held back until it lands, a block's frames were in memory twice — in the record being built and in the stores — so a COPY of 250 000 768-dim rows in one command peaked 1.57 GB over what it left. Once a block's frames amount to 16 MB, a server appends them as record kind 10, a spill, whose body is a block record's, and the stores read those documents from the file from then on. The block lands as record kind 11, which names its spills by where their bodies are in the file and how long they are, and holds its writes since the last. A load applies a spill only where a land names it: one that a rollback, a lapsed lease or a crash left is dead in the file, and the ones a file ends with are cut off, as a record cut short is. The land never travels: a replica and an archive are sent the block as the one kind 9 record it would have been. A binary from before spills refuses kinds 10 and 11 as unknown.

The history record is not a write

Kind 8 records which replication history the writes belong to. It is the one record that must not move the change counter.

Details

Record kind 8 says which history the writes belong to: a list of (id, from change) pairs, one per fork, and whether the file is a replica's. A replica is fed a primary's writes by their number on the change counter, so this is the one record that must not move the counter — a replica would be numbered one change off its primary. It is appended when a history forks or a replica follows one, and written into every image while it is set; a file that never had a replica holds none. An old binary cannot open a file with one and reports unknown record kind 8.

The id counter exists because of compact

Kind 7 keeps a collection's next document id, so a compact can never hand a deleted id out again. In an image it also carries an index of the data record after it, which makes opening faster.

Details

A document id is normally derived from the records: a replay takes one more than the largest id it saw. Compaction throws tombstones away, so that derivation falls short — the highest deleted id disappears from the image entirely and would be handed out again on the next open.

An id coming back silently binds everything still holding it — a link handed out, a row a subscriber holds — to the wrong document. The record is per collection and comes right after the schema. Only snapshot writes it; the append path does not need it, because the tombstones are still there. Old files without the counter still load correctly.

Behind the counter an image writes an index of the collection's data record, which comes right after it: the record's length, the bytes in it that are dead, and each live document's id, payload length and place, each written as its difference from the one before — four bytes a document for records of 590 bytes. A mapped open takes the offset index from it rather than walking the record's frames, whose heads each say where the next one starts: a chain of cache misses that was 5.5 ms of a 14.2 ms open at 100 000 × 128, which opens in 8.4 ms with it. An index that does not fit the record — another length, ids out of order, a payload past its end — is passed over and the record walked. Every reader of the record, older ones included, reads the counter and nothing after it.

Maintenance operations

Four operations read or rewrite the whole file. A rewrite goes to a side file that is renamed into place, so a crash cannot leave it half written.

OperationWhat it doesPeak memory
snapshotBuilds the image in memory: what the browser persists, and what a tenant's move and a replica's first stream send≈ 1× the file
checkpointLands the graph in the file so the next open does not rebuild it; written into the new file as it is producedthe indexes
compactDrops the dead records, keeping every index but a graph holding tombstones: the documents are the same onesthe indexes
openMaps the file and builds the indexes from the documentsthe indexes
Details

A graph holding tombstones is rebuilt by compact from the live vectors: nothing else takes a tombstone out, and every write that changes a document's vector, or deletes it, leaves one. A graph without them is kept as it is.

The rewrite goes to a side file and is renamed, so a half-written checkpoint cannot corrupt the database — and since an image is only ever whole, a record cut short inside it, or an image longer than the file, is refused as a damaged file rather than cut off as a crash's torn tail is. A server's compact writes its image beside the database into <file>.fenec.beside, with no lock held; the documents written meanwhile go into it as a data record at the end of the image, and its header takes the counter as it stands when it is renamed into place. A side file left by a crash is written over by the next compact, and can be deleted.
