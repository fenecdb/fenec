Your language

fenecdb speaks HTTP and JSON, so every language reaches it with the HTTP client it already has. No driver to install.

Every example on this page is a program that runs against a real server on each change to fenecdb (make languages-test). Python, JavaScript, Go and .NET have official clients, each its standard library alone; in the other languages these few lines are the whole client. Swift, Kotlin and Dart embed the database in the app, a file on the device (Mobile and native apps), and reach a server with Fenec.connect; their tabs run the same flow in their own tests. Each tab ends with a full example: one app, Notes, in every language, a folder of a few files to clone and run (examples), and beside them a whole shop in Next.js (shop), a double-entry payments ledger on Node (ledger) and courier dispatch across tenants (dispatch).

Start a server

fenec-server --file app.fenec --http 127.0.0.1:8080 --http-token secret

Then pick your language. Each example makes a collection of a text and a number, each indexed, writes two rows, reads them back by a filter and an order, searches the words with a typo in them and handles a refusal. Each sends one FenecQL statement a request to POST /query, its values as $1, $2, ... in params, and the token as Authorization: Bearer.

batch([(text, params), ...]) runs statements as one block, all or none -- a FenecError that stops it says which (e.at, from 0) and, where a write's require=1, reason="..." said why, e.reason; idempotency_key= on query and batch, or with_idempotency_key(key) for every write of a copy, makes a write once however often it is sent (db.replayed), and db.seq is the change the last write left the database at. AsyncClient does the same in an event loop, the endpoints of its collection(...) awaited; LangChain and LlamaIndex have stores of their own (Integrations).

async function query(q: string, params: unknown[] = []) {
  const res = await fetch('http://127.0.0.1:8080/query', {
    method: 'POST',
    headers: { 'content-type': 'application/json', authorization: 'Bearer secret' },
    body: JSON.stringify({ query: q, params }),
  });
  const body = await res.json();
  if (!res.ok) throw Object.assign(new Error(body.error), { status: res.status });
  return body;
}

Without the SDK, net/http and encoding/json:

// query runs one FenecQL statement and decodes its answer into out.
func query(out any, q string, params ...any) error {
	body, _ := json.Marshal(map[string]any{"query": q, "params": params})
	req, _ := http.NewRequest("POST", "http://127.0.0.1:8080/query", bytes.NewReader(body))
	req.Header.Set("Content-Type", "application/json")
	req.Header.Set("Authorization", "Bearer secret")
	res, err := http.DefaultClient.Do(req)
	if err != nil {
		return err
	}
	defer res.Body.Close()
	if res.StatusCode >= 300 {
		e := &FenecError{Status: res.StatusCode}
		json.NewDecoder(res.Body).Decode(e)
		return e
	}
	if out == nil {
		return nil
	}
	return json.NewDecoder(res.Body).Decode(out)
}

async Task<JsonElement> Query(string query, params object[] args)
{
    var json = JsonSerializer.Serialize(new { query, @params = args });
    var res = await http.PostAsync("/query", new StringContent(json, Encoding.UTF8, "application/json"));

The builder

Python, JavaScript, Go, .NET, Swift, Kotlin and Dart each have a query builder: a chain of calls that writes the FenecQL statement, every value a parameter and every name checked against FenecQL's own rule, which is where an injection would have to get through. All seven build the same text from the same chain, to the byte, and refuse the same mistakes with the same message. Python's builder starts with collection, since from is a keyword there.

A short tour, the same in every tab, over two collections:

create collection docs (slug text @unique, title text @text, year int,
  lang text, tags [text], views int)
create collection comments (doc_id int @hash, body text)

A page of documents, filtered by a comparison and an or, in Turkish order, each with its first three comments; a search that forgives a misspelt word; one document and a count; then the writes — an insert, an insert passed over because its slug is held (slug is @unique), a counter moved and a delete by a filter. db is the client each language's section above connects, and Go's ctx a context. The FenecQL tab is what each chain writes; the block under the tabs is what it sends, its parameters apart.

{{builder "docs: a page of documents with their comments" "docs: documents matching a misspelt word" "docs: the document of a slug" "docs: documents counted since a year" "docs: a document inserted" "docs: a document inserted unless its slug is held" "docs: a document's views counted" "docs: the documents before a year deleted"}}

Each has select with aggregates and group, where with every operator, in, null, paths into a json field and or, and, not and raw; match; near, a vector's nearest rows (near('embed', v, { ef: 64 }) in JavaScript, Vector search), and fuse and rerank, which rank by the words and a vector together; highlight, snippet and facet, the facets beside the rows; lookup and its chains; order with a collation; limit and offset; and the writes, an update or delete with no filter refused unless it says all, a value worked out over the row with inc and expr (Writes that read the row), and an insert if absent. A query is immutable, so a base query can be kept and branched from.

Rows come back as each language holds a document, and three builders also decode them into a type of the app's: Go's fenecdb.RowsAs[T](ctx, q), .NET's RowsAsync<T>() and Swift's rows(as: T.self). Go's endpoints take the ctx that bounds the request, .NET's are …Async, and Kotlin's suspend, with rowsBlocking() and countBlocking() for code outside a coroutine.

How one golden file holds every builder

integrations/builder-golden.json is the contract: each case a chain of steps ({op, args}, the JavaScript builder's names) and the statement it must make, its text and parameters, or the refusal and its message. The JavaScript builder is the reference: make builder-golden runs every chain through it and writes what it made, and its own tests run the file again, so the two cannot drift. The Python, Go, .NET, Swift, Kotlin and Dart tests each read every case, call their own builder, and compare the text and parameters exactly. The cases cover every method and option, each operator and kind of value, parameter numbering across where, near, match and the levels of a lookup chain, and the names and combinations each builder refuses. Each SDK's tests also run builder queries against a real server and hold their answers to the same statements sent as text. The tour above and the tabs of the FenecQL reference's examples are cases of the file written in each language (Text search has some): the JavaScript and Python tabs run as the page shows them, and each other language's tests hold a copy of its tabs' code, so a tab is code that sends the statement beside it.

What a language has no word for is written its own way: Go's object conditions are Fields and Ops, names and values in turn, since a Go map has no order and the order is the text's; a Go document keeps its order as a fenecdb.D(...), and a map's fields go in sorted. Options are keyword arguments in Python, named arguments in C# and functional options in Go, where a struct could not tell limit 0 from no limit. A refusal is a FenecError with status 0 in Python, a *fenecdb.QueryError in Go and a FenecQueryException in .NET. Swift's dictionaries have no order either, so a document or an object condition is a Value or Row literal, which keeps the order written, or a Codable type, its fields in the order it encodes them; Kotlin's and Dart's maps keep their order. A refusal there is a FenecError, a FenecException and a FenecException, each with the code builder, and every builder method throws as it is called, so a Swift chain takes one try.

A require's reason (require 1 else 'no such account', A reason for the refusal) is written the same way: on a read, Python's .require(1, reason="..."), Go's q.Require(1, fenecdb.Reason("...")), .NET's Require(1, reason: "..."), Swift's and Dart's require(1, reason: "..."), Kotlin's require(1, reason = "..."); on a write, the same name among its options (require=1, reason="..." in Python, fenecdb.Reason("...") in Go). The refusal reads it back as FenecError.reason in Python and Swift, Error.Reason in Go, FenecException.Reason in .NET, FenecException.reason in Kotlin and the error's reason in Dart.

From the shell

The same request from curl:

curl -X POST localhost:8080/query -H 'authorization: Bearer secret' \
  -d '{"query":"get docs select title, year where year >= $1 order year desc limit $2","params":[2020,5]}'
# [{"title":"Night at the oasis","year":2024},{"title":"Dunes","year":2021}]

The REST routes, subscriptions and the change stream are on HTTP reference, and batches on HTTP endpoint.

What the examples and SDK tests run against

The programs under integrations/languages are the examples above with their asserts: make languages-test starts a fenec-server over a new file for each language and runs Python, Java, PHP and Ruby from their official images in Docker, and JavaScript, Go, C# and Rust with the toolchains on the machine — Go and C# both through their SDK and without it, and each SDK's program through its query builder too. The SDKs' own tests (make go-test, make dotnet-test) start a primary, a replica of it and a node of tenants and cover the rest: every type of parameter, the errors, a batch put back whole, an idempotency key, reading a write on the replica, a subscription, the change stream, a tenant and a scoped token. CI runs it on every change, so a change to the HTTP endpoint that would break one of them is caught before it ships.

The JavaScript tab's programs are TypeScript, and run there as the JavaScript they are without their types; the tab's code itself is type-checked under tsc --strict against the client's declarations, as every TypeScript example in these docs is (make docs-types).

Every answer is JSON: a read is an array of rows, a ranked search's rows (match, near) carry their _score, a write is {"affected": n}, and a refusal is a status of 400 and up with {"error": "..."} — 401 for a missing or wrong token, 404 for a collection that is not there, 409 for an id insert finds taken. A vector goes in as a JSON array of numbers and comes out as the shortest text that reads back as each f32. Values always go in params, never into the statement's text.

The server keeps a connection open between requests (HTTP/1.1 keep-alive) for a client that reuses it, as Go's, .NET's, Java's and ureq's do. A body is read by its Content-Length; a chunked one is refused.
