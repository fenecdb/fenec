Auth with your identity provider

Sign-in stays with a provider you already use. fenec-server checks the token it hands out, and a policy file decides, row by row and field by field, what that person may read and write.

A backend platform bundles three things: sign-in, rules about who may touch which rows, and a database. fenecdb is the last two. The provider (Clerk, Auth0, Supabase Auth, Amazon Cognito, Cloudflare Access) signs a user in and issues a JSON Web Token. The app, or the browser, sends it to fenec-server as Authorization: Bearer. The server checks the signature against the provider's public keys and holds every statement the token sends to the policy.

Four things to check for your provider before anything else. fenec-server fetches no URL, so the provider's keys are a file you keep fresh (Keys). It takes RS256 and HS256 tokens only, so a provider that signs with ES256 needs an RSA key. It checks neither iss nor aud. And a policy names a claim by a plain, top-level name, which leaves out cognito:groups, Auth0's namespaced claims and everything nested (What each provider's token carries says what each of five does about it). Each of the four is shown below with a run, against a stand-in provider that signs RS256 tokens of the shapes the five providers' documentation describes.

Try it with nothing to sign up for

Make a secret, start a server that takes tokens signed with it, and mint some. --mint-token prints a token for the claims it is given, signed with the secret (or the first oct key of a keys file) and good for an hour unless the claims say otherwise.

head -c 32 /dev/urandom | od -An -tx1 | tr -d ' \n' > jwt.secret

fenec-server --file app.fenec --http 127.0.0.1:8080 --http-token "$ROOT" \
    --jwt-secret-file jwt.secret --policy policy.txt

fenec-server --jwt-secret-file jwt.secret --mint-token '{"sub":"alice"}'
fenec-server --jwt-secret-file jwt.secret --mint-token '{"sub":"carol","role":"admin"}'

The policy is one line a rule. It holds per-user rows, an admin role, fields that only their owner reads, and an audit trail nobody edits:

# collection  access                      rows                           role

# Per-user rows: a person reads and writes their own notes.
notes         read,write                  where owner = $jwt.sub

# An admin also reads every note, and changes none. `role` is a claim of the
# token (a text, or a list holding the role).
notes         read                                                       for admin

# Field read rules: every profile's name is public, the rest is its owner's.
profiles      read(name)
profiles      read,update(name, phone)    where owner = $jwt.sub

# An audit trail a person adds lines about themselves to, and nobody edits.
audit         read,insert                 where actor = $jwt.sub
audit         read                                                       for admin
audit         append-only

What the server answered alice, bob, an admin and a token that has lapsed, statement by statement. sh examples/recipes/auth.sh runs it from a clone, with a fenec-server built by cargo build -p fenec-server (or any binary, as FENEC_SERVER=), and it needs Node, curl and jq; it also creates the collections of schema.fenecql. What the server checks, and what it does not

 What the server does
CheckedThe signature: RS256 against an RSA key of at least 2048 bits, HS256 against an oct key of at least 32 bytes. A key is used for its own algorithm alone, so a provider's public RSA key is never taken as an HMAC secret.
kid: a token that names one is checked against that key and no other. One that names none is tried against every key of its algorithm.
exp, which a token must have (401 otherwise; --jwt-require-exp off takes tokens without); --jwt-max-age <s> also refuses an exp further ahead than that. nbf too.
Not checkediss, aud, azp, client_id, token_use: not read. Every token the keys sign is a token for this database. That is right when the provider's keys belong to one app, and wrong where they do not; Pin the audience is the answer.
Revocation. A token is good until its exp (Expiry).
Not supportedA keys URL. --jwt-keys takes a path, read again when the file changes.
ES256, EdDSA, PS256, RS384 and RS512. Such a token is 401, only HS256 and RS256 tokens are accepted. Keys of any other kind in a JWKS (EC, OKP) are skipped, and a file with no RSA or oct key is refused at the start.
A claim by any name. $jwt.<name> takes letters, digits and _, from the top of the token. cognito:groups, custom:tenant, https://example.com/role and app_metadata.role have no name in a policy.
A role under another name: the role of for admin is the claim called role, a text or a list holding it.

The server reads the token from Authorization: Bearer and from no other header.

Details

A rule whose filter names a claim the token lacks does not apply, so a missing claim narrows what a token may do, never widens it. A token that has been checked is kept by its text, up to 4 096 of them, and the kept ones are dropped whenever the keys change; exp and nbf are asked again on every request. A claim holding a list of more than 1 000 values is refused (401). The whole story of rules and claims is in HTTP security and scoped access.

Keys: the provider's JWKS, in a file kept fresh

Every provider publishes its public keys as a JWKS, a JSON document {"keys": [...]}. fenec-server reads one from a file. A job that fetches it every few minutes is the other half.

ProviderKeysSigns with
Clerkhttps://<Frontend API URL>/.well-known/jwks.jsonRS256
Auth0https://<your domain>/.well-known/jwks.jsonRS256 or HS256 per application; a JWKS publishes the RS256 keys
Supabase Authhttps://<project>.supabase.co/auth/v1/.well-known/jwks.jsonES256, RS256 or HS256 per signing key. Create an RSA 2048 one: an ES256 key is skipped, and the legacy HS256 secret is not in the JWKS
Amazon Cognitohttps://cognito-idp.<region>.amazonaws.com/<userPoolId>/.well-known/jwks.jsonRS256, one key pair for access tokens and another for ID tokens, both in the JWKS
Cloudflare Accesshttps://<team>.cloudflareaccess.com/cdn-cgi/access/certsRS256

How often a key changes, as each one's documentation says:

  • Auth0: one key signs at a time, and the endpoint may hold several during a rotation.
  • Supabase: a standby key is rotated in and the old one revoked once its tokens have expired. The edge caches the JWKS 10 minutes, and the docs say to wait at least 20 minutes after creating a standby key or revoking one.
  • Cognito: keys "might rotate"; cache by kid and refresh.
  • Cloudflare Access: every 6 weeks, and the previous key stays valid for 7 days.
  • Clerk: not said on the pages read.

The job below fetches the file beside the one in use and renames it over. The server looks at the file at most once a second and reads it again when its modification time has changed, so the rename is the rotation: no restart, and no half-written file to read. A fetch that fails, or that returns a page with no RSA key, leaves the file that works where it is.

#!/bin/sh
# Keep the JWKS file fenec-server reads (--jwt-keys) as fresh as the provider's.
# fenec-server fetches no URL itself: it reads this file, and again whenever
# its modification time changes (at most once a second). Run this from cron or
# a systemd timer every few minutes.
#
#   refresh-jwks.sh https://acme.us.auth0.com/.well-known/jwks.json /etc/fenec/jwks.json
#
# The new file is written beside the old one and renamed over it, so the server
# never reads half of one, and only a file holding an RSA key replaces the one
# in use: an error page, an empty body or a provider that went EC-only leaves
# the keys that work where they are, and the job fails for whoever watches it.
set -eu
url=$1
file=$2
tmp=$(mktemp "$file.XXXXXX")
trap 'rm -f "$tmp"' EXIT
curl -fsS --max-time 10 "$url" -o "$tmp"
jq -e '[.keys[]? | select(.kty == "RSA")] | length > 0' "$tmp" >/dev/null ||
    { echo "refresh-jwks: $url holds no RSA key; $file left as it was" >&2; exit 1; }
chmod 644 "$tmp"
mv "$tmp" "$file"
trap - EXIT
# crontab: every five minutes, well inside what any of the five asks
*/5 * * * *  /usr/local/bin/refresh-jwks.sh https://acme.us.auth0.com/.well-known/jwks.json /etc/fenec/jwks.json

fenec-server --file app.fenec --http 0.0.0.0:8080 --http-token "$ROOT" \
    --jwt-keys /etc/fenec/jwks.json --policy policy.txt

  • Behind a rotation a token is 401 with no key has the token's kid until the next fetch. Cloudflare's overlap of seven days and Supabase's twenty minutes are both longer than a five-minute job.
  • A fetch that fails (the 404 above, a provider that is down) makes the job exit non-zero and touches nothing; the keys read last stay in use.
  • A file that no longer reads (written over by hand above) is logged, the keys read before stay, and the server goes on with the keys it has. A file with no usable key is refused at the start: ec.json: no HS256 or RS256 key in the JWKS file.
  • A token already checked is dropped from the server's memory when the keys change, so a key taken out takes its tokens with it.
  • Cloudflare Access answers with keys and, beside them, public_cert and public_certs in PEM. A file of that shape loads (tried here with a stand-in, not with Cloudflare's endpoint), and the job's filter looks at keys alone.

What each provider's token carries

The claim shapes below are taken from each provider's documentation and carried by the stand-in (examples/recipes/idp.mjs). For each: who the user is, where a role or a tenant can come from, and what a policy cannot reach.

Clerk

  • sub is the user id, user_… (session token).
  • A role, a tenant: add role and tenant as claims of the session token (Dashboard, Sessions, Customize session token; shortcodes such as {{user.public_metadata.role}}). Up to 1.2 KB of custom claims fit the cookie.
  • Out of reach: the active organization's role is o.rol, nested. A JWT template lives 60 seconds unless set otherwise.

Auth0

  • sub is the connection's name, a bar and the id: auth0|…, facebook|… (docs).
  • A role, a tenant: an access token for an API carries RBAC permissions as a list (docs), which a rule tests: 'read:notes' in $jwt.permissions. A login to an Organization carries org_id (docs): --jwt-tenant-claim org_id.
  • Out of reach: custom claims in an access token for an API must be namespaced URLs (docs): such a token "cannot have private, non-namespaced custom claims". https://example.com/role has no name in a policy, so a role set that way is out of reach.

Supabase Auth

  • sub is the user's id (claims).
  • A role: role is authenticated for every signed-in user (anon and service_role are the others), so for authenticated admits every signed-in user and cannot single out an admin.
  • Out of reach: app_metadata and user_metadata are objects, so a role kept there has no name. Keep admins as rows (below).

Amazon Cognito

  • sub is the user's id. An access token has client_id and no aud; an ID token has aud (docs).
  • A role, a tenant: add a plain claim (role, tenant) with a pre token generation trigger: version 1 for the ID token, 2 or 3 for access tokens, which needs the Essentials or Plus plan. The trigger may add any claim not in the pool's token schema.
  • Out of reach: cognito:groups and custom:… attributes: a colon is not part of a name.

Cloudflare Access

  • sub is the user's id, unique to an email address per account; email is a claim too (docs).
  • A role: none of its own. Rows (below), or the email.
  • Out of reach: the token reaches the origin in Cf-Access-Jwt-Assertion, and fenec-server reads Authorization: Bearer alone: a Worker or proxy in front moves it. aud is a list holding the application's tag, and a team's applications are signed with the same keys: pin it.

The user's sub is what owner = $jwt.sub compares with, so a row's owner holds it exactly as the provider writes it. The same stand-in alice is five different people to five providers; a note written for each one's sub and read back with that one's token:

clerk: sub user_2xYzAbc                    [{"owner":"user_2xYzAbc","title":"clerk note"}] [200]
auth0: sub auth0|0123456789                [{"owner":"auth0|0123456789","title":"auth0 note"}] [200]
supabase: sub 7c9e6679-7425-40de-944b-e07fc1f90ae7 [{"owner":"7c9e6679-7425-40de-944b-e07fc1f90ae7","title":"supabase note"}] [200]
cognito: sub a1b2c3d4-5678-90ab-cdef-111111111111 [{"owner":"a1b2c3d4-5678-90ab-cdef-111111111111","title":"cognito note"}] [200]
access: sub 3d9a0f0e-5c1b-4a3e-8f61-2b7d9c4e1a55 [{"owner":"3d9a0f0e-5c1b-4a3e-8f61-2b7d9c4e1a55","title":"access note"}] [200]

When the claims a provider offers do not fit, there is a last way round that needs nothing from it: the app verifies the provider's token with the provider's own SDK and signs one of its own, short, with the role and tenant the policy reads (examples/saas does that, with RS256 and its own keys file).

Rules that name a claim's value

A rule is a filter over a row, and a filter may hold a claim on its own side of a comparison. That reads what for <role> cannot, and it fails closed: a token without the claim does not meet the rule.

# Rules that name a claim's value, for what the policy cannot name as a role.
# (policy.txt's `for admin` reads the claim `role`; a claim the provider
# names `cognito:groups` or `https://example.test/role` has no name here.)

# Cloudflare Access signs every application of a team with the same keys, so
# a token for another application would verify: pin the audience, a list.
notes         read                        where owner = $jwt.sub and '32eafc7626e974616deaf0dc3ba5c0a0eb5f4d2d1e3b8f0a6c1a2e7d9a4b5c6d' in $jwt.aud

# Auth0's `permissions` is a list claim, which a rule can test.
notes         read                        where 'read:notes' in $jwt.permissions

# Whatever the provider sends: staff are rows, and a rule asks for them.
staff         read                        where user = $jwt.sub
notes         read                        where $jwt.sub in (get staff select user)

profiles      read(name)
audit         read,insert                 where actor = $jwt.sub
access token for this app, alice           [{"owner":"alice","title":"alice note"}] [200]
access token for another app, alice        [] [200]
auth0 token holding read:notes             [{"owner":"alice","title":"alice note"},{"owner":"bob","title":"bob note"}] [200]
auth0 token without it                     [] [200]
dana, a row of staff                       [{"owner":"alice","title":"alice note"},{"owner":"bob","title":"bob note"}] [200]
frank, not in staff                        [] [200]
  • Pin the audience. The first rule asks the token's aud to hold this application's tag, as Cloudflare asks any verifier to; a token for another application on the same team verifies and reads nothing. Without the pin the keys are the only thing that tells applications apart. The same works with Cognito's access token, whose claim is client_id: $jwt.client_id = 'app-1'. It must be in every rule that grants the token anything: a rule without it is a rule for tokens of any application.
  • A list claim is a test. 'read:notes' in $jwt.permissions is true or false for the whole token, and a rule holding it grants what it grants to the tokens for which it is true.
  • Admins are rows. The last rule asks a collection, and works with any provider because it asks nothing of the token but sub. staff read where user = $jwt.sub lets the inner get see the token's own row and no one else's; a rule's inner get reads what the token's own would (Rules that read another collection).

Expiry

A token is good until its exp and the server asks no one whether it was revoked. Keep tokens short, and for a person to turn away sooner, make it a row and let every rule that grants them anything ask for it:

# A token is good until its `exp`, and the server asks no one whether it was
# revoked. A person to turn away sooner is a row, and every rule that grants
# them anything asks for it: they read `banned` for their own row alone, so
# the rule sees whether it is there.
notes         read,write                  where owner = $jwt.sub and $jwt.sub not in (get banned select user)
banned        read                        where user = $jwt.sub
bob reads                                  [{"title":"bob note"}] [200]
bob reads, banned, the same token          [] [200]
bob writes, banned                         {"error":"the document is outside what this token may write to `notes`"} [403]
alice reads                                [{"title":"alice note"}] [200]
  • Short tokens are normal. A Clerk JWT template lives 60 seconds by default. FenecHttp holds the token it was made with, so an app that gets a fresh one per request makes a client per token (connect opens no connection), and one that keeps a client makes a new one when its provider refreshes.
  • A stream ends at its token's exp, with event: error and {"error":"the token has expired","status":401}: the client fetches a fresh token and opens the stream again. A member taken off a team stops hearing the team no later than that.
  • --jwt-max-age <s> refuses a token whose exp lies further ahead than that: set to 3600, a provider configured for day-long tokens is refused, and the fix is at the provider, where the lifetime is set.
  • The ban is read at every statement, so it takes hold on the next one, whatever the token's age. It is the same for a subscription: a scoped one is bound again when the collection its rules read is written.

One database a tenant

On a --dir node (Tenants and sharding) a token reaches /t/<tenant>/ only when its tenant claim names the tenant, as a text or a list holding it. The policy is the node's, not a tenant's: owner = $jwt.sub would match the same user in every tenant's file, so a token that names none is refused on such a node, unless it is started with --jwt-unbound-tenants. --jwt-tenant-claim <name> reads another claim than tenant: Auth0's org_id below, a claim you add to Clerk's session token or Cognito's.

-- the claim `tenant`, which Clerk's session token carries once customized
alice, token for acme, asks acme               [{"title":"acme note"}] [200]
alice, token for acme, asks globex             {"error":"this token is for another tenant"} [403]
a token naming no tenant, asks acme            {"error":"this token names no tenant, and this node serves tenants"} [403]
-- --jwt-tenant-claim org_id, which Auth0 puts in a token for an organization
alice, token for org_acme, asks org_acme       [{"title":"org_acme note"}] [200]
alice, token for org_acme, asks org_globex     {"error":"this token is for another tenant"} [403]
a token naming no tenant, asks org_acme        {"error":"this token names no tenant, and this node serves tenants"} [403]
  • The tenant check comes before the tenant is looked up, so a refused token learns nothing of which tenants exist. It holds on every route under the prefix, streams and /_changes among them.
  • A tenant is the unit of isolation; rows inside it are the policy's. A person in two organisations carries both in a list.

What a provider needs that the server lacks

A short list, so that none of it is found out in production:

  • Fetching a JWKS from a URL, and following its rotation by itself. The server reads a file; a cron job or a timer is the fetch (Keys).
  • ES256, EdDSA and the other signatures. Supabase's and others' EC keys are skipped. Choose RSA where the provider offers it.
  • Checking iss and aud. A rule can pin aud or client_id (Pin the audience); the issuer is the keys file's.
  • Claims by their provider's names (cognito:groups, namespaced URLs, nested objects). Add a plain claim at the provider, use a list claim, or keep the fact in a collection.
  • Revocation before exp, other than a row a rule asks (Expiry).
  • The token in a header other than Authorization (Cloudflare Access's Cf-Access-Jwt-Assertion, a cookie).
