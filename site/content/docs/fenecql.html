FenecQL

The query language you use to create collections, write documents and search them by vector, by text or by filter.

Statements

FenecQL is a small language with vectors in the core. It is not SQL and does not try to be, though the familiar select … from word order is accepted. These are all its statements.

create collection [if not exists] <name> ( <field> <type> [required] [collate und|tr] [@index], ... )
drop collection [if exists] <name>
create index [if not exists] on <name> (<field> | <path>) @index
alter collection <name> add field <field> <type> [collate und|tr] [@index]
alter collection <name> drop field <field>
alter collection <name> rename field <field> to <new name>
alter collection <name> alter field <field> @ttl(<duration>) | @sorted

put <name> { field: value, ... }              -- or [ {...}, {...} ]
insert [into] <name> { field: value, ... }     -- as put, refusing an id that is taken
put <name> { field: value, ... } if absent     -- a held id or @unique value passed over, and not counted
get <name> [select a, b] [where <expr>]
           [near <field> <vector> [ef N] [exact]]
           [match <field> <text>] [rerank <field> <vector> [candidates N]]
           [fuse [k N] [candidates N]]             -- match and near, both ranking
           [order <field> [collate und|tr] [asc|desc], ...] [limit N] [offset N]
           [facet <field> [top N | ranges [..]] [disjunctive], ...]   -- value counts over every matched row
           [lookup <name> on <child> [= <parent>] [required] <clauses...>]...
get <name> select a, highlight(f [, pre, post]), snippet(f, N [, ellipsis [, pre, post]])
           match <field> <text> ...           -- where the words matched
get <name> where <field> in (get <name> select <field> ...)  -- a subquery's list
get <name> [where <expr>] count               -- number of matching rows
get <name> select [<key>,] count(*), count(distinct e), sum(e), avg(e), min(e), max(e),
           first(e [by k]), last(e [by k]) [as <name>], ... [where <expr>]
           [group <key>, ... [order <column> [desc]] [limit N] [offset N]]
get <name> select a, <expr> as <name> ...     -- a column worked out over each row
explain get <name> ...                         -- the path the query took
select a, b from <name> [where ...]           -- the classic SQL order works too
set <name> { field: value, path: value } [where <expr>]  -- a value may read the row: {n: n + 1}
del <name> [where <expr>]
<put | insert | set | del ...> require N    -- refused, and its batch put back, unless it wrote N rows
get <name> ... require N [lookup ...]       -- refused, and its batch put back, unless it answered N rows

collections | describe <name> | compact [<name>]

-- a path, meta.source.rank, reads into a json field wherever a field is read
  • Every document gets an id on its own. Give one in a put and it writes over the document with that id.
  • insert never writes over. If an id is taken, the whole statement is refused; put … if absent passes over it instead, and the answer counts what was written.
  • A set can read the row it writes. set hits {n: n + 1} where key = "ip1" is an increment, made under the write lock — see Writes that read the row.
  • require N makes a count a condition. A write that does not write exactly N rows, or a get that does not answer exactly N, is refused, and the batch it is in is put back whole — see Writes that must find their rows.
  • alter collection rewrites no document. A field added reads null in the documents already there; a field's type does not change — see Changing a collection.
Details

The id field is automatic. Supplying id inside a put turns it into an upsert. insert makes documents and never writes over one: a document naming an id that is taken refuses the statement, and nothing of it is written — 409 over HTTP, as PostgreSQL's INSERT refuses a taken key. Without an id the two are the same. A retried write that must not be made twice either way sends an Idempotency-Key.

The vector clause

near finds the documents whose vector is closest to the one you pass. Add a where to search only the rows that match.

get articles near embed $1 limit 10
get articles where year >= 2024 near embed $1 ef 200 limit 10
get articles near embed $1 exact limit 10
  • ef trades speed for accuracy for one query.
  • exact checks every vector, which is how you measure recall.
  • Each row gets a _score column.
Details

ef raises the search beam for this query only, trading latency for recall. exact replaces the ANN walk with a full scan, which is how you verify recall against ground truth. A query that uses near gains a _score column. Over a sparse<N> field near ranks by dot product and is exact already, so it takes no ef — see Sparse vectors.

A filter next to near is planned, not stacked: the filter's rows are read only until it is clear whether there are more of them than the ANN would measure anyway, and the planner picks between searching that set exactly and running the ANN with each candidate tested against the filter. The mechanism, and the fallback that keeps it correct, is in How it works.

The text clause

match ranks documents by how well their text matches your words. rerank then reorders the best of them by vector distance.

get articles match body $1 limit 10
get articles where year >= 2024 match body $1 limit 10
get articles match body $1 rerank embed $2 candidates 500 limit 10
  • match needs a @text index and adds a _score column.
  • rerank needs no vector index. It reads the vectors of the matched rows directly.
  • Reranking cannot find what the words missed. For that, use hybrid search.
Details

match ranks by BM25 over a @text index and adds a _score column. Like near it decides the ordering, so it combines with neither order nor near — unless fuse says how the two rankings make one (below). A where filter is applied while the postings are merged, so it costs no second pass.

rerank reorders what match found by exact vector distance. It needs match — there is nothing to reorder without it — but it does not need an @hnsw index: the vectors are read straight out of the store, so this path builds, holds and validates no graph at all. candidates sets how many of the matched rows are rescored (default 200); it is never allowed below limit + offset.

The two stages answer different questions. match is recall and knows nothing about meaning; rerank is precision but only over what the first stage handed it. Measured on BEIR: on SciFact 50 candidates score nDCG@10 0.656 against 0.645 for a full dense scan of the same vectors, and on FiQA 1 000 candidates come within 0.0001 of the full scan — each while scoring under 2% of the corpus. If the lexical stage cannot find the answer at all, no amount of reranking will.

Hybrid search

fuse combines a text search and a vector search into one ranking. Use it when some answers share your words and others only your meaning.

get articles match body $1 near embed $2 fuse limit 10
get articles where year >= 2024 match body $1 near embed $2 fuse limit 10
get articles match body $1 near embed $2 fuse k 60 candidates 50 limit 10
  • It adds ranks, not scores, so there is no weight to tune.
  • It needs an @hnsw index for the vector side.
Details

fuse lets match and near rank the same query together. Each side takes its own first candidates — 20 unless given, never fewer than limit + offset — with the where filter applied to both, and a document scores 1 / (k + rank) from each list it is on, k being 60 unless given. The sum is the _score; ties go to the lower id.

Ranks rather than scores, because the two have no scale in common: a BM25 score grows with the length of the query and the rarity of its words, a cosine distance does neither, and a weighted sum would need its weight tuned again for every corpus. Where rerank can only reorder what the words found, fuse also takes what they missed — at the price of the @hnsw graph near walks.

Measured on BEIR, nDCG@10, all-MiniLM-L6-v2 vectors (the whole table). On SciFact, where a claim shares its words with the evidence, fuse scores 0.700 against 0.662 for match and 0.645 for near alone. On FiQA, where a question shares few words with its answer, it scores 0.366 against 0.232 and 0.366: the weak side does not drag the strong one down. Up to 61 candidates a side at k = 60, a document both searches found outranks every document only one found; deeper, agreement in the middle of both lists starts to outvote the top of one, and at 100 a side the two scores fall to 0.688 and 0.359.

Highlights and snippets

highlight() and snippet() in the select list show where the words of a match are in a row's text, so a results page can mark them.

get articles select title, highlight(body) match body $1 limit 10
get articles select title, highlight(body, "<mark>", "</mark>") match body $1 limit 10
get articles select title, snippet(body, 20, "…") match body $1 limit 10
get articles select title, snippet(body, 20, $2, $3, $4) match body $1 limit 10
  • Without tags you get positions: highlight(body) is a list of [start, end] pairs; snippet(body, 20) is {"text": …, "marks": [[start, end], …]}.
  • With tags you get the marked text, each mark between the two values you pass — literals or parameters. The engine adds no markup of its own and escapes nothing.
  • Offsets count UTF-16 code units, what a JavaScript, Java, Kotlin, C#, Dart or Swift NSString index counts: text.slice(start, end) is the marked word.
  • They need match, and go with fuse and rerank; a query without match has no words to mark, and is refused.
Details

A row's text is read again at query time by the tokenizer of the @text index the match searched — the same splitting, the same folding (İstanbul, ISTANBUL and istanbul are one word), the same prefixes and runs of characters — and every span a term of the query was read from is marked. So a mark is exactly what the index matched: a word; the whole word a prefix of @text(prefix=N) was cut from (kitapların for kitap); the characters of a pair or a triple of Han, kana, Hangul or Thai, overlapping pairs made one mark (東京都 for 東京都). Nothing is kept in the index for it, and the file does not change. Marks come in order and never overlap; a mark never ends inside a character, and takes the marks that belong to the characters at its ends — a combining accent, a Thai tone mark, the variation selector and keycap after a digit — so tagged text never splits a letter from its accent.

Any text field can be marked, read by the tokenizer of the field match searched: select highlight(title) beside match body $1 marks the title's words the query holds. Under fuse a row only near found holds no word of the query and has no marks; a null field is null. Each item answers under its label, highlight(body) or snippet(body), after the fields select names, where the list puts it — and after every field with select *, highlight(body). The same item twice is refused: the two columns would answer to one name.

A snippet is the window of N words holding the most marks, centred on the first and the last of them — the first N words when none is marked — each character of a run of Han, kana or Hangul counted a word. The ellipsis, when given, stands for what it leaves out at either end; a window holding the start or the end of the text has none there. Its marks count from the start of its text, the ellipsis included.

The text is not escaped. A page that puts a marked text into HTML lets the text's own < through. Build the page from the offsets instead — the text as text nodes, each mark a <mark> element — or escape the text first and the tags after.

Over 100 000 documents of 30 words, a mark costs a row about 1 to 3 µs (2 to 4 for a snippet) on top of the match; a query that asks none runs as it did, match 0.06 ms either way (make search-bench).

The lookup clause

lookup attaches matching documents from another collection to each row — reviews to their products, say. A limit after it counts children per parent.

get products limit 20 lookup reviews on product_id order created desc limit 3
  • Clauses after lookup apply to the child collection; clauses before it apply to the parent.
  • The child's key needs id or a @hash index.
  • required keeps only parents that have a match.
Details 
get products lookup reviews on product_id
get products limit 20 lookup reviews on product_id order created desc limit 3
get products where price >= 10000 select name
  lookup reviews on product_id select body where stars >= 4 limit 3
get products lookup tags on sku = sku

lookup attaches the matching documents of another collection to the row they belong to. on names the child's field; the parent's key is id unless = <parent> says otherwise, which is the foreign-key-to-primary-key case spelled out.

It is terminal: everything before it binds to the driving collection, everything after it to the looked-up one. That is the whole scoping rule, and it is why there are no qualified names in the language — where on either side means what it has always meant. The price is that a parent clause cannot follow a child one, which reads the way the query runs anyway.

get shops limit 20
  lookup orders on shop_id limit 3
  lookup lines on order_id limit 5

A second lookup chains onto the first: its clauses bind to its collection, and on <child> = <parent> names a field of the level immediately above. Position keeps scoping the query one level deeper, so exactly one collection is in scope at any point and it is the last one named — which is what keeps qualified names out of the language at any depth. Up to 8 levels; deeper is an error, not a silent truncation.

limit after lookup counts children per parent. This is the clause's reason to exist. A join's limit counts pairs, so a single product with 56 374 reviews consumes the whole page and the other nineteen never appear; asking a join for three reviews each needs a window function. Here twenty products with three reviews apiece is one query with a bounded answer.

The child key must be id or carry @hash. Refusing an unindexed one is the same rule near and match follow: the clause is one bucket probe per parent, and quietly becoming a full scan of the child collection instead — 12.98 ms against 0.092 ms on the same 200 000 rows — is not a thing a query should do without saying so.

get products limit 20 lookup reviews on product_id required where stars = 5
get products count lookup reviews on product_id required where stars = 5

required drops a parent that no child matches — "products that have a five-star review" rather than "products, with their five-star reviews". It is tested before offset and limit, so a page of twenty comes back with twenty parents that have children rather than whatever survived; a child offset that walks past every match does not undo it, because the parent has matches all the same. It is the one shape where count combines with lookup: nothing is being attached, so counting the parents that have a match is a question with an answer.

required is a pass, and it is not cheap. It is answered from whichever side is smaller: walking the candidate parents and probing each, or — when the child filter carries a @hash equality and the parent's key is id — reading the children that equality names and taking their parents. Both counts that decide are exact, so the choice is not a guess; what neither plan escapes is that one full pass has to happen. Over 20 000 products and 200 000 reviews, for a page of twenty:

required, child filter on a @hash field12.07 ms
the same, walking the parents instead15.63 ms
required, no child filter2.19 ms
count … required4.50 ms
a bool @hash field on the parent0.02 ms

Ask it occasionally and required is the right tool. Ask it on every page load and the answer belongs in a field on the parent, maintained on write — which is the same trade the rest of this database makes.

In a chain, required is a statement about its own level: it drops rows of the level immediately above it and stops there. Requiring lines drops the orders that have none; the shops keep their rows, with an empty group, unless the orders level says required as well. Said at every level it composes into "shops with an order that has a line", and the existence check walks the whole way down — a row is only kept if it has a descendant that is itself kept. Nothing acts at a distance, and the flag means the same thing wherever it is written.

lookup combines with neither near, match nor rerank: each ranks one collection's documents, and a score spanning a parent and its children has no defensible meaning. count is refused as well unless the clause is required, since otherwise it collapses the very rows the children would hang from.

order inside a lookup is bounded in advance: the clause carries its own limit, so only offset + limit children can ever be emitted and the rest are never put in order. On a parent with 56 374 children, order created desc limit 3 costs 3.71 ms rather than 7.52 ms. What remains is reading one key per child, which no ordering can avoid — you cannot know the first three without having seen all of them. The query's own order works the same way.

Over JSON the children are nested under the collection's name, and a chain nests all the way down. Flattened into rows, for a caller that wants a table, they arrive the way a join presents them — the same data; a chain widens once per level, one row per root-to-leaf path, and a level that ran out fills its own columns and every column below it with nulls. A parent with no matches keeps its row either way: the page is the parents. What the flat shape cannot show is the per-level limit, which is exactly why the nesting is what the other transports carry.

What it buys, measured (5 000 products, 100 007 reviews, twenty parents with three children each): the clause is 22.7 µs in process and 0.188 ms over HTTP, against 0.332 ms for the same work as a /batch of twenty-one queries merged on the client.

The larger gain is that there is one way to write it. The same question in SQLite, over the same data: a correlated subquery takes 0.053 ms, a window function with the restriction pushed inside the partition 0.331 ms, and the same window function with the restriction left outside 81.34 ms — a factor of 1 500 between three spellings of one question, with nothing in the query text to tell them apart.

A second level is where batching stops being an answer. One level of N+1 fits in a single round trip, because every query in it can be written from the page's ids; the level below cannot, because its keys are in rows that have not come back yet — so the client pays two round trips whatever it does. Over 2 000 shops, 20 000 orders and 200 000 lines, for a page of 20 × 3 × 5: 49.1 µs in process against 139.8 µs for the same page as 81 separate queries, and 0.204 ms for the one HTTP request against 0.415 ms for two /batch trips — measured on loopback, where the extra trip costs almost nothing and still doubles it.

Subqueries

in (get …) filters by rows of another collection: the reverse of lookup. The inner get runs once, before the query, and the one column it selects is the list.

get orders where customer in (get customers select id where country = "TR")
  • It answers as its list written out. One bucket per value over a @hash field or id, a scan otherwise — the in [..] you would have written.
  • The inner get selects exactly one column. A field, or one aggregate; no lookup and no count.
  • It goes wherever a filter goes: get, count, aggregates, a near's or a match's filter, a lookup level's, set … where and del … where.
  • At most 100 000 distinct values and 4 levels of nesting; past either the query is an error, never a set cut short. A value held by many rows counts once.
Details 
get orders where status = "open" and customer in (get customers select id where tier >= $1)
get orders where not customer in (get customers select id where country = "TR") count
del sessions where user in (get users select name where banned = true)
get customers limit 20 lookup orders on customer
  where id in (get returns select order_id) limit 3
get orders where customer in (get customers select id
  where tier in (get tiers select n where active = true))

It is uncorrelated: the inner get reads nothing of the row being tested, so it runs once, with the same parameters as the query around it — $1 inside is the query's $1. Its column is a field, or one aggregate (get orders select max(total)); a null in it is left out of the list, since it would otherwise find the rows whose field is null, and not … in would lose every row. not is FenecQL's own not, written before: not customer in (get …); customer not in is not FenecQL.

The values become the list an in [..] is answered with, and the same rule holds: a list reaches the @hash index only when every value is one the field's type can express, or the whole list goes to the scan. A long list is looked up rather than walked — a scan of 200 000 rows by an unindexed field against the 2 000 codes an inner get handed it took 2 302 ms compared a value at a time and takes 16. The bound is on the values the list holds, not on the rows that hold them: a funnel's 125 000 buy events from 937 users is a list of 937. Past 100 000 rows the values are told apart, and the inner get read until they number more than 100 000; with a limit, group or ranking it is read one row past the bound, and a limit inside is the query's own cut, and answers. explain names what each inner get found.

Over HTTP a scoped token's rules hold the inner get as they hold any get: the list holds only rows the token may read, so nothing of the others reaches it through what the outer query finds. A token's rule itself takes no subquery. The JavaScript builder takes a query as an in's value: { customer: { in: db.from('customers').select('id').where({ country: 'TR' }) } }. A subscription's shape takes a list only — its stream follows its own collection's writes, and an inner set would not follow the other's.

What it costs, measured (make subquery-bench, 20 000 customers and 200 000 orders, the median of 21). The orders of one country's 2 000 customers by the @hash on customer: 0.83 ms, against 0.72 ms with the 2 000 ids written out; by an unindexed code, 16.1 ms against 15.9. The customers with a rare order — the inner get reading a bucket — 0.20 ms against 0.065 written out and 0.44 for lookup orders on customer required where status = "rare", the same question asked from the other side; with a filter on the customers as well, 0.56 against lookup's 0.95. Where the inner get scans 200 000 orders it is that scan, 10.4 ms, and lookup … required probes each customer's orders instead, 32.5. The difference to the list written out is the inner get: a subquery is one round trip where the list is two.

Indexes

An index makes one kind of question fast. Declare it on a field when you create the collection, or add it later with create index.

create collection articles (
  title      text,
  body       text @text(k1=0.9, b=0.4, prefix=0),
  year       int @hash,
  slug       text @unique,
  published  timestamp @sorted,
  embed      vector<768> @hnsw(cosine, m=16, ef_construction=200)
)
  • One index per field: @hash for equality, @sorted for ranges and order, @text for ranked text search, @hnsw for nearest neighbours. A path into a json field takes @hash, @unique or @sorted of its own (Objects and paths).
  • @unique is a @hash that refuses a second document holding a value one holds already. null is no value: any number of documents may hold it.
  • Only filters joined by and use an index. Anything under or, and !=, ~ or has, reads every row.
  • For Turkish, Chinese or Japanese text, see prefix and chars below.
Details 
create index on articles (embed) @hnsw(cosine)
create index on articles (body) @text
create index on articles (body) @text(prefix=6)   -- for an inflected language
create index on products (title) @text(chars)     -- short Chinese or Japanese text
create index on articles (title) @sorted
create index on users (email) @unique             -- refused if a value is held twice

A field takes one index. @hash answers equality, @sorted ranges and order, @text ranked text retrieval, @hnsw nearest neighbours. @sorted is for int, float, timestamp and text — the types with an order.

@unique is a @hash index that refuses a second document holding a value one holds already: a put, an insert or a set that would write one is refused, and nothing of the statement is written — 409 over HTTP, as a taken id is. It answers equality and a lookup as @hash does. A block — a /batch, a run of several — is checked against its own earlier writes, so it may free a value and take it again, and a document keeping its own value is no second one. null is no value, as in SQL: any number of documents hold it. Values are one where = finds them one, so -0.0 and 0.0 collide. create index ... @unique over documents that hold a value twice is refused and names the value and two of its documents. A replica takes what its primary took and does not ask again; describe shows the index as @unique. The refusal names the document holding the value and the value, but to a scoped token it names the field alone (`users.email` is unique, and the value is taken): the row is another user's, which the token may not read.

The check asks the bucket the value would go in, so the index has to hold every document: the first write after an open builds it, where a plain @hash waits for the first read that wants it. An open costs what it did — 19 ms for an image of a million rows either way — and that first write takes 15 ms over 100 000 rows and 259 ms over a million; after it a put takes 940 ns against 850 for the same field under @hash, the price of the lookup. A collection with no unique field writes as fast as before (848 and 852 ns).

An @hnsw graph holds a vector once. Documents written with the same vector — the embedding of an empty chunk, a line of boilerplate, a zero vector — share its node, and near hands back each of them at the one distance. A node each, a vector written hundreds of times filled its neighbours' lists with copies of itself: over 20 000 rows of 128 dimensions, a third of them copies of 20 vectors, 1 812 copies were found by no search and other queries' recall fell from 0.82 to 0.67; one node each, none is missed and it is 0.87.

prefix=N indexes each word's prefixes alongside it (3..N by default; prefix_min moves the lower bound). It is a stemmer that needs no dictionary and no language setting, and it is off unless asked for because it is a trade the corpus decides. Word-boundary matching suits English; it does not suit a language that inflects by gluing suffixes on, where kitap, kitabı and kitapların are three terms sharing a stem the index never sees.

Measured on Turkish WebFAQ (144 846 documents, 10 000 queries): nDCG@10 0.4841 → 0.5547, +14.6%, closing about two fifths of the gap to a 278M-parameter multilingual transformer (0.650). The cost is the 3.4× postings it indexes — 58 MB → 182 MB, and 82 → 485 µs per query. On English SciFact the same option is worth +0.0137.

A script written without spaces is indexed in runs of characters. Chinese, Japanese and Thai run their words together, and Korean hangs its particles on them, so a word is not a term there: a run of Han, kana or Hangul is indexed as its overlapping pairs of characters — 東京都に is 東京, 京都, 都に — and one of Thai, Lao, Khmer or Myanmar, whose characters are letters, as its triples. A query is split the same way, so match body "東京" finds the run it is written in. There is no dictionary and no language setting; a script that spaces its words keeps its words.

chars indexes each character of Han, kana and Hangul as well, so a query of one character finds every run holding it, which pairs alone do only for a run of one. It pays on short text and costs on long: product titles gain a fifth, news and questions lose a little, and the index holds 1.6 to 1.9× the postings for a query 3 to 8× slower. Off unless asked for.

The same pipeline as BEIR (make beir over each set in its layout); English SciFact scores what it did, to the fourth decimal. A query over those sets takes 0.09 to 0.66 ms at the median.

A filter reaches an index only inside an and chain. Equality — = and in [..] — reaches a @hash field; in is a set of equalities written short, so it is answered as the union of one bucket per element. Either reaches id, which the store's own id index answers without a @hash being declared or possible. Comparisons — <, <=, >, >= and = — reach a @sorted field, which narrows them to a range of keys.

Everything else — !=, ~, has, comparisons on a field without @sorted, and anything under an or — is a full scan: each matching row is decoded and evaluated. ~ in particular is substring matching without ranking and reaches no index; ranked retrieval is match over a @text field.

A full scan reads rows in id order, and starts at the lowest id an id > x or id >= x in the and chain lets through, so a page read after the last id of the one before — where id > $1 limit 1000 — reads only its own rows: a million rows read that way a page at a time took 8.6 s and take 110 ms. The browser module leaves this out.

Changing a collection

A collection takes a field, lets one go, or renames one, and none of it rewrites a document: it is as quick over a million documents as over none.

alter collection orders add field note text
alter collection orders add field code text @unique
alter collection orders drop field note
alter collection orders rename field total to amount
  • A field added reads null in every document written before it, and cannot be required.
  • A field dropped is gone from every read and write, and its index with it. compact gives its space back.
  • A type does not change in place. Add a field of the new type, set it from the old one, and drop the old one.
Details

A document is its values one after another in field order, so what a change costs is what it does to that order. A field added goes last: a document written before it ends before the field's place, and reads null there. A rename is the schema alone. A field dropped leaves its place in the documents written before the drop — skipped on read, written as null after it, refused by name everywhere — and compact writes every document without it, copying each other value as its bytes stand. A field added under a dropped one's name is a new field: the old values stay in the dropped place, and the new field reads null until it is written. A change of type is the one thing that would rewrite every document under the write lock, and is not done.

Each is a write as a create index is: one of a block, put back by its ROLLBACK with the writes after it, seen by a subscriber as a schema change, applied by a replica, carried by the change stream (op: "alter", the documents after it read by the schema it made). In the file it is record kind 12, and a dropped place a nameless field of type tag 12, both of which a binary from before them refuses rather than read the fields after a dropped one a place early. The index of a field added is built over the documents there, every one of them null; a dropped field's goes, and a renamed one's goes with the name, a vector field's graph included.

Measured over a million rows in memory: an add, a rename and a drop take 0.025, 0.021 and 0.004 ms. Reading a field past where a document ends costs nothing a scan can measure: five scans of the million took 21.2 to 39.1 ms before the feature and 21.6 to 39.3 after, from 1.7% slower to 1.7% faster by the scan — as the same build with the reads written as before was, which makes it where the code lands, not what it does — and the browser module's scan of 20 000 rows 1.70 ms against 1.71. A compact that takes a dropped field out took 95 ms against 56 for one with none to take: it writes each document again rather than copy it. On a server it holds the write lock, where a compact otherwise runs beside the database.

Objects and paths

A json field holds any value JSON does — an object, a list, a number, text, true, false or null — with no type declared for what is inside. A path reads into it wherever a field is read.

create collection docs (title text, meta json)
put docs {title: "a", meta: {lang: "tr", source: {site: "x", rank: 3}}}

get docs where meta.lang = "tr" and meta.source.rank >= 2
get docs select title, meta.source.site order meta.source.rank desc
set docs {meta.lang: "en"} where title = "a"

create index on docs (meta.lang) @hash
create index on docs (meta.source.rank) @sorted
  • A path that leads nowhere is null: a key a document does not have, or a value on the way that is not an object.
  • A path takes @hash, @unique and @sorted, and they answer what the scan would, row for row.
  • set with a path changes one key and keeps the rest of the object; it makes the object where there is none.
  • Typed fields are unchanged. An int or a text field still refuses an object.
Details

An object's keys are kept sorted and unique: a key given twice — in FenecQL, in a JSON body, in a parameter — refuses the write rather than keep one of them, since which one a reader keeps differs from reader to reader. Its numbers are kept as written, an integer an integer and 19.99 the decimal it is, everywhere one comes in: FenecQL, a parameter over HTTP and in the browser, a JSON body, a row fenec import reads. A list of numbers alone is read the quick way, into the f32s of the vector it nearly always is; where it is given a json field, or compared with a path into one, the statement's text or the parameter's JSON is read again as written, so [0.1, 12345678901] is kept as those two numbers. A vector that was never text — a Float32Array handed to the browser module, a vector built through the Rust API — is refused there rather than kept as numbers it was not given. A timestamp becomes its ISO text, as JSON writes one; bytes, a sparse vector and a number that is not finite have no JSON and are refused. A value nests at most 64 levels, and a path names at most 64 keys past its field: past either a write or a query is refused, never cut.

A path is a field's name, a dot, and keys, each a name as a field's is (meta.source.rank); a key with a space or a dash in it cannot be named, and is reached by reading the whole field. It works in every comparison, in, has, ~ and is null, in select — answering under the path's text as its column's name — in order, and in set and put, which set the one key inside the field. A filter binds a path once a query, as it binds a field, and walks its keys over each row's bytes, passing the members before the key without decoding them. An aggregate and group read a field, not a path; a lookup's keys are fields too. Comparisons are the ones every value already has: 3 equals 3.0, every number orders below every text, text below a list and a list below an object, and null is equal only to null.

An index on a path is a field of its own beside the fields, named by the path, and its kind is the field's: @hash keys a value as a typed field's does, a whole float filed as the int it equals so that 3 and 3.0 share a bucket; an equality or an in reaches it with null, a boolean, text and a number an f64 holds exactly, and anything else — an int past 253, which equals floats near it that no bucket holds — is answered by the scan. @unique refuses a value held twice as a field's does, 3 and 3.0 the same value. @sorted orders the numbers as f64s and the text by its bytes, every number before every text; a value it has no place for — true or false, a list, an object, an int past 253 — is held apart, and while the index holds one it answers nothing and the scan does: a wrong order is never what an index costs. tests/json.rs holds both to a twin collection without them, every filter, order and page, through writes and a reopen. Text, vector and sparse indexes stay on the fields that declare their type. On a server an index on a path is built under the write lock, as it reads one value a row: 11 ms for @hash and 21 for @sorted over 100 000 documents.

Renaming a json field renames the paths into it, indexes and all, and dropping it drops them. In the file a json field is type tag 14 and an object value tag 13 — not 11 or 12, which a schema writes for a collation and a dropped place — and each index on a path is written inside its field's entry, its keys and its kind: a binary from before them refuses the file (unknown type tag 14) rather than read it. The indexes are derived, as every hash and ordered index is: rebuilt from the documents by the first read after an open.

Measured over 100 000 documents of a title, a year, a price and a meta object of three keys: where meta.lang = "tr" scans in 5.7 ms where the same comparison of a text field takes 4.2; meta.source.rank >= 990 in 7.2; both together in 10.4; the first 20 by meta.source.rank in 7.3. With @hash and @sorted on the two paths: 0.025, 0.009, 0.12 and 0.010 ms. A scan of a collection with no json field takes what it took before them (3.47 against 3.38 ms by two numbers, 4.17 against 4.21 by a text, 3.06 against 3.08 by ~, 2.72 against 2.60 for an ordered page), and the browser module's filter 1.67 against 1.66.

Quantized vector indexes

quant= makes a vector index smaller by storing a compact code for each vector. Scores stay exact, because the final order uses the full vectors.

create collection articles (embed vector<768> @hnsw(cosine, quant=int8))
create index on articles (embed) @hnsw(cosine, quant=bit)
  • int8 is a quarter of the size; bit about a thirtieth, and cosine only.
Details

quant= sets what the index holds of each vector: int8 a byte a component, a quarter of f32, and bit a bit a component, about a thirtieth: the signs of how far the vector lies from the nearest of 128 centres the index learns from its first 2 048 vectors, which it holds whole until then — cosine only, since the vectors are taken at unit length. The documents keep their vectors whole. The codes find the candidates, the beam's ef of them, and the documents' own vectors put those in order, so _score is the exact distance. An int8 code knows how far off it can be, so a candidate is read only while it can still make the page; a bit code does not, and the whole beam is read. A filtered set small enough to search without the walk is ranked by its codes the same way, and exact reads every vector. Bit codes take a wider beam: ef_search is 200 there unless it is named. What they save and what they cost is in How it works.

Sparse vectors

sparse<N> stores the output of a learned sparse model such as SPLADE. near over it finds the documents with the largest dot product, exactly.

create collection passages (body text @text, splade sparse<30522> @inverted)
put passages {body: "...", splade: "{1037:0.84,2003:1.27,7592:2.1}/30522"}
get passages near splade $1 limit 10
get passages match body $1 near splade $2 fuse limit 10
  • It is written as pgvector's sparsevec: {index:value,...}/N, indices from 1.
  • Index it with @inverted.
Details

sparse<N> holds a vector of N dimensions by its non-zero entries alone: what a learned sparse model such as SPLADE gives a text, a weight for a few dozen or hundred of its vocabulary's 30 522 words. It is written and read in pgvector's sparsevec text form, {index:value,...}/N with the indices counted from 1, as a string in JSON and in FenecQL; entries come back in index order and zeros are dropped. @inverted indexes it as a word index is indexed, dimension by dimension, and near over it returns the documents with the largest dot product — the exact ones, walked with the pruning match uses — and ranks only documents sharing at least one dimension with the query. A filter is tested as the lists are merged; exact scores every document instead, and fuse takes a sparse near as it takes a dense one.

Ordered indexes

@sorted makes ranges, counts over a range and order … limit fast. It always gives the same rows as reading every row would.

get articles order published desc limit 20
get articles where published >= "2026-09-01" order published desc limit 20
  • It costs memory and write time: about 20 bytes a row for a number, plus the text for text.
  • It is rebuilt after an open by the first query that needs it; it is never written to the file.
Details 
get articles where title >= "k" and title < "l" count
get articles where published >= "2026-01-01" near embed $1 limit 10

order over a @sorted field with a limit walks the index in order and stops at the page, testing the rest of the filter on each row it passes; without one, every match's key is read and only offset + limit of them are put in order. A filter that matches too little to fill the page within an eighth of the collection sends the walk back to the scan: over a million rows one matching nothing cost 152 ms against the scan's 121, while one matching 1% fills the page in 0.29 ms against 125. A range on a @sorted field is read from the index as a set of ids — for a filter, a count, or the allowed set of a filtered near.

Rows that expire

@ttl on a timestamp field makes a row expire that long after its value — for sessions, caches and anything else kept for a while.

create collection sessions (user text @hash, seen timestamp @ttl(30m))
  • Reads are exact at once. A row past its time is never returned, even before it is deleted: every read of the collection leaves it out.
  • The server deletes it. A primary sweeps once a minute, as ordinary deletes that replicas, /_changes, archives and subscriptions see as any.
  • Durations are whole ms, s, m, h or d: @ttl(45s), @ttl(12h), @ttl(7d).
Details 
put sessions {user: "ada", seen: now()}
set sessions {seen: now()} where user = "ada"        -- seen again: lives on
get sessions where user = "ada"                       -- nothing once 30 minutes pass
create index on events (at) @ttl(7d)                  -- an existing timestamp field
alter collection sessions alter field seen @ttl(1h)   -- another expiry
alter collection sessions alter field seen @sorted    -- none: the rows live

A read of the collection — get, count, an aggregate, near, match, a lookup level, an inner get, a set or del by filter, and a subscription's shape — has not (seen <= now - ttl) added to its filter, the way a token's rule is added: a row is gone at the moment its time plus the ttl is reached. A row whose field is null has no time to expire from, and lives. In the browser the module has no clock: now is the page's, Date.now() unless db.now is set, as every time is handed to it; the page deletes nothing, and a row past its time stays in its file, out of every read. A live query in the page is woken by writes, not by time passing.

@ttl is an ordered index whose rows expire, so the field also does everything @sorted does, and a collection's rows expire by one such field. The sweeper deletes a range of it at a time rather than scan for the rows past their time: found under the read lock, deleted under the write lock 1 000 at a time, each batch a block of ordinary deletes, its fsync run once the lock is let go. A replica never sweeps — its writes are its primary's, the sweep's among them — and neither does a tenant that follows another node. The server's Idempotency-Keys are kept this way.

The ttl is a kind of index in the file (kind 9, the milliseconds behind it), so a binary from before it refuses the file rather than hand out the rows past their time. A write takes the place of a row past its time: an insert naming its id writes over it, and a @unique value it holds is let go of with it, the row deleted in the same statement — so a lock taken by insert and left to expire can be taken again at once (Instead of Redis). BM25's statistics count the row until the sweep.

What it costs, measured (make ttl-bench, a million rows, half past their time). A read tests each row's time as part of its filter, as the same test written by hand does: count becomes a scan, 68.8 ms against 1.1 with no expiry, and a filter that scanned already reads one field more, where s = "w7" count 68.5 ms against 51.9 — 70.1 with the test written out. A collection with no @ttl reads as it did. The sweep of 100 000 rows past their time out of a file of 200 000 took 0.56 s in batches of 1 000, each holding the write lock 1.06 ms at the median and 2.3 at most.

Details

Text is ordered by its bytes unless a key says otherwise, and the bytes are wrong in every language: every capitalised word comes before every lowercase one, an accented letter lands after z, and every script past ASCII falls where its code points do. collate und orders the key as Unicode's root collation does — CLDR's, which PostgreSQL calls und-x-icu — the order every language's starts from: each script in a run of its own, its letters in their order, accents and case deciding only between words whose letters are the same. A language whose letters sort otherwise is a tailoring over it, and collate tr is Turkish, PostgreSQL's tr-x-icu: ç after c, ğ after g, ı before i with I as its capital and İ as the capital of i, ö, ş and ü after o, s and u.

It compares a level at a time over the whole string, as ICU does: the letters, then their accents (kar < kâr < kara), then their case (ince < İnce), so an accent or a capital only decides between strings whose letters are the same. What all three leave equal goes by its bytes, as under a deterministic PostgreSQL collation — the order is total, and a page never changes with the plan. It applies wherever order does: the query's rows, a lookup's children, an aggregate's groups by their key or a min or max of text. A key that holds no text — a number, id, count(*) — refuses it rather than ignore it.

A field can be declared in a collation, name text collate und, and its text is in it wherever it compares: order without naming one, <, <=, > and >= in where, min and max, and a @sorted index over it, which holds that order and is walked for it. So a listing pages by the last name it showed — where name > $last order name limit 20 — and the index answers as the scan does, row for row. Equality stays the bytes', since the collation ties no two different strings. The collation is the field's: it is written with the schema into the file, and describe shows it. A @sorted field without one keeps its bytes' order, so a key collated in the query is sorted rather than walked, and a comparison in where compares bytes.

Columns worked out

An item of the select list can be an expression over the row: its fields and paths, parameters and functions, with + - * /. It answers under the name as gives it; a field can be named again the same way.

get ticks select sym, px * qty as notional where qty > 100
get ticks select px as price, bucket(at, 1m) as minute, greatest(px, $1) as floor
get orders select id, case when total >= 100 then "large" else "small" end as size
Details

The types are a set's (Writes that read the row): two ints make an int, and one past 64 bits is refused, never wrapped; a null is null. An expression is bound to the collection once a query — each field it reads by its place, every field the list reads decoded in one pass a row — and its error comes at the first row it fails on. An item that is neither a field nor an aggregate of one has no name of its own: select px * qty is refused, and asks for as.

Aggregates

Put count(*), count(distinct …), sum, avg, min, max, first or last in the select list to get totals. Add group for one row per distinct set of its keys' values.

get orders select count(*), sum(total), avg(total), min(at), max(at)
get orders select status, count(*), avg(total) where year = 2026 group status
get orders select customer, sum(total) group customer order sum(total) desc limit 10
get events select bucket(at, 1h) as hour, name, count(distinct user) as users group hour, name
get ticks select bucket(at, 1m) as bar, first(px by at) as open, max(px) as high, min(px) as low,
  last(px by at) as close, sum(qty) as volume where sym = $1 group bar
get ticks select sym, sum(px * qty) / sum(qty) as vwap group sym
get events select props.plan, sum(props.v) group props.plan
  • Nulls are skipped, as in SQL, by everything but count(*).
  • An aggregate folds any expression — sum(px * qty) — and an item can be an expression over aggregates and keys — sum(px * qty) / sum(qty).
  • Groups can be ordered and paged by any column of the list.
  • Aggregates do not combine with near, match or lookup.
Details

A select list with an aggregate in it folds the rows the query finds — through the same indexes any where reaches — into one row, or, with group, one row per distinct set of the keys' values. Each column answers under its name, in the order the list is written: the name as gives it, or for a field or an aggregate of one the text it was written as — sum(total), count(distinct user), first(px) (its by left out). Anything else needs as.

  • Keys. group takes one key or several, each a field, a path, or an expression — group sym, bucket(at, 1m). A name the list gives an item with as stands for that item, before a field of the same name: select bucket(at, 1h) as hour, count(*) group hour. A plain item of the list is a key itself, or is refused as neither aggregated nor grouped by; an expression written out again in group is not matched to the list's — name it once, with as.
  • count(*) counts rows. count(distinct e) counts the values e takes, a null none, two values the same when their encodings are — as group tells its keys apart. It is exact: every value is held once a group, up to a million over every group and item of the query — about 70 MB — and a query past that is refused, never counted short.
  • sum and avg take numbers: an int sum is an int, and one past 64 bits is an error rather than a wrapped number; a float among the values makes the sum a float, and an average is one. min and max take any value with an order — numbers, timestamp, text, bool — a text field's in its collation. A field whose type cannot be folded is refused before any row is read, an expression's value at the first row that cannot.
  • first(e by k) and last(e by k) are the value of e on the group's row least, or greatest, by k — a bar's open and close are first(px by at) and last(px by at), whatever order the ticks were written in. A tie on k goes to the row written first for first and last for last; without by, the order is the one the rows were written in. A row whose value or key is null is passed over, as every aggregate passes a null over. The query's order orders the groups, not the rows inside them, so it says nothing to these.
  • Nulls are skipped, as SQL skips them, by everything but count(*). Over no rows — or only nulls — a sum, an average, a minimum and a maximum are null, not 0.
  • Groups come out by their keys, in the order group names them, the null key first, unless order names a column of the list — order sum(total) desc, order vwap — and limit and offset page them. A whole-set aggregate is one row, which order and limit have nothing to do with; they are refused there.
  • What does not combine is what does not combine with count: near, match and lookup rank or attach rows that an aggregate collapses.

How it runs. Every item is bound to the collection once a query: each field and path the list reads is decoded in one pass a row, a field folded as it is is read with nothing copied, and a bucket over a constant interval works the interval out once. Rows written in time order come a bucket at a time, so the group the row before went to is asked first. A count(*) by bucket of a timestamp or int field with an ordered index (@sorted, @ttl), whose filter is a range of that field and nothing more, reads the index's keys and no row; explain says so.

A million rows in 100 groups, select cat, count(*), avg(price) group cat, took 80 ms in process where PostgreSQL 17 — one worker, as make pgvector-up runs it — took 189 ms of execution time on the same rows; the whole set's count, sum, minimum and maximum, 37 ms; the same groups over the tenth a @sorted range found, 9.3 ms. The rows are read, not an index: a filter narrows them, nothing precomputes the totals. The questions analytics and market data ask — bars, VWAP, distinct users, counts by the minute — are on Analytics and market data, each with what it costs over a million rows.

Functions over a row

Functions work wherever an expression goes: where, a set's values, a select list's items and a group's keys.

get events select bucket(at, 15m) as q, count(*) group q
get events where bucket(at, 1d) = "2026-05-03" count
set bars {high: greatest(high, $1), low: least(low, $1)} where key = $2
get orders select id, case when total is null then 0 when total < 0 then -1 else 1 end as sign
  • bucket(ts, interval) is the start of the interval a timestamp falls in, in UTC: ms, s, m, h and d count from the epoch, w from a Monday as ISO's weeks begin, and mo and y by the calendar — bucket(at, 3mo) is a quarter. The interval is written as a duration, 15m, or passed as a parameter holding one as text or a number of milliseconds. An int of epoch milliseconds gives an int.
  • greatest(a, b, …) and least(a, b, …) are the largest and smallest of their values, as PostgreSQL's are: a null is passed over, and the answer is null only when every value is.
  • case when c then v … else e end is the value of the first condition that holds, or the else, or null. Only the branch taken is worked out: case when qty = 0 then null else px / qty end divides only where it may.

Facets

facet counts the values of a field over every row the query matches — not only the page — for a filter sidebar: how many results each brand, color or tag has.

get products where price < 500 facet brand, color limit 20
get products match title $1 where price < 500 facet brand top 10, tags limit 20
get products where category = "phones" count facet brand
get products facet meta.origin top 5 limit 0

{"rows": [ ... ],
 "facets": {"brand": [{"value": "acme", "count": 12}, {"value": "nova", "count": 7}],
            "color": [{"value": "red", "count": 9}, {"value": null, "count": 2}]}}
  • Most first, ties by value; top N keeps the commonest N.
  • A list counts each value it holds: a row tagged ["sale", "new"] counts once under each.
  • null is a value, so a field's counts add up to the rows.
  • They come back beside the rows, never in one: the answer is {"rows": [...], "facets": {...}} when a query asks for facets, and the bare list of rows when it does not.
Details

The rows counted are the rows the query selects before offset and limit: those the where keeps, and with match, those holding a word of the query (rerank reorders them and counts the same). A lookup ... required decides who is counted, as it decides who is on the page; with count the facets go beside the number. near ranks every row the filter passes rather than selecting some, so counts beside it would be the filter's alone whatever the vector: a facet with near or fuse is refused. Ask them without near, in the same /batch.

A field is a field or a path into a json one. The counts are group ... count's over the same filter, value for value (tests/facets.rs holds them to it), but for a list, counted a value at a time, and a path, which group does not read. A @hash field of text, int, bool or timestamp is counted from its buckets — over every row a bucket's length, under a filter how many of a bucket's rows the set holds — and anything else reads the field of every matched row. Without top a facet answers every value it found, and one holding more than 10 000 is refused rather than cut: a list cut where it happened to stop is a wrong answer believed right.

Over 100 000 rows (make search-bench): a @hash field over every row 0.01 ms, read from every row 6.1 ms (a list of tags 17); under a filter keeping half, 5.8 and 9.3 ms against the filter's own 5.9 ms for a count. Beside a match reaching about 16 667 rows, two facets took a query from 0.06 to 1.6 ms.

Counted without its own filter

With a brand chosen, a sidebar's "Brand" should still list the other brands to add, each with the count it would have. disjunctive counts a facet over the rows the query selects with the filter's own conditions on that field left out; the page, and every other facet, stay the query's.

get products where category = "tents" and brand in ["acme", "nova"] and color = "red"
  facet brand disjunctive, color disjunctive, material
  order price limit 24

Here brand counts over the red tents of every brand, color over the acme and nova tents of every colour, and material over the page's rows. A condition left out is a term of the where's and chain that reads the field alone — brand = ..., brand in [...], (brand = "a" or brand = "b"), a range — and one reading the field beside another (brand = "a" or sale) is refused rather than guessed at. A token's rules and a collection's expiry are never left out: they are ANDed into each facet's own filter too.

Ranges

ranges [b1, b2, ...] counts the rows whose number falls in each range — from a bound, included, to the next, excluded — rather than by value: every range, in order, an empty one with 0, its value the [from, to] pair. A null, a NaN and a number outside every range count in none; a list counts once in each range a value of it falls in.

get products where category = "tents" limit 24
  facet price ranges [0, 2500, 5000, 10000, 25000] disjunctive

"price": [{"value": [0, 2500], "count": 31}, {"value": [2500, 5000], "count": 112},
          {"value": [5000, 10000], "count": 204}, {"value": [10000, 25000], "count": 96}]

The bounds are numbers written out, rising, two to 10 001 of them, and no top goes with them. A @sorted field counts them from its index when every bound is a key it holds exactly — over every row two searches a range and the lengths of the chunks between, under a filter its entries walked against the filter's rows — and anything else reads the field of every row (12.5 against an int field is read).

Measured

Over 100 000 rows (make search-bench, an M1 Air): six ranges of a @sorted price over every row 0.004 ms against 4.7 ms read from every row; under a filter keeping 3%, 0.15 against 0.19 ms; keeping half, 5.1 against 8.1. A category page with a brand and a colour chosen, its page and two disjunctive facets beside a range facet in one statement, took 0.75 ms in process against 0.75 ms for the three statements it was before; over HTTP 0.95 ms against 1.19 for the three in turn and 0.61 for the three at once on three connections. What one statement buys is one request, one connection and counts read under one lock — the same rows every facet counted — not less work.

Explain

Put explain in front of a get to see how the query ran: which index it used and how many rows each step read.

explain get events where cat = "c7" order created desc limit 20

plan
order: the ordered index on created not walked, an equality names fewer rows
filter: the hash index on cat, 9753 rows, which is the answer
order: created desc, every key read, 9753 matches, the first 20 put in order
rows: 20
  • It runs the query, because some choices depend on the data.
  • The wording is for reading, not parsing; it may change between versions.
Details

explain in front of a get runs the query and answers with the path it took instead of its rows: one row a step, in the order the steps ran, in a single plan column. The last row is the size of the answer.

explain get events where cat ~ "c77" order created desc limit 20

plan
order: walked the ordered index on created desc, 2153 rows tested, 20 kept
rows: 20

Both are over a million events, cat carrying @hash and created @sorted. The first filter names a hundredth of the rows through an index, so they are sorted; the second is one no index narrows, so the walk tests rows newest first until twenty pass.

It runs the query because several choices depend on the data rather than the text: whether a filter's rows outnumber the ANN's budget, whether a walk along an ordered index fills the page before it gives up, whether the ANN came up short and fell back. The steps name each of them.

A step that startssays
filter:which index narrowed the filter — the id index, a hash index, an in over one, an ordered index's range — or that it was a full scan, how many rows were tested, and whether the scan stopped at the page
order:a walk along an ordered index and how many rows it tested, why one was not walked, or the sort: how many matches, how many put in order
near:the ANN and its ef, the filter's set searched exactly, the probe that stopped past the budget, the fallback when the ANN came up short, and the wider beam or exact search when tombstones cut it short
match:, rerank:the text index and how many rows it ranked, the vectors read for the rerank
fuse:the rank offset, and how many candidates each side brought — after its own match: and near: steps
lookup:, required:the probe per parent and how many children it attached; which side required was answered from

The same statement goes through every transport: the shell prints the rows, POST /query returns them as JSON, and the JavaScript builder has .explain(), which resolves to the lines. The steps are for reading, not parsing — their wording may change between versions.

Writes that read the row

A value in a set can be an expression over the row it writes: its fields, parameters and functions, with + - * /. Every write answers how many rows it changed, so a write that names what it expects to find says whether it found it.

set hits {n: n + 1, seen: now()} where key = "ip1"      -- an increment
set hits {n: coalesce(n, 0) + $1} where key = $2         -- from nothing, by a parameter
set docs {body: $1, version: version + 1}
  where id = $2 and version = $3                          -- compare-and-set: 1 or 0
put locks {name: "nightly", owner: $1, at: now()} if absent   -- 1 if taken, 0 if held
  • An increment is atomic. The row is read and written under the write lock, and there is one writer, so increments from any number of clients all land.
  • A field read is the row as it was. In {n: n + 1, m: n} both read the old n; a name on the value side is a field, a quoted string a string.
  • null stays null. n + 1 over a row with no n is null, as in SQL; write coalesce(n, 0) + 1 to count from nothing.
  • Every write answers its count — {"affected": n} over HTTP, the count of the browser module's answer, and the write result of every SDK.
Details

Types. The result goes through the field's type check as a literal would. Two ints make an int, and a result past 64 bits is refused, never wrapped; / between ints divides whole, toward zero, as PostgreSQL's does (7 / 2 is 3), and a division by zero is refused. An int and a float make a float, which an int field takes when it is whole and refuses when it is not — n * 2.0 fits, n + 0.5 does not, as the literal 2.5 does not. A float that is no longer finite is refused. A timestamp plus or minus an int is a timestamp that many milliseconds on (now() + 30000), and two timestamps apart are the milliseconds between them. Anything else — text and a number — is a type error. An error refuses the statement whole, a block of one, so nothing of it is written; over no rows there is no error, as there is no row to work it out over.

Precedence. * and / bind tighter than + and -, and all four tighter than a comparison: where n + 1 > 2 * m. -1 where a value starts is a number; after a value, n-1 and n - 1 are a subtraction.

Time. now() is worked out once a statement, so every row a set writes holds the same time. In the browser it is the time the page hands the module with every statement, which has no clock of its own.

What travels. The record holds the document as written, the value worked out, never the expression: a replica, /_changes, an archive and a subscriber see the result, and a restore replays it as it was. A scoped token's rules test the document a set writes, as they test a literal's (Scoped access). A replica of Sync works the expression out over its own row at once and sends the statement, which the server works out again over its own: two replicas' offline increments both land, and both replicas come to the server's sum.

How it runs. The pairs are bound to the collection once a statement, as a filter is: each field written and read by its position, and a value that reads no field — a literal, a parameter, now() — worked out once rather than a row. Each row is read once: a set read it twice before, once for the values and once for the indexes it takes out.

if absent passes over a document whose id, or whose @unique value, a live row holds, where insert refuses the statement: the others are written, and the answer counts those alone. That is Redis's SET NX in one statement, and it neither aborts a /batch nor makes an error a client has to catch. A row past its @ttl holds nothing — it is out of every read — so a write takes its place.

What it costs, measured (make counters-bench, in process over 100 000 rows of a text, an int and a note). A set of a constant over every row took 65.0 ms against 85.5 before expressions — the row read once instead of twice — and {n: n + 1} 66.6 ms; one row by id 1.07 us against 1.26, and 1.18 for n + 1. Sixteen threads incrementing one key 10 000 times each ended at 160 000, 320 000 increments a second, and sixteen HTTP clients the same against fenec-server, 102 000 a second.

Writes that must find their rows

A write that matches no row is no error: it answers {"affected": 0}, and a /batch goes on to the next statement. require N after a set, a del, a put or an insert makes the count a condition: unless the statement wrote exactly N rows it is refused, and the block it is in — a /batch, a run of several in the page, a keyed write — is put back whole, as on any other error.

set accounts {balance: balance - $1} where name = $2 and balance >= $1 require 1
del holds where order_ref = $1 and state = "held" require 1
put locks {name: "nightly", owner: $1} if absent require 1      -- refused while it is held
  • Refused over HTTP with 412, the error naming the statement: `set accounts` wrote 0 rows, and requires 1. A /batch also says which statement stopped it ("at", from 0). Every SDK has its own kind for it (unmet), and every builder an option: .update(patch, { require: 1 }).
  • The count is the write's own, taken under the write lock that made it, so nothing can come between the check and the write. A scoped token's count is of the rows its rules let it write.
  • require 0 asserts that nothing matches.

A read that must find its rows

require N after a get guards a read the same way: unless the get answers exactly N rows it is refused (412, "at" naming it) and its batch put back. In a /batch it reads under the batch's write lock, after the statements before it and before those after, so what it saw is what the writes around it see: "the price is still 12", "the coupon is still good".

get products where sku = $1 and price = $2 and stock > 0 require 1
get coupons where code = $1 and uses < max_uses limit 1 require 1     -- one is enough
get holds where order_ref = $1 and state = "held" require 0           -- none may be held
  • It counts the rows the get answers, after offset and limit: limit 1 require 1 asks that one exists, and reads no further. A lookup's children are not counted, and require goes before the lookup, whose clauses are the children's.
  • Not with count or an aggregate without group, which answer one row whatever matched; over groups it counts the groups. An inner get of in (get …) takes none.
  • On its own it is a read like any other, refused with 412 when the count is not met. A scoped token's count is of the rows it may read.
  • Every builder has it as a step, .require(1); a write takes it as its option instead. A replica's sync refuses one in a batch of synced writes: it would count the replica's rows, and the server, which lands the batch, would never see it — send a guarded batch to the server itself.

Transfers

Moving money between two accounts is a debit where the money is, a credit where the account is, and a journal of both, as one /batch. Without require an overdraft's debit matched nothing, answered 0, and the credit went ahead: the sum of the balances grew with every refused transfer. With it, a debit that finds too little money or a credit that finds no account puts the whole transfer back, journal and all:

create collection accounts (name text @unique, balance int)
create collection journal (tx text @hash, account text @hash, amount int)

set accounts {balance: balance - $3} where name = $1 and balance >= $3 require 1
set accounts {balance: balance + $3} where name = $2 require 1
insert journal [{tx: $4, account: $1, amount: 0 - $3}, {tx: $4, account: $2, amount: $3}]

printf '%s\n' \
  '{"query":"set accounts {balance: balance - $3} where name = $1 and balance >= $3 require 1","params":["ada","bob",30,"t1"]}' \
  '{"query":"set accounts {balance: balance + $3} where name = $2 require 1","params":["ada","bob",30,"t1"]}' \
  '{"query":"insert journal [{tx: $4, account: $1, amount: 0 - $3}, {tx: $4, account: $2, amount: $3}]","params":["ada","bob",30,"t1"]}' |
curl -s -X POST localhost:8080/batch -H "Idempotency-Key: t1" --data-binary @-
# an overdraft: 412 {"error":"unmet: `set accounts` wrote 0 rows, and requires 1","completed":0,"at":0}
  • Amounts are whole minor units in an int, so a sum is exact.
  • An Idempotency-Key makes a retry after a timeout answer what the first try did, rather than move the money twice (Retrying a write).
  • Who may move what is the app's. The credit is another user's row, which a scoped token may not write: transfers go through an app server holding the server's token.
  • A read can guard it too. A client that showed a balance and moves money only while it is still that puts get accounts where name = $1 and balance = $5 require 1 first; changed meanwhile, the transfer stops there, 412 with "at":0.
  • Held to it: eight threads making 4 800 random transfers among six accounts in process, and eight clients making 2 400 as /batches over HTTP, an eighth of them to an account that is not there, leave the sum where it started, no balance below zero, and a journal that accounts for every balance (crates/fenec-core/tests/require.rs, crates/fenec-http/tests/require.rs).

Checkout

An order is placed at the price the shopper saw, against stock that is there, with a coupon that is still good — or not at all. Each condition is a require: the price and the coupon read, the stock taken, the coupon's use counted and the order written, as one /batch.

create collection products (sku text @unique, price int, stock int)
create collection coupons (code text @unique, off int, uses int, max_uses int)
create collection orders (ref text @unique, sku text @hash, paid int)

get products where sku = $1 and price = $2 require 1
get coupons where code = $3 and uses < max_uses require 1
set products {stock: stock - 1} where sku = $1 and stock > 0 require 1
set coupons {uses: uses + 1} where code = $3 require 1
insert orders {ref: $4, sku: $1, paid: $2 - $5}
  • A price that moved stops the batch at its first line, 412 with "at":0: the shopper is shown the new price, and nothing was written.
  • A coupon used up stops it at the second, no stock at the third; the order's @unique ref refuses the same checkout twice (409), and an Idempotency-Key answers a retry what the first try did.
  • Under the write lock, every line sees the ones before it: two shoppers taking the last one cannot both pass the stock line.

Time

A timestamp field takes an ISO-8601 date or epoch milliseconds, and always comes back as ISO-8601 in UTC.

put events {name: "login", t: "2026-09-19T12:34:56Z"}
put events {name: "logout", t: 1758285296000}        -- epoch ms
get events where t >= "2026-01-01" and t < now()
Details

timestamp holds UTC epoch milliseconds as an i64. Writes accept both text and numbers; a text literal in a comparison is parsed.

The representation is always ISO-8601 (2026-09-19T12:34:56.789Z), in JSON and in FenecQL alike. The calendar conversion is integer arithmetic including leap-year and century rules — no table, no dependency.

It exists as a separate type rather than an alias over int because ResultSet does not carry the schema, so an alias would show every client a raw number.

Bulk loading

For a bulk load, build the index afterwards. The write path becomes a pure append and the graph is built in one parallel pass.

create collection docs (title text, embed vector<768>)
put docs [ ... 100 000 documents ... ]
create index on docs (embed) @hnsw(cosine)
