FenecQL

A small query language with vectors in the core. It is not SQL and does not try to be, though the familiar select … from word order is accepted.

Statements

create collection [if not exists] <name> ( <field> <type> [@index], ... )
drop collection [if exists] <name>
create index [if not exists] on <name> (<field>) @index

put <name> { field: value, ... }              -- or [ {...}, {...} ]
get <name> [select a, b] [where <expr>]
           [near <field> <vector> [ef N] [exact]]
           [match <field> <text>] [rerank <field> <vector> [candidates N]]
           [fuse [k N] [candidates N]]             -- match and near, both ranking
           [order <field> [collate tr] [asc|desc], ...] [limit N] [offset N]
           [lookup <name> on <child> [= <parent>] [required] <clauses...>]...
get <name> [where <expr>] count               -- number of matching rows
get <name> select [<key>,] count(*), sum(f), ... [where <expr>]
           [group <key> [order <column> [desc]] [limit N] [offset N]]
explain get <name> ...                         -- the path the query took
select a, b from <name> [where ...]           -- the classic SQL order works too
set <name> { field: value } [where <expr>]
del <name> [where <expr>]

collections | describe <name> | compact [<name>]

The id field is automatic. Supplying id inside a put turns it into an upsert.

The vector clause

get articles near embed $1 limit 10
get articles where year >= 2024 near embed $1 ef 200 limit 10
get articles near embed $1 exact limit 10

ef raises the search beam for this query only, trading latency for recall. exact replaces the ANN walk with a full scan, which is how you verify recall against ground truth. A query that uses near gains a _score column.

A filter next to near is planned, not stacked: the filter's rows are read only until it is clear whether there are more of them than the ANN would measure anyway, and the planner picks between searching that set exactly and running the ANN with each candidate tested against the filter. The mechanism, and the fallback that keeps it correct, is in How it works.

The text clause

get articles match body $1 limit 10
get articles where year >= 2024 match body $1 limit 10
get articles match body $1 rerank embed $2 candidates 500 limit 10

match ranks by BM25 over a @text index and adds a _score column. Like near it decides the ordering, so it combines with neither order nor near — unless fuse says how the two rankings make one (below). A where filter is applied while the postings are merged, so it costs no second pass.

rerank reorders what match found by exact vector distance. It needs match — there is nothing to reorder without it — but it does not need an @hnsw index: the vectors are read straight out of the store, so this path builds, holds and validates no graph at all. candidates sets how many of the matched rows are rescored (default 200); it is never allowed below limit + offset.

The two stages answer different questions. match is recall and knows nothing about meaning; rerank is precision but only over what the first stage handed it. Measured on BEIR: on SciFact 50 candidates score nDCG@10 0.654 against 0.645 for a full dense scan of the same vectors, and on FiQA 1 000 candidates come within 0.0003 of the full scan — each while scoring under 2% of the corpus. If the lexical stage cannot find the answer at all, no amount of reranking will.

Hybrid search

get articles match body $1 near embed $2 fuse limit 10
get articles where year >= 2024 match body $1 near embed $2 fuse limit 10
get articles match body $1 near embed $2 fuse k 60 candidates 50 limit 10

fuse lets match and near rank the same query together. Each side takes its own first candidates — 20 unless given, never fewer than limit + offset — with the where filter applied to both, and a document scores 1 / (k + rank) from each list it is on, k being 60 unless given. The sum is the _score; ties go to the lower id.

Ranks rather than scores, because the two have no scale in common: a BM25 score grows with the length of the query and the rarity of its words, a cosine distance does neither, and a weighted sum would need its weight tuned again for every corpus. Where rerank can only reorder what the words found, fuse also takes what they missed — at the price of the @hnsw graph near walks.

Measured on BEIR, nDCG@10, all-MiniLM-L6-v2 vectors (the whole table). On SciFact, where a claim shares its words with the evidence, fuse scores 0.699 against 0.662 for match and 0.645 for near alone. On FiQA, where a question shares few words with its answer, it scores 0.366 against 0.232 and 0.365: the weak side does not drag the strong one down. Up to 61 candidates a side at k = 60, a document both searches found outranks every document only one found; deeper, agreement in the middle of both lists starts to outvote the top of one, and at 100 a side the two scores fall to 0.687 and 0.358.

The lookup clause

get products lookup reviews on product_id
get products limit 20 lookup reviews on product_id order created desc limit 3
get products where price >= 10000 select name
  lookup reviews on product_id select body where stars >= 4 limit 3
get products lookup tags on sku = sku

lookup attaches the matching documents of another collection to the row they belong to. on names the child's field; the parent's key is id unless = <parent> says otherwise, which is the foreign-key-to-primary-key case spelled out.

It is terminal: everything before it binds to the driving collection, everything after it to the looked-up one. That is the whole scoping rule, and it is why there are no qualified names in the language — where on either side means what it has always meant. The price is that a parent clause cannot follow a child one, which reads the way the query runs anyway.

get shops limit 20
  lookup orders on shop_id limit 3
  lookup lines on order_id limit 5

A second lookup chains onto the first: its clauses bind to its collection, and on <child> = <parent> names a field of the level immediately above. Position keeps scoping the query one level deeper, so exactly one collection is in scope at any point and it is the last one named — which is what keeps qualified names out of the language at any depth. Up to 8 levels; deeper is an error, not a silent truncation.

limit after lookup counts children per parent. This is the clause's reason to exist. A join's limit counts pairs, so a single product with 56 374 reviews consumes the whole page and the other nineteen never appear; asking a join for three reviews each needs a window function. Here twenty products with three reviews apiece is one query with a bounded answer.

The child key must be id or carry @hash. Refusing an unindexed one is the same rule near and match follow: the clause is one bucket probe per parent, and quietly becoming a full scan of the child collection instead — 12.98 ms against 0.092 ms on the same 200 000 rows — is not a thing a query should do without saying so.

get products limit 20 lookup reviews on product_id required where stars = 5
get products count lookup reviews on product_id required where stars = 5

required drops a parent that no child matches — "products that have a five-star review" rather than "products, with their five-star reviews". It is tested before offset and limit, so a page of twenty comes back with twenty parents that have children rather than whatever survived; a child offset that walks past every match does not undo it, because the parent has matches all the same. It is the one shape where count combines with lookup: nothing is being attached, so counting the parents that have a match is a question with an answer.

required is a pass, and it is not cheap. It is answered from whichever side is smaller: walking the candidate parents and probing each, or — when the child filter carries a @hash equality and the parent's key is id — reading the children that equality names and taking their parents. Both counts that decide are exact, so the choice is not a guess; what neither plan escapes is that one full pass has to happen. Over 20 000 products and 200 000 reviews, for a page of twenty:

required, child filter on a @hash field12.07 ms
the same, walking the parents instead15.63 ms
required, no child filter2.19 ms
count … required4.50 ms
a bool @hash field on the parent0.02 ms

Ask it occasionally and required is the right tool. Ask it on every page load and the answer belongs in a field on the parent, maintained on write — which is the same trade the rest of this database makes.

In a chain, required is a statement about its own level: it drops rows of the level immediately above it and stops there. Requiring lines drops the orders that have none; the shops keep their rows, with an empty group, unless the orders level says required as well. Said at every level it composes into "shops with an order that has a line", and the existence check walks the whole way down — a row is only kept if it has a descendant that is itself kept. Nothing acts at a distance, and the flag means the same thing wherever it is written.

lookup combines with neither near, match nor rerank: each ranks one collection's documents, and a score spanning a parent and its children has no defensible meaning. count is refused as well unless the clause is required, since otherwise it collapses the very rows the children would hang from.

order inside a lookup is bounded in advance: the clause carries its own limit, so only offset + limit children can ever be emitted and the rest are never put in order. On a parent with 56 374 children, order created desc limit 3 costs 3.71 ms rather than 7.52 ms. What remains is reading one key per child, which no ordering can avoid — you cannot know the first three without having seen all of them. The query's own order works the same way.

Over JSON the children are nested under the collection's name, and a chain nests all the way down. On the PostgreSQL wire, which has no nested row, they arrive flattened into the parent row the way a join presents them — the same data, the shape the transport can carry; a chain widens once per level, one row per root-to-leaf path, and a level that ran out fills its own columns and every column below it with nulls. A parent with no matches keeps its row either way: the page is the parents. What the flat shape cannot show is the per-level limit, which is exactly why the nesting is what the other transports carry.

What it buys, measured (5 000 products, 100 007 reviews, twenty parents with three children each): the clause is 22.7 µs in process and 0.188 ms over HTTP, against 0.332 ms for the same work as a /batch of twenty-one queries merged on the client.

The larger gain is that there is one way to write it. The same question in SQLite, over the same data: a correlated subquery takes 0.053 ms, a window function with the restriction pushed inside the partition 0.331 ms, and the same window function with the restriction left outside 81.34 ms — a factor of 1 500 between three spellings of one question, with nothing in the query text to tell them apart.

A second level is where batching stops being an answer. One level of N+1 fits in a single round trip, because every query in it can be written from the page's ids; the level below cannot, because its keys are in rows that have not come back yet — so the client pays two round trips whatever it does. Over 2 000 shops, 20 000 orders and 200 000 lines, for a page of 20 × 3 × 5: 49.1 µs in process against 139.8 µs for the same page as 81 separate queries, and 0.204 ms for the one HTTP request against 0.415 ms for two /batch trips — measured on loopback, where the extra trip costs almost nothing and still doubles it.

Indexes

create collection articles (
  title      text,
  body       text @text(k1=0.9, b=0.4, prefix=0),
  year       int @hash,
  published  timestamp @sorted,
  embed      vector<768> @hnsw(cosine, m=16, ef_construction=200)
)

create index on articles (embed) @hnsw(cosine)
create index on articles (body) @text
create index on articles (body) @text(prefix=6)   -- for an inflected language
create index on articles (title) @sorted

A field takes one index. @hash answers equality, @sorted ranges and order, @text ranked text retrieval, @hnsw nearest neighbours. @sorted is for int, float, timestamp and text — the types with an order.

prefix=N indexes each word's prefixes alongside it (3..N by default; prefix_min moves the lower bound). It is a stemmer that needs no dictionary and no language setting, and it is off unless asked for because it is a trade the corpus decides. Word-boundary matching suits English; it does not suit a language that inflects by gluing suffixes on, where kitap, kitabı and kitapların are three terms sharing a stem the index never sees.

Measured on Turkish WebFAQ (144 846 documents, 10 000 queries): nDCG@10 0.4841 → 0.5547, +14.6%, closing about two fifths of the gap to a 278M-parameter multilingual transformer (0.650). The cost is the 3.4× postings it indexes — 58 MB → 182 MB, and 82 → 485 µs per query. On English SciFact the same option is worth +0.0137.

A filter reaches an index only inside an and chain. Equality — = and in [..] — reaches a @hash field; in is a set of equalities written short, so it is answered as the union of one bucket per element. Either reaches id, which the store's own id index answers without a @hash being declared or possible. Comparisons — <, <=, >, >= and = — reach a @sorted field, which narrows them to a range of keys.

Everything else — !=, ~, has, comparisons on a field without @sorted, and anything under an or — is a full scan: each matching row is decoded and evaluated. ~ in particular is substring matching without ranking and reaches no index; ranked retrieval is match over a @text field.

Quantized vector indexes

create collection articles (embed vector<768> @hnsw(cosine, quant=int8))
create index on articles (embed) @hnsw(cosine, quant=bit)

quant= sets what the index holds of each vector: int8 a byte a component, a quarter of f32, and bit the sign of each, a thirty-second — cosine only, since the signs are a unit vector's. The documents keep their vectors whole. The codes find the candidates, the beam's ef of them, and the documents' own vectors put those in order, so _score is the exact distance, and exact and a filtered set searched exactly read the vectors rather than the codes. Bit codes estimate coarsely and take a wider beam: ef_search is 400 there unless it is named. What they save and what they cost is in How it works.

Ordered indexes

get articles order published desc limit 20
get articles where published >= "2026-09-01" order published desc limit 20
get articles where title >= "k" and title < "l" count
get articles where published >= "2026-01-01" near embed $1 limit 10

order over a @sorted field with a limit walks the index in order and stops at the page, testing the rest of the filter on each row it passes; without one, every match's key is read and only offset + limit of them are put in order. A filter that matches too little to fill the page within an eighth of the collection sends the walk back to the scan: over a million rows one matching nothing cost 152 ms against the scan's 121, while one matching 1% fills the page in 0.29 ms against 125. A range on a @sorted field is read from the index as a set of ids — for a filter, a count, or the allowed set of a filtered near.

1 000 000 rows unless notedscan@sorted

The planner prefers a smaller set when it has one: an equality over a @hash field, or a narrow range on another @sorted field, names fewer rows than the walk would pass, so those are sorted instead. A range wider than half the collection is left to the scan, which is cheaper than gathering and sorting that many ids.

A comparison reaches the index only when its literal says exactly what the scan would compare. price < 12.5 on an int field, or an integer past 253 against a timestamp, is evaluated row by row — the index narrows with the comparisons it can express and the rest are tested — because an answer that differs from the scan's is a wrong answer, not a fast one. Ties come out in ascending id either way, as the scan leaves them.

The cost is paid on write and in memory: about 20 bytes a row for a number, plus the text for text, and an insert into a sorted run. Over a million rows two ordered indexes took a bulk load from 0.52 s to 0.88 s, and the index is rebuilt from the documents on open, like the hash and text indexes — it is never written to the file.

Collation

get people order name collate tr limit 20
get people order city collate tr desc, name collate tr
get people select city, count(*) group city order city collate tr

Text is ordered by its bytes unless a key says otherwise, and for Turkish the bytes are wrong twice over: every letter past ASCII — ç ğ ı İ ö ş ü — lands after z, so Çağla follows Zeynep, and every capitalised word comes before every lowercase one. collate tr orders the key as ICU's Turkish collation does, the one PostgreSQL calls tr-x-icu: ç after c, ğ after g, ı before i with I as its capital and İ as the capital of i, ö, ş and ü after o, s and u.

order nameorder name collate tr
Irmak, Zeynep, cem, Çağla, İlker, ılgazcem, Çağla, ılgaz, Irmak, İlker, Zeynep

It compares a level at a time over the whole string, as ICU does: the letters, then their accents (kar < kâr < kara), then their case (ince < İnce), so an accent or a capital only decides between strings whose letters are the same. What all three leave equal goes by its bytes, as under a deterministic PostgreSQL collation — the order is total, and a page never changes with the plan. It applies wherever order does: the query's rows, a lookup's children, an aggregate's groups by their key or a min or max of text. A key that holds no text — a number, id, count(*) — refuses it rather than ignore it.

A @sorted field keeps its bytes' order, so a collated key is sorted rather than walked, and a comparison in where stays a comparison of bytes: page a Turkish listing with offset, not with name > $last. Over a million names (160 797 of them distinct) one comparison costs 30 ns where the bytes cost 6.6, because the comparison starts where two strings part — Ahmet Yılmaz against Ahmet Kaya is Y against K — which took it from 68 ns:

1 000 000 namesbytescollate trPostgreSQL, "C"PostgreSQL, "tr-x-icu"

fenecdb in process, PostgreSQL 17 by its own execution time with the sort in memory; both on one core (make collate-bench).

The weights are ICU's own, over the Latin script. The table (crates/fenec-core/src/collate/table.rs, generated from ICU by tools/collate/gen.py) covers Latin-1, Latin Extended-A to -C, the IPA letters and spacing modifiers, the combining marks, general punctuation and the currency signs. Over those the order is ICU's exactly, and a decomposed letter — c and U+0327 — sorts as the composed one: checked against Intl.Collator("tr") over a million generated pairs, and over three thousand words in the browser module on every test run. What it does not do is ICU's normalisation: two marks on one letter, written out of their canonical order, can sort apart from where ICU puts them — not something Turkish text holds.

Past the table the order keeps ICU's broad shape without its data: a letter of another script after every Latin one, by the code point of its lowercase, and any other symbol before the digits, by its code point. The table and the code that reads it cost the browser module 8.5 KB, 3.2 KB after compression.

Aggregates

get orders select count(*), sum(total), avg(total), min(at), max(at)
get orders select status, count(*), avg(total) where year = 2026 group status
get orders select customer, sum(total) group customer order sum(total) desc limit 10

A select list with an aggregate in it folds the rows the query finds — through the same indexes any where reaches — into one row, or, with group <field>, one row per value of that field. Each column answers under its own name, sum(total), in the order the list is written, and a plain field in the list has to be the group's.

  • count(*) counts rows; sum and avg take an int or float field, min and max any field with an order — numbers, timestamp, text, bool. count needs its parentheses in a list: bare, it is a field of that name.
  • Nulls are skipped, as SQL skips them, by everything but count(*). Over no rows — or only nulls — a sum, an average, a minimum and a maximum are null, not 0. An int sum is an int, and one past 64 bits is an error rather than a wrapped number; an average is a float.
  • Groups come out by their key, the null key first, unless order names a column of the list — order sum(total) desc — and limit and offset page them. A whole-set aggregate is one row, which order and limit have nothing to do with; they are refused there.
  • What does not combine is what does not combine with count: near, match and lookup rank or attach rows that an aggregate collapses.

A million rows in 100 groups, select cat, count(*), avg(price) group cat, took 80 ms in process where PostgreSQL 17 — one worker, as make pgvector-up runs it — took 189 ms of execution time on the same rows; the whole set's count, sum, minimum and maximum, 37 ms; the same groups over the tenth a @sorted range found, 9.3 ms. The rows are read, not an index: a filter narrows them, nothing precomputes the totals.

Explain

explain in front of a get runs the query and answers with the path it took instead of its rows: one row a step, in the order the steps ran, in a single plan column. The last row is the size of the answer.

explain get events where cat = "c7" order created desc limit 20

plan
order: the ordered index on created not walked, an equality names fewer rows
filter: the hash index on cat, 9753 rows, which is the answer
order: created desc, every key read, 9753 matches, the first 20 put in order
rows: 20

explain get events where cat ~ "c77" order created desc limit 20

plan
order: walked the ordered index on created desc, 2153 rows tested, 20 kept
rows: 20

Both are over a million events, cat carrying @hash and created @sorted. The first filter names a hundredth of the rows through an index, so they are sorted; the second is one no index narrows, so the walk tests rows newest first until twenty pass.

It runs the query because several choices depend on the data rather than the text: whether a filter's rows outnumber the ANN's budget, whether a walk along an ordered index fills the page before it gives up, whether the ANN came up short and fell back. The steps name each of them.

A step that startssays
filter:which index narrowed the filter — the id index, a hash index, an in over one, an ordered index's range — or that it was a full scan, how many rows were tested, and whether the scan stopped at the page
order:a walk along an ordered index and how many rows it tested, why one was not walked, or the sort: how many matches, how many put in order
near:the ANN and its ef, the filter's set searched exactly, the probe that stopped past the budget, and the fallback when the ANN came up short
match:, rerank:the text index and how many rows it ranked, the vectors read for the rerank
fuse:the rank offset, and how many candidates each side brought — after its own match: and near: steps
lookup:, required:the probe per parent and how many children it attached; which side required was answered from

The same statement goes through every transport: psql prints the rows with the EXPLAIN tag, POST /query returns them as JSON, and the JavaScript builder has .explain(), which resolves to the lines. The steps are for reading, not parsing — their wording may change between versions.

Time

timestamp holds UTC epoch milliseconds as an i64. Writes accept both text and numbers; a text literal in a comparison is parsed.

put events {name: "login", t: "2026-09-19T12:34:56Z"}
put events {name: "logout", t: 1758285296000}        -- epoch ms
get events where t >= "2026-01-01" and t < now()

The representation is always ISO-8601 (2026-09-19T12:34:56.789Z). On the wire fenec-pg reports PostgreSQL's own output format (2026-09-19 12:34:56.789+00) and the timestamptz OID, because client parsers expect the server format. The calendar conversion is integer arithmetic including leap-year and century rules — no table, no dependency.

It exists as a separate type rather than an alias over int because ResultSet does not carry the schema, so an alias would show every client a raw number.

Bulk loading

For a bulk load, build the index afterwards. The write path becomes a pure append and the graph is built in one parallel pass.

create collection docs (title text, embed vector<768>)
put docs [ ... 100 000 documents ... ]
create index on docs (embed) @hnsw(cosine)

Worked examples

A hybrid query

get articles select title, year
  where year >= 2024 and tags has "rust" and not (title ~ "draft")
  near embed $1 ef 128
  limit 10

Counting

get articles where year >= 2024 count
-- one row, one column

Totals per group

get orders select status, count(*), sum(total) where year = 2026 group status
  order sum(total) desc limit 3

Update and delete

set articles {year: 2025} where id = 42
del articles where year < 2000
