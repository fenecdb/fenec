fenecdb and PostgreSQL with pgvector

PostgreSQL is a relational database server, and pgvector adds vector types and indexes to it. fenecdb is a document database with vector and full-text search that runs in a page, in an app, or as a server over HTTP.

The facts about PostgreSQL and pgvector on this page were checked on 2026-10-02 against the pages each one links to. fenecdb is at version 0.1.8, and is alpha software.

Which to choose

Choose PostgreSQL with pgvector when

  • You want SQL: joins, subqueries, window functions, and every ORM, driver and tool written for it.
  • Several clients write at once, in transactions they hold open across statements (MVCC).
  • You need what a mature server has: row-level security, logical replication, extensions such as PostGIS, and managed services from many providers.
  • Your vectors already live beside relational data you query together.

Choose fenecdb when

  • The same database runs in the browser, in a mobile app and on the server, with one query language.
  • You search by meaning and by words together: BM25 and rank fusion are built in (Hybrid search).
  • The client keeps a replica that reads offline and redraws live (Sync).
  • A file per tenant suits your service (Tenants and sharding).
  • Search latency at a million vectors matters (measured below).

Details

What fenecdb gives up for its size is listed in Limits: no SQL and no join (a query reads one collection and attaches related rows with lookup), one writer a file, no transaction held open across requests, and no TLS on the server. PostgreSQL's server has none of those limits.

pgvector's HNSW indexes take vector up to 2 000 dimensions, halfvec up to 4 000, bit up to 64 000 and sparsevec up to 1 000 non-zero elements (README). pgvectorscale adds a disk-based index, StreamingDiskANN, for data larger than memory (pgvectorscale). fenecdb keeps its indexes in memory and its documents in a mapped file (Memory and scale).

Method and details

The numbers are make scale-bench's and make load-bench's, as At scale and Loading rows report them.

make pgvector-up      # PostgreSQL 17 with pgvector, the pgvector/pgvector:pg17 image
make scale-bench
make load-bench
  • Hardware. An Apple M1 MacBook Air. It has no fan and slows under minutes of load, so each side was run on its own after four idle minutes, once.
  • Where each ran. fenec-server on the host, asked over kept-alive HTTP connections. PostgreSQL in Docker's virtual machine (4 GB, 8 CPUs, shared_buffers 1 GB), asked through the postgres crate. An empty query's round trip was 0.13 to 0.22 ms to PostgreSQL and 0.06 to 0.11 ms to fenec-server: part of each answer, not the rest of it.
  • Same index settings. HNSW with m 16 and ef_construction 64, pgvector's defaults, on both.
  • Each side's best way to load. fenec-server builds its graph as JSON arrays of rows arrive. pgvector builds after a binary COPY, on every core, then reads its index into its buffers (pg_prewarm) and searches a filter with hnsw.iterative_scan = relaxed_order.
  • Data. Vectors spread along 32 directions around 64 centres, 1 000 held-out queries, recall against the exact ten found by brute force.

Not measured yet: a Linux machine, PostgreSQL outside Docker, data larger than memory and pgvectorscale. Several clients writing at once are YCSB's.

Moving from PostgreSQL

fenec import copies a table into a collection over the network, vectors and index included. With --follow it keeps applying the table's changes as they commit.

fenec import postgres://app@db:5432/app --table docs --into articles \
    --index "embed@hnsw(cosine)" --follow
  • pgvector's types come across: vector, halfvec and sparsevec keep their dimensions. A numeric needs --cast (Type mapping).
  • Following needs wal_level = logical and an integer key. fenec-server --follow serves the mirror as it follows (Serving the mirror).
  • Queries are rewritten. fenecdb does not speak SQL or PostgreSQL's protocol, so a pgvector client library cannot connect to it.

The same search in each:

SELECT title FROM articles
WHERE year >= 2024
ORDER BY embed <=> $1
LIMIT 10;

get articles select title
  where year >= 2024
  near embed $1
  limit 10
Details

A join becomes lookup, which attaches each row's related rows, or in (get …), which filters by another collection's rows (The lookup clause, Subqueries). A transaction of several statements becomes a /batch, which lands whole or not at all but cannot read between its writes (Batches). Row-level security becomes a JWT rule (Scoped access).

The import reads the table with COPY ... TO STDOUT and needs nothing installed on the server, and the follower reads a logical replication slot through PostgreSQL's own pgoutput. Drop the slot when you stop following, or PostgreSQL keeps its log for it (Following changes).
