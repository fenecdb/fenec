Tenants and sharding

A single fenecdb is bounded by one machine's memory and one writer. Past that, the data is split by tenant: each tenant is a file of its own, a node holds many of them, and fenec-shard knows which node holds which.

# two nodes, each a directory of tenant files
fenec-pg --dir /data/n1 --http 127.0.0.1:8081 --admin-token a1
fenec-pg --dir /data/n2 --http 127.0.0.1:8082 --admin-token a2

# the router, and its directory of which tenant lives where
fenec-shard --listen 127.0.0.1:8090 --directory shard.fenec --token root

curl -X PUT localhost:8090/_shard/nodes/n1 -H 'Authorization: Bearer root' \
     -d '{"addr":"127.0.0.1:8081","token":"a1"}'
curl -X PUT localhost:8090/_shard/nodes/n2 -H 'Authorization: Bearer root' \
     -d '{"addr":"127.0.0.1:8082","token":"a2"}'
curl -X PUT localhost:8090/_shard/tenants/acme -H 'Authorization: Bearer root'
# {"tenant":"acme","node":"n1"}

curl -X POST localhost:8090/t/acme/query -d '{"query":"create collection notes (title text)"}'
curl -X POST localhost:8090/t/acme/notes -d '{"title":"hello"}'
curl localhost:8090/t/acme/notes

Below /t/<tenant> the surface is exactly the HTTP endpoint of a single database — routes, /query, /batch, subscriptions. A client changes its base URL and nothing else; the sync layer included:

const db = await sync({ url: 'http://127.0.0.1:8090/t/acme', shapes: [...] });

A file per tenant

The tenant is picked by the request path, never by the query text, so nothing rewrites a query to add tenant = .... Two tenants sharing a collection would then read each other's rows. A file each keeps them apart by construction, and the same decision settles four things a shared file would have had to solve:

  • Ids are counted per file, so they never collide and a moved tenant keeps its own.
  • The change sequence behind /changes is one number per file, so a client's cursor stays a plain number.
  • BM25 statistics — document count, average length, document frequency — are the tenant's own, which is what ranking inside a tenant should mean.
  • lookup never crosses a file, so it stays one bucket probe per parent.

Why tenants and not hash partitioning

With a tenant whole on one node, every query runs where all of its data is: near, match, order, count and lookup keep their single-database meaning, and the router never parses a query. Spreading one collection across nodes would need a merge for every read shape — and global statistics before match could rank anything, because per-node IDF gives scores that do not compare and a merged order that is quietly wrong. That is a different feature, and the case for it is a single tenant that outgrows a node. Until then, a tenant has to fit one node's memory.

The node: fenec-pg --dir

--dir serves a directory of <tenant>.fenec files instead of one file. It is still one process per directory — the single-writer rule is per file, and one process owning all of them is what keeps it. --http is required; --listen opens the PostgreSQL wire as well, where the database in the startup packet is the tenant:

fenec-pg --dir /data/n1 --http 127.0.0.1:8081 --listen 127.0.0.1:5433 --admin-token a1
psql postgres://fenec@127.0.0.1:5433/acme

A session is bound to its tenant for its lifetime, and the tenant is looked up again for every statement — so one created after the session opened is there for it, one closed as idle reopens, one deleted meanwhile answers 3D000 as an unknown database does, and one frozen for a move refuses writes with 57P03 while its reads go on. A name that is no tenant of this node is refused at connect.

  • Opened on first use. Open cost is proportional to the file, so a node does not spend its start-up on tenants nobody asks for. A tenant that has not been created is 404 — a request never brings one into being, or a typo would make an empty database.
  • Closed when idle. --idle-close <s> (default 300) syncs, checkpoints when there is a vector index, and closes a tenant nothing has touched for that long. One with an open request or subscription is never closed.
  • --max-memory covers the open tenants together. Opening one more over the ceiling first closes idle tenants, least recently used first. With everything busy the open goes ahead anyway: refusing a read because other tenants are busy would turn a memory warning into an outage.
  • Shutdown syncs every open tenant and checkpoints the ones with a graph, holding their write locks until exit.

The router drives the node through /_admin/, which answers only to --admin-token and is off (404) without it — a client allowed to read and write a tenant must not be able to delete it or take another tenant's image:

RouteDoes
GET /_admin/statstenant count, bytes on disk, memory of the open ones
GET /_admin/openthe open tenants: name, memory, frozen
GET /_admin/tenantsnames on disk
PUT /_admin/tenants/<t>create an empty tenant (409 if it exists)
DELETE /_admin/tenants/<t>end its streams, close it, remove the file
POST /_admin/tenants/<t>/freezerefuse writes and wait for the ones in flight
POST /_admin/tenants/<t>/thawaccept writes again
GET /_admin/tenants/<t>/filethe whole image, graph included
PUT /_admin/tenants/<t>/fileinstall an image as a new tenant

An image is replayed in memory before it is written, so a truncated transfer is refused rather than installed, and the file appears by rename, never half-written. Tenant names are [a-z0-9_-], 1 to 64 characters: they become file names, and that set means the same thing on every file system.

The router: fenec-shard

The router reads a request's head and body, looks the tenant up, and forwards it byte for byte — the original target, not a re-encoding of it. An answer with a length is read and passed back on a kept-alive connection; one without is a subscription, copied as it arrives until either side closes, so the stream format lives in one place, the node.

Its only state is the directory: two collections in a fenecdb file of its own, nodes and tenants. Every change is written and synced before it takes effect, and a tenant's node and state change in one statement, so there is no moment on disk where a tenant belongs to both nodes or to neither. The node admin tokens stay in it; GET /_shard/nodes does not return them.

RouteDoes
GET /_shard/nodesname and address of each node
PUT /_shard/nodes/<n>{addr, token}; checked against the node before it is recorded
DELETE /_shard/nodes/<n>refused while the node holds a tenant
GET /_shard/tenantsname, node and state of each tenant
PUT /_shard/tenants/<t>place and create; {node} to choose, otherwise the node with the fewest bytes on disk
DELETE /_shard/tenants/<t>delete on the node, then forget
POST /_shard/tenants/<t>/move{to}; see below

Placement goes by disk rather than memory: memory counts only the open tenants, and which ones are open depends on who asked last.

Moving a tenant

curl -X POST localhost:8090/_shard/tenants/acme/move -H 'Authorization: Bearer root' \
     -d '{"to":"n2"}'
# {"tenant":"acme","from":"n1","to":"n2","bytes":58685634,"ms":267,"source_removed":true}
  1. The directory marks the tenant moving; it is still routed to the source.
  2. The source freezes it: writes in flight finish, new ones get 503 with Retry-After: 1. Reads go on being served.
  3. The image is copied from the source and installed on the target.
  4. The directory points the tenant at the target, in one statement.
  5. The source copy is deleted. Its open subscriptions end with an error event, and the client reconnects through the router to the target. A client that had seen everything resumes from its cursor without a reseed: the change sequence travels in the image and the source was frozen, so nothing happened in between. One that was behind is reseeded, as after any restart — the target has the sequence but not the history before it.

The router refuses nothing itself during a move, so there is no window in which the tenant is nowhere — only one in which writes are asked to retry. If a step before the flip fails, the source is thawed and the directory put back. A router that stops mid-move comes back with the tenant still served from the source and marked moving; moving it again replaces whatever copy the interrupted attempt left on the target, which is stale by definition, since the directory never pointed at it.

What it costs

Node and router in one process on loopback, one keep-alive client, 5 000 requests after 500 of warm-up (make shard-bench):

 p50p95p99
straight to the node23.1 µs31.5 µs38.1 µs
through the router44.7 µs53.2 µs64.0 µs

About 21 µs per request, which is one more loopback round trip; across a network the extra hop is whatever that network charges for one. Moving a tenant of 100 000 × 128 with an HNSW index — a 58.7 MB image — took 188–267 ms end to end over three runs, and the first query on the target about 70 ms, most of it opening the file: the graph travels in the image, so nothing is rebuilt.

What it does not do

  • No replicas of tenants. A single file has read replicas; a --dir node does not yet, so a node that is down takes its tenants with it and the router answers 502 for them until it is back. Tenant files are ordinary files, so backups are file copies.
  • No query across tenants. Each request names one.
  • No tenant larger than a node. A tenant has to fit one node's memory, with the same 2× open and 3× checkpoint peaks as any file.
  • One router takes changes at a time. A standby follows its directory and forwards from the same placements, but only the primary places, moves and deletes; promoting the standby is a decision someone makes, not a vote the routers hold.

A standby router

The directory is a fenecdb file, so it replicates the way any other does. A second router follows it and forwards from the same placements; the primary is the one that changes it.

fenec-shard --listen 127.0.0.1:8090 --directory shard.fenec --replication-token r1
fenec-shard --listen 127.0.0.1:8091 --directory standby.fenec --replication-token r1 \
            --replica-of http://127.0.0.1:8090

Both forward /t/<tenant>/...; the standby's /_shard/ answers reads and refuses changes with 409, since its directory takes no write of its own. When the primary is gone, POST /_replication/promote on the standby forks its directory's history and it starts taking them — the same promotion a replica of a database gets, and the same rule after it: the old primary rejoins with --replica-of pointed at the new one, or its file is refused.

A standby is behind by whatever the last directory change has not reached it yet, which is one write and a sync: placements change when someone places, moves or deletes a tenant, not when clients read and write. Nothing of the tenants' own data goes through the router's directory, so a standby that is a second behind still forwards every request correctly.

Tokens

Three, each for a different job. Data requests carry whatever the nodes' --http-token expects, and the router passes Authorization through untouched. Each node has its own --admin-token, which only the router holds. The router's --token guards /_shard/; like the nodes, it refuses to listen on a non-loopback address without one unless given --insecure.
