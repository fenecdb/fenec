Tenants and sharding

When one machine is not enough, give each tenant a file of its own, spread the files over nodes, and put fenec-shard in front.

Get started

Start two nodes and a router, tell the router about the nodes, create a tenant, and use it through the router.

# two nodes, each a directory of tenant files
fenec-server --dir /data/n1 --http 127.0.0.1:8081 --admin-token a1
fenec-server --dir /data/n2 --http 127.0.0.1:8082 --admin-token a2

# the router, and its directory of which tenant lives where
fenec-shard --listen 127.0.0.1:8090 --directory shard.fenec --token root

curl -X PUT localhost:8090/_shard/nodes/n1 -H 'Authorization: Bearer root' \
     -d '{"addr":"127.0.0.1:8081","token":"a1"}'
curl -X PUT localhost:8090/_shard/nodes/n2 -H 'Authorization: Bearer root' \
     -d '{"addr":"127.0.0.1:8082","token":"a2"}'
curl -X PUT localhost:8090/_shard/tenants/acme -H 'Authorization: Bearer root'
# {"tenant":"acme","node":"n1"}

curl -X POST localhost:8090/t/acme/query -d '{"query":"create collection notes (title text)"}'
curl -X POST localhost:8090/t/acme/notes -d '{"title":"hello"}'
curl localhost:8090/t/acme/notes
  • Same API. Under /t/<tenant> everything works as on a single database; a client only changes its base URL.
Details

A single fenecdb is bounded by one machine's memory and one writer. Past that, the data is split by tenant: each tenant is a file of its own, a node holds many of them, and fenec-shard knows which node holds which.

Below /t/<tenant> the surface is exactly the HTTP endpoint of a single database — routes, /query, /batch, subscriptions. A client changes its base URL and nothing else; the sync layer included:

const db = await sync({ url: 'http://127.0.0.1:8090/t/acme', shapes: [...] });

A file per tenant

Each tenant is its own file, chosen by the request path and never by the query. Tenants cannot see each other's rows, and ids, change numbers, search ranking and lookup all stay per tenant.

Details

The tenant is picked by the request path, never by the query text, so nothing rewrites a query to add tenant = .... Two tenants sharing a collection would then read each other's rows. A file each keeps them apart by construction, and the same decision settles four things a shared file would have had to solve:

  • Ids are counted per file, so they never collide and a moved tenant keeps its own.
  • The change sequence behind /changes is one number per file, so a client's cursor stays a plain number.
  • BM25 statistics — document count, average length, document frequency — are the tenant's own, which is what ranking inside a tenant should mean.
  • lookup never crosses a file, so it stays one bucket probe per parent.

Why tenants and not hash partitioning

A tenant lives whole on one node, so every query runs where all its data is and means what it means on a single database. The cost: one tenant has to fit in one node's memory.

Details

With a tenant whole on one node, every query runs where all of its data is: near, match, order, count and lookup keep their single-database meaning, and the router never parses a query. Spreading one collection across nodes would need a merge for every read shape — and global statistics before match could rank anything, because per-node IDF gives scores that do not compare and a merged order that is quietly wrong. That is a different feature, and the case for it is a single tenant that outgrows a node. Until then, a tenant has to fit one node's memory.

The node: fenec-server --dir

A node is one fenec-server serving a directory of tenant files instead of one file. The path names the tenant: /t/acme/ is acme.fenec.

fenec-server --dir /data/n1 --http 127.0.0.1:8081 --admin-token a1
curl -X POST 127.0.0.1:8081/t/acme/query -d '{"query": "get notes limit 5"}'
  • Opened on first use, closed when idle (--idle-close, 300 s by default).
  • Unknown tenants are 404. A request never creates one.
  • /_admin/ is how the router drives the node; it needs --admin-token.
  • A user's token is bound to its tenant. A JSON Web Token reaches /t/acme/ only when its tenant claim names acme (Tokens).
  • Archived as a whole by fenec archive --tenants, one connection for every tenant (Archiving a node).
Details

--dir serves a directory of <tenant>.fenec files instead of one file. It is still one process per directory — the single-writer rule is per file, and one process owning all of them is what keeps it. --http is required. The tenant is looked up for every request — so one created a moment ago is there, one closed as idle reopens, one deleted meanwhile answers 404, and one frozen for a move refuses writes while its reads go on.

  • Opened on first use. Open cost is proportional to the file, so a node does not spend its start-up on tenants nobody asks for. A tenant that has not been created is 404 — a request never brings one into being, or a typo would make an empty database.
  • Closed when idle. --idle-close <s> (default 300) syncs, checkpoints when there is a vector index, and closes a tenant nothing has touched for that long. One with an open request or subscription is never closed.
  • --max-memory covers the open tenants together. Opening one more over the ceiling first closes idle tenants, least recently used first. With everything busy the open goes ahead anyway: refusing a read because other tenants are busy would turn a memory warning into an outage. A write that grows a tenant is refused once that tenant alone is past the ceiling, over either listener.
  • Shutdown syncs every open tenant and checkpoints the ones with a graph, holding their write locks until exit.

The router drives the node through /_admin/, which answers only to --admin-token and is off (404) without it — a client allowed to read and write a tenant must not be able to delete it or take another tenant's image:

The router: fenec-shard

The router looks up which node holds a tenant and passes the request there unchanged. Its only state is a small directory of nodes and tenants, managed under /_shard/.

  • New tenants go to the node with the least data on disk — in the region you name, if you name one (Regions) — unless you name the node.
  • A page on another origin needs --http-cors on the router, as it would on a node: fenec-shard --http-cors https://app.example.
Details

The router reads a request's head and body, looks the tenant up, and forwards it byte for byte — the original target, not a re-encoding of it. An answer with a length is read and passed back on a kept-alive connection; one without is a subscription, copied as it arrives until either side closes, so the stream format lives in one place, the node.

Connections to a node are kept and reused, and each is looked at before a request goes out on it: one the node closed for its silence (--idle-timeout) is let go of. A request that fails before it is wholly sent goes again on a fresh connection. One sent whole whose connection ends before an answer goes again only where running it twice is harmless — a GET, HEAD or OPTIONS, or a write with an Idempotency-Key, which the node makes once (Retrying a write). Any other write is answered 502, since the node may have run it: a client that sends it again should send it with a key.

Its only state is the directory: two collections in a fenecdb file of its own, nodes and tenants. Every change is written and synced before it takes effect, and a tenant's node and state change in one statement, so there is no moment on disk where a tenant belongs to both nodes or to neither. The node admin tokens stay in it; GET /_shard/nodes does not return them.

Placement goes by disk rather than memory: memory counts only the open tenants, and which ones are open depends on who asked last.

A page on another origin — an app, the sync layer, FenecHttp.live, the studio served by a node — reaches its tenants through the router once the router has --http-cors <origin>, read as fenec-server reads it (Security): * or one origin. The router answers a browser's preflight itself, before it looks the tenant up, and puts the CORS headers on every answer it gives. Its own — an unknown tenant's 404, a standby's 503, an unreachable node's 502, the 503 past --max-connections, the 401 of /_shard/ without its token — reach the page as the refusals they are; without the headers a browser hands the page a network error for each, and the sync layer backs off from what was an answer. On a node's answer the router's headers take the place of the node's, so the page is told the rule the router's preflight told it, and never two Access-Control-Allow-Origins, which a browser refuses whole. The 503s carry their wait as Retry-After and as retry_after in the body, as a quota's refusal does. Without the flag the router sends none of its own and passes a node's through as the node wrote them, and a preflight goes to the node.

A tenant with its schema

A tenant is created empty. Applying its schema afterwards took the nodes' data token, which reaches every tenant on every node, so the app that creates tenants -- one an organisation signs up -- held it. Hand the schema to the router instead, and the app needs the router's token alone:

curl -X PUT localhost:8090/_shard/tenants/acme -H 'Authorization: Bearer root' \
     -d '{"schema":"create collection notes (owner text @hash, title text)"}'
# {"tenant":"acme","node":"n1","schema":{"kind":"schema","applied":true,...}}
  • Applied on the node with the admin token the router holds for it (POST /_admin/tenants/<t>/schema), as /_schema/apply applies a description: one block, synced as a write is.
  • With its schema or not at all: a schema that does not read is refused (400) before anything is placed, and one the node refuses takes the tenant back off the node and out of the directory.
  • Under leases it is applied once the node's lease names the tenant, since the node takes no write before; a replica follows it as it follows every write.

Quotas

Tenants share a node: its disk, its memory, its threads. A quota keeps one tenant from taking all of them. Set defaults on the node, and a tenant's own through the router, which sends it wherever the tenant goes.

# every tenant on this node, unless its own quota says otherwise
fenec-server --dir /data/n1 --admin-token a1 \
    --tenant-max-bytes 1G --tenant-max-rows 1000000 \
    --tenant-max-streams 50 --tenant-max-held 200 --tenant-max-requests 16 \
    --tenant-writes-per-sec 500 --tenant-write-bytes-per-sec 8M

# a tenant on a plan of its own: set as it is created ...
curl -X PUT localhost:8090/_shard/tenants/acme -H 'Authorization: Bearer root' \
     -d '{"schema":"create collection notes (title text)","quota":{"bytes":104857600,"rows":50000}}'

# ... or changed later: the whole set, 0 for none, left out for the node's
curl -X PUT localhost:8090/_shard/tenants/acme/quota -H 'Authorization: Bearer root' \
     -d '{"bytes":1073741824,"rows":0,"writes":100}'

# what it is held to, and what it uses
curl localhost:8090/_shard/tenants/acme/quota -H 'Authorization: Bearer root'
# {"tenant":"acme","open":true,"set":{"bytes":1073741824,"rows":0,"writes":100},
#  "quota":{"bytes":1073741824,"rows":0,"streams":50,...},
#  "usage":{"bytes":48211,"rows":312,"streams":1,"requests":0,"held":0}}

A refusal names its quota in the body and in a header, and every SDK's error carries it typed (quota, retryAfter). A 429 says its wait twice: in whole seconds, rounded up, in Retry-After and retry_after, as HTTP has it, and to the millisecond in retry_after_ms, which every SDK and a replica's sync read first -- a bucket of 600 rows a second refills a row in 1.7 ms, and fifty couriers told to come back in a second waited fifty seconds between them:

HTTP/1.1 429 Too Many Requests
Fenec-Quota: writes
Retry-After: 1

{"error":"the tenant writes past its quota of 600 rows a second","quota":"writes","retry_after":1,"retry_after_ms":2}
HTTP/1.1 507 Insufficient Storage
Fenec-Quota: rows

{"error":"the write would take the tenant past its quota of 50000 rows: delete rows, or raise the quota","quota":"rows"}
  • A write that writes nothing costs nothing. writes counts the rows of the tenant's collections a write landed -- a put of ten rows ten, a claim that took no job, a require unmet or a held claim looking none -- and lets a write through while the bucket holds a row's worth, so one of many rows goes through and the next waits out the debt. Charged as a write started, 45 claims held at once by a fleet on a small plan were refused for writes before any for being held. A held claim the rate refuses as it is to run stays held, and runs once a row's worth is back. The node's own landings -- the sweep of rows past their @ttl, a compact -- are not the tenant's rate.
  • A tenant waits in a share of the node. Every stream and every held write is a connection and its thread, and a node's --max-connections is what all its tenants share: --http-max-streams counts each tenant's own subscriptions, and nothing counted a tenant's held writes, so a hundred workers of one tenant waiting for jobs took every connection of a default node and its neighbours were answered 503. Where the node sets neither --tenant-max-streams nor --tenant-max-held, each is a quarter of --max-connections -- 25 of a default node's 100 -- so no one tenant's dashboards and workers hold more than half; a node serving a fleet raises --max-connections (each is about 50 KB of memory) and sets its plans' quotas.
  • Deletes always land. A write that only takes away — a del, a drop — is never refused, and neither is a compact, which gives bytes back. A tenant at its quota deletes its way under it.
  • A replica's sync knows them. A synced write a 507 refuses is put back on the replica and the app told, the quota named, and the writes behind it -- a delete that makes the room among them -- go on; a 429 is waited out for its Retry-After, as a move's 503 is (Sync).
  • A full file is compacted by the node once an eighth of its quota is dead, where a file of its own waits for 64 MB: deleted rows become room without the tenant running compact itself.
  • Never passed by a write that adds. Bytes and rows are asked as the write lands, its record built, under the write lock: writers at once cannot take the file a byte past its quota, nor the rows one past theirs.
  • It goes with the tenant. The router keeps each tenant's quota in its directory and sends it to the tenant's node, its standby and its replica; a move sends it to the target before the directory points there, and a failover finds it on the copy it promotes.
  • Seen by quota, not by tenant: /_metrics counts refusals as fenec_quota_refused_total{quota="rows"}, the audit log writes each as a quota event naming the tenant, and GET /_admin/quotas on a node — or /_shard/tenants?quota on the router, which the studio's admin view shows — lists every tenant's usage against its quota.
Details

What is bounded is what is known exactly and cheaply. A file's bytes are the engine's count of what it appended, read with no system call; rows are each store's count, a sum over the collections (those whose names start with _ are the server's: idempotency keys, consumers' places); streams and requests are counters a request takes and gives back; the rates are a token bucket each. A tenant with no quota touches none of it. Left out: the memory an open tenant holds (memory_bytes counts what has been built, and a read builds an index on first use — a quota on it would refuse a write because of a search, and the same data holds less after a restart; --max-memory closes idle tenants for the node as a whole), a statement's time (the engine cannot stop a running scan; requests in flight bound how many cores one tenant's long reads take), and rows per collection (a tenant's own design: @ttl on a log).

The block is refused before it lands. A quota asked before a write runs would let that write past it by whatever it adds, and a set over every row adds the whole collection again. The engine asks the quota as a block lands, with its record's length to the byte and its documents counted (Database::set_limit); one past it is put back as a failed one is. A block larger than 16 MB spills into the file before it lands, and each spill is asked first: let through and refused after, its bytes would stay in the file, dead and past the quota. The file passes its quota only by what a write that takes away adds — a delete's tombstones, a drop's record — and by what no client writes: the graphs a server keeps in its file's tail. The next compact gives both back. A rate is not asked at the landing: a write lands while its bucket holds a row's worth or any bytes, and its rows and bytes are charged as it lands -- the rows of the tenant's collections it wrote, not the server's own, such as an Idempotency-Key's -- so a write larger than a second's worth goes through and the next waits out the debt.

A refusal tells the quota, not what the tenant holds: a scoped token's user is told the tenant is full, not how many rows the other users make. Only the admin token reads usage.

The router enforces none of it. It holds no keys and parses no query, and a tenant lives whole on one node, so the node's count is the tenant's. A quota a node does not take — a node down when it was set — is logged, and sent again as that copy is promoted.

What it costs. A tenant with no quota touches none of it: against the code before quotas, in turns, a request to a tenant took 19.5–21.7 µs straight to the node and 43.7–46.0 µs through the router, against 19.9–21.8 and 43.6–45.7. A tenant with every quota answered as one with none over HTTP — reads 20.9 µs either way, writes 23.7 against 23.6 — and in process a put held to bytes and rows took 593 ns against 566, 618 with a bytes-a-second bucket besides (make quota-bench).

Moving a tenant

Move a tenant to another node with one call. Reads keep working throughout; writes are asked to retry for the moment the copy takes.

curl -X POST localhost:8090/_shard/tenants/acme/move -H 'Authorization: Bearer root' \
     -d '{"to":"n2"}'
# {"tenant":"acme","from":"n1","to":"n2","bytes":58685634,"ms":267,"source_removed":true}
  • Writes during a move get 503 with Retry-After: 1, and "retry_after": 1 in the body, which a replica's sync waits out (Sync).
  • Subscribers reconnect and, if they were caught up, carry on without a reseed.
  • A failed move puts everything back on the source.
Details
  1. The directory marks the tenant moving; it is still routed to the source.
  2. The source freezes it: writes in flight finish, new ones get 503 with Retry-After: 1. Reads go on being served.
  3. The image is copied from the source and installed on the target.
  4. The directory points the tenant at the target, in one statement.
  5. The source copy is deleted — once every standby router keeping up has been sent the new placement, a second at most, so one that forwards from it sends the tenant's requests to the target rather than to a node that no longer holds it. Its open subscriptions end with an error event, and the client reconnects through the router to the target. A client that had seen everything resumes from its cursor without a reseed: the change sequence travels in the image and the source was frozen, so nothing happened in between. One that was behind is reseeded, as after any restart — the target has the sequence but not the history before it.

The router refuses nothing itself during a move, so there is no window in which the tenant is nowhere — only one in which writes are asked to retry. If a step before the flip fails, the source is thawed and the directory put back. A router that stops mid-move comes back with the tenant still served from the source and marked moving; moving it again replaces whatever copy the interrupted attempt left on the target, which is stale by definition, since the directory never pointed at it.

Archiving a node

Every tenant of a node is archived by one process over one connection to the node — not a connection, a thread and an open tenant each — an archive a tenant under a root, which restores a tenant or the whole node to a moment.

fenec archive --tenants http://n1:8081 /backups/n1 --token "$REPL" --image-every 1h --keep 7d
fenec verify  --tenants /backups/n1
fenec restore --tenants /backups/n1 /data/n1 --to 2026-09-22T10:14:59Z
  • Moved or deleted: a tenant that leaves the node is no longer followed and its archive is kept, noted gone, and noted back if it returns; the target node's archiver takes it up from its image. A restore of the node to a moment it was away leaves it out, as it does a tenant deleted before.
  • Restored in place: a tenant restored on its primary's node keeps its lineage, and fails over as before once its copies have taken the restored file (automatic failover).
  • Replicas and standbys can be archived the same way: their tenants' writes are the primary's, numbered alike, and a promotion goes on in the same archive.

The node needs --replication-token. What it costs and how the archive follows tenants made, closed, moved, restored and promoted: Archiving every tenant of a node.

A query across tenants

An operator's question about every tenant — how many orders each took since yesterday, the twenty newest sign-ups of all of them — is one request to the router, which runs the read on each tenant and merges the answers as the request says.

# each tenant's count, a row each with its tenant
curl -X POST localhost:8090/_shard/query -H 'Authorization: Bearer root' \
     -d '{"query":"get orders select count() as n where at >= $1","params":["2026-10-11T00:00:00Z"]}'
# {"rows":[{"tenant":"acme","n":31},{"tenant":"globex","n":7}],"tenants":2,"answered":2,"failed":[],"ms":2}

# the twenty newest of all of them: each tenant's twenty, merged
curl -X POST localhost:8090/_shard/query -H 'Authorization: Bearer root' \
     -d '{"query":"get users select email, created order created desc limit 20",
          "merge":{"order":["created desc"],"limit":20}}'

# counts added up by day, over the tenants whose names start with eu-
curl -X POST localhost:8090/_shard/query -H 'Authorization: Bearer root' \
     -d '{"query":"get orders select bucket(at, 1d) as day, count() as n group day",
          "merge":{"sum":["n"],"group":["day"]},"prefix":"eu-"}'

# the first twenty names of all of them in Turkish's order, a field
# declared `name text collate tr nocase`
curl -X POST localhost:8090/_shard/query -H 'Authorization: Bearer root' \
     -d '{"query":"get people select name order name limit 20",
          "merge":{"order":[{"column":"name","collate":"tr","nocase":true}],"limit":20}}'
  • The router's token alone. A user's token, bound to its tenant, and the nodes' data token are refused (401).
  • Reads only. A statement that writes is refused on every node (403) and writes nothing.
  • Never cut. A tenant that fails or times out fails the query, named; "partial": true answers the others' rows with the failures listed. The rows and bytes gathered are bounded, and a query past either is refused (413).
  • Each answer is its tenant's own. Tenants are read at different moments: there is no one moment across them.
Details

Tenants are the isolation boundary, and this crosses it, so it is a /_shard/ endpoint behind the router's --token. A JSON Web Token is refused there as any token other than the router's is: the router holds no keys, and a token bound to one tenant must not reach the others through it. The router asks each tenant through its node's POST /_admin/tenants/<t>/query with the node's admin token, which it holds already: a token that can take a tenant's whole image (GET /_admin/tenants/<t>/file) learns nothing more by reading it, where the nodes' data token, which nothing else here needs, would reach every tenant and write. The node refuses a statement that writes before it runs, and runs the rest in read-only mode besides.

The router still parses no FenecQL. The statement and its parameters go to every node as they came, and what is done with the rows is said in the request, never read out of the query:

MemberDoes
query, paramsthe statement each tenant runs, as /query takes it
tenants or prefixthe tenants named, or those whose names start so; every tenant in the directory without either. A name the directory does not hold is refused (404), nothing asked
mergenone: the rows one after another, tenants in name order, each with its tenant's name first; {"order": [..], "limit": n}; {"sum": [..], "min": [..], "max": [..], "group": [..]} (below)
columnthe name of the tenant's column, tenant by default
partialanswer the rows of the tenants that answered, the failures listed beside them
timeout_msthe query's one timeout, under the router's --fanout-timeout (30 s)

Three merges, each exact from the tenants' answers alone:

  • One after another, the default: every row, its tenant named.
  • An order: a k-way merge by the named columns, each asc or desc, of rows each tenant gives in that order. With each tenant's own order ... limit 20, the first twenty of the merge are the first twenty of all of them. The router checks each tenant's rows come in the order, and a tenant whose do not — its statement orders otherwise — fails, never merged wrong. Values compare as the engine compares them, text by its bytes; a timestamp travels as ISO text, which leaves its milliseconds out where they are 0, so a text that is one compares as its time. Ties go in tenant name order. A key whose text is not ordered by its bytes says how it is (below).
  • A fold: sum, min and max of the named columns, by the group columns, groups in order. These are the aggregates that combine across tenants: a count is a sum of counts. An average of averages is not an average, so there is none: sum its sum and its count. Every column of a row must be grouped by or folded, or the tenant fails: a column the merge would drop is an answer cut. A sum of whole numbers past 64 bits is refused, as the engine refuses one. A min, max or group column may be an object naming its text order as an order's key is: a tenant's min over a collated field is the collation's least, so the least of those is too, and a nocase group is one for every text folding to it, under the first tenant's text.

A column whose text the tenants compare otherwise than by its bytes is an object in place of its name: {"column": "name", "collate": "tr", "nocase": true, "desc": true} where "name desc" would be. The router reads no schema, so what the field declares — collate tr or und, nocase — or what the statement's order name collate tr names is said again here, and the column compares by the engine's own rule: the collation over the case folds, the texts that fold to one tied, and a text read as text even where it looks like a timestamp. "nocase": true folds as a field in the column's collation does, Turkish's under tr (I the capital of ı) and Unicode's otherwise; where the statement's collate names another than the field's own, "nocase" names the field's, as "nocase": "und" for a plain nocase field ordered collate tr. A collation other than tr or und is refused (400), named, and desc is an order's alone. Not told, the router compares bytes: the tenants whose rows come in another order fail, and a min or max is the bytes' least or greatest of the tenants' own.

A tenant that fails — its node unreachable, its call past the timeout, an answer that does not fit the merge, or one the node refused — is named with its node, the status and why. Without "partial": true the query fails with every failure named; the first stops the asking, and the answer says how many tenants were not asked. Its status is the tenants' own where they all failed alike — a statement every node refused is 400 or 403 — and 502 otherwise. A tenant moved while the query runs is asked again on the node the directory names now; one deleted meanwhile is a failure. The tenants come from the directory as the query begins: one created after that is not in it.

The rows gathered from the tenants together are bounded by --fanout-max-rows (100 000) and the bytes of their answers by --fanout-max-bytes (64 MiB), counted as the answers arrive: a query past either is refused (413), its partial rows or not, and the asking stops. The calls go out over the router's connections to the nodes, --fanout-concurrency (16) at once, the tenants taken node by node in turn, and each tenant's answer is read for the merge on the thread that fetched it, beside the calls still out.

Each tenant's answer is one statement's, as /query's is. Tenants are separate databases read at different moments, so two answers are of no one moment, and a write landing in one while the query runs may or may not be in its answer. A read that opens a tenant opens it on its node, which closes it again once idle.

A query across tenants is a span of the router's trace, a span a node under it, and each tenant's read on its node under that node's span, all with the request's id; the router counts them in fenec_router_fanouts_total and two more (Monitoring), no label naming a tenant. Each is a line of the router's audit log; the nodes' reads for it are not, as a read is not.

What it does not do

No join across tenants -- a query across them is an operator's read, merged as it says -- no tenant bigger than a node, and only one router makes changes at a time. Failover is never guessed.

Details
  • Failover is decided on a lease, not a guess. A router cannot tell a node that is gone from one it cannot reach, and guessing would make two primaries for one tenant. Without --auto-failover someone who knows the node is gone calls the failover; with it, the router promotes a node's tenants only once the node's own lease has certainly lapsed, and the node stops its writes as it does (Automatic failover).
  • No join across tenants. A data request names one tenant. The router's query across tenants runs one read on each and merges the answers by a rule the request states -- one after another, the first rows of an order, sums and extremes by group -- and never parses the query: nothing joins one tenant's rows to another's, and the answers are each tenant's own, of no one moment.
  • No tenant larger than a node. A tenant has to fit one node's memory, with the same 2× open and 3× checkpoint peaks as any file.
  • One router takes changes at a time. A standby follows its directory and forwards from the same placements, but only the primary places, moves and deletes; promoting the standby is a decision someone makes, not a vote the routers hold.

Replicas of tenants

Pair a node with a standby node, and every tenant on it is copied there as it is written. When the node is lost, one call promotes its tenants on the standby.

fenec-server --dir /data/n1 --http 127.0.0.1:8081 --admin-token a1 \
         --replication-token r1 --sync always
fenec-server --dir /data/n2 --http 127.0.0.1:8082 --admin-token a2 \
         --replication-token r1 --replica-of http://127.0.0.1:8081

curl -X PUT localhost:8090/_shard/nodes/n1 \
  -d '{"addr":"127.0.0.1:8081","token":"a1","standby":"n2"}'
  • Failover: POST /_shard/nodes/<n>/failover.
  • Use --sync always on the primary so a failover loses no write.
Details

Every tenant file has a feed of its own, so a node's tenants are followed by another node's — the standby — tenant by tenant, through /t/<tenant>/_replication.

The router creates a tenant on both, so the replica has a file to follow into, and deletes it from both; a move takes the replica with it. Recording a pair gives the standby a following copy of every tenant already on the node. A replica node opens every tenant it holds at start and keeps them open — a follower that is not running is a replica falling behind — so --idle-close does not apply to them. No tenant is placed on a standby or moved to one: it would open there as a replica of a tenant the other node does not have.

A tenant's role is its file's, not the node's. On a node started with --replica-of, a replica's file follows and a new one follows, but a primary's file stays a primary — a tenant a failover promoted there included, whatever the node restarts with. Were every file on such a node made to follow, a restart with the same flags would undo the failover, and the old primary's copy would wipe the writes taken since.

When a node is gone, POST /_shard/nodes/<n>/failover promotes its tenants on the standby, one at a time, and points the directory at it. They are separate databases: there is nothing to make atomic between them, so the answer lists what was promoted and what was not. A copy that is not its tenant as the directory knows it — of another lineage, or an old primary's copy that never heard from the new one — is refused by its node and listed as not promoted, the tenant left where its rows are; with -d '{"force": true}' it is promoted whatever it holds, which the audit log records.

curl -X POST localhost:8090/_shard/nodes/n1/failover
{"node":"n1","to":"n2","promoted":["acme","beta"],"failed":[]}

Measured with make shard-bench, node, standby and router in one process on loopback: a write through the router is answered in 2.93 ms (--sync always on the primary, which is an fsync a write) and is on the standby 0.089 ms later, 0.448 ms at p99 — timed by reading the standby's own copy. A failover of 20 tenants took 63.5 to 79 ms, the medians of three rounds of four to twelve runs, 3 to 4 ms each, and the first write on the promoted node 0.18 ms.

A promoted tenant's history forks where the replica stood, so what the primary had not sent is gone — the same trade a database's failover makes, and --sync always on the primary is what makes it none. A failover that moved every tenant ends the pair; one that left a tenant behind keeps it, so a second call can take it. The old node rejoins as the standby of the new one: point its --replica-of there and record the pair the other way round. The router then has each of its tenants follow (POST /_admin/tenants/<t>/follow) — its own files are a primary's, and follow only when told to — and the writes it took that were never sent are gone.

fenec-server --dir /data/n1 --http 127.0.0.1:8081 --admin-token a1 \
         --replication-token r1 --replica-of http://127.0.0.1:8082
curl -X PUT localhost:8090/_shard/nodes/n2 \
  -d '{"addr":"127.0.0.1:8082","token":"a2","standby":"n1"}'
{"node":"n2","unreplicated":[]}

A tenant file that still follows on a node that follows nobody — a failover that left it behind, and the node restarted without --replica-of — refuses writes, says so in the log, and is promoted where it stands with POST /_admin/tenants/<t>/promote (with -d '{"force": true}' where it holds no write and has heard nothing from its primary since it opened).

Replicas of their own

Instead of an idle standby, fenec-shard --replicas gives each tenant its own replica on another node, so every node holds both primaries and replicas and a lost node's tenants spread over the rest.

fenec-server --dir /data/n1 --http 127.0.0.1:8081 --admin-token a1 --replication-token r1 --sync always
fenec-server --dir /data/n2 --http 127.0.0.1:8082 --admin-token a2 --replication-token r1 --sync always
fenec-server --dir /data/n3 --http 127.0.0.1:8083 --admin-token a3 --replication-token r1 --sync always
fenec-shard --replicas

curl -X PUT localhost:8090/_shard/tenants/acme -d '{"node":"n1"}'
{"tenant":"acme","node":"n1","replica_on":"n2"}
  • After a failover, POST /_shard/replicas gives every tenant without a replica a new one.
Details

A standby waits idle, and takes every tenant of its node at once when the node goes. With --replicas the router gives each tenant a replica of its own instead, on another node in no pair: the one holding the fewest replicas of that tenant's node, then the fewest tenants and replicas altogether. Each node's tenants then follow on all the others, and every node holds primaries and replicas both.

The replica's node is told which node to follow (POST /_admin/tenants/acme/follow with {"from": "http://127.0.0.1:8081"}) and keeps it in acme.follows beside the file, so the tenant follows again when the node starts over. The replication token is the nodes', one for the cluster. A move takes the replica along: the copy goes on following the tenant on its new node, since the image carried its history, and when the tenant moves onto the node holding its replica, that copy goes and another is placed. A delete removes both.

A failover of a node in no pair promotes each of its tenants on its own replica, one at a time, and routes it there. The tenants whose replicas it held are named as unreplicated. POST /_shard/replicas gives every tenant without a replica one, on a node holding a copy of it first: a node back from a failover has its old primaries follow the nodes that took them over, and nothing of theirs is left lying there.

curl -X POST localhost:8090/_shard/nodes/n1/failover
{"node":"n1","promoted":[{"tenant":"acme","to":"n2"},{"tenant":"beta","to":"n3"}],"failed":[],"unreplicated":["gamma"]}
curl -X POST localhost:8090/_shard/replicas
{"replicated":[{"tenant":"acme","replica":"n1"},{"tenant":"beta","replica":"n1"},{"tenant":"gamma","replica":"n1"}],"failed":[]}

Measured with make shard-bench, three nodes and the router in one process, 30 tenants: each is created with its replica in 33 ms, the replicas 10 a node, and a write is on its replica 0.179 ms after it was answered, 0.421 ms at p99. A failover of one node's 10 tenants took 57 ms, 5 onto each of the other two, and the repair after it gave 20 tenants a replica in 176 ms, all on the returning node's copies. Placed by the fewest altogether alone, every tenant of one node followed on the same other: a tie went by name each time, and its failover put them all there.

Automatic failover

With --auto-failover the router fails a node over by itself. It works on leases: a node stops writing when its lease runs out, and only after that does the router promote its tenants elsewhere, so a tenant never has two primaries.

fenec-server --dir /data/n1 --http 127.0.0.1:8081 --admin-token a1 \
         --replication-token r1 --sync always --lease
fenec-shard --listen 127.0.0.1:8090 --directory shard.fenec --replicas --auto-failover 5
  • Nodes need --lease; a node without it is never failed over automatically.
  • With a 5-second lease, a lost node's tenants cannot be written for 5.5 to 7.2 s. A node cut off from the router while its clients still reach it stops writing two thirds of a lease after its last renewal at the most: its lease runs from the grant before that one.
Details

With fenec-shard --auto-failover <s> the router fails a node over on its own. It leases each node the tenants it places there for that long, renews the lease as it starts and every third of it after while the node answers, and fails over a node that has gone a tenth past its lease unrenewed. A node started with --lease writes a tenant only while its lease names the tenant and has not lapsed, and starts with none.

The router still cannot tell a node that is gone from one cut off from it while its own clients reach it, and it does not have to. A node that hears from the router no more stops taking writes when its lease lapses, by its own clock, and the router promotes its tenants elsewhere only a tenth of a lease later, measured from the answer that came back rather than from the grant it sent — so no tenant has two primaries, whichever it was. What such a node took from clients of its own before its lease lapsed, and had not sent its replicas, goes with the failover as a crash takes it; a client going through the router loses nothing that way, since the router could not reach the node either. A write is refused as a replica's is: 503 with Retry-After.

That holds of a grant however late the node reads it. Each grant is numbered and names the newest grant whose answer came back to the router in time, and the node runs its lease from the moment it answered that one, never from when it reads a grant. A grant read late — held on its way, or left unread by a node stopped or slow — acknowledges only answers the router had already counted, whose lease ran out before the failover; a grant whose answer never came back is acknowledged by no grant after it. Neither gives the node a lease, so a node that reads grants waiting in its socket after its tenants were promoted elsewhere takes no write for them: with the lease run from when it read them, as it was, it took a whole lease's writes beside the new primary. A grant newer than the one the lease came from — by the answer it acknowledges, then by its own number — is taken whole, its list with its lease, which may cut the lease held short: a router restarted or promoted with a shorter lease shortens the node's with its first acknowledged grant. One that is not newer is taken not at all while a lease runs, so a late one cannot hand back a tenant failed over elsewhere, and a node says so in its answer (took), which has the router send the grant acknowledging it at once, with the list. The price is about a round: a node's lease runs from the grant before the last it read, so a node cut off stops writing a third of a lease sooner than it did, while the failover comes when it did; and a node holding no lease — new, restarted, back from a failover — needs a second grant, acknowledging the first, which the router sends at once. A router from before numbered grants sends none, and a node takes its grants from when it reads them, as before: a late grant can still outlast a failover until every router is upgraded. A node from before them is leased as before too, and the router says so once in its log.

What leases do not cover. A node measures its lease on the system's monotonic clock, which stands still while a virtual machine is paused (KVM's clock across a stop and a continue) or a machine is suspended: a node paused so wakes with lease left and writes beside its tenants' new primaries until the lease runs out, with no late grant needed; and a write that passed the lease's check just before its process stopped lands once it resumes. A stall of sixteen rounds or more can leave a node without the answer its next grant acknowledges, holding no lease until the grant after it, which the router sends at once. Two directories leasing one node — a misconfiguration — can take it in turns as each other's lease lapses, neither holding one for long.

A router may start with a shorter lease than the one before it — --auto-failover lowered, then a restart or a standby promoted. A node it never reaches may still hold the longer lease, so the directory records the longest lease a router leasing from it may have granted, raised before a router's first grant with a longer one and sent to its standbys first. A router counts a node by that record until the node has run a lease from one of its grants, which the node says in its answer (ran); from then on, by its own lease, since that grant cut the longer one short. A grant taken for its list alone, by a node whose lease had lapsed, runs none, and a late grant of the router before could still run the longer lease again. Once the router has led for the recorded lease and a tenth, every lease granted before it has run out, and it lowers the record to its own. Where the record cannot be written, a grant runs no longer than the record, renewed every third of that, or the router's own lease where there is none.

What the record does not cover: it is a directory's own, so a node leased by one directory and then by another — the global one's, then a region's — is counted by the second's record, which knows nothing of the first's lease. And a router from before the record writes none, so the first router with it after an upgrade starts with no record, and counts by its own lease. Lower --auto-failover at a restart after that one; never at the upgrade itself.

The lease names tenants, not the node. A node failed over comes back with the files of tenants served elsewhere now, primaries' files still; a lease over the whole node would have them take writes again the moment it was renewed. Its new lease names none of them, and the router runs a repair as the node answers, which has those copies follow the tenants' new primaries. The list rides with a grant only when it changed, and a create or a move grants the node its new one at once, so a tenant takes writes as soon as it is placed. A router that starts leasing — a restart, or a standby promoted — counts every node as granted then, at its first round as the primary: its predecessor may have granted a lease just before it stopped. A grant names the directory's term, which a promotion moves on, and a node refuses grants from a lower term once it has taken a higher one, so a router promoted over one still running fences it at every node it reaches (Fencing). A node started without --lease answers that it takes none, and is never failed over on its own.

No node waits for another. Each node's grant goes out on a thread of its own and the router judges the leases without waiting for any, so a node slow to answer — or to be found at all: one recorded by a name its resolver is slow to refuse once the machine is gone — holds up its own renewal and its own failover, nobody else's. A name is looked up within the call's own bound, a third of the lease for a grant; the repair a node's return triggers runs beside the leasing, as do failovers; and a replica being promoted stops reconnecting to the node it followed at once rather than wait out the connect. A node's lapse is judged only once the router has stopped waiting for any grant it sent the node, so an answer that comes back is counted (a grant it gave up on gives the node nothing). A tenant that another operation was holding — a quota being set, a move — when its node was failed over is failed over once that operation ends, onto the copy it had then and no other, and its node's grants name it no more meanwhile, so the node does not take it back as it answers again. A copy that is not its tenant as its primary has it is never promoted: the router tells the node the tenant's lineage and the history its primary forked at its last failover, and the node refuses a copy of another lineage — one that never took its primary's image, or a file put in its place — and an old primary's copy that has not heard from the new primary since, which would take back every write after that failover; the tenant waits for its node, where its rows are. A copy that has heard from the node it follows since it was last told to follow it is promoted whatever history it holds, and its node remembers the hello across a restart, so a tenant restored in place on its primary's node — fenec restore installed with DELETE and PUT .../file, or the whole node with fenec restore --tenants — fails over as before once its copies have taken the restored file. A tenant not yet written fails over as any other. A file of another lineage put in a primary's place by hand — another tenant's, or one made again under the name — is not the tenant the router knows: every failover of it is refused until a read replica's look teaches the router the new lineage, or an operator forces one. An operator who knows better sends {"force": true} to POST /_shard/nodes/<n>/failover or to the node's POST /_admin/tenants/<t>/promote, which promotes the copy whatever it holds and is written to the audit log. Nor is a tenant given a new replica while its primary does not answer; the repair looks again a few times over the next minutes, and POST /_shard/replicas asks at once. Before, one such node held up the leasing of its whole region: in a drill on GitHub's runner, whose Docker resolver is slow to refuse a removed container's name, the region's healthy nodes went 18 s without a write and one was failed over, and the dead node's tenants wrote again only after 30 s. In the same drill run locally, every unknown name sent to a resolver that never answers, the router now fails the dead node over 2.1 to 3.3 s after its kill at a lease of 2 s, and the region's other tenants never pause more than 19 ms.

Measured with make shard-bench, three nodes and the router in one process and a lease of a second: a node cut off stopped taking writes 386 to 406 ms after — its lease ran from the grant before its last renewal, about two thirds of a lease before the cut — and its 10 tenants took writes on their replicas again 1.27 to 1.36 s after, the lease and a tenth from the last answer, the next round and the promotions. Before grants were numbered, the node ran its lease from its last renewal and stopped 714 to 777 ms after the cut, and the failover came as it does now, 1.26 to 1.42 s after (four runs each, in turns). With a lease of five seconds, a node lost costs its tenants' writes 5.5 to 7.2 s.

A standby router

A second router can follow the first one's directory and forward requests too. Only the primary router makes changes; promote the standby when the primary is gone.

fenec-shard --listen 127.0.0.1:8090 --directory shard.fenec --replication-token r1
fenec-shard --listen 127.0.0.1:8091 --directory standby.fenec --replication-token r1 \
            --replica-of http://127.0.0.1:8090
  • Promote: POST /_replication/promote on the standby.
Details

The directory is a fenecdb file, so it replicates the way any other does. A second router follows it and forwards from the same placements; the primary is the one that changes it.

Both forward /t/<tenant>/...; the standby's /_shard/ answers reads and refuses changes with 409, since its directory takes no write of its own. When the primary is gone, POST /_replication/promote on the standby forks its directory's history and it starts taking them — the same promotion a replica of a database gets, and the same rule after it: the old primary rejoins with --replica-of pointed at the new one, or its file is refused.

A standby is behind by whatever the last directory change has not reached it yet, which is one write and a sync: placements change when someone places, moves or deletes a tenant, not when clients read and write. Nothing of the tenants' own data goes through the router's directory, so a standby that is a second behind still forwards every request correctly. One whose directory has not arrived at all — just started, its primary not yet reached — answers 503 with Retry-After rather than 404: it knows of no tenant, which is not knowing there is none.

Each change the primary makes reaches the standby's maps through the change ring, as a subscription's rows do: the placements it put or deleted since the last one, 4 µs at 100 000 tenants, where reading every map again took 38 ms under the router's write lock. An image adopted, or more changes than the ring holds, and the maps are read again whole.

Regions

Give each node a region and a zone — a datacenter in the region. A tenant lives in one region, its node's, and its replica is kept in the same region in another zone, so a failover keeps both its latency and where its data is.

curl -X PUT localhost:8090/_shard/nodes/eu1 \
     -d '{"addr":"10.1.0.11:8081","token":"a1","region":"eu","zone":"fra"}'
curl -X PUT localhost:8090/_shard/nodes/eu2 \
     -d '{"addr":"10.1.1.11:8081","token":"a2","region":"eu","zone":"ams"}'

curl -X PUT localhost:8090/_shard/tenants/acme -d '{"region":"eu"}'
{"tenant":"acme","node":"eu1","region":"eu","replica_on":"eu2"}
  • A tenant is placed in the region it names, on the node with the fewest bytes there. A region with no node is refused with 409, and nothing is created.
  • It leaves its region only by a move that names the region it goes to: {"to":"us1","region":"us"}.
  • Run one router a region: standby routers follow the primary's directory and forward every tenant to its node, wherever it lives.
Details

Nodes. PUT /_shard/nodes/<n> takes region and zone beside addr and token, names of [a-z0-9_-] as a tenant's are. One left out is the one recorded, so a node given a new token stays where it is. A node's region is fixed while it holds a tenant, a tenant's replica, or a place in a pair — its tenants' residency would change under them — so it changes once they are moved off; its zone may change at any time. A node recorded without a region is in the unnamed region, which is one region like any other: a directory that names none places, replicates and fails over as it did before regions, and "" names it in a request.

Tenants. A tenant's region is its node's — kept on the node alone, so a move or a failover changes it with the node and there is no second record to drift. PUT /_shard/tenants/<t> takes region, node or both, which must agree (409 otherwise). With neither it goes to the region fenec-shard --default-region names, and without that flag to the node with the fewest bytes whatever its region, as before. GET /_shard/tenants/<t> answers its node, state, region and zone, its copy's node — a replica of its own or its node's standby — and "same_zone": true where that copy is in its zone; the list carries each tenant's region, and ?region=eu gives one region's tenants.

curl localhost:8090/_shard/tenants/acme
{"name":"acme","node":"eu1","state":"active","region":"eu","zone":"fra","replica":"eu2"}

Copies. With --replicas a tenant's replica goes to a node of its region only — the replica is what a failover promotes, and one in another region would carry the tenant out of its own. Among those, a node of another zone comes first, before one holding a copy already and before the fewest replicas: a datacenter lost would take a replica in its primary's zone with it. A zone not recorded is ranked between, neither known to be another nor the same. Where every free node of the region is in the primary's zone, the replica goes there all the same: the router logs it, the tenant answers "same_zone": true, and fenec_router_same_zone_copies{region} counts it for as long as it stays. A region with no other node gives none ("unreplicated": "there is no other node in region `eu` to keep it") until a repair finds one. A pair's standby must be in its node's region (409 otherwise), and one in its zone is logged. So a failover — by hand or on a lease — promotes a tenant within its region: its copy was never placed anywhere else.

Moves. {"to": "eu2"} moves a tenant to a node of its region; to a node of another, it is refused naming the region the request must name. {"region": "us"} picks the node with the fewest bytes there, {"to": "us1", "region": "us"} names both; either way the answer carries the region the tenant is in now. Its replica goes with it where it still fits — in the new region, in no worse a zone than a node free there — and is otherwise taken off and placed again in the new region: kept, a failover would take the tenant back out of the region it moved to. A move across regions copies the tenant's image over the network between them, the tenant frozen for writes meanwhile.

One router a region. The directory is one file with one primary router, which takes every change. A standby router in each other region follows it (A standby router) and forwards every tenant, from the same placements, to its node wherever it is; its /_shard/ answers reads, GET /_shard/tenants/<t> and POST /_shard/query included, and refuses changes with 409 naming the primary — asked again it would refuse again, so it is no 503. Clients reach the router nearest them, by GeoDNS or an anycast address in front; a request for a tenant in another region crosses between regions once, router to node, as it would going there itself. A standby router added 23.7 µs p50 to a request over the node's own, as the primary did — 23.0 to 23.8 and 23.1 to 23.9 over five runs, the two asked in turns: following costs a request nothing (make shard-bench ARGS=standby, node and routers in one process on loopback).

A standby router is behind the primary by a directory change on its way, one network trip between regions; a move deletes the source copy only once every standby keeping up has been sent the new placement, so a standby in another region routes the tenant's next request to the target and not to a node that no longer holds it. A promotion is the same as with one standby: POST /_replication/promote on the router to take over, the others pointed at it with --replica-of.

A region's leases. Under --auto-failover the router that keeps a node's directory leases it. With one directory that is the primary router, so a region cut off from the primary's would stop taking writes as its leases lapse, and could not be failed over until the router reached its nodes again. A region that keeps its own directory is leased and failed over by its own router, and goes on writing through a partition. A client far from a tenant's home reads near itself where the tenant has a read replica in its region; no SDK picks a router by region: a client is given the router nearest it.

The directory's format. nodes took region and zone fields, which a directory written before them is given as it opens (an alter); its nodes read the unnamed region. A router from before them reads the directory as it always did — it ignores the fields, forwards every tenant where it is, and, promoted, places without regard to regions.

A region that keeps its own directory

Give a region a router of its own that keeps the region's directory: its nodes and tenants. That router leases the region's nodes and fails them over, so the region goes on taking writes — and fails a node over inside itself — while it is cut off from every other region.

# us: the region's router, its directory in us.fenec, the global one followed from eu
fenec-shard --listen 0.0.0.0:8090 --token $ROOT --directory us.fenec \
            --replication-token $DIR --replicas --auto-failover 5 \
            --region us --global http://router.eu.internal:8090

# on the global router: us keeps its own directory, kept by that router
curl -X PUT router.eu.internal:8090/_shard/regions/us -H "Authorization: Bearer $ROOT" \
     -d '{"routers":["http://router.us.internal:8090"]}'

# us's nodes and tenants, through either router
curl -X PUT router.eu.internal:8090/_shard/nodes/us1 -H "Authorization: Bearer $ROOT" \
     -d '{"addr":"10.2.0.11:8081","token":"a3","region":"us","zone":"iad"}'
curl -X PUT router.eu.internal:8090/_shard/tenants/acme -H "Authorization: Bearer $ROOT" \
     -d '{"region":"us"}'
{"tenant":"acme","node":"us1","region":"us","replica_on":"us2"}
  • Inside the region, nothing waits for another: leases, failovers, repairs, moves between its nodes, quotas and its nodes are its router's.
  • What needs every region waits for them: a create (the name is global), a delete and a move across regions go through the global router and are refused with 503 and Retry-After while a region they touch cannot be reached — nothing is done by half.
  • Every router reaches every tenant: one asked for a tenant of another region relays the request to that region's router.
Details

Two levels. The global directory — the router started without --region, and its standbys — holds every tenant's name, the regions keeping their own directory and their routers (PUT /_shard/regions/<r> {"routers": [...]}, the one keeping it first, its standbys after). For each tenant of such a region it holds a home, the region and no node. The region's router holds the region's nodes and placements in a directory of its own (--region us), the same collections, and follows the global one from --global. A region that keeps no directory of its own — the unnamed one, and every region of a deployment that names none — is the global directory's, so a deployment without --region places, leases and fails over exactly as before, and one may move its regions out one at a time.

Who changes what. A change touching one region's nodes or tenants is that region's router's: a node added, a tenant's quota, a move between two of its nodes, a failover by hand, a repair. A change the global directory takes is the global router's: a create takes the tenant's name there first and then asks the region's router to make it (the name given back if that router refuses or cannot be reached; kept where it says the tenant exists, which takes in a create whose answer was lost), a delete asks the region's router first and then gives the name back. Either router takes either kind: what is not its own it relays, once — a region's router to the global one, the global router to the region's, marked so it goes no further.

A move across regions is the global router's, step by step: the tenant frozen in the region it leaves and its image taken, installed and recorded in the region it goes to — leased and given its replica there — let go of in the region it left, whose directory then places it nowhere, so no lease there names it; and only then its home moved in the global directory, one statement, which routes it to its new region. Each step is undone where the next fails: a region not reached leaves the tenant where it was, taking writes again, and the move is answered 503. A move between a region keeping its own directory and one the global directory keeps works the same way, the global router doing that region's part itself.

Forwarding. A router asked for a tenant its own directory does not place looks it up in the global directory — its own, or its copy — and sends the request to its node, or, for a tenant of a region keeping its own, to that region's routers, the one that answered last first. They forward it to the node as the region's last failover left it: nobody outside the region needs to have heard of the failover, and after a partition every router reaches the new placement with its first request. The relay costs a request a hop inside the tenant's region, which a client asking the router of its own region never pays: 32 to 42 µs p50 on loopback, a router's 24 and the proxy that stood for the link between the regions (make shard-bench ARGS=regions). A router relaying names the client beside it, marked with an HMAC of the routers' shared --token, so a refused token waits by the client's address, at the first router alone.

Fencing. A lease names its holder: the directory it comes from and that directory's term, the number of times its history forked. Promoting a router forks it, so a region's router promoted over the one before — a standby following its directory, in the region or in another — grants at a higher term, and every node that hears from it refuses the old one from then on: its grants (409 naming who holds the node), its promotions and its re-pointing of replicas. A node that only the old router still reaches cannot be told; that is why a router is promoted once the one before it is gone, as with one directory. A node from before terms takes a grant without checking its term, so a region's router leases it but never fails it over on its own. List a region's standby routers after its router in routers: a relay moves to the next one where the first cannot be reached, and a standby forwards from its copy of the directory and refuses changes until it is promoted.

A partition, step by step. The global router in eu, us keeping its own directory; the link between the regions goes down.

  • Inside us, nothing changes: us's router renews its nodes' leases, and its clients write as before. A request from eu for a us tenant is answered 502 — a region out of reach, as a node out of reach is — and a client asks again; inside eu, eu's tenants are written as before.
  • A node of us lost or cut off stops taking writes as its lease lapses, and us's router promotes its tenants on their replicas in us, a tenth of a lease later. With a lease of a second, a node cut off stopped writing 0.38 to 0.63 s after the cut and its 10 tenants wrote again on their replicas 1.41 to 1.70 s after, ten runs; with five seconds, 3.9 to 4.1 s and 5.5 to 6.7 s — as the global router fails over its own, 1.27 to 1.36 s at a second (make shard-bench ARGS=regions, the region cut off from the global router throughout, three nodes and both routers in one process).
  • A create in us, a delete of a us tenant, a move into or out of us are refused with 503 and Retry-After, through any router, and change nothing.
  • The link comes back: the global router's next relay reaches us's router, which places the failed-over tenants where it put them; the refused changes go through when asked again.

Formats. The global directory took a regions collection, and a tenant at home in such a region is a row of tenants whose node is @<region>, which no node can be named; a region's directory names its region in scope, and a router opened over the wrong one refuses it. A router from before regional directories reading the global one forwards no request of such a tenant (no node @us: 404), refuses every change of it, takes no name it holds, and leases none of the region's nodes, which it does not know. A lease grant carries authority, term and history, and its own number and the one it acknowledges (grant, acked); a node from before reads the grant as it did. Not done: a query across tenants (POST /_shard/query) asks the tenants the router's own directory places, and names each tenant of another region's directory as failed rather than leave it out; ask that region's router for its own.

One URL for every region

A Cloudflare Worker in front of the regions' routers gives every tenant one URL: https://db.example.com/t/<tenant>/... goes to the routers of the region the tenant lives in, and their answer comes back as it comes. It is a plain Worker, not a Workers for Platforms dispatch, which would put a dispatch in every request's path.

# entry/wrangler.jsonc: REGIONS, each region's routers, the one keeping its directory first
cd integrations/cloudflare
npx wrangler secret put ENTRY_TOKEN --config entry/wrangler.jsonc
# a Cloudflare Access service token, where Access guards the tunnels' hostnames
npx wrangler secret put ACCESS_CLIENT_ID --config entry/wrangler.jsonc
npx wrangler secret put ACCESS_CLIENT_SECRET --config entry/wrangler.jsonc
npx wrangler deploy --config entry/wrangler.jsonc

# every router: the same token, so it believes the client the entry names
FENEC_SHARD_ENTRY_TOKEN="$ENTRY_TOKEN" fenec-shard --token "$ROOT" ...

curl https://db.example.com/t/acme/query -H "Authorization: Bearer $TOKEN" \
     -d '{"query":"get notes count"}'
  • It learns where a tenant lives from the routers: every request asks for the tenant's home, and the router that forwards it to the tenant's node names the node's region in its answer, to the entry alone. A tenant the entry has not seen goes to the region nearest the client, whose router serves it or relays it home once; its next request goes home.
  • A tenant moved to another region is relayed by the router of the region it left, as any client's request is, and the answer names its new home: a stale home costs one hop, never an error.
  • A read marked for a replica (Fenec-Read: replica, read replicas) goes to the region of the client's continent first, whatever the tenant's home: its router answers it from the tenant's read replica there, or relays it home — a hop, where the region keeps none — and the home is asked where that region fails. A continent no region names sends it home alone: the default region is where an unknown tenant is guessed, no nearer such a client than the home. A marked read runs read-only wherever it lands, so it may go to two; an unmarked request never leaves a known home. Sent to the home the entry had learned, every marked read crossed to it, and the replica near the client was never asked.
  • Streams pass through as they come — a subscription, /_changes?wait, a held write, a long /batch. A stream is let go of when its client goes; a held write is let go of at the router, which does not yet let go of it at the node.
  • Only /t/<tenant>/... is served: /_shard/ goes to the global router only where the entry is told to (ADMIN), and /_admin/, /_replication and the rest are a 404, however the path is spelled.
  • A router that cannot be reached is passed over for the region's standby router. An unmarked request of a tenant whose home the entry knows is never sent to another region: its region's routers all failing is a 503 with Retry-After. One it has not heard goes on to the next region, whose router relays it home, and a marked read goes home past its continent's region.
  • Set CORS wherever the routers have --http-cors: without it the entry's own answers — a region down, a path refused — carry no CORS headers, and a page reads them as the network failing. The entry says so in its log once it sees the routers send them.
Details

Where a tenant lives. Nothing remote is asked on the way: a request carries Fenec-Home: 1, and the router that forwards it to the tenant's node answers with Fenec-Home: <region>, the node's — a router relaying it to another region names nothing of its own, and the answer it passes back carries the home router's. The entry takes the header off before the answer goes to the client: a router names the home on a refusal too, so to anyone holding a tenant's name. The entry keeps 50 000 tenants' homes an isolate (HOMES), forgotten first-heard first, and shares each one it learns with the colo's other isolates through the Cache API, read only by an isolate that has not heard the tenant (HOMES_CACHE; it does nothing on workers.dev, so the entry wants a custom domain). A tenant heard nowhere goes to the region REGIONS names for the client's continent (Cloudflare's request.cf.continent), else DEFAULT_REGION, then to each other region in turn where one's routers cannot be reached — any region's router relays the tenant home, and only the home's router places it on a node, so no write lands anywhere else. A region whose routers failed is asked last: by a read or a keyed write for ten seconds, then first again; by any other write until one of its routers answers, since a write that may have reached a router cannot be sent to another. A guessed region's router that answers 5xx naming no home — cut off from the home's region, say — sends a read on to the next region too; a write it answered is its answer. Asking the global router at each miss would have needed its --token, which moves and deletes every tenant, in the Worker, a round trip to the global router's region, and would have turned every unknown name a client tries into a question for that one router; a table in Workers KV is read eventually consistently and billed by the read, and still needs something to write it. A router answers the header only to a request asking for it, so no other client is told one; a router from before it answers none, and the entry keeps sending such a tenant to the nearest region, relayed each time.

Streams and Cloudflare's limits. The answer is handed back as its body arrives, so a server-sent event reaches the client as the router sends it. Cloudflare's Workers limits: waiting on a fetch is not CPU time, and an HTTP-triggered Worker has no limit on its duration while the client stays connected, so a subscription or a held write is not cut; an invocation may have six connections waiting for their headers, and the entry has one. A router behind a hostname Cloudflare proxies must start its answer within the proxy read timeout (100 seconds, fixed below Enterprise): a Fenec-Wait holds a write 30 s at most, and a silent stream writes a keep-alive every 20 s (--http-keepalive). The Worker's request.signal (the enable_request_signal flag) is handed to the fetch, so a client gone cancels the request to the router. Under wrangler dev a stream is let go of at a stand-in router 2 s after its client goes, workerd noticing as the next keep-alive is written, and at a node through a router in 4 to 8 s, each hop noticing at its next. A client gone before its answer's head is not told to the Worker there at all — workerd notices a client only as it writes to it, past wrangler's own proxy too — so that case is held in Node, the handler over Node's fetch. Past the entry it goes on to the node: a router waiting on a node's held answer watches its client and passes the client's end on, as the node would read it from a client of its own — a region's router relaying the request to the home router, which passes it to the node — so a claim whose client went hands its job to the next claim held, as it does asked of the node itself, rather than lease it to nobody; a client that only half-closed is answered as the node answers it.

Headers. Everything a client sends goes on — Authorization, Idempotency-Key, Fenec-*, traceparent, X-Request-Id (Cloudflare's ray id where the client sent none, so the routers' and the nodes' lines carry it) — but the hop-by-hop headers, the routers' own marks (Fenec-Router, Fenec-Global, Fenec-Verified), which a router believes from another router alone, a Fenec-Client of the client's own, and every way a client names an address (X-Forwarded-For, X-Real-IP, Forwarded, True-Client-IP, CF-*). Fenec-Verified and Fenec-Home are dropped from answers. The routers' CORS headers come back as they sent them; with CORS set to their --http-cors, the entry answers a preflight itself with the same headers, a round trip saved and a region that is down no reason for a page to see a network error, and puts them on its own answers alone — two Access-Control-Allow-Origins are refused whole by a browser. A path is judged as the router and the node will read it, decoded as fenec-http decodes one: /t/acme/%5Freplication and /t/acme%2F_replication are a tenant's replication stream to them, which a URL's own parsing leaves encoded.

The client's address. Behind the entry every request reaches a router from Cloudflare's addresses, so the wait after a refused token would count every client's refusals together, and any good token would start the count again. The entry names its client in Fenec-Client: <address> <seconds> <mark>, the address Cloudflare's CF-Connecting-IP, the seconds the Unix time the entry made it at, the mark 16 bytes of HMAC-SHA256 of fenec-client <address> <seconds> under ENTRY_TOKEN, base64url. Bound to the address and the time, a mark seen names that one address for a minute, where a mark of the token alone would let whoever saw one name any address for good. Not CF-Connecting-IP or X-Forwarded-For believed from Cloudflare's addresses: a Worker sets CF-Connecting-IP and X-Real-IP as it likes on a request to an origin outside Cloudflare (Cloudflare's HTTP headers page), so any account's Worker could claim any address from those ranges.

A router started with the entry's token — fenec-shard --entry-token, or FENEC_SHARD_ENTRY_TOKEN — checks the mark against its own HMAC, in constant time, and the time within 60 seconds of its clock either way, and takes the address for that request's in the connection's place. A refused token waits by it, and a good one starts its count again and no other's; the audit log names it as peer, the entry's address beside it as via, and a trace as client.address, the connection's as network.peer.address; and it is the client the router names to the tenant's node, or to the home region's router it relays the request to, which names it to the node in turn. A header seen on the wire can be replayed for that minute, and names that one address: what the minute costs, where a mark of the token alone would name any address for good. A header that does not check, or a router without the flag, counts the connection's address, and fenec_router_entry_clients_total says which (named, bad_mark, stale, or absent for a tenant's request carrying none, as every one from an entry whose ENTRY_TOKEN is unset does), the router's log a minute apart at most of each kind not believed — not the audit log, which a header costing its sender nothing would fill at the router's request rate. On a router only the entry reaches, alert on all but named (Monitoring). Every router drops the header from what it forwards, flag or not, so a node never reads a client's claim. A mark costs a request one HMAC-SHA256, 0.75 µs on this machine, which a round trip does not show: through a router with the flag and one without, in turns, a request the entry named its client in took 41.7 µs p50 against 42.1, and one with no header 42.0 against 42.05 — a look among its headers and a count — the runs' differences a few tenths of a microsecond either way (make shard-bench ARGS=latency, eight runs). Without the flag the router's added p50 stayed 20.4 µs, as before.

The entry's token is its own. The Worker holds it, so a router refuses it where it holds it for anything else: equal to its --token, which moves and deletes tenants, to its --replication-token, whose stream carries every node's admin token, or to the admin token of a node in its directory, at the start and as a node is added. The nodes' data and replication tokens the router never sees: keep the entry's apart from those too. A router takes one entry token at a time. To change it, start each router with the new one, then put it in the Worker (npx wrangler secret put ENTRY_TOKEN): in between every request is served, and its client counted by Cloudflare's address, as bad_mark shows — a few minutes of the counting there was before, against a second token held by every router.

When a router cannot be reached. A region's routers are tried in turn from the one that answered last. Every answer a router writes carries its mark, Fenec-Shard: 1, and an answer at a router's URL without it is not the router's — not X-Request-Id, which a router's answers carry too and a load balancer may write on its own 502. Cloudflare's own answers for an origin it never reached (521, 523, 525, 526, and 530, a tunnel with no connector) go on to the next router whatever the request. One that may have reached the router — a fetch that fails, which workerd says alike of a connection refused and of one reset after the request was written; Cloudflare's 520, 522 (a request whose bytes went unacknowledged for 90 seconds is among its time-outs) and 524; and any other 5xx without the router's request id, such as a tunnel's connector answering 502 for a router it cannot reach — goes on only for a GET, HEAD, OPTIONS or a request carrying an Idempotency-Key, as the router's own rule towards a node; any other is a 502 saying it may have run, and the region's next request goes to the next router. A router's own 502 — a node it could not reach — names the home and is its answer, passed on, no other region tried. A body up to a mebibyte is kept for the next router; a longer one is streamed to one, its length kept (a router takes no chunked body), and one sent with no length past a mebibyte is refused with 411: read whole, it was as large as a client cared to send, in isolates whose 128 MB are shared.

What it costs. Under wrangler dev on this machine, a read by id of a tenant in us took 81 µs p50 asked of us's router directly, and through the entry with its home heard 1.18 to 1.22 ms, 0.66 to 0.68 past wrangler's own proxy Worker — workerd taking the request, the entry and its fetch, all on loopback; with the client named besides (ENTRY_TOKEN, an HMAC a request), 1.23 to 1.24 ms (0.68 to 0.70). Never heard, it went to eu first, whose router relayed it: 1.29 to 1.31 ms (0.71 to 0.75), eu's router asked directly relaying it in 114 to 115 µs. Heard only through the colo's cache, 1.60 to 1.61 ms (1.00), miniflare's cache a service of its own (make entry-bench: two runs of six rounds of 2 000 in turns, at loads of 3.4 to 5). That is not what Cloudflare adds: there a client reaches its nearest colo and the router is a region away, the leg it would pay to reach the router itself; a home not heard costs a relay between regions, where the cache is read inside the colo. A router asked for the home answered in 82 to 83 µs p50 against 81 not asked; not asked, its mark on every answer, its added p50 was 23.75 µs against main's 23.9 (23.4 to 24.1 and 23.7 to 24.0, six runs a side in ABBA turns, make shard-bench ARGS=latency).

Read replicas

A tenant lives in one region, and a client on another continent pays the trip between them on every request — Frankfurt to Singapore is 158 ms. Give the tenant a read replica in the client's region: a follower of its primary there, which the router of that region answers the client's reads from, while its writes go home.

# a read replica of acme in ap, on the node of ap holding the least
curl -X PUT router.eu.internal:8090/_shard/tenants/acme/read-replicas/ap \
     -H "Authorization: Bearer $ROOT"
{"region":"ap","node":"ap1","follows":"http://10.1.0.11:8081"}

# ap's router stands in ap: a marked read of a tenant with a replica there goes to it
fenec-shard --listen 0.0.0.0:8090 --token $ROOT --directory standby.fenec \
            --replication-token $DIR --replica-of http://router.eu.internal:8090 --near ap

import { connect } from '@fenecdb/web/client';

// Through ap's router: reads near, writes home.
const db = connect('https://ap.example.com/t/acme', { token: 'a token', reads: 'nearest' });
await db.from('orders').insert({ number: 'SG-1' });        // home, in eu
const mine = await db.from('orders').rows();               // ap's replica, after that write
  • A read never comes from before the client's own write. A client reading near sends each read after the furthest position home named to it — the change and the history it is a change of (Fenec-After, Fenec-History) — and the replica answers once it holds that change of that history; one it cannot in the wait goes home. A failover that loses a write does not fool it: the copy left on the old branch holds a change of that number, of another history.
  • A replica answers nothing before it has caught up. One placed a moment ago, its image still to come — or reopened, or pointed at a new primary, until that primary has said hello — sends the read home.
  • Only a read the client marks goes near (Fenec-Read: replica): the router parses no statement. The SDKs mark the builder's reads, and a text the caller says reads; every other request goes home, as it always did.
  • A read replica is never promoted. A failover of the tenant's home promotes its standby or its replica, in its region; the read replica follows the new primary.
  • Cut off from home, it serves what it last applied — stale, to a read that names no write — and catches up once the link is back; reopened or pointed at a new primary meanwhile, it serves nothing until that primary has said hello.

Behind the global entry (one URL for every region) a marked read goes to the region of the client's continent first, whatever the tenant's home, and its router answers it from the read replica there; every other request goes to the home the entry has learned.

Details

Placing one. PUT /_shard/tenants/<t>/read-replicas/<region> makes the tenant on the node of that region holding the fewest tenants and copies — never a standby — has it follow the tenant's primary node, as a replica of its own does, and records it once it follows; 201 with the node, 200 where the region has one already, 502 where the node would not follow, the file it made there deleted again. One a region, and none in the tenant's own region (409: its standby and its replica are there), none in a region with no node (409). It is held to the tenant's quota, as the tenant's standby and replica are: sent it as it is placed, and each quota set after — handed at once to a sender of its node's by the directory setting it, the quota request answered once the directory records it, and within a look by a router keeping a read replica in another region's directory, which reads the quota with the tenant's placement. One sender a node, on a thread of its own: a node that does not answer holds up its own replicas' quotas alone, never a look or a quota request, and each replica is sent its quotas in the order they were set, an older one never after a newer. DELETE takes it out of the directory and, once the standby routers have been sent that, off its node; a node that does not take it off keeps it recorded (502) — a copy following its primary unrecorded would never be stopped — and DELETE ...?forget lets go of the record of a node gone for good. A node holding a read replica is not removed (409) until it is taken off. GET /_shard/tenants/<t>/read-replicas lists them, {tenant, read_replicas: [{region, node, follows}], failed, changing}, changing whether a change of one is under way. Every node shares --replication-token: the replica's node asks the primary's feed with its own. The record is kept by the directory that holds the replica's node — the global one, or the region's where it keeps its own — so that region's router places it, leases its node, routes to it, and goes on doing so cut off from the tenant's home. Asked of another router, the request is relayed there; the list is gathered from every directory by the global router, a region not reached named in failed.

Routing. A router stands in a region: --near ap, or the region whose directory it keeps (--region). Asked for a request marked Fenec-Read: replica of a tenant with a read replica in that region — and not living in it — it forwards the request to the replica; every other request goes where it went. A marked read the replica does not answer — its node not reached, or the request not written or answered by the wait its Fenec-After asks, a /_changes page's own wait for a write, and --replica-timeout past them (2 s); not caught up with its primary yet, or going down (503); still behind the position it was sent after at the end of the wait (504); its file gone from the node (a 404 with Fenec-Tenant: absent) — is sent home, so the client is answered either way and from nothing older than its write; and so is one whose answer breaks off before its end, the router reading a replica's answer whole before any of it goes to the client (a stream's goes on as it comes). A replica that did not answer is let be for 5 s, its reads going home at once meanwhile: the node's, every tenant's, where it was not reached or took no whole request. A tenant's copy that answered 504 could not reach the position in the wait it was given, and asked again at every read, a replica cut off from its primary held each one that long — every run of a live query reading near came the wait late for as long as the partition lasted: for 5 s the tenant's reads sent after a position, with no longer a wait, go home at once through that router, the trip home a region away in place of a wait. A read naming no position, which the copy answers as it stands, and one willing to wait longer still go to the copy, home out of reach or not. So a client holding a token of the tenant can send its positioned reads through that router home: a Fenec-After past the tenant's last change, with a wait of a second or more, once every 5 s — as a failover that lost writes does on its own, its clients' positions on the lost branch. What that costs is the trip home, never a wrong answer. Where it took one and did not answer in time, the tenant's copy is let be at once and the read goes home, while the router asks the node's /_health — answered before any token, lock or routing — on a connection of its own, within 500 ms (--replica-timeout where shorter), one question a node at a time. Answered, the copy alone is let be, since its answer comes once the query has run and a slow read is that read's, not the node's: no tenant's slow reads, nor several tenants', let the node be. Not answered, the node is too — it takes connections and answers nothing, stopped or deadlocked — and no other tenant waits it out. A node that answers its health while every query on it stalls — its disk stalled under the queries — costs each tenant with a copy there one timeout every 5 s for as long as that lasts. fenec_router_replica_reads_total counts marked reads by where they were answered: outcome="replica", "fallback", "home". Every server runs a marked request read-only on every route — a statement, REST, /batch, an MCP tool, a change-stream consumer's commit — home as much as a replica, so a write marked by mistake is refused with 403 the day it is written, never landed; a value the header does not take is 400. A tenant frozen for a move, or on a node whose lease has lapsed, answers a marked read, which can only read.

Read your writes. A write's answer carries Fenec-Seq, the change it left the tenant at, and Fenec-History, <term>-<id>: the history that change is of, which a failover forks where the copy promoted stood, one term more. A replica numbers the primary's changes as the primary did, and a read sent with Fenec-After: n and that Fenec-History is answered once the replica holds change n of that history, 5 s at most unless Fenec-Wait says. The history is what makes it hold across a failover: a write the old primary acknowledged and the promoted copy never got is lost, the new primary's next write takes its number, and a replica still on the old branch holds a change of that number — the lost one. It answers no read after the new write until it is pointed at the new primary and takes its image. A client reading near keeps the furthest position an answer from home named — a write's, a read-only /batch's; of a later term, or further in one, so an answer arriving late is not the last — and sends it with every marked read, whose own answers move nothing: it reads its own writes and every write before them, and another client's writes after its own may or may not be there yet. A marked /query read's answer names where the copy that answered it stood as it read (Fenec-Seq, Fenec-History), replica or home; the SDKs take nothing of it as the client's, since a replica may be behind home or on a branch a failover left, and a JavaScript live query sends its next run after it (below). A subscription and a /_changes page sent so wait for it as a read does, before their head, and go home on the replica's 504: a stream is seeded with the client's write, never from the copy as it stood behind it, and a page's Fenec-Seq is never behind it. Go's Read() and .NET's AsRead() copies send the position on a subscription and /_changes too, and take a stream's 504 as a read's. A marked stream open on a copy that refuses its primary — the tenant deleted and made again under its name — ends as the copy deletes itself, as the reads after it are sent home. A client that has written nothing reads the replica as it stands. Where the failover lost the client's last acknowledged write, no copy holds its position: home answers 504 at once, naming where it stands and of what history, the SDK takes that as the client's position — only over the position that read was sent after, so a write answered meanwhile is never set back, and never an earlier term of the same lineage, which only a fenced old primary names — and asks home once more with no mark. A history's lineage is the top half of its id: every fork of the tenant keeps it, and a tenant deleted and made again under its name, which starts again at term 1, has another — whose position the client takes, from a 504 or any answer from home, its term lower or not. A node from before lineages keeps none: a promotion or a restore it makes starts a fresh one, so while a deployment is upgraded node by node a router lagging a failover can again set a client back onto the old branch.

Failovers and moves. Every router looks once a second at where the primary of each tenant it keeps a read replica of is — its own directory, its copy of the global one, or, for a tenant of another region keeping its own directory, that region's router, asked once for all of its tenants — and re-points the ones that follow another address, on a worker a node the look waits for none of, each call to a node bounded by 10 s and no lock held across one, so a node that does not answer holds up its own replicas alone. A failover — by hand or on a lease — or a move it makes has that look come at once, on a thread of its own: the failover waits on no replica's node, which may be a region away or cut off. So a region keeping its own directory follows a failover in the tenant's home within about a second; a marked read sent after a position meanwhile waits on the replica, and goes home past the wait. The replica goes on from where it stood where the new primary's history passed through it, and is sent an image otherwise; either way it answers again once the new primary has said hello. Every 10 s, on a thread apart from the looks, each router asks each replica's node it keeps which tenants it holds, and makes again a copy gone — a node wiped, a file deleted by hand — which a marked read meanwhile finds absent and sends home; a node out of reach holds up that check alone, never a re-pointing. A tenant deleted takes its read replicas with it, at once in its own directory — a change of one under way waited out, 15 s at most and with no claim on the tenant held, so none is left when the delete answers, and one whose node does not take it off keeps the tenant (502), as DELETE .../read-replicas keeps a record — and at the next look in another; the name is not made again (409) while any directory keeps one of it, or is changing one: made again, the look would point the old copy at another owner's tenant, in a region nobody chose. A region keeping its own directory tells the global router as it places one, before any copy exists, and that it keeps none once the last is taken off; a create asks the regions so named for the name alone, all at once, each within 10 s, and one not reached — or answered by a router following the region's, which cannot see what the one it follows has under way — refuses that name (503) and no other. A name no region named asks none, so a region out of reach holds up no create anywhere else. For a region gone for good, DELETE /_shard/tenants/<t>/traces/<region> on the global router lets go of its trace, and the name is made again. That cannot copy the new tenant into the region: each read replica is bound to its tenant's lineage — the top half of its history's id, which a failover and a move keep and a tenant made again does not, recorded by the directory as the tenant's node makes it or takes its image in — and its copy is told it with every follow and keeps it across restarts. A copy whose primary turns out to be of another lineage takes nothing from it and deletes itself, file and .follows, so the deleted tenant's rows do not outlive it on the node either (fenec_copies_refused_total counts them); a look finding a replica's tenant of another lineage takes it off rather than point it anywhere. So does every other way a record outlives its tenant — ?forget of a node that comes back, a router lost between a follow and the record. A primary of another lineage than the directory's, on the node the directory places its tenant on, is the tenant: another file of it promoted by force, an older file restored, a file put in place by hand. (A copy of another lineage, such as a standby that never took its first image, is promoted only by force: its node refuses it, and the tenant stays where its rows are.) A failover records the lineage the promotion answers, and a read replica's copy lost has the primary's node asked which lineage it is of; the directory takes its word, keeping the lineage before as one the tenant was, and the read replicas bound to that one are bound to the new one rather than taken off. A copy lost three times in a row anyway is made again no more — "given_up": true in its list, counted in fenec_router_read_replicas_given_up — until its primary or lineage changes or it is placed again; its region's marked reads pass it by meanwhile, rather than each meet its node's 404 and go home. The router keeps that in memory alone: started again, it makes the copy again up to three times more, and a standby router knows nothing of it. A tenant made before lineages were kept has its lineage asked of its node at the next check, and each of its read replicas is bound to it where its copy's node says the copy holds its primary's history and is of it — taken off where the copy is another tenant's, asked again later where it has not caught up. Mixed versions protect less and break nothing: a node from before lineages ignores "lineage" in a follow and has no /_admin/tenants/<t>/lineage, and a router from before them ignores lineages — no copy refuses on their word, until every node and router runs a build that keeps them. A marked read goes to no read replica of a tenant no directory places. One moved into a region holding its read replica takes that replica off — the tenant's own copies are nearer still — a change of it under way waited out, and the replica held until the tenant is placed there, so no look's follow lands on the node it moved to.

A partition. The replica's region cut off from the tenant's home: writes from that region are answered 502, as a node out of reach is; a marked read naming no position is answered by the replica from the state it last applied — as old as the cut, and, cut off across a failover of home, on the branch the failover left — and one naming a position the replica does not hold waits, goes home, and is answered 502. Nothing is answered from before a write the client was told landed. Once healed, the replica's feed reconnects and it catches up. Reads that tolerate a bounded staleness — a replica answering while it is at most so far behind, without a write of the client's to wait for — are not offered.

SDKs. JavaScript connect(url, { reads: 'nearest' }) and { read: true } on run and batch (a batch of builder queries alone is marked on its own); Python Client(url, reads="nearest") and read=True; Go fenecdb.WithReadsNearest() and db.Read(); .NET ReadsNearest = true and db.AsRead(); Swift Fenec.connect(url:reads: .nearest), Kotlin Fenec.connect(url, reads = FenecRemote.Reads.NEAREST) and Dart Fenec.connect(url, reads: Reads.nearest), each with db.asRead() (Without a file). Each marks the builder's reads and the copy's requests alone, and keeps one position for every copy of the client it makes. A subscription opened through a Go Read() or a .NET AsRead() copy, and its /_changes reads, are marked and sent after that position too, and a server holds a stream for Fenec-After as it holds a read: the read replica seeds it once it has the client's own writes, and where it cannot in the wait its 504 sends the stream home, so no stream is seeded from behind them. JavaScript's live keeps its streams home, unmarked, and sends each of its runs near: after the furthest of the client's position and the one its streams named — a stream's head says where home stood as it opened, Fenec-Seq and Fenec-History, and each event's seq is a change of that history; a stream opened again after a failover names the later term, and never sets the position back. A run waits a second on the replica (Fenec-Wait: 1000), not five: the replica has a write once home's fsync covers it — 283 ms behind at most under --sync 250 — and a link later, so one later than that is behind, and home answers in a region's round trip; the router then lets the copy be, so a replica cut off from home costs one second every 5 s, not one every change. The second assumes that: a primary syncing its file every second or more slowly (--sync 1000 and up), or a link to the replica slower than about half a second, has a replica take a write past a run's second, and every run of a live query near it misses it — answered from home, fenec_router_replica_reads_total{outcome="fallback"} rising where "replica" does not, the rows a round trip home later, a second later once every 5 s: right, never stale, but slower than a client reading home (reads: 'home'), which such a deployment's live queries are better made with. The read replica answers a run once it holds the change that ran it and the router sends one it cannot hold home; each answer names where it read, and the next run goes after that too, so rows a run answered from home showed — a change whose event is still on its way — never go back. A 504 from home — the change lost in a failover — has the live query take home's position and the run asked near again after it, home unmarked if that fails too; answered home unmarked, the run names no position, so a run after it may again show rows from before it — only after a failover that lost writes, whose lost write the rows lose anyway. A stream whose head names no history — a server from before heads named one — has the runs go home until every stream's head names one again: its positions would pass none of the client's. The rows never come from before a change the streams told of, and the streams tell of every change home takes. Its polls ({ poll }) go home: sent after its tag's change, a replica would judge the tag as home does up to where it stands, but nothing in a poll names a change home took since, so a replica behind — or cut off from home — would answer 304 while home holds a write the query reads. Its subscribe streams go home. A synced replica's streams, in the browser and in the native libraries, go home; Python's client and the Swift, Kotlin and Dart remotes open none.

What it costs. A marked read through the router of the replica's region costs what one sent home does: 67.0 to 67.8 µs p50 against 66.2 to 66.9, three runs, with each node behind a loopback proxy standing for its link, and 67.6 to 68.3 with a Fenec-After the replica holds already (make shard-bench ARGS=reads, nodes and router in one process). A client's read of the write it was just answered took 368 to 379 µs p50 on the replica — its wait for the write included — against 341 to 342 at home, both right after a durable write: under --sync always the primary answers a write once its replicas' streams are sent it, and the replica's part is applying it. A request no client marks pays a header looked for: the router added 20.55 µs p50 to a request over the node's own against 20.7 for the code before read replicas, sixteen runs a side in ABBA turns, both writing the node's answer in one writev, which took the router from 23.6 µs (make shard-bench ARGS=latency). Between regions the read near saves the round trip to the tenant's home, every read.

Tokens

There are three tokens: one for data, one per node for the router, and one for managing the router. A user's JSON Web Token is bound to the tenant its tenant claim names:

fenec-server --dir /data/n1 --http 127.0.0.1:8081 --admin-token a1 \
         --jwt-secret-file jwt.secret --policy policy.txt
fenec-server --jwt-secret-file jwt.secret --mint-token '{"sub":"alice","tenant":"acme"}'
Details

Three, each for a different job. Data requests carry whatever the nodes' --http-token expects, and the router passes Authorization through untouched. Each node has its own --admin-token, which only the router holds. The router's --token guards /_shard/; like the nodes, it refuses to listen on a non-loopback address without one unless given --insecure.

With --jwt-secret or --jwt-keys a node also takes JSON Web Tokens held to its --policy, and the policy is the node's, not a tenant's: notes read,write where owner = $jwt.sub matches alice's rows in every tenant's file alike. So on a --dir node a token reaches /t/<t>/ only when its tenant claim names <t>, a text or a list holding it, and is refused with 403 elsewhere: on every route under the prefix, the statements, REST, /batch, a subscription, /_changes, /_schema and the statement counts. The check comes before the tenant is looked up, so a refused token learns nothing of which tenants exist. A token naming no tenant is refused on a --dir node unless it is started with --jwt-unbound-tenants, which takes such a token for every tenant it serves; --jwt-tenant-claim <name> reads another claim than tenant. The node's own --http-token and --admin-token are not bound. The router forwards Authorization as it came and holds no keys, so the node is what enforces it, behind the router or reached directly. What a scoped token writes to a tenant is checked against its rules as on a single file (Scoped access).

Every token is also read from the environment, which keeps it off a command line every user of the machine reads with ps: a node's from FENEC_HTTP_TOKEN, FENEC_ADMIN_TOKEN and FENEC_REPLICATION_TOKEN, a router's from FENEC_SHARD_TOKEN, FENEC_SHARD_REPLICATION_TOKEN and FENEC_SHARD_ENTRY_TOKEN, an archiver's from FENEC_REPLICATION_TOKEN. A variable set and empty, as an environment file leaves a line it does not use, is no token; a token given empty as a flag is refused at the start. A request carrying no Authorization reads as the empty token, so an empty FENEC_SHARD_TOKEN, taken for one, let anyone into /_shard/ -- and past the check that keeps a router with no token off a public address. The kit's systemd units hand every one over from an environment file (Deploying it).

Deploying it

The repository's deploy/ is a kit for running all of the above on machines of your own: systemd units, their environment files, alert rules, and the operator's runbook. make drill breaks a deployment of two regions on purpose, in Docker, and holds it to losing no acknowledged write.

make deploy-check   # the units under a real systemd, the alert rules under promtool
make drill          # two regions: a node killed and back, a router killed, the global router cut off, a restore
  • A unit for each part: a tenant node, a region's router and its standby, the global router and its standby, a node's archiver and its copy to a bucket (rclone), and the Cloudflare Tunnel the global entry reaches a router through. Each runs sandboxed as its role's user -- a node, the routers, the archiver and the bucket copy each their own, so none reads another's tokens -- its tokens in an environment file only root reads. The tunnel lets a tenant's paths alone through, and Cloudflare Access with a service token the entry holds says who; the entry passes no cookie Access sets on to its clients, and the routers no Access header on to a node. The bucket copy refuses a new disk's first copy over the bucket's archive.
  • Alerts for Prometheus and for Grafana: nodes and routers down, a region's primary router told from a standby, failovers and late leases, tenants without a replica, copies in their primary's zone, read replicas given up, connections near their ceiling, the bucket copy gone stale or unreadable by node_exporter, quota refusals, the entry's marks not believed, refusals and errors.
  • The drill's figures, lease 2 s, three runs on one laptop -- what they saw, not bounds: a node cut off the network and killed, as a machine lost, was failed over 1.9 to 2.6 s after the kill, the other tenants of its region never more than 18 ms between two answered writes, none of 41 577 acknowledged writes was lost, and a tenant restored from its node's archive held exactly the rows acknowledged by the moment it was restored to.
Details

make deploy-check boots systemd in two privileged containers, installs every unit and environment file as the runbook installs them, and runs them: systemd-analyze verify on each, a region, two nodes and a tenant made through the global router, rows written through the router and its standby, no token on any process's command line or in an environment another role's user can read, the limits and the sandbox in force (systemd-analyze security puts each unit at 1.2), a node's stop syncing within its timeout, a sealed archive verified with the key the unit hands its archiver and copied to a bucket by real rclone while its tenant is written, a real node_exporter scraped for the copy's success, a new disk's archive refused over the bucket's and copied once the bucket is copied back, and a standby router promoted and its unit switched as the runbook does it. cloudflared's own matcher is asked where the tunnel sends 28 paths, every spelling of a tenant's replication stream among them. promtool checks the alert rules and runs their tests, and a test of fenec-shard holds every metric and label value they read to a real scrape of every kind of process.

make drill runs each process in a container of its own on one Docker network -- two regions, each a router keeping its own directory and that router's standby, two nodes in two zones under --lease and --replicas, an archiver for each node, and the global router and its standby -- every token in the processes' environments and no port fixed. A writer a tenant puts rows by id, the next only once the one before was answered, while the drill cuts the global routers off the network (each region writes on), cuts the node holding the most primaries off the network and kills it, as a machine lost, and starts it again, kills a region's router and promotes its standby as an operator would, and marks a moment it later restores a tenant to from its node's archive. Then every acknowledged write is read back from each tenant's primary and its replica, and the times are printed. The router fails a killed node over a lease and a tenth after its last renewal and the promotions after: 1.92, 2.56 and 1.90 s after the kill in three runs at a lease of 2 s. Its tenants' writers write again once the request each had in flight to the dead node is let go of, at the router's upstream timeout -- 4 s in the drill, twice its lease, as the kit's routers run at twice theirs: 3.90, 3.97 and 3.93 s. The tenants whose replica it held went 17, 18 and 17 ms between two answered writes at most, the rest 16, 18 and 17; a reviewer's runs on another machine saw 28-30 ms, so these are what three runs saw, not bounds. The runbook says what each alert means, the order to bring a deployment up in, how to rotate each token and upgrade with no downtime, and what is not measured yet.
