fenecdb and SQLite

SQLite is an embedded SQL database in one file; FTS5 adds full-text search to it and sqlite-vec vector search. fenecdb is an embedded document database, which also runs as a server over HTTP, with full-text and vector search built in.

The facts about SQLite, sqlite-vec and FTS5 on this page were checked on 2026-10-02 against the pages each one links to. fenecdb is at version {{version}}, and is alpha software.

Which to choose

Choose SQLite when

  • You want the database that is already everywhere: SQLite is "likely used more than all other database engines combined" (sqlite.org), with bindings, ORMs and tools in every language.
  • You want SQL with joins, and transactions you hold open across statements, with savepoints (transactions).
  • Readers must never wait for the writer: in WAL mode they do not (WAL).
  • You need a long track record: 100% branch coverage in its tests (testing), and an on-disk format kept backwards compatible, supported through 2050 (long-term support).
  • Exact vector search over a modest table is enough, through sqlite-vec.

Choose fenecdb when

  • The page or app should stay in step with a server: a replica with live queries and offline writes (Sync).
  • The same file should also be served to other languages over HTTP, with replicas (Server).
  • Many threads write at once: durable writes share their disk syncs, 516 a second from 16 writers against SQLite's 258, and readers keep reading beside them (measured below).
  • A search box needs typos and facets in the query that ranks the words (Typos and words begun, Facets).
  • You want an approximate vector index: HNSW with quantization and filtered search (The vector clause). sqlite-vec's approximate indexes are in its alpha releases.
  • You search by meaning and by words in one query, fused by rank (Hybrid search).

Where the two differ in storage, search and vectors

Of the official build's browser storage, opfs-sahpool needs no COOP/COEP headers but "does not support multiple simultaneous connections to the same database" (persistence). fenecdb's openFile also holds its file for one worker; other tabs reach it through the one that holds it, or share a synced replica (Multiple tabs).

FTS5's bm25() has its constants fixed at k1 = 1.2 and b = 0.75 (FTS5). fenecdb's @text also splits Chinese, Japanese, Korean and Thai text into character runs and can index word prefixes (The text clause).

sqlite-vec's first stable release, v0.1.0, searched by brute force (announcement). Its ANN indexes arrived in v0.1.10-alpha.1 on 2026-03-31: rescore and DiskANN, with IVF "experimental, not enabled"; the latest is v0.1.10-alpha.4, from 2026-05-18 (releases).

  • fenecdb writes a record again at its file's end on every update, where SQLite updates its page in place; the file compacts itself once half of it is dead, beside the reads. Before it did, C at one thread read 30.1 k after the updates, where SQLite read 279 k.
  • SQLite opens faster, and its readers never wait for a block of writes. fenecdb's wait only while one lands: its rows are built and encoded beside them first, and the block holds the lock about 0.15 ms for 1 000 rows.
  • Not measured yet: sqlite-vec, by brute force or with its alpha indexes; FTS5; and either in the browser.
Method, and the YCSB, concurrency and vector-comparison runs

The numbers are make ycsb's, make concurrency-bench's and make compare's, as Everyday reads and writes, Writers and readers at once and Against SQLite and pgvector report them, on an Apple M-series laptop.

make ycsb
make concurrency-bench
make compare
  • YCSB: SQLite 3.53 through rusqlite, a connection a thread, WAL, the file mapped; durable is synchronous=FULL with fullfsync, buffered its default synchronous=NORMAL. Each cell 30 s after a 5 s warm-up.
  • The 100 000 rows: SQLite 3.53, in WAL mode with synchronous=NORMAL, the rows written in one transaction and the index built afterwards; the median of three runs.
  • SQLite had no vector index. Its exact search reads every row and scores it with the same kernel fenecdb uses, so the difference is in reading the rows, not in the arithmetic.
  • Writers and readers ran in one process, after idle minutes, once: fenecdb's threads share one database behind a lock, SQLite's hold a connection each with a 30 s busy timeout. Durable is an fsync a commit, F_FULLFSYNC for both.

Moving from SQLite

fenec import reads a SQLite file directly, with no SQLite library installed, and makes a collection of a table.

fenec import data.sqlite --table docs --into articles \
    --vector embed:384 --index "embed@hnsw(cosine)" --dry-run
  • --dry-run prints the schema it would make and writes nothing.
  • Vectors stored as BLOBs of little-endian f32s become vector<N> with --vector.
  • INTEGER PRIMARY KEY becomes the document id.

A query in each, and then a search by meaning and its filter:

SELECT title FROM articles
WHERE year >= 2024
ORDER BY published DESC
LIMIT 10;

get articles select title
  where year >= 2024
  order published desc
  limit 10

-- sqlite-vec, year a metadata column of the vec0 table
SELECT rowid, distance FROM vec_articles
WHERE embed MATCH ?1 AND k = 10 AND year >= 2024;

get articles select title
  where year >= 2024
  near embed $1
  limit 10
What carries over from SQLite

The import reads the file format itself, and resolves untyped columns from the first 1 000 rows. A table with no equivalent type is refused until --cast says what to do (Type mapping). A join becomes lookup or in (get …) (The lookup clause), and a transaction becomes a batch that lands whole (Batches).
