Documentation

fenecdb is an embedded document database small enough to run inside a browser tab. It also keeps an app's file on a phone and serves any language over HTTP, a file per tenant; search is built in.

Try it now. The Playground runs the engine in this tab -- nothing to install. To put it to work, the Quickstart installs a release and runs a first query in a few commands.

What it is

Your documents live in one file, indexed as you declare, and you query them with one language, FenecQL — in the page, in an app, from Rust, or over HTTP from a server. A screen's live query runs again when a write changes what it reads, a replica on the device syncs with the server, and the server takes many clients' writes into the one file through one writer, their disk syncs shared, and many tenants into a file each.

create collection articles (
  title     text  @text,
  tags      [text],
  year      int   @hash,
  published timestamp @sorted
)

get articles select title
  where year >= 2024 and tags has "rust"
  order published desc
  limit 10

get articles select title, highlight(title)
  match title $1 fuzzy
  limit 10
Details

fenecdb keeps its documents in one file and indexes them — hash, unique, ordered, text, points and vectors. The indexes are held in memory and built from the documents, the first time a query reads each, and a vector graph is saved in the file too, so an open need not build it again. It answers queries from inside a browser tab, in an app, or from a server any language reaches over HTTP.

Everything in these docs describes the engine as it is built today. Where something costs you a capability, that cost is stated next to the feature rather than at the bottom of the page.

One file. Records are appended to immutable 8 MiB segments and the byte sequence on disk is the byte sequence in memory, so a read decodes directly over the arena. A HashMap<DocId, Loc> offset index is the only helper structure in the whole store.

Search is not bolted on. @text is an index and match a query clause, ranked by BM25, with fuzzy, highlight() and facet beside it; for search by meaning, vector<N> is a type, @hnsw an index and near a clause. The planner knows them all, so a filter and a search are planned together rather than stacked on each other.

What it gave up

Staying small meant leaving some things out on purpose. The main ones:

  • One writer. Many readers, but one write or batch at a time.
  • No SQL dialect, and a join only on a key. Every client speaks FenecQL, over HTTP or in process; it reads SQL's everyday spellings as the statements they mean, a JOIN on an indexed key among them (From SQL).
  • No decimals. Store money as cents.
Details

The list is short, and it is made of consequences of the design rather than a roadmap.

  • One writer, no MVCC. A write, or a /batch of them, holds the write lock for as long as it runs and lands whole or not at all; readers read beside it. There are no interactive transactions held open across requests.
  • A join only on a key. A query reads one collection, plus the children lookup attaches to each of its rows — and, chained, the children of those — and filters by another's rows only through an uncorrelated in (get …). SQL's JOIN on an indexed key reads as one of those, answered flat; a join of any other condition is none.
  • No SQL dialect. FenecQL is the one language, in the page, in Rust and over HTTP. It reads CREATE TABLE, INSERT … VALUES, UPDATE … SET, JOIN, IN (…), EXISTS, BETWEEN, LIKE and ON CONFLICT as the statements they mean and refuses the rest saying what to write; there is no wire protocol for SQL drivers, and no ORM speaks it.
  • No multi-writer replication, and no change of a field's type in place: it would rewrite every document under the write lock.
  • No decimal type. float is binary floating point and unfit for money; the answer is an int in cents.
  • Objects only in a json field. A typed field refuses one and a list holds one type; a json field holds any value JSON does, and a path reads into it.
