Mobile and native apps

Keep the database in a file on the device: no server, no network, the same engine and file format as the server and the browser.

An iOS, macOS, Android or Flutter app opens a fenecdb file, writes to it and asks it questions in FenecQL or through the query builder, with near, match and lookup as anywhere else. A live query hands the UI its rows again after every write to what it reads.

Details

Each binding calls the same native library, crates/fenec-ffi: the engine built for the device, behind a C ABI of a few functions -- open, query, the change notice, sync, flush, checkpoint, close. A statement goes in as text with its parameters as JSON, and its answer comes back as the JSON the browser module answers with, from the same code (fenec-abi), so a page and an app handed the same text get the same bytes. A vector goes in as its f32 bytes beside the JSON, never as digits. Syncing an app's file with a server is not here yet; reaching a server from an app is plain HTTP meanwhile (Your language).

A todo list

The file in the app's own directory, a collection made once, a list on screen that is a live query, and writes from the buttons. The list redraws itself: nothing calls it after a write.

import FenecDB
import SwiftUI

struct Todo: Codable, Sendable, FenecValue {
    var id: Int?
    var title: String
    var done: Bool
}

@main struct TodosApp: App {
    @State var db: Fenec?

    var body: some Scene {
        WindowGroup {
            if let db { TodoList(db: db) } else { ProgressView().task { db = try? await open() } }
        }
    }

    func open() async throws -> Fenec {
        let dir = try FileManager.default.url(for: .applicationSupportDirectory, in: .userDomainMask,
                                              appropriateFor: nil, create: true)
        let db = try await Fenec.open(dir.appendingPathComponent("todos.fenec"))
        try await db.execute("create collection if not exists todos (title text, done bool @hash)")
        return db
    }
}

struct TodoList: View {
    let db: Fenec
    @StateObject var open: LiveQuery<Todo>

    init(db: Fenec) {
        self.db = db
        _open = StateObject(wrappedValue: LiveQuery(db, try! db.from("todos").where("done", false), as: Todo.self))
    }

    var body: some View {
        List(open.rows, id: \.id) { todo in
            Button(todo.title) {
                Task { try await db.from("todos").where("id", todo.id!).update(["done": true] as Value) }
            }
        }
        .toolbar {
            Button("Add") { Task { try await db.from("todos").insert(Todo(title: "milk", done: false)) } }
        }
    }
}

On iOS 17 and macOS 14, LiveRows is the same as an @Observable, held in @State.

import io.github.fenecdb.*

class TodosModel(app: Application) : AndroidViewModel(app) {
    val db = Fenec.open(File(app.filesDir, "todos.fenec").path)   // in a background start-up, or openAsync

    init {
        db.executeBlocking("create collection if not exists todos (title text, done bool @hash)")
    }

    val open: Flow<List<Row>> = db.live(db.from("todos").where("done", false))

    fun add(title: String) = viewModelScope.launch { db.from("todos").insert(mapOf("title" to title, "done" to false)) }

    fun finish(id: Long) = viewModelScope.launch { db.from("todos").where("id", id).update(mapOf("done" to true)) }

    override fun onCleared() = db.close()
}

@Composable
fun Todos(model: TodosModel) {
    val open by model.open.collectAsState(emptyList())
    LazyColumn {
        items(open) { todo -> Text(todo.string("title") ?: "", Modifier.clickable { model.finish(todo.long("id")!!) }) }
    }
    Button(onClick = { model.add("milk") }) { Text("Add") }
}

A live query is a conflated Flow: a collector that falls behind sees the latest rows.

import 'package:fenecdb_flutter/fenecdb_flutter.dart';
import 'package:flutter/material.dart';
import 'package:path_provider/path_provider.dart';

Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  final dir = await getApplicationSupportDirectory();
  final db = await Fenec.open('${dir.path}/todos.fenec');
  await db.execute('create collection if not exists todos (title text, done bool @hash)');
  runApp(MaterialApp(home: Todos(db)));
}

class Todos extends StatelessWidget {
  final Fenec db;
  const Todos(this.db, {super.key});

  @override
  Widget build(BuildContext context) => Scaffold(
        body: StreamBuilder(
          stream: db.live(db.from('todos').where('done', false)),
          builder: (context, snap) => ListView(children: [
            for (final todo in snap.data ?? const <Map<String, Object?>>[])
              ListTile(
                title: Text(todo['title'] as String),
                onTap: () => db.from('todos').where('id', todo['id']).update({'done': true}),
              ),
          ]),
        ),
        floatingActionButton: FloatingActionButton(
          onPressed: () => db.from('todos').insert({'title': 'milk', 'done': false}),
          child: const Icon(Icons.add),
        ),
      );
}

The builder

The same query builder as JavaScript, Python, Go and .NET: from, select, where with every operator, near, match, fuse, rerank, lookup, order, limit, and the writes, each value a parameter and each name checked. All seven make the same text of the same chain, to the byte, held to one golden file; each language's spelling is on Your language. A builder query also knows the collections it reads, which is what a live query runs again for.

let near = try await db.from("notes")
    .select("title")
    .where("lang", "en")
    .near("embed", embedding, ef: 64)   // a [Float]
    .limit(5)
    .rows(as: Note.self)

Live queries

A live query hands over its rows at once, and again after a write to a collection it reads. The writes of a burst -- several at once, a loop, a text of several statements -- run it once, a frame after the last of them lands. A write to another collection runs nothing, and a text that fails is put back whole and runs nothing either.

Details

The engine keeps a ring of the writes it landed, and fenec_changes(since) names the collections written since a cursor -- or answers "everything" when the cursor fell behind the ring or a collection written since was dropped. A write asks for a look; the looks asked for within a frame (16 ms) are one, taken once no write through the database is under way, and each query that reads a collection named runs again from scratch -- well under a millisecond over a local file, where keeping track of which rows changed would cost more than the query. Knowing costs a write nothing: the ring is asked once after a burst, and only by a database holding a live query. It is how the browser's Fenec.live works, with a frame in place of a microtask: an app's writes run on other threads and come back one at a time.

A builder query reads its own collection and each lookup's; a FenecQL text names its collections, or runs after every write.

Where the file lives

Anywhere the app may write. On iOS the app's Application Support directory, which is backed up and never shown in the Files app; on Android context.filesDir, or noBackupFilesDir to keep it out of a backup; in Flutter path_provider's getApplicationSupportDirectory(). Beside the file the library keeps <name>.lock while it is open.

  • Open a file once. A second open of the same file, in the app or in another process -- an app extension sharing the app group's container -- is refused (locked): two databases over one file corrupt it.
  • iOS file protection. A file under the complete protection class cannot be read while the device is locked, and a page of a mapped file read then is the app's end, not an error. Keep the default class (complete until first user authentication), or open the file with .inMemory.
Details

The file is mapped, as a server maps its own: the documents stay in it and the app holds only what it derived from them, the indexes and the graph. The mapping takes address space past the file's end -- a gigabyte at least -- for the writes to grow into; where the system refuses that much, as an iOS app's address space may, the file alone is mapped and mapped again as it grows. A 32-bit Android device (armeabi-v7a) reads the file into memory. The lock is a file of its own, held with flock: a checkpoint renames a new file over the database, which a lock on the database itself would not survive.

Durability

Every write is on disk before the call returns: written and fsynced, outside the database's lock, so reads go on meanwhile and writes arriving together share one fsync. On a Mac that fsync is about 4 ms. For a burst of writes, open the file without it and sync when they are done:

A phone ends an app in the background without a word, so an app opened with noSync calls flush() or sync() as it goes there -- scenePhase turning to .background, onStop, AppLifecycleState.paused.

Details

A write the disk refuses stops the database's writes, as on a server: every later write and sync is refused with io until the file is opened again, and reads go on. The vectors a database holds are linked into its graph as they are written; the open links those written since the graph was last saved. close() saves a graph once the file has grown three times the graph's record since its last save, so an app that opens and closes often does not grow its file by a graph each time; checkpoint() saves everything, and an open after it links nothing.

Threads

One database is safe to use from every thread, task or coroutine at once: a read runs beside other reads, a write takes the database to itself, and a lone create index or compact is built beside the database while reads and writes go on. Every binding makes its calls off the main thread, since any of them may wait -- for the lock, an fsync, a whole open.

The C ABI

Any language with a C FFI can call the library: the header is crates/fenec-ffi/include/fenec.h, and make ffi builds the library for this machine, or TARGET=... for another. Every call returns a code -- 0, an error's kind, or the boundary's own: FENEC_MISUSE, FENEC_LOCKED, FENEC_PANIC -- and writes its answer or its error as NUL-terminated JSON, freed with fenec_free_string.

Details

A handle is a number, not a pointer: a handle used after its close finds nothing and is refused, where a pointer would reach freed memory, and a call holds its database for as long as it runs whatever closes meanwhile. A panic never crosses the boundary: each call runs under catch_unwind and answers FENEC_PANIC with its message, which is why the library is built to unwind, not to abort. The Kotlin binding reaches the same calls through JNI functions the library carries itself (its jni feature): each call answers one byte[], its code then its JSON, and text goes in as UTF-8 bytes, since JNI's own strings write an emoji as two halves.
