Files with S3 and R2

Keep the bytes in an object store and the facts about them in a collection. A policy says who may have a link; the link itself comes from the store.

A file is two things. The bytes are what an object store (Amazon S3, Cloudflare R2, anything that speaks the S3 API) keeps cheaply and serves from a CDN. The facts are whose it is, how big, what type, whether the upload finished, and those are rows. fenecdb keeps the rows. The app's backend, which can be a Worker, makes the links, and makes one only after fenec-server has said that this person may.

Why the bytes stay out of the database file

A text field can hold a megabyte, and a request can carry up to 64 MiB. A file full of them is the wrong place, for reasons that belong to the file:

  • The file only grows until it is compacted. Records are appended; a document that is replaced or deleted leaves its old bytes behind. 200 puts of 1 MiB into a server started with --auto-compact off made a file of 200 MiB; deleting a hundred of them left it 200 MiB; compact brought it to 100 MiB (104 858 600 bytes reclaimed). By default the server compacts a file itself once half of it is dead and it is 64 MB, and each compaction copies every live byte, so its cost follows the bytes you keep (Compaction); fenec-server --help says compact peaks at about 3x the file in memory.
  • The file is mapped and lives in the page cache. A 40 MB photo sits beside the rows that are read a thousand times a second, and the operating system has room for fewer of those.
  • Every byte is replicated, archived and fed. A replica follows the writes, an archive keeps them, and /_changes hands them to consumers from a buffer of 64 MiB by default: a few uploads, and a consumer a moment behind is answered 410 and starts over.
  • Requests have a ceiling. A body is at most 64 MiB, and chunked uploads are refused (Limits).
  • The store is built for it. Ranges, multipart uploads, lifecycle rules, a CDN in front, a price a gigabyte.

A bytes field is for what is small and belongs with the row, a thumbnail's worth or a hash.

The shape

  1. Add. The client asks the backend for an upload, sending its own token. The backend inserts the row, pending, as that person: the policy decides whether they may, pins owner to their sub and caps size. Only then does it make a presigned PUT URL for the key files/<id>.
  2. Upload. The client sends the bytes to the store with that URL. They never pass the backend.
  3. Done. The client tells the backend. It reads the row as the person, asks the store for the object's size, and, if it is the size announced, moves the row to ready with a token of its own.
  4. Download. The backend reads the row as the person, and if it is theirs and ready, makes a presigned GET URL.
  5. Delete. The person deletes the row, by the backend or with their own token from a page. A consumer of the change stream sees the deletion and deletes the object.

The backend holds no JWT library and checks no token itself. It passes the Authorization header on, and fenec-server verifies it (Auth with your identity provider). The policy is the whole of who may do what:

# collection  access                  rows                                          role

# A person lists, reads and deletes their own files' metadata ...
files         read,delete             where owner = $jwt.sub

# ... and adds a file of up to 10 MiB, pending: only the backend, once the
# object is in the bucket, marks it ready.
files         insert                  where owner = $jwt.sub and state = "pending" and size > 0 and size <= 10485760

# ... and renames it.
files         update(name)            where owner = $jwt.sub

# The backend's own token: reads rows to check, and moves a pending one to
# ready -- a transition, because one filter asked of the row before and after
# would refuse the move it grants (`new.` is the row as the write leaves it).
files         read                                                                  for app
files         update(state)           where state = "pending" and new.state = "ready"   for app
  • A person adds what is theirs and pending, up to 10 MiB. The insert rule is checked against the document written, so a client that sends state: "ready" or a size of 20 MiB straight to the database with its own token is refused (403). The backend does not have to remember to check.
  • Only the backend moves a file to ready, and only from pending. A rule that names new. is a transition: a plain where state = "pending" would refuse the very write it grants, because the row after it is not pending. (Transitions.)
  • The key is the id, files/<id>, not the name a person typed. The change stream names a deleted row by its id alone, and a key made from it needs no lookup to delete. The name is a column, and Content-Disposition carries it on download.

The backend

The calls are the AWS SDK's, the same for S3 and for R2. Two settings matter, shown after the code.

files-backend.mjs 
// Files in an object store (S3, R2 or anything that speaks S3), their metadata
// in fenecdb: the app's small backend, docs/files. It holds no JWT library and
// checks no token itself. Each request's `Authorization` goes to fenec-server
// as it came, and the server's rules (files-policy.txt) say whether this
// person may add a file, see it or delete it; a presigned URL is made only
// after the server has said yes.
//
//   POST   /files          {name, type, size}  a row, pending, and a URL to PUT the bytes to
//   POST   /files/:id/done                     the bytes are there: the row is ready
//   GET    /files                              the person's files
//   GET    /files/:id                          a URL to GET the bytes from
//   DELETE /files/:id                          the row; the bucket's copy goes with it (blobs.mjs)
//
// The object's key is `files/<id>`, never the name a person gave it: the
// stream of changes names a deleted row by its id alone.
import { createServer } from 'node:http';
import { GetObjectCommand, HeadObjectCommand, PutObjectCommand, S3Client } from '@aws-sdk/client-s3';
import { getSignedUrl } from '@aws-sdk/s3-request-presigner';
import { connect } from '@fenecdb/web/client';

export const keyOf = (id) => `files/${id}`;

export function s3From(env) {
  return new S3Client({
    region: env.S3_REGION ?? 'auto', // R2 wants "auto"; S3 proper, the bucket's region
    endpoint: env.S3_ENDPOINT, // https://<account>.r2.cloudflarestorage.com for R2
    forcePathStyle: env.S3_PATH_STYLE === '1', // a local server has no bucket.localhost
    credentials: { accessKeyId: env.S3_KEY, secretAccessKey: env.S3_SECRET },
    // Since 3.729 the SDK adds a CRC32 of the body to a request it signs. A
    // presigned PUT is signed before there is a body, so the checksum is the
    // empty body's, and the bucket answers 400 BadDigest to the bytes that
    // follow (seen on SeaweedFS; R2's docs ask for these two settings too).
    requestChecksumCalculation: 'WHEN_REQUIRED',
    responseChecksumValidation: 'WHEN_REQUIRED',
  });
}

export function backend({ fenec, appToken, s3, bucket, expiresIn = 300 }) {
  const as = (token) => connect(fenec, { token });
  const app = as(appToken);

  const bearer = (req) => (req.headers.authorization ?? '').replace(/^Bearer /, '');

  return createServer(async (req, res) => {
    const reply = (status, body) => {
      res.writeHead(status, { 'content-type': 'application/json' });
      res.end(body === undefined ? undefined : JSON.stringify(body));
    };
    try {
      const token = bearer(req);
      if (!token) return reply(401, { error: 'no token' });
      const me = as(token); // fenec-server verifies it, and holds every query to its rules
      const [, route, id, verb] = new URL(req.url, 'http://x').pathname.split('/');
      if (route !== 'files') return reply(404, { error: 'not found' });
      const body = ['POST', 'PUT'].includes(req.method) ? JSON.parse((await text(req)) || '{}') : {};

      if (req.method === 'POST' && !id) {
        const { name, type, size } = body;
        // The row first: if the rules refuse this person, no URL is made.
        const [file] = await me.from('files').insert(
          { name, type, size, state: 'pending', created: new Date() },
          { returning: true },
        );
        const url = await getSignedUrl(
          s3,
          new PutObjectCommand({ Bucket: bucket, Key: keyOf(file.id), ContentType: type, ContentLength: size }),
          { expiresIn, signableHeaders: new Set(['content-type', 'content-length']) },
        );
        return reply(201, { id: file.id, url, headers: { 'content-type': type } });
      }

      if (req.method === 'POST' && verb === 'done') {
        const file = await me.from('files').where('id', Number(id)).first(); // a row this person may read
        if (!file) return reply(404, { error: 'no such file' });
        let held;
        try {
          held = await s3.send(new HeadObjectCommand({ Bucket: bucket, Key: keyOf(file.id) }));
        } catch {
          return reply(409, { error: 'the bytes are not in the bucket yet' });
        }
        if (held.ContentLength !== file.size) {
          await me.from('files').where('id', file.id).delete(); // blobs.mjs removes the object
          return reply(422, { error: `the object is ${held.ContentLength} bytes, not the ${file.size} announced` });
        }
        await app.from('files').where('id', file.id).update({ state: 'ready' }, { require: 1 });
        return reply(200, { id: file.id, state: 'ready' });
      }

      if (req.method === 'GET' && !id) {
        const rows = await me.from('files').select('id', 'name', 'type', 'size', 'state')
          .order('created', 'desc').limit(100).rows();
        return reply(200, rows);
      }

      if (req.method === 'GET') {
        const file = await me.from('files').where('id', Number(id)).first();
        if (!file) return reply(404, { error: 'no such file' }); // not found, whether it is another's or nobody's
        if (file.state !== 'ready') return reply(409, { error: 'not uploaded yet' });
        const url = await getSignedUrl(
          s3,
          new GetObjectCommand({
            Bucket: bucket,
            Key: keyOf(file.id),
            ResponseContentType: file.type,
            ResponseContentDisposition: `attachment; filename="${encodeURIComponent(file.name)}"`,
          }),
          { expiresIn },
        );
        return reply(200, { url, name: file.name, type: file.type, size: file.size });
      }

      if (req.method === 'DELETE') {
        await me.from('files').where('id', Number(id)).delete({ require: 1 });
        return reply(204);
      }
      return reply(405, { error: 'not a route' });
    } catch (e) {
      // 412: `require 1` found no row of this person's. The server's own
      // refusals (401, 403) are passed on as they came.
      if (e.status === 412) return reply(404, { error: 'no such file' });
      return reply(e.status ?? 500, { error: e.message });
    }
  });
}

const text = async (req) => {
  let s = '';
  for await (const chunk of req) s += chunk;
  return s;
};

if (import.meta.url === `file://${process.argv[1]}`) {
  const env = process.env;
  const server = backend({
    fenec: env.FENEC_URL,
    appToken: env.APP_TOKEN,
    s3: s3From(env),
    bucket: env.BUCKET,
  });
  server.listen(Number(env.PORT ?? 0), '127.0.0.1', () =>
    console.log(`files backend on http://127.0.0.1:${server.address().port}`));
}
  • R2 or S3 is the client's configuration. For R2: endpoint: https://<ACCOUNT_ID>.r2.cloudflarestorage.com and region: 'auto', which is all R2 asks of the SDK (R2's presigned URLs). For S3 the bucket's region and no endpoint.
  • A presigned URL is a bearer token. Anyone holding it can do what it signs until it expires, which is why the backend asks the database first and keeps the lifetime short (300 seconds here; S3 allows up to 7 days with an IAM user's credentials, and R2 from 1 second to 7 days). The key is no secret, and nothing here relies on it being one.
  • R2 signs GET, HEAD, PUT and DELETE, not a POST form, and only on the S3 domain, not on a custom domain (R2's docs). A browser that uploads straight to the bucket needs CORS rules on it for the page's origin.
  • Recent SDK versions checksum the request they sign. A presigned PUT is signed before there is a body, so the checksum is the empty body's, and the store answers the real bytes 400 BadDigest. requestChecksumCalculation: 'WHEN_REQUIRED' (and the response one beside it) turns that off; R2's documentation asks for the same. It was seen here, on the store below.

The object goes with its row

The store is not part of fenec-server's write, so a deleted row could leave its object behind if the delete ran in the backend and the backend died after it. A consumer of the change stream closes that. It runs beside the server (--cdc), reads every write once it is on disk, and deletes the object of each deleted row, whoever deleted it: the backend, a page's own token, the sweep of pending uploads.

// The bucket follows the table, docs/files: a consumer of the change stream
// (`fenec-server --cdc`) that deletes an object once its row is gone, whoever
// deleted the row -- the backend, a person's own token from a page, the sweep
// of pending uploads. The server keeps the consumer's place, so a restart
// carries on where it stopped; a crash between the delete and the commit
// deletes again, which an object store answers as it answered the first time.
//
//   FENEC_URL=... ADMIN_TOKEN=... S3_ENDPOINT=... S3_KEY=... S3_SECRET=... BUCKET=... node blobs.mjs
//
// /_changes takes the server's own token and no scoped one: it carries every
// row of every person, documents and all.
import { DeleteObjectCommand } from '@aws-sdk/client-s3';
import { keyOf, s3From } from './files-backend.mjs';

export async function follow({ fenec, adminToken, s3, bucket, name = 'blobs', wait = 10_000, signal }) {
  const headers = { authorization: `Bearer ${adminToken}`, 'content-type': 'application/json' };
  // Made once; asking again answers that it exists.
  await fetch(`${fenec}/_changes/consumers/${name}`, { method: 'POST', headers });
  let deleted = 0;
  while (!signal?.aborted) {
    const page = await fetch(`${fenec}/_changes?consumer=${name}&wait=${wait}`, { headers, signal }).catch(() => null);
    if (!page) break;
    if (!page.ok) throw new Error(`/_changes: ${page.status} ${await page.text()}`);
    const next = Number(page.headers.get('fenec-next'));
    for (const line of (await page.text()).split('\n').filter(Boolean)) {
      const change = JSON.parse(line);
      if (change.collection === 'files' && change.op === 'del') {
        await s3.send(new DeleteObjectCommand({ Bucket: bucket, Key: keyOf(change.id) }));
        deleted += 1;
        console.log(`blobs: row ${change.id} deleted, so object ${keyOf(change.id)} too`);
      }
    }
    // Only now: the consumer's place moves once everything it read is done.
    await fetch(`${fenec}/_changes/consumers/${name}`, { method: 'POST', headers, body: JSON.stringify({ since: next }) });
  }
  return deleted;
}

if (import.meta.url === `file://${process.argv[1]}`) {
  const env = process.env;
  await follow({ fenec: env.FENEC_URL, adminToken: env.ADMIN_TOKEN, s3: s3From(env), bucket: env.BUCKET });
}
  • At least once, and deleting twice is fine. The server keeps the consumer's place; a crash between the delete and the commit repeats it, and a store answers the second delete as the first. A consumer is the server's token alone: /_changes carries every row of every person, so a scoped token is refused (Change data capture, Consumers).
  • A queue job is the other way. When a key cannot be made from the id, write the job in the same /batch as the delete: del files where id = $1 require 1 and put jobs {kind: "delete-object", ...} land together or not at all, and a worker with a lease and a back-off deletes the object (Functions and webhooks).
  • An upload never finished leaves a pending row and no object. A statement on a timer sweeps it, and the consumer sees the deletion like any other: del files where state = "pending" and created < now() - 3600000.

A run

Two people, a real fenec-server with files-policy.txt, the backend above, the consumer, and an S3-compatible server in Docker (npm install in examples/recipes, then node files-demo.mjs, which starts and removes the container; give S3_ENDPOINT, S3_KEY, S3_SECRET and BUCKET to use a store of your own). The signed URLs are shortened here. The store was SeaweedFS's S3 gateway: MinIO's container images and binaries could not be downloaded when this was written (quay.io refused the pull, dl.min.io answered 410), and any S3-compatible server takes the same SDK calls. S3 and R2 themselves were not run for this page.

fenec-server http://127.0.0.1:57250, bucket recipes at http://127.0.0.1:55003

-- alice adds a file
POST /files             201 {"id":1,"url":"http://127.0.0.1:55003/recipes/files/1?X-Amz-Algorithm=…&X-Amz-Signature=…"}
the row the server holds: [{"id":1,"owner":"alice","name":"hello.txt","type":"text/plain","size":17,"state":"pending"}]

-- she sends the bytes to the bucket herself, with the URL
PUT <presigned>         200
GET /files/1 before done 409 {"error":"not uploaded yet"}
POST /files/1/done    200 {"id":1,"state":"ready"}

-- she downloads it; bob is told there is no such file
GET /files/1 (alice)   200 {"url":"http://127.0.0.1:55003/recipes/files/1?X-Amz-Algorithm=…&X-Amz-Signature=…","name":"hello.txt","size":17}
GET <presigned>         200 "hello from alice\n"
GET /files/1 (bob)     404 {"error":"no such file"}
DELETE /files/1 (bob)  404 {"error":"no such file"}
GET /files (bob)        200 []
alice's total, for a quota   200 [{"sum(size)":17}]

-- what the rules and the bucket refuse
POST /files, 20 MiB     403 {"error":"the document is outside what this token may write to `files`"}
alice's own token, state ready  403 {"error":"the document is outside what this token may write to `files`"}
PUT 20 bytes to a URL signed for 5   403 SignatureDoesNotMatch
POST /files/2/done            409 {"error":"the bytes are not in the bucket yet"}
POST /files/2/done, 20 bytes there   422 {"error":"the object is 20 bytes, not the 5 announced"}
blobs: row 2 deleted, so object files/2 too
HEAD files/2: 404, the row having gone

-- alice deletes the file: the object goes with the row
DELETE /files/1 (alice) 204
blobs: row 1 deleted, so object files/1 too
HEAD files/1: 404

-- a pending upload nobody finished is swept
del files where state = "pending" and created < now() - 3600000: {"affected":1}
  • No row, no URL. The 20 MiB request, and the insert with state: "ready" sent straight to the database, were refused by the rules (403): the backend never got as far as the store.
  • Another person's file is no file. Bob's request for alice's is a 404, whether it is hers or nobody's, and so is his delete: his del with require 1 found no row of his.
  • A URL signed for 5 bytes does not take 20. The store refused (403) because the length is part of what was signed. That is this store; the check at done is what holds whatever a store does, and it deletes the row and the object of one whose size is not the announced one (422 above, with the 20 bytes put there directly).
  • The sweep deleted the abandoned row, and the consumer deletes whatever object it had.

What this does not do

  • It does not stop a replaced upload. The upload URL stays good until it expires, 300 seconds, and a client holding it can send other bytes to the key after done. A short lifetime narrows the window; closing it is the store's job (a copy of the object to a key the client never held, say), not the database's.
  • It does not scan, resize or transcode. A consumer of the change stream that sees a file go ready is where that belongs (Functions and webhooks).
  • It does not do multipart or resumable uploads, for files past what one PUT takes. The row and the check at done stay the same; the URLs for the parts are the store's and the SDK's.
  • It does not meter a person's total. The policy caps one file; a quota across files is a statement the backend reads before it presigns, run above as get files select sum(size).
