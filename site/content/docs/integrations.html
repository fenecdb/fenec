Integrations

A vector store for LangChain and one for LlamaIndex, over fenec-pg's HTTP endpoint, and useLiveQuery for React, over a replica the sync layer keeps. Each passes the tests its framework holds its own integrations to.

LangChain

pip install "fenecdb[langchain] @ git+https://github.com/fenecdb/fenec#subdirectory=integrations/python"

from fenecdb.langchain import FenecVectorStore

store = FenecVectorStore(
    embeddings, "handbook",
    url="http://127.0.0.1:8080", token="...",
    metadata_fields={"source": "text", "year": "int"},
)
store.add_documents(documents)
store.similarity_search("how do I compact", k=4, filter={"source": "ops"})
retriever = store.as_retriever(search_kwargs={"k": 8})

A document is a row: its id, its text, its metadata as JSON and its vector under @hnsw, in a collection created on the first write, once the embedding's size is known. Adding an id that is already there replaces it — the old row out and the new one in, sent as one /batch and run under one write lock, so no reader sees the id twice or not at all.

A metadata field named in metadata_fields gets a column of its own under @hash, and filter takes equality and $in over those: {"source": "ops"} becomes where source = $2, answered by the index before near looks for neighbours among the rows that passed. A filter on a field not declared is refused rather than applied to the JSON after the search, which would return fewer than k rows and not say so.

The score is fenecdb's own, the one the HTTP endpoint and the PostgreSQL wire return: the cosine similarity under cosine (the default), the distance under l2, the product under dot. similarity_search_with_relevance_scores maps them the way LangChain's own functions do.

LlamaIndex

pip install "fenecdb[llama-index] @ git+https://github.com/fenecdb/fenec#subdirectory=integrations/python"

from fenecdb.llama_index import FenecVectorStore
from llama_index.core import StorageContext, VectorStoreIndex

store = FenecVectorStore("handbook", url="http://127.0.0.1:8080", token="...",
                         metadata_fields={"author": "text", "year": "int"})
index = VectorStoreIndex.from_documents(
    documents, storage_context=StorageContext.from_defaults(vector_store=store)
)
index.as_retriever(similarity_top_k=4).retrieve("how do I compact")

A node is a row with its document's id beside it, so index.delete_ref_doc(...) is one del over a hashed field. Filters take ==, !=, <, <=, >, >=, in and nin over the declared fields, joined by and or or and nested; node_ids and doc_ids narrow the same way. get_nodes, delete_nodes and clear are there; delete_nodes() with neither ids nor filters deletes nothing — everything is clear, asked for by name. The query mode is the default one: LlamaIndex's hybrid mode is not answered yet, though fenecdb's own fuse is.

React

import { sync } from './fenec.js';
import { FenecProvider, useFenec, useLiveQuery } from '@fenecdb/react';

const db = await sync({ url: 'http://127.0.0.1:8080', shapes: [{ collection: 'tasks' }] });

function Open() {
  const rows = useLiveQuery(useFenec().from('tasks').where('done', false).order('title'));
  if (rows === undefined) return <Spinner />;
  return rows.map((t) => <Task key={t.id} {...t} />);
}

<FenecProvider db={db}><Open /></FenecProvider>

The rows come from the local replica, so no render waits on the network: the sync layer runs the query again after every local change — a write of this tab's, or one the server streamed in from another client — and the component renders what it answers. useLiveQuery is undefined until the first answer, and subscribes by the query's text and parameters, so the query built again on every render, which is the natural way to write one, does not subscribe again unless it asks something else; the rows of the query it asked before are not handed out as this one's. A query that fails throws while rendering, to the nearest error boundary. It lives in integrations/react, with React as its one peer dependency.

LangChain's suite writes the same documents twice under the same ids, and that is how it found a bug in the graph: a node whose every candidate neighbour had been deleted was linked to nothing, so a collection deleted and written again answered near with nothing.
