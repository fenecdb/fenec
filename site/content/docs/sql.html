From SQL

The SQL you write by habit, read as the FenecQL it means — and refused, saying what to write, where it has no exact meaning here.

FenecQL is not SQL, but the everyday spellings of SQL are FenecQL too. The parser reads INSERT INTO … VALUES, UPDATE … SET a = …, IN (…), BETWEEN, LIKE and the rest of the table below into the very statements FenecQL writes, so a text in either reaches the engine the same way — over HTTP, through MCP, in the fenec shell, in the page and in an app. There is no SQL mode and no second parser: the two spellings mix in one statement. What has no exact meaning here — CREATE TABLE, JOIN, a transaction left open — is refused with the FenecQL that does it, so an agent writing SQL by habit learns the language from its first error.

Every SQL text on this page is run by a test (crates/fenec-core/tests/sql_docs.rs): the session below statement by statement, each -- → x the answer it checks, and each line of the tables held to the FenecQL beside it — the two parse to the same statement — or refused.

A session written as SQL

create collection users (name text, email text nocase @unique, age int @sorted, city text, visits int)
INSERT INTO users (name, email, age, city) VALUES ('Ada', 'ada@example.com', 36, 'London'), ('Bob', 'bob@example.com', 25, 'Leeds'), ('Cem', 'cem@example.com', 52, 'İzmir') RETURNING name  -- → "Ada"
SELECT name FROM users WHERE age BETWEEN 25 AND 36 ORDER BY age DESC LIMIT 10  -- → "Ada"
SELECT name FROM users WHERE city IN ('Leeds', 'İzmir') AND name LIKE 'C%'  -- → "Cem"
SELECT count(*) AS n FROM users WHERE email ILIKE '%@EXAMPLE.COM'  -- → 3
UPDATE users SET visits = coalesce(visits, 0) + 1 WHERE name = 'Ada' RETURNING visits  -- → 1
INSERT INTO users (email, visits) VALUES ('ADA@example.com', 1) ON CONFLICT DO UPDATE SET visits = users.visits + excluded.visits RETURNING visits  -- → 2
INSERT INTO users (email) VALUES ('bob@example.com') ON CONFLICT DO NOTHING  -- → 0
SELECT name || ' <' || email || '>' AS who FROM users WHERE id IN (SELECT id FROM users WHERE age > 30) ORDER BY id  -- → "Ada "
SELECT name FROM users WHERE visits IS DISTINCT FROM 2  -- → "Bob"
DELETE FROM users WHERE age NOT BETWEEN 20 AND 40  -- → 1

The collection is made in FenecQL: CREATE TABLE is not read yet. email is nocase, so its =, its @unique and its LIKE compare by the case fold, and 'ADA@example.com' is Ada's row.

Where the meaning is not SQL's

Nulls: two values, not three

SQL's logic has three values: a comparison with a null is unknown, and WHERE keeps only what is true. FenecQL's has two. A null is equal to a null and to nothing else, so = and != take it as a value — they are SQL's IS NOT DISTINCT FROM and IS DISTINCT FROM — while <, <=, >, >=, LIKE and BETWEEN are false with a null on either side, and NOT makes a false true. Where SQL's unknown leaves a row out, FenecQL may take it in:

Where x is nullSQLFenecQL
x = NULLnever truetrue: it is x IS NULL
x <> 1, NOT (x > 1)left outtaken in
x NOT IN (1, 2), x NOT LIKE 'a%', x NOT BETWEEN 1 AND 3left outtaken in
x IN (1, NULL)left outtaken in: the list holds a null
2 NOT IN (1, NULL)never truetrue
x NOT IN (SELECT y …), where some y is nullnever truethe subquery's nulls are left out of its list

Add AND x IS NOT NULL to leave out what SQL leaves out. Arithmetic and || with a null are null, as in SQL; aggregates skip nulls, as in SQL — count(x) counts the rows where x is not null — and sum over none is null. A null sorts first ascending and last descending, as in SQLite and MySQL — PostgreSQL's default is the other way round — so NULLS FIRST is read after ASC and NULLS LAST after DESC, and either other way is refused. x LIKE 'a%' in a select list is null for a null.

<> is !=, null and all. One could read <> as SQL's and keep != FenecQL's, but not exactly: SQL's unknown runs through every NOT above it, which no rewrite of the one comparison carries, so the two would part somewhere else instead. Two operators that differ on null alone would be the subtler trap, and FenecQL read <> as != before it read any other SQL, so a text that used it would change its answer. One meaning, then, written here.

Double quotes are text

In SQL "name" is a column; in FenecQL it is text, as 'name' is. Where only a name can stand — a collection, the fields of an INSERT, a field SET assigns, RETURNING, an index's fields, a facet — "name" is the name, as in SQL. Where a value can stand it is text, as it always was: where title = "Rust". Where SQL would read a column and text would make the answer the same for every row, it is refused rather than answer all the rows or none:

  • alone on the left of a test against values: "name" = 'Ada', "age" > $1, "x" IS NULL, "x" IN (1, 2), "x" LIKE 'a%', "x" BETWEEN 1 AND 2;
  • on the right of a test against a literal: 'Ada' = "name";
  • an item of a select list, a key of ORDER BY or GROUP BY, an aggregate's argument: SELECT "name", max("at").

A parameter tested against double-quoted text stays a test: a policy's $jwt.role = "admin". Text on the right of a field stays text: UPDATE t SET a = "b" sets a to the text b, where SQL would copy the column b.

~ is contains

In PostgreSQL ~ matches a regular expression; in FenecQL it finds the text as written, case-insensitively: email ~ "@example.org". Written as a pattern, it would run and match nothing — and an agent that ran email ~ '@example\.org$' told its user there were no such rows. So a text that reads as a regular expression — anchored, ^a or a$, or holding .* or .+ — is refused, pointing at LIKE: like 'abc%' for a start, like '%abc' for an end, like 'a%b' for a gap. A parameter is taken as the text it is.

LIKE and ILIKE

% stands for any run of characters and _ for one character — of however many bytes. There is no escape character unless ESCAPE names one, as in standard SQL and SQLite; PostgreSQL's default is \, and a FenecQL string reads \ as an escape of its own, so '50\%' is the text 50%: write LIKE '50!%' ESCAPE '!'. A pattern that ends in its escape is refused.

A nocase field compares by its case fold wherever it is compared, LIKE too, as PostgreSQL's citext does. ILIKE compares the case folds — Unicode's full fold, the one nocase uses — so 'Straße' ILIKE 'STRASSE', and _ stands for one character of the fold. Its escape takes no character with a case. A collated field's LIKE compares its bytes, as its = does. ~, FenecQL's own, is a case-insensitive contains.

LIKE reads every row the rest of the filter leaves: no index answers it. A prefix over a @sorted field walks its index written as a range, name >= 'abc' and name < 'abd'.

An insert names its fields

INSERT INTO t VALUES (…) without its fields is refused. The parser reads no schema, and a collection's fields have no order a statement could lean on: id is the database's and no field's, and a field added goes last. Each row of VALUES has as many values as there are fields named. An id among them names the row's id; one that is taken is refused, as a key is, unless ON CONFLICT says otherwise.

ON CONFLICT

FenecQL's upsert is held by any unique key — the id, or a @unique value, a field's or several fields' — and ON CONFLICT is read with no target, as SQLite reads it: DO NOTHING passes a row over where any of them is held, and DO UPDATE SET sets the row holding its id, or else the first @unique value it holds, in the order the fields are declared. A target, ON CONFLICT (email), is refused: where the collection has a second unique key the two would part, and the parser reads no schema to tell. In DO UPDATE SET, excluded.f is the row offered (new.f) and t.f, or f, the row held; a WHERE is refused.

Text, ||, numbers

  • || is +. It joins two texts, and a text and a number are refused rather than made text: 'n' || 1 is an error where PostgreSQL gives n1. MySQL's ||, an OR, is not read.
  • Text compares by its bytes, as COLLATE "C" does. A field declared collate tr or und orders by that collation, and its = and LIKE compare bytes — see Collation.
  • Division between integers is whole, toward zero: 7 / 2 is 3, as in PostgreSQL and SQLite (MySQL's is 3.5); an integer and a float make a float.
  • Every row has an id, an int the database makes and no field declares; /_schema?as=fenecql and the MCP schema tool say so in a comment. rowid and _id are refused naming it.
  • Errors name what to write. contains(…), starts_with(…) and ends_with(…) are answered with LIKE; users.email — a column named with its table — with the field written bare.
