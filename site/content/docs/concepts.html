How it works

Six decisions carry the whole engine. Each one bought something and cost something, and both halves are written down here.

No page cache

Classic databases cut the disk into pages and copy those pages into a cache in user space. The eviction policy, dirty-page tracking, checkpoints and most of the locking cost all follow from that one structure.

fenecdb skips the layer:

  • Segments are immutable. A write only appends to the active one, which is sealed at 8 MiB.
  • The byte sequence on disk and the byte sequence in memory are the same format, so there is no caching stage — a read decodes directly over the arena slice.
  • The only helper structure is the HashMap<DocId, Loc> offset index.
  • Projection and filters decode a single field; the fields in front of it are skipped without allocating.

No eviction policy, no dirty pages, no warm-up. Dead bytes are reclaimed by compact.

The file is mapped

Because the format on disk is the format in memory, the file can be the memory: fs::open maps it where the target maps files, and a document is decoded from the pages the operating system brings in — and can drop again. What the process holds is what it derived from the documents: the offset index, the hash, ordered and text indexes, the graph, and the writes since the open. One file of 1 GB, 2.3 million rows with a hash and an ordered index (make open-bench):

 read into memorymapped
open2.26 s, 1 095 MB held2.13 s, 188 MB
compact1.52 s, peak 2 012 MB2.08 s, peak 236 MB
held afterwards969 MB117 MB

A 10 GB file of 23 million rows opens on an 8 GB machine this way, which reading it cannot: that would want about 20 GB. The trade is the one every mapped file makes: a page the disk cannot read ends the process rather than the query, and a file copied over in place while it is open does too — replace one by rename, as fenecdb's own rewrites do. What it does not change is the open's cost — the records are still walked to build the offset index and the indexes are still built from the documents, so opening is proportional to the file either way.

A rewrite writes the new file and points the stores at it, so the file just written is the one being read and the old one is let go of. The rewrite knows where it put each record, so the stores work their new places out without reading the new file back: that read cost 1.8 to 2.3 s of a 1 GB checkpoint, under the write lock, where working the places out takes 19 ms. A compact over a mapped file therefore copies no record into memory — on a server either, where it runs beside the database — and rebuilds no index but a graph holding tombstones: the documents are the same ones, and every index is keyed by id.

fenec-pg --no-mmap reads the file into memory instead — a replicated one, and every tenant of a --dir node, as well — over a network file system, where mapping is a bad bet, or to have --max-memory cover the data as well as the indexes.

Vectors are first-class

vector<N> is a type, @hnsw is an index, near is a clause. Not a plugin — the language itself.

get articles where year >= 2024 near embed $1 ef 200 limit 10
get articles near embed $1 exact limit 10        -- exact scan, for verification
  • HNSW is written in-house. Every vector lives in one contiguous arena.
  • Under the cosine metric vectors are normalised inside the index, so the query reduces to a dot product.
  • Neighbour selection uses the diversity heuristic (Malkov & Yashunin, Algorithm 4). Taking only the m nearest candidates trapped the graph in local clusters and lowered recall.
  • The read-only part of the build — descent, beam search, neighbour selection — runs in parallel over a batch; only writing the links is serial. The result is independent of thread count and deterministic.
  • The graph is written to the file, but only the links, not the vectors: the vectors are already in the document records, and the expensive part is the build.

A filter and a vector together

The filter's rows are found first, but only as far as the plan needs them. An index hands them over directly — a @hash equality, a @sorted range. Otherwise they are probed: rows are tested in blocks spread across the collection until more of them match than an ANN walk would measure anyway (ef × m0, 3 200 at the defaults), or until none are left. Then one of two paths runs:

  • if the set stayed smaller than that, it is searched directly — cheaper, and exact;
  • otherwise the ANN runs and each candidate is tested against the filter. If the result lands under the limit, the probe carries on to the end and the whole set is searched exactly.

The probe changes when the rows are found, never the answer: it is the one finding the whole set first gave, row for row. What it saves is the scan. Over 200 000 × 128, year >= 2020, 23% of the rows, took 16.4 ms with the set found first, 0.14 ms of it the ANN, and takes 1.1 ms probed. A filter under the budget is still read in full unless an index narrows it: 17.9 ms for 1% of the rows, 0.16 ms over @sorted. The blocks are spread out so that a filter for the newest rows, which sit at the end of the id order, is found as fast as one for rows everywhere: 1.7 ms for the newest 23%.

The fallback is not an optimisation, it is required. The filter is tested after the candidates are gathered. When the filter field correlates with the vector, every one of the ef nearest neighbours can be eliminated and the query would return empty while thousands of documents match.

Deleted documents do the same without a filter. Every write that changes or deletes a document's vector leaves a tombstone in the graph until compact, and a beam full of them holds fewer live rows than the page. A short answer is walked again with the beam wider by the tombstones, since no more than all of them can be in it — or, where a walk that wide would cost more than reading every vector, searched exactly. Either way the page is full, and explain says which ran.

Half precision

Precision is part of the type, not of the index — the same choice pgvector makes with halfvec. That shrinks the record and the arena together; as an index option only the arena would shrink, and in the browser the file image is in memory too.

create collection docs (embed vector<768, f16> @hnsw(cosine))

The runtime representation does not change: values are f32 everywhere and conversion happens only at the storage boundary. Same data, 100 000 × 128:

 vector<128>vector<128, f16>
vector arena51.2 MB25.6 MB
file image57.9 MB32.3 MB
index build10.4 s12.5 s
ANN p500.127 ms0.147 ms
recall@10100%99.6%

The cost is arithmetic: distance over an f16 arena unpacks inside the loop. Two things were measured and fixed. The expansion has to be branchless — the first version called the exact conversion in codec, whose subnormal branch killed auto-vectorisation and made the build five times slower (52 s); the branchless version is one multiply and is bit-identical over all 65 536 values. And the fixed side of the diversity loop is unpacked once rather than per comparison: 22.6 s down to 12.4 s.

The win is at the memory boundary. One million 768-dimension vectors take about 3 GB as f32 and about 1.5 GB as f16. In WASM32's 4 GB address space that is the difference between fitting and not. Embedding model output sits comfortably inside the f16 range (±65 504, roughly three decimal digits) and the measured recall loss is 0.3 points.

Quantized indexes

Half precision shrinks the record and the arena together. A quantized index leaves the record alone and shrinks the arena further, by holding codes instead of vectors: a byte a component with quant=int8, the sign of each with quant=bit.

create collection docs (embed vector<768, f16> @hnsw(cosine, quant=int8))

A code only estimates a distance, so it is used for what an estimate is good for: walking the graph to the right neighbourhood. The candidates the beam holds, ef of them, are then put in order by the documents' own vectors, read out of the store as rerank reads them, and the first limit are the answer. The scores are exact; the codes decide only which candidates are found.

Not every candidate has to be read. An int8 code rounds each component to a step of its scale, so it knows how far off its estimate can be: the candidates are read nearest estimate first, and one that can no longer make the page is left unread. A bit code keeps no step, and the whole beam is read. A filtered set too small for the walk to pay — fewer rows than the distances a walk would measure, ef × 2m — is ranked by its codes and read the same way.

One million vectors of 768 dimensions, stored as f16, in 64 clusters each spread along 32 directions — embeddings vary along far fewer directions than they have — with a @hash field of 333 groups for the filtered rows, on an 8 GB machine that was swapping, so the latencies are high for all three (make quant-bench):

int8 codes follow the vectors closely enough for the default beam of 100, and closely enough that 20 of its hundred candidates are read, with the recall of reading them all. What is left unread is further off than six times the spread of its rounding, which a candidate passes less than 1.5e-8 of the time. Bit codes take the wider beam, and a quant=bit index searches 400 unless told otherwise, reading all of it; they are for the arena, an eighth of int8's. The rest of the heap is the documents, whose vectors the answers are ordered by.

How well a bit code estimates depends on the vectors. Spread in every dimension instead — as many degrees of freedom as dimensions, the hardest case for any graph — 100 000 such vectors gave full vectors 97.8% at a beam of 100, int8 codes 98.0%, and bit codes 36%, 75% at 400: when a cluster is crowded around its centre, most of its members' signs are the centre's, and the signs cannot tell them apart. int8 codes held with full vectors on every set measured; measure bit codes on the vectors they are for.

The kernels over codes are scalar on every target, in the eight-strip order of the vector kernels: natively LLVM vectorises them, and in the browser they add in the same order, so a graph over codes is the same graph in both.

Sparse vectors

A learned sparse model weighs a text's vocabulary: SPLADE gives each of BERT's 30 522 word pieces a weight, and all but a couple of hundred come out zero. It learns which words a text is about, including ones it never uses — an abstract on damage to cerebral white matter is weighted for disability as well as the disabilities it says. sparse<N> holds such a vector by its non-zero entries, and @inverted indexes it the way @text indexes words: a list per dimension of the documents with a weight there.

create collection passages (body text @text, splade sparse<30522> @inverted)
get passages near splade $1 limit 10

near over it scores by dot product and walks the lists with MaxScore, the pruning match uses, so what comes back is the exact top ten rather than an estimate of it; only documents sharing a dimension with the query are ranked. Encoded with SPLADE++ and scored on BEIR (make beir, Benchmarks):

nDCG@10SciFactFiQA

near, dense (all-MiniLM-L6-v2)0.6450.366

On SciFact, where a claim shares its words with the evidence, SPLADE alone scores what BM25 and the dense vectors do fused, with one index. On FiQA, where a question shares few words with its answer, it lifts BM25 from 0.232 to 0.331 but stays under the dense vectors, and fusing it with BM25 there costs it: the two are both lexical, and the weaker one drags. The index holds 968 928 postings for SciFact's 5 183 documents — 186.9 a document — in 13.1 MB, built in 0.07 s; FiQA's 57 638 hold 8.8 million in 107 MB, built in 1.2 s. Like the text index it is derived from the documents and rebuilt on open, never written to the file.

A SPLADE query reaches most of the corpus. Its 37 to 65 expanded terms touch 38 262 of FiQA's 57 638 documents, and MaxScore gives up on 99.7% of them only after reading their share of those lists: 2.6 ms at the median, against 0.38 ms for a dense near, which walks a graph instead, and 0.25 ms for match. On SciFact it is 0.60 ms. The pruning is exact; bounds per block of a list, which would let it skip blocks rather than documents, are not built.

Bulk load first, index after

Writing the index during the load makes every insert a graph mutation. Building it afterwards turns the write path into a pure append and builds the graph in one parallel pass.

create collection docs (title text, embed vector<768>)
put docs [ ... 100 000 documents ... ]
create index on docs (embed) @hnsw(cosine)

This is already the recommended order for SQLite and PostgreSQL. In fenecdb create index exists for exactly this reason, and the comparison in Benchmarks uses that order for all three engines.

Zero dependencies

The core uses std and nothing else: its own binary codec, its own JSON, its own HNSW, its own lexer and parser, its own SCRAM, even its own decimal-to-f64 — str::parse reaches for a 12 KB table of powers of five, which is a twelfth of the module and incompressible. The reason is the WebAssembly output — it has to stay small and auditable.

The rule covers fenec-core, fenec-ql, fenec-wasm, fenec-http, fenec-pg, fenec-catalog, fenec-import and fenec-shard. fenec-core does dev-depend on fenec-ql, which Cargo permits through a dev dependency, so tests can be written as real queries.

What it costs. Every bug is ours, and so is every protocol detail. The server and client halves of SCRAM are both hand-written, which at least means they test each other.

Straight into the browser

fenec-wasm exposes a C ABI and there is no wasm-bindgen. The glue is about 305 lines of JavaScript inside web/fenec.js, alongside the query builder, the HTTP client and the sync layer — one dependency-free ES module.

persist(db) and restore(db) move the database in and out of IndexedDB the way a file holds it: an image, and the writes since as chunks after it. The first persist stores the image; every later one stores only what was written since the last, from a journal the wasm side keeps once asked to. In Chrome, over a 32 MB database, persisting one new row takes 0.6 ms where writing the image again took 136 ms. Once the chunks outgrow half the image, a new image replaces them, and compact replaces them too. restore reads the image and its chunks back as one file, so the graph restored from the image takes the chunks' writes rather than being rebuilt.

Threads are compiled out of wasm32. The parallel HNSW build path must not enter that target. now() errors there too — wasm32-unknown-unknown has no clock, so time is passed in as a parameter.

Single writer

Reads take a shared lock (Database::query), writes take the exclusive one (execute_with). There are no transactions: fenec-pg accepts BEGIN and COMMIT for the drivers that send them, and refuses a ROLLBACK that would have had something to undo.

That is what removes MVCC row headers, the WAL and the visibility map — about 2.8 MB of headers over 100 000 rows. Most of the 2.5× between this file and the same data under pgvector is elsewhere: pgvector's HNSW index keeps its own copy of every vector, while this graph stores only the links (Benchmarks).

Two processes opening the same file corrupts it. This is why the HTTP endpoint is a second listener inside fenec-pg and never its own binary — one process, one file, one sync policy, one shutdown signal.

Concurrency still exists on the read side. HNSW search buffers are kept thread-locally so the same index can be searched in parallel; eight concurrent full scans on eight cores measured a 4.3× speed-up.

The replica is an endpoint, not a library

Because the same engine runs in the browser and on the server, the local-copy architecture needed no new layer — only two things: the server being able to say "these changed", and the client being able to choose where to bind a query. bind() already existed, and the first was sitting in the file format, because the file is already a change log.

const db = await sync({ url, shapes: [{ collection: 'tasks', key: 'key' }] });
await db.from('tasks').where('priority', '>=', 3).rows();   // local, no network

It is TanStack DB's model with two differences. There is no incremental dataflow: there a collection is a Map, and re-running a filter on every keystroke over a large set is unacceptable — here the local side is indexed and the query is already under a millisecond. And a shape is mandatory: the whole database is in memory, so the client cannot pull all of it. Details in Sync.
