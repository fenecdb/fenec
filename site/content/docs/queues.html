Job queues

Many workers taking jobs from one collection: each job claimed by one of them under a lease, then acked, extended or failed — every step a statement.

One statement claims. A set with order and limit writes the rows a get with the same clauses would answer, and returning hands them back as written:

set jobs {owner: $1, run_at: now() + 30000, attempts: attempts + 1}
  where run_at <= now() order run_at limit 10 returning *

The ten oldest ready jobs are found and written under the one writer's lock, so two workers never take the same one — what PostgreSQL's FOR UPDATE SKIP LOCKED is for, with no locks to skip. A job's run_at is the time it may next run: when it was enqueued, or later for a delayed one, and while a worker holds it, the end of its lease. So a worker that dies holds nothing for long: its lease lapses, the job is ready again, and the next claim takes it. See Writes that pick their rows for the rules.

Every FenecQL block on this page is run, statement by statement, by a test (crates/fenec-core/tests/queues_docs.rs), and each -- → x is the answer it checks: a write's count, or the first value of the first row it answered. A line -- 20 s later moves the test's clock. The costs are make queue-bench on an M1 Air, over a million jobs.

The queue

A collection a queue. run_at takes @sorted, so a claim walks the ready jobs from the oldest and stops at its page.

create collection jobs (payload json, run_at timestamp @sorted, owner text, attempts int, error text)
put jobs {payload: {"to": "ada@example.com"}, run_at: now(), attempts: 0}
put jobs [{payload: {"to": "bo@example.com"}, run_at: now(), attempts: 0}, {payload: {"to": "cy@example.com"}, run_at: now(), attempts: 0}]
put jobs {payload: {"to": "di@example.com"}, run_at: now() + 3600000, attempts: 0}     -- → 1: delayed an hour
  • A delayed job is one whose run_at is ahead: no claim takes it before then.
  • Jobs enqueued at the same time come out in the order they were written, their ids'.
  • Several queues are several collections. Kept in one, a queue field goes without @hash: the walk tests it on each job it passes, where through a hash index a claim would read the whole queue to put it in order.

Claim

Each worker claims a batch, the oldest ready jobs, each its own for 30 seconds:

set jobs {owner: "w1", run_at: now() + 30000, attempts: attempts + 1} where run_at <= now() order run_at limit 2 returning id, payload.to   -- → 1: jobs 1 and 2
set jobs {owner: "w2", run_at: now() + 30000, attempts: attempts + 1} where run_at <= now() order run_at limit 2 returning id, payload.to   -- → 3: the one left ready
set jobs {owner: "w3", run_at: now() + 30000, attempts: attempts + 1} where run_at <= now() order run_at limit 2 returning id   -- → no row: none ready
  • None is taken twice. The claim finds and writes its jobs under the write lock. Sixteen threads claiming batches of ten from 6 000 jobs, and eight HTTP clients from 2 000, never handed a job to two of them, and every job was acked (crates/fenec-core/tests/claims.rs, crates/fenec-http/tests/claims.rs).
  • returning * answers every field; a list answers those, paths into a json field among them. Without returning the answer is the count.
  • limit 1 require 1 is one job or a refusal (412): require counts the rows the claim answers.
  • An empty queue answers no rows. Nothing waits for a job to come: a worker sleeps and claims again, or holds a subscription to the queue and claims when it hears a write.

Ack, extend

A worker acks a job it holds by deleting it, and keeps one longer by moving its lease on. Each names the owner it was claimed by and requires its row, so a worker whose lease lapsed, and whose job another worker claimed meanwhile, finds out:

del jobs where id = 1 and owner = "w1" require 1                       -- → 1: done
-- 20 s later
set jobs {run_at: now() + 30000} where id = 2 and owner = "w1" require 1   -- → 1: 30 s more
-- 15 s later
set jobs {owner: "w3", run_at: now() + 30000, attempts: attempts + 1} where run_at <= now() order run_at limit 10 returning id, attempts   -- → 3: w2's lease lapsed
del jobs where id = 3 and owner = "w2" require 1                       -- → refused: 412, w3 holds it now
del jobs where id = 3 and owner = "w3" require 1                       -- → 1
  • At least once. A job whose worker died is taken again once its lease lapses, so a job can run twice — once by a worker that was only slow. Work that must not happen twice keeps a check of its own: a @unique key on what it writes, or an Idempotency-Key on the request it sends.
  • A token a claim rather than the worker's name as the owner — "w1:1842" — also tells apart two claims of one job by the same worker.
  • To keep a job done rather than delete it, give it no ready time: set jobs {run_at: null, owner: null} where id = $1 and owner = $2 require 1. No claim takes a job without one.

Fail, back off, dead-letter

A job that failed goes back with a backoff that grows with its attempts, and after the fifth it has no ready time — a dead letter, which no claim takes and a read finds:

set jobs {owner: null, error: "smtp timeout", run_at: case when attempts >= 5 then null else now() + 1000 * attempts * attempts end} where id = 2 and owner = "w1" require 1   -- → 1: again in 1 s
-- 2 s later
set jobs {owner: "w1", run_at: now() + 30000, attempts: attempts + 1} where run_at <= now() order run_at limit 1 returning id, attempts   -- → 2: its second attempt
set jobs {attempts: 5} where id = 2                         -- three failures on
set jobs {owner: null, error: "smtp timeout", run_at: case when attempts >= 5 then null else now() + 1000 * attempts * attempts end} where id = 2 and owner = "w1" require 1   -- → 1: the fifth: dead
get jobs select id, error where run_at is null              -- → 2: the dead letters
set jobs {run_at: now(), attempts: 0, error: null} where id = 2 and run_at is null   -- → 1: sent again by hand
  • The backoff here is the square of the attempts in seconds — 1, 4, 9, 16 — worked out over the row. One that doubles, or has jitter, is the worker's to send: it read attempts in its claim.
  • A worker that dies on a job never fails it, and its lease lapses instead: attempts counts claims, so a job that comes back to a worker with attempts past five is failed by it, not run again — SQS's receive count.

Priorities

With a priority, a claim takes the highest first, and among jobs of one priority those written first:

create collection tasks (payload json, run_at timestamp @sorted, priority int @sorted, owner text, attempts int)
put tasks [{payload: {"n": 1}, run_at: now(), priority: 0, attempts: 0}, {payload: {"n": 2}, run_at: now(), priority: 9, attempts: 0}]
set tasks {owner: "w1", run_at: now() + 30000, attempts: attempts + 1} where run_at <= now() order priority desc limit 1 returning payload.n   -- → 2: the higher priority
  • The walk is the priority's index, testing each job's ready time as it passes: jobs of a high priority that are leased or delayed are passed over at every claim, so a queue holding many of them is a collection of its own. While the ready jobs number a few thousand at most, the claim reads them by run_at and puts them in order instead.

A pop

Where a job may be lost but never run twice — Redis's LPOP — a del takes and answers it at once:

del tasks where run_at <= now() order priority desc limit 10 returning id, payload   -- → 1: taken and gone

A worker

The loop, in JavaScript over HTTP: claim a batch, run each job, ack it or fail it, and wait a little when there was none.

import { connect, expr, inc, raw } from '@fenecdb/web/client';

const db = connect('http://127.0.0.1:8080', { token: 'a worker token' });
const jobs = db.from('jobs');
const me = `w-${crypto.randomUUID()}`;

async function send(to: unknown): Promise<void> {
  // the work
}

for (;;) {
  const owner = `${me}:${Date.now()}`;
  const claimed = await jobs
    .where(raw('run_at <= now()'))
    .order('run_at')
    .limit(10)
    .update({ owner, run_at: expr('now() + ?', 30000), attempts: inc(1) }, { returning: true });
  if (claimed.length === 0) {
    await new Promise((r) => setTimeout(r, 500));
    continue;
  }
  for (const job of claimed) {
    try {
      await send((job.payload as { to: string }).to);
      await jobs.where('id', job.id).where('owner', owner).delete({ require: 1 });
    } catch {
      const backoff = 1000 * 2 ** Number(job.attempts);
      await jobs.where('id', job.id).where('owner', owner).update(
        { owner: null, run_at: expr('now() + ?', backoff) },
        { require: 1 },
      ).catch(() => {});
    }
  }
}
  • Every builder writes the claim — Python's .update(patch, returning=True), Go's Update(ctx, patch, fenecdb.Returning("*")) and its Result.Rows, .NET's UpdateAsync(patch, returning: ["*"]), and Swift's, Kotlin's and Dart's updateReturning — held to the same text.
  • Over HTTP the claim is a POST /query; sent under an Idempotency-Key, a retry after a timeout is answered the jobs the first try took, and takes none.
  • A worker's token claims through its rules: a policy line jobs update(owner, run_at, attempts) where queue = $jwt.queue for worker lets it take its queue's jobs alone and change nothing else of them, and what it answers is held to its read rules as well (Security).
  • Not on a sync replica. A replica would pick its own rows and answer them, and the server its own: a claim there is refused, and goes to the server itself.

  • The three statements a client sends without returning — read the ready page, set the jobs only where they are still ready, read back which it won — lose a race whenever two workers read the same page: 43% of the jobs read in process, and 77% over HTTP, had gone to another worker by the time it wrote, and were read again. Half the jobs a second in process, a third over HTTP.
  • Sixteen claims wait for each other, as every write does: a claim's p99 among sixteen threads is the lock's queue, where one worker's is 25.8 us.
  • The claim reads its page and no more: the ready jobs are a range of the index, the time worked out once before the plan. A queue holding a million leased or delayed jobs and three ready claims the three, where a walk testing each job's time would pass every leased one.

Compared

  • PostgreSQL: UPDATE jobs SET ... WHERE id IN (SELECT id FROM jobs WHERE run_at <= now() ORDER BY run_at LIMIT 10 FOR UPDATE SKIP LOCKED) RETURNING *. Its row locks let claims run side by side; here the one writer runs them one after another, each a few microseconds, and none has rows to skip.
  • SQS: a claim is ReceiveMessage, the lease its visibility timeout, an extension ChangeMessageVisibility, attempts its receive count and a dead letter its redrive. A delayed job is DelaySeconds, with no fifteen-minute ceiling.
  • BullMQ: delayed, prioritised, retried with a backoff and kept as failed, as here; its jobs live in Redis's memory, these in the file, durable by the server's --sync policy, replicated with it, and read with any query.

What this does not cover

  • A blocking claim — a worker held until a job arrives, as BLPOP holds one. A subscription wakes a worker on a write; the claim does not wait.
  • Exactly once. A lease that lapses under a slow worker hands its job to another; the work's own check makes the second run harmless.
  • Claims side by side. They are writes, so each waits for the one before: tens of thousands a second, not millions.
