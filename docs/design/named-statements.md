# Named statements (proposal)

**Status: slices 0 and 1 built, the rest a proposal revised after an adversarial review.** `require <n> else '<reason>'` (slice 0) and the parser and the tree (slice 1) are on main: every form below reads into its tree, and the engine, `scoped()` and MCP refuse each definition, drop and call as *not built yet* ([what is built](#what-is-built)), so no statement is defined with nothing to check it nor called with nothing to scope it. The rest is a proposal: no record, check, call or grant exists, and the figures past slice 1's are quoted from the design notes they cite, the ones this would owe named with the bench that would take them. The review found the model sound and the first draft too loose in its authority, its storage, its read path and its slices; this revision adopts its findings as the proposal's decisions, and five that are the owner's to approve are [listed at the end](#decisions-for-the-owner) with the choice recommended. Once built, each section's rule moves into CLAUDE.md in a few sentences (the drafts are in [the plan](#the-plan-in-slices)) and this file becomes its long form, as the others are; slice 1's rule is there already.

A named statement is a FenecQL statement, or a block of them, defined once in a database and called by name with typed arguments: `create statement transfer($from int, $to int, $amount int) claims (sub text) as begin ... end`, then `POST /_call/transfer` with `{"params": {...}}`, `call transfer {...}` in FenecQL or `db.call('transfer', {...})` in the SDKs. Its authority is its own: a token may be granted `transfer call` with no write rule on the collections it touches. It is fenecdb's answer to PostgreSQL functions used as an API (`SECURITY DEFINER` and PostgREST's `/rpc/`, Supabase's `rpc()`), Convex's mutations and queries and Firebase's callable functions -- without running user code: the body is FenecQL, parsed once, bounded, and run as one block under the single writer.

What it answers. Under a scoped token today the policy is the API: a ledger's app token needs `update(balance)` on `accounts` to move money, and nothing in the policy can say "only as one debit and one credit of the same amount, from an account you own". `require <n>` made a transfer's `/batch` safe against the race ([writes.md](writes.md#require)), but a client holding the grant can still send the debit alone or the credit alone. Transitions ([access.md](access.md#scoped-tokens)) say which way a row may move, never which rows must move together. So an app that wants an operation rather than a grant runs a server of its own in front of fenecdb -- the code fenecdb exists to spare it. A named statement is that operation, kept in the database beside the data it moves.

## Definitions

**A named statement is a record of its database, defined by its text, checked against the schema it reads, and marked broken rather than ever failing an open.** `create statement` writes a record of its own kind (13, `REC_STATEMENT`), a write moving the change counter by one (`writes_in` must count it: its fallthrough, `_ => Ok(0)`, would leave every replica a change behind); it rides in a block, is undone by a variant of its own (`Undo::Statement`), is kept by every image and applied by a replica as a schema record is. Its version is `(history, change)`. A schema change that would break one is refused at its commit, naming it; an internal writer that cannot refuse marks it broken instead.

```fenecql
create statement transfer($from int, $to int, $amount int)
  claims (sub text)
  comment 'Moves an amount from an account the caller owns to another'
  check $amount > 0 and $from != $to
as begin
  get accounts select id where id = $from and owner = $jwt.sub
    limit 1 require 1 else 'not your account';
  set accounts {balance: balance - $amount} where id = $from and balance >= $amount
    require 1 else 'insufficient funds';
  set accounts {balance: balance + $amount} where id = $to
    require 1 else 'no such account';
  insert entries {from: $from, to: $to, amount: $amount, by: $jwt.sub, at: now()}
    returning id, at
end
```

Each statement of that body runs today through the shell as written, literals in place of the parameters, but for `else '<reason>'` (below). A deployment trusting more than one issuer keys `owner` on `sub` and `iss` together -- `sub` is unique only within its issuer, which is why Convex's `tokenIdentifier` joins the two ([Convex](https://docs.convex.dev/auth/functions-auth)) -- and never on a claim a user can edit, an email or a profile's metadata, which an identity provider may let its user change.

**The signature.** A name, then its parameters, its claims and its markers.

- *The name* is ASCII letters, digits and `_`, starting with a letter, at most 59 bytes, in a namespace of its own (a statement and a collection may share one): a path segment with nothing to escape, and `call_<name>` within the 64 characters of the tool names model APIs take (MCP, below).
- *Parameters* are `$name type`, the type one the schema's types name -- `bool`, `int`, `float`, `text`, `bytes`, `timestamp`, `json`, `geo`, `vector<N>`, `sparse<N>`, `[T]` -- read by the parser's `data_type`, so a parameter's type is a field's. One is required and never null unless it has a default, a literal (`$n int = 10`, `$note text = null`). At most 32.
- *Claims* are declared with their types, `claims (sub text, accounts [int])`, the token's top-level claims alone; a name FenecQL does not write as a name is quoted and given one, `claims (groups [text] from "cognito:groups", plan text from "https://example.com/plan")`, the forms Cognito's groups and Auth0's namespaced claims take. A body reads only the claims it declares (`$jwt.sub`, `$jwt.groups`); a nested path into a claim is refused. Declared, a claim's type is checked as an argument's is, and a statement's claims are part of what `describe` shows a caller, since they say which token it takes.
- *`check <expr>`* is a condition over the parameters, the claims and `now()` alone -- a field named in it is refused at definition -- asked before the call takes any lock: a negative amount is a 400 naming the check, never a debit that found the money.
- *`comment '<text>'`* is what `describe`, the MCP tool and generated types say of it.
- *`public`* marks a writing body that reads no claim: one that writes on behalf of nobody in particular -- a vote counted by the poll alone -- must say so, since every token granted it writes the same rows the same way. Without it, such a body is refused at definition.
- *`scans`* acknowledges a writing body whose plan walks a collection no index narrows (below).

**The body** is one statement, or `begin` and statements cut by `;` to `end` -- the shape of PostgreSQL's SQL-standard `BEGIN ATOMIC ... END` body, which [its manual](https://www.postgresql.org/docs/current/sql-createfunction.html) says "is parsed at function definition time" and "tracks dependencies between the function and objects used in the function body" (it stores the parsed tree, below, which this does not). At most 64 statements, each one of:

- `get` (and SQL's `select`);
- `insert`, and `insert ... if absent`, with its documents written in the text -- an `insert` never writes over a row (409);
- `set ... where` and `del ... where`, or with a pick (`order`, `limit`) -- a row is written over only by a `set` whose filter, in the text, is its guard.

Refused at definition, each with the form to write: `put` in any form, since a `put` naming an id writes over whatever row holds it and an argument could name anyone's; `insert <c> $n` and `put <c> $n`, whose documents -- fields, ids and values -- would be the caller's, past every guard the text holds; `if absent else set` in this first version, whose row is found by a key the caller's document names (a later version may take it where the key is the statement's own); a `set` or a `del` with neither `where` nor a pick (`where true` says it is meant, as REST's `PATCH /<name>/all` does); a schema change (that authority is the server token's, and a statement holding one would hand it to every caller), `compact` and `call` (no recursion to bound, and a body is read whole where it is defined). A body names no collection the database calls its own -- `declared::own`, every name starting with `_`: `_idempotency`, whose rows would let a call forge a replayed answer, `_consumers` and `_follow`, the sync's `_sync_*`, `_migrations`. A name is never a parameter in FenecQL, so a call cannot be pointed at another collection: the trap PostgreSQL's dynamic SQL (`EXECUTE format(...)`) sets has no way in.

**Parameters and claims are names in the text and places in the tree.** The lexer reads `$` followed by a letter as a name (`Tok::Named`) -- `$` and anything but a digit is refused today, so no text that parsed reads otherwise -- and the definition's parser numbers them: the declared parameters first in the signature's order, then the declared claims in theirs, so the body is the same `Expr::Param`s every statement holds and the engine's every path takes it unchanged. `$1` in a body is the first declared parameter, PostgreSQL's "older numeric approach" ([SQL functions](https://www.postgresql.org/docs/current/xfunc-sql.html)). A named parameter outside a definition is refused ("`$from` names a named statement's parameter; a statement sent alone numbers them, `$1`"); a policy keeps reading `$jwt.<claim>` as it does.

**The answer names its fields.** The body's last statement is what a call answers (below), and it names every field it answers: a `get` has a `select` list, `returning` names its fields, a `lookup` level its own, and `*`, or a `get` with no list, is refused at definition. Run with an authority of its own, a `select *` would start answering a field added to the collection after it was defined -- a `password_hash` -- through every call already granted. PostgreSQL's views expand `*` once, at creation: "columns added later to the table will not be part of the view" ([CREATE VIEW](https://www.postgresql.org/docs/current/sql-createview.html)); refused rather than expanded here, so the text shown is the answer given. The answer's *types* need an inference pass the engine does not have: `describe`, MCP's `outputSchema` and `fenec types` type a column only where it is a field or a path read as stored (its field's type, a path `json`), `id` or `count` (`int`), and give every other column -- an expression, any other aggregate -- no type until such a pass is built, a slice of its own.

**Checked at definition, and at the commit of every schema change.** At definition the body passes the checks every statement passes before it reads a row -- names against the schema (`Flat::names`, `path_of`), `check_counts`, `check_order`, `check_subquery`, a `lookup`'s child key indexed -- and a plan: a writing body's statement no index narrows (no `and` term an index answers, no pick an ordered walk answers) is refused unless the definition says `scans`, since it would walk the collection under the write lock at every call any granted token makes. Each statement keeps what it depends on: the collections and fields it reads and writes, the indexes its `lookup`s read and the unique indexes its `insert ... if absent` and its `insert`'s duplicate refusal rely on. A schema change -- `alter`, `drop collection`, a field dropped or renamed, an index taken off, `declared::plan`'s apply -- is checked against the statements depending on what it touches *as its block commits*, against the schema the block leaves, not statement by statement: `drop statement transfer; alter collection accounts drop field balance; create statement transfer ...` lands, and so does an `alter` whose block redefines the statement after it. A change leaving one broken is refused naming it ("statement `transfer` reads `accounts.balance`: replace or drop it first"), as PostgreSQL refuses `DROP` over a dependent view without `CASCADE`; a rename is refused too, since a statement's text is never rewritten for it, as `declared::plan` never guesses one. `rebuild`, the declared schema's migration that adds a field again as declared, `set`s it from the old, drops the old and renames the new, is one block, so its commit finds the field under its name again and passes where the statement still checks, and is refused with the plan's resolution where it took away what one relies on. The writers that cannot refuse -- a follower re-copying a collection from its primary, the sync's remake of a collection, a load, a restore -- mark the statements they break broken instead: a broken statement is listed with why, and called it is refused (409) until redefined. Late binding was the alternative -- PL/pgSQL's bodies are strings parsed at their first run -- and a deploy that renamed a field would have broken an API at its next call rather than at the deploy.

**Stored as its text, held to its tree.** The record is `[13][0][length][op][history][change][epoch][digest][name][depends][text]`: `op` a definition or a drop; the text the definition's own bytes from `create` to its end (`spans`), comments and all; `epoch` the grammar's epoch, a number fenec-ql raises whenever a change could read a stored text otherwise; `digest` a hash of the canonical tree the text parsed to; `depends` the names it depends on, so a build that cannot parse it still knows what it touches. An open parses each text again; where the tree's digest is not the one stored -- a later grammar reading the text otherwise, which the corpus rule exists to prevent ([fenecql.md](fenecql.md#sql-spellings): 7 620 texts, none parsed to another tree) -- the statement is marked broken, and calls are refused until it is defined again. An open never fails on a statement: an API's definition must not hold the data hostage. A fixture of stored statements, written by each release and opened by every later binary in its tests -- as `tests/language.fenec` is for the language's features, `FENEC_WRITE_FIXTURE=1` -- holds each digest across epochs. PostgreSQL stores the tree itself (`prosqlbody`, "pre-parsed SQL function body", [pg_proc](https://www.postgresql.org/docs/current/catalog-pg-proc.html)), so a column renamed under it follows; storing text, this refuses the rename instead and claims no parity there. A binary from before refuses kind 13, as the file format requires of a new kind ([storage.md](storage.md#file-format)), and so a block holding one -- which sets the upgrade's order (below).

**Replicated, archived, compacted.** The record goes through `wal` and moves the counter by one, counted by `writes_in` as a create's is, so a replica's counter stays the primary's write for write ([replication.md](replication.md#replication)) and applies it as it applies an alter, checking the digest and nothing more; a promotion, a tenant's move, a restore and a read replica carry the statements in the file. An image writes the live definitions after the collections, each with its version, epoch and digest, so a compact keeps them as they were. `/_changes` passes over the record as over a schema record naming no collection's rows -- the cursor moves past it and no row is told -- and a sync replica's stream does too: the server owns its statements, and remaking collections for one would reseed every shape.

**Versions and replacements.** `create statement` refuses a name held (409); `create or replace statement` replaces it and `drop statement [if exists]` drops it, each a schema change: refused to a scoped token and logged by the audit as every `create` and `drop` shape is ([http.md](http.md#audit)). A replacement keeps the statement's contract or is refused: one changing whether it writes, the claims it reads or the fields it answers is a new statement, written as `drop` and `create` -- whose `drop` every grant naming it then visibly names nothing (logged, below) -- since a token granted a statement that read nothing would otherwise start writing, or one keyed on `sub` start reading `groups`, with no line of the policy changed. Whether such a replacement is refused, or allowed and logged as an event of its own, is [the owner's](#decisions-for-the-owner). A version is `(history, change)`: the history the database was on and the change it was defined at -- after a promotion forks the history, a change number alone names two definitions -- carried in the record through compaction, the place an archive's restore names, so a version says both which text ran and where the archive holds it. Every version is in the archive; the file holds the live one. A call runs the definition it finds under the lock it runs under, and a replacement lands under the write lock, so a call runs one version whole. Two versions callable side by side (`transfer@2`) were weighed and left: a change that breaks callers is a new name, `transfer_v2`, as an HTTP API's is.

**Listing and describing.** `statements` lists them, as `collections` lists collections; `describe statement transfer` answers its name, version, parameters with their types and defaults, the claims it reads and their types, its `check`, `comment` and markers, whether it writes and whether it can be held (`Fenec-Wait`, below), the fields it answers with the types it can give, whether it is broken and why, and -- to the server's token alone -- its text and what it depends on. `describe statement` alone stays a collection named `statement`'s description, and `describe statement x` was refused before, so no text that parsed reads otherwise. `GET /_schema` lists them beside the collections, and `?as=fenecql` writes their definitions after the collections.

**Declared in code.** `schema.fenecql` may hold `create statement`s (`fenec_ql::schema_text` reads them after the collections they name), and `declared::plan` compares each with the database's by its canonical tree, never its text -- a comment or a line break is no change -- in the order the migrations leave the schema, so a statement is planned against the collections as the pending migrations will have made them. A statement the database lacks is planned as its `create`; one whose tree differs as its `create or replace`, under the contract rule above (a contract change is reported as the `drop` and `create` it needs, a refusal with its resolution as every other change the plan cannot make alone) -- the one change the plan makes rather than refuses, since a statement holds no data and the code owns its API; one the database holds and the code no longer declares is reported, never dropped, as a collection the code does not declare is left alone. `Mode::Follow` holds them to be there and equal. `integrations/schema-golden.json` gains the cases.

**Limits error.** 64 statements a body, 32 parameters, 16 claims, a name of 59 bytes, 1 000 statements a database, a definition of 64 KB: each refused at definition, never cut ([crates.md](crates.md#limits)). The statements' own limits -- 512 levels of an expression, a `lookup` chain of 8, `in (get ...)` at 100 000 values and 4 levels, `near` and `match` at 10 000 rows -- hold in a body as anywhere.

## Calls

**A call is one block, its arguments values bound by place.** The arguments are checked against the signature where they arrive -- a missing or extra one, a null where none is taken, a value its type refuses: 400, naming it -- and read by each parameter's type as a document's field of that type reads a body's value (`parse_documents_json`: a `json` argument exact, a `vector<N>` its `f32`s, a timestamp from its text or milliseconds); then `check`; then the body runs as `execute_block` runs a `/batch`, every statement with the call's values: its writes land as one record, or none do, and a read in it sees the writes before it ([engine.md](engine.md#blocks)). Nothing is spliced: the body was parsed at definition, and a value is never text again.

**The answer is the last statement's**, as `/query` answers that statement -- the rows of a `get` or a `returning`, a write's count otherwise -- with `Fenec-Seq` and `Fenec-History`; the statements before it answer nothing. PostgreSQL's SQL functions return "the result of the last query in the list" ([SQL functions](https://www.postgresql.org/docs/current/xfunc-sql.html)); an answer of every statement, as `/batch` gives, would make each guard's rows part of the API.

**Guards, not branches.** FenecQL has no `if` and no loop, and a body gets none: a call holds the write lock for its whole block, so a body whose cost a value could make unbounded would stall every writer behind the single writer ([engine.md](engine.md#single-writer)). What branching an API needs is the block's all-or-nothing over guards: `require <n>` makes a statement's count a condition and puts the block back otherwise ([writes.md](writes.md#require)); a `get ... limit 1 require 1` is "this row exists", a `get` with `require 0` "it does not"; `check` holds the arguments; `insert ... if absent require 1` is "only the first time"; a `where` picks the rows a write applies to and `order ... limit` the one a claim takes. A `like` that counts each user once, over `create index on likes (post, user) @unique`:

```fenecql
create statement like($post int)
  claims (sub text)
as begin
  insert likes {post: $post, user: $jwt.sub} if absent require 1 else 'already liked';
  set posts {likes: likes + 1} where id = $post require 1 else 'no such post'
    returning id, likes
end
```

The statement depends on that unique index -- without it `if absent` would let a user like twice -- so dropping the index is refused while it stands.

**A guard may say why.** `require <n> else '<reason>'` -- a text literal of at most 200 bytes and no backtick, never a parameter, as `n` is never one -- puts the reason in the 412 beside `at`: `{"error": ..., "completed": 0, "at": 1, "reason": "insufficient funds"}`. An API's caller must tell "insufficient funds" from "no such account", and `at` alone made the body's order part of the API, which a statement added in front would shift. It is FenecQL's, not a call's, and lands first, in a slice of its own ([the plan](#the-plan-in-slices)): a `/batch` takes it, `render_batch_stop` and fenec-abi's error carry it beside `at`, every builder's `require` takes a `reason`, held to the golden file, every SDK's error has it, and the sync reports it with a write it puts back. `require 1 else` was refused before it ("unknown command `else`"), so no text that parsed reads otherwise. The shell needs no mark in `Parser::cut` for it: the parser reads `else` straight after the count, so nothing at the text's end is read two ways, and an `else` on the next line goes on with a write as any clause does. Built first, as slice 0 ([writes.md](writes.md#require)).

**Every call is a write, until a read-only executor exists.** Whether a statement writes is asked before the lock at a dozen places, and each chooses something a wrong answer breaks: which lock, whether a read-only server or a marked read refuses, whether a key is kept, whether a held write may wait, which path the native library and the module take. A call's answer to `is_read_only()` cannot come from its definition there, since a replacement may land between the question and the lock, and a body judged a read that writes under the read lock is a write with readers beside it. So `Statement::Call` answers `false` everywhere: every call takes the write lock, keeps an `Idempotency-Key`, is refused by a read-only server, a replica and a marked read, and is counted a write. A body of `get`s alone becomes a read only through an executor of its own, taking `&Database` -- which cannot write, by its type -- that reads the definition again under the read lock it holds and refuses a body that writes; with it come pins for long ones ([engine.md](engine.md#pinned-reads)), replicas and marked reads. The sites, on main as of `6bc5e277`, each held by a test that replaces the definition between its question and the lock:

| Where | What the answer chooses |
|---|---|
| fenec-http `lib.rs` 2314 | a lone statement's read path or write path |
| fenec-http `lib.rs` 2390-2454 | the `Idempotency-Key` kept, `--http-read-only`'s refusal, the hold, the lock taken |
| fenec-http `lib.rs` 2655 | a scoped read's own path |
| fenec-http `lib.rs` 2871-2881 | a `/batch`'s read-only refusal, its lock, whether it writes |
| fenec-http `handle_admitted` (1565) | a frozen tenant's or a lapsed lease's request run read-only |
| fenec-http `waits.rs` 417 | whether a statement may be held |
| fenec-http `mcp/tools.rs` 523, 1029, 1173 | the read-only server's refusal, the write tool's lock, the read tool's path |
| fenec-abi `lib.rs` 221 | a text's read path in the module and the native library |
| fenec-core `engine.rs` 6153-6420 | a block's start, its spill, a collation chunk's refusal, a lone statement's block |

**The definitions in a cell of their own.** The table of statements is an `Arc` of its own in `Database` -- as a collection's schema is (`SchemaCell`) -- so a server reads a definition under a short read lock for what it asks before the lock (its claims, whether it can be held), takes the write lock and runs only where the table is that very `Arc` (`Arc::ptr_eq`), reading it again otherwise, as a REST insert's early body is held to its schema ([engine.md](engine.md#prepared-blocks)); a definition changes the table by a new `Arc`, never in place. Its `put`s are `insert`s with documents in the text, so a call prepares beside the readers as a `/batch` does where they write `PREPARE_AT` documents or more.

**Bounded.** A call examines at most `--call-max-rows` rows (100 000 by default), counted where the scan and the indexes hand rows to its statements: past it the block is put back and the call refused as a query error naming the bound ([crates.md](crates.md#limits)), never answered from the rows it reached. With `scans` at definition, that bound and the write lock are what one call can cost every other writer. A call is held to `--call-rate` a second for its token's subject (`sub` and `iss`), the server's token unheld, answered 429 with `Retry-After` past it: a statement granted to every user is a write path every user can lean on, which the tenant's quota bounds in bytes and rows but not in time.

**Held, keyed and after.** `Fenec-Wait` holds a call as it holds a `/batch` ([waits.md](waits.md#fenec-wait)): a body with no `insert`, whose filters read the time only as `holdable` allows, can be held (`describe`'s `holdable`), its group planned from the body with the arguments and claims bound in (`waits::plan`), each look running `handle` whole -- token, grant and definition again; a replacement or a drop is a schema mark, which wakes every group (`wrote(None)`). A worker given `claim call` and nothing on `jobs` waits for a job with one held request:

```fenecql
create statement claim($queue text)
  claims (sub text)
as set jobs {owner: $jwt.sub, run_at: now() + 30000, attempts: attempts + 1}
   where queue = $queue and run_at <= now() order run_at limit 1
   returning id, payload
```

An `Idempotency-Key` makes a call once as it makes a write once ([http.md](http.md#idempotency-keys)): its block and the key's `_idempotency` row land together, the key the subject's for a scoped token, the request's hash over the path and body, so a retry after a replacement is answered what the first try answered -- the call was made once. `Fenec-After` makes it wait for a change first, as any request.

**Parsed once.** `POST /_call/<name>` parses nothing: the body's tree is the definition's, shared by every call, and run with the call's values where a scoped `/batch`'s statements are copied to have the scope ANDed in ([http.md](http.md#parse-cache)). `call transfer $1` over `/query` is a short text the parse cache keeps.

**Counted and traced by name.** `/_stats/statements` counts a call by the shape `call transfer $1`, whichever surface made it -- its arguments are one parameter -- never its body's statements apart: the call is the unit an operator tunes ([http.md](http.md#statement-counts)). The slow log's `statement` is that shape, its line naming the version; the trace's `db.query.text` is the shape and `db.stored_procedure.name` the name, OpenTelemetry's stable attribute for "the name of a stored procedure within the database" ([registry](https://opentelemetry.io/docs/specs/semconv/registry/attributes/db/)). `/_metrics` counts the route as `call`, never its name: a statement's name is the tenant's API, as a collection's name is the tenant's, and no label names those ([http.md](http.md#metrics)).

## Authority

**A call runs its statement's text with the statement's own authority, and nothing else.** The authority is the text, not a role: there is no owner whose rights a call borrows, so what a statement can do is what it says, fixed when it is defined, and its contract cannot change under a grant (above). A scoped token calls only what a `call` line grants it; its collection rules hold nothing in the body; the caller reaches the body only as the claims the statement declares.

**Granted by name, by role, and to no one by default.** A policy line `<statement>[, <statement> ...] call [for <role>]` grants calling, as every line grants by role:

```text
# statements        access   role
transfer            call     for customer
claim               call     for worker
transfer, refund    call     for teller
```

`call` stands alone on its line -- beside `read` or a `where` it is refused at startup: a grant is all or nothing, as PostgreSQL's `EXECUTE` privilege is. `* call` is refused, with or without a role: a statement defined later would be granted by a line no one reads again, and the policy is the one place that says what a token may do. A line naming a statement the database does not hold is logged as the server starts (on a tenant node, as each tenant opens) -- a typo grants nothing, silently, otherwise -- and so is one whose statement a `drop` took away. A statement a token is not granted is a 404 to it, the answer a statement no database holds gets, so a name tried says nothing -- as a collection no rule grants does not exist for a token ([access.md](access.md#scoped-tokens)). The server's token calls every one. `/_whoami` lists a token's `call` grants. A grant named in a JWT claim (`"calls": ["transfer"]`) was weighed and left: whoever mints tokens picks among the policy's lines by `role` already. So was a `where` on a grant over the arguments (`transfer call where $from in $jwt.accounts`): two places to read what a statement allows, where the statement's own `check` and `where`s are one; two roles with two bounds are two statements.

**Refused in one order.** A call is judged tenant, token, grant, existence, claims, arguments, `check`, each answered before the next is asked. The tenant and the token are `route_tenant`'s pair, as for every route below `/t/<t>/` ([access.md](access.md#tenant-binding)): the token verified (401, with the audit's wait) and held to the tenant it names (403) before the tenant is looked up, so neither says anything of the tenant's statements; the subject's rate is charged once the token is known. Then the grant before the statement is looked up, so an ungranted name and a missing one are the same 404 in the same time; the claims before the arguments, so a token that may never call it is told nothing of the signature's arguments; `check` last, over values already typed.

**The caller is its declared claims.** Each `$jwt.<claim>` a statement declares is bound from the verified token, read exact and held to its declared type; a list claim is spread after `in` and refused past `MAX_CLAIM_VALUES` as a policy's is. A claim the token does not carry, or carries as `null`, as an empty text or an empty list, or as a value of another type, is missing, and the call is refused (403), never run with that value in place: "a filter with a hole in it would match rows it was never meant to", as a policy rule naming a missing claim does not apply (`Access::scope`). Today's policy binding has the same hole for a claim present as `null` or `""` -- `Some(v)` binds it -- which a separate pull request closes there; a statement's binding is written closed from the start. The server's token carries none: it calls a statement reading claims with `as {sub: 'alice'}`, which a scoped token is refused (403) -- the server's token reads and writes everything already, so a call as another user gives it nothing new, and the shell, the studio's admin and a test need it. Convex's functions read `ctx.auth.getUserIdentity()` and Firebase's callable functions get `request.auth` the same way, the authorization written in the function ([Convex](https://docs.convex.dev/auth/functions-auth), [Firebase](https://firebase.google.com/docs/functions/callable)); here it is written in the `where`s and `check`.

**The one statement run outside `within()`.** `scoped()` is where a token meets a statement, and a `call` passes there: the grant asked, the claims bound into the call, `as` refused, and the `append-only` collections held -- a scoped token's call whose body updates or deletes in one is refused (403), since `append-only` takes updates and deletes from every scoped token whatever its rules say ([access.md](access.md#scoped-tokens)), and the server's token keeps corrections there. Then the body runs with no scope installed: the `Check` hook finds none, `fields::hold` and `fields::write` hold nothing, `Hook::answering` passes the answer. CLAUDE.md's "a scoped write run outside `within()` goes unchecked" is this path's point and must stay its only instance. So a scoped token's `/batch` holds no call beside its own statements, and in this first version no more than one call: the hook finds its scope through a thread-local set around the execution, and switching it inside one block is code in the engine, which knows nothing of scopes; and two calls in one block -- each refused by the other's guard, each holding the other's writes -- are a composition whose answers, `at`s and holds this version does not define. The server's token runs any `/batch`.

**The answer is the statement's, not masked by the caller's rules.** A leaderboard over scores no player may read, a balance by an account the caller owns, a job's payload a worker has no `read` on: the statement answers what it names, which is why it must name it. Masking it by the caller's field lists (`Scope::shown`) would make a call's answer depend on who called it -- the property it replaces -- and a statement wanting the caller's rows writes `owner = $jwt.sub` where it reads. Supabase warns that a `security definer` function "can return rows the caller isn't allowed to read" ([database functions](https://supabase.com/docs/guides/database/functions)); here that is the purpose, made safe by the named answer, the grant by name and the text being the whole authority.

**A refusal tells a scoped caller its kind, `at` and `reason` alone.** A body's error message names the collections, fields and values it met -- "document 3 holds `bob@x.io` already" -- which a token that may read none of them is told nothing of, as `access::told` keeps a `@unique` clash to the field. The status stays; the message is the server's, in the trace and, at `--slow-ms`, the slow line, under the request id.

**Bound to its tenant.** The policy and its `call` lines are the node's; the statements are the tenant's, in its file. A call reaches `/t/<t>/_call/<name>` only past `route_tenant`, and a tenant holding no `transfer` answers 404 to a token granted it.

**Audited where schemas are.** `create statement`, `create or replace statement` and `drop statement` are audit events by their shapes, as every `create` and `drop` is; a call is no event, as a write is none, but an MCP tool's (below) is a `mcp` line. Who called is the statement's to write -- `by: $jwt.sub` in the entry the transfer inserts -- which lands in the block, replicates and is restored with the money it moved, where a log line would be beside it.

**Against `SECURITY DEFINER`'s pitfalls.** PostgreSQL's manual and Supabase's guide name them; each has its answer here:

| PostgreSQL's pitfall | Here |
|---|---|
| `search_path`: "malicious users ... creating objects ... that mask objects intended to be used by the function", `pg_temp` searched first ([CREATE FUNCTION](https://www.postgresql.org/docs/current/sql-createfunction.html)) | One namespace a database, no schemas to search; names checked at definition and at each schema change's commit; only the server's token changes the schema |
| "execute privilege is granted to `PUBLIC` for newly created functions"; Supabase: "any role can call it by default, including `anon`" ([functions](https://supabase.com/docs/guides/database/functions)) | Granted to no scoped token until a line names it; `* call` refused; a 404 until then |
| The owner's privileges, which change after the function is written | No owner: the authority is the text; a replacement keeps the contract and is a logged schema change |
| Dynamic SQL built from arguments | None: parsed once; arguments are values by place; a name is never a parameter; no document an argument makes |
| String bodies parsed at their first run, "the form using string literals may leave dangling functions" | Parsed at definition, held by a digest of its tree; a schema change breaking one is refused at its commit. PostgreSQL's SQL-standard body stores the tree and follows a rename, which this, storing text, refuses -- no parity claimed |
| `SELECT *` gaining columns | The answer names its fields |

**Models weighed.** *Invoker* -- the caller's rules applied to the body, PostgreSQL's and Supabase's default -- gives no statement an authority of its own, the one thing asked; what it adds over sending the text to `/query`, a name and a typed signature, does not pay for a second model whose answers mean different things by caller. *The caller's scope intersected with the definer's* has a customer unable to credit another's account, the one write a transfer is. *A role declared per statement* (`as role ledger`) runs the body under a role's rules: two layers to read for what it may do, where the `where`s and `check` are one. *Definer, as the text, with declared claims* is the least surprising: what the statement does is what is written, every guard is in it, and the token it takes is in its signature.

## Surfaces

**`POST /_call/<name>`**, a body `{"params": {...}}` (none for no arguments), answers as `/query` answers the call's last statement. A path of its own, so a proxy, a firewall's rule or the router in front tells one call from another without reading a body, and an underscore's, as `/_mcp` and `/_schema` are, kept out of every collection's way: PostgREST prefixes `/rpc/` for the same reason, "to avoid route collisions with tables/views of the same name" ([PostgREST](https://docs.postgrest.org/en/stable/references/api/functions.html)). It translates to the `call` statement and runs where FenecQL runs, as every REST route does (`api::route`), and asks `answered_under_lease` as every route answering a write must ([tenants.md](tenants.md#scaling-out-by-tenant)). CORS lets it in as `/query`. GET for a read-only call (PostgREST's "if the function doesn't modify the database, it will also run under the GET method") was left: typed arguments in a query string are texts, and a read goes near by `Fenec-Read: replica` once the read-only executor exists. HTTP stays the one protocol: a call is a request, never an RPC wire of its own. In the order a call is judged:

| Answer | Status |
|---|---|
| no token, or one that does not verify | 401 |
| a token not bound to the tenant | 403, before the tenant is looked up |
| the subject past `--call-rate` | 429, `Retry-After` |
| a statement not granted to a scoped token, or none of that name | 404 |
| a claim the statement declares missing, null, empty or of another type; `as` from a scoped token | 403 |
| an argument missing, extra, null or of another type; `check` false; a scoped `/batch` holding a call beside anything else, or two calls | 400 |
| the body updating or deleting in an `append-only` collection for a scoped caller; a call on a replica, a read-only server or a marked read | 403 |
| a broken statement | 409, with why |
| `insert` over a held id, a `@unique` value taken | 409 |
| `require` unmet: `at`, `reason` | 412 |
| past `--call-max-rows` | 400, naming the bound |
| the `Idempotency-Key` with another request | 422 |
| an MCP answer past `--mcp-max-rows` or `--mcp-max-bytes`, put back | 413 |
| the tenant's quota | 507 |
| a lease lapsed | 500, `outcome: unknown` |
| a tenant closed, a ceiling: `retry_after` | 503 |
| `Fenec-After` not reached | 504 |
| answered | as `/query`: 200 |

**FenecQL: `call`.** `call transfer {from: 1, to: 2, amount: 300}` takes its arguments as a document, named; `call transfer $1` from a parameter's object, as `put <c> $n` takes documents; `as {sub: 'alice'}` after either, for the server's token. A command word that begins no statement today (refused as "unknown command `call`"), and one more of `TAKEN`, the words no alias takes. `Statement::Call { name, args, claims }` -- `args` a document, a parameter or SQL's positional list, matched to the signature by the engine, since the parser reads no schema. `Database::exactly` walks a call's arguments by its signature, a `json` one read as written.

**SQL: `CALL`, where the meaning holds.** `CALL transfer(1, 2, 300)`, and `name => value` for an argument by name (PostgreSQL's form, [CALL](https://www.postgresql.org/docs/current/sql-call.html)), are `call`: a stored routine run by name, which may write -- its answer the last statement's rows where PostgreSQL's is the output parameters' row, the one difference, in a column list nobody reads by position. `SELECT transfer(...)` and `SELECT * FROM transfer(...)` are refused naming `call`, without consuming the word: in SQL the first is a function's value in a row and the second a table, and a FROM names a collection here. `CREATE FUNCTION` and `CREATE PROCEDURE` are refused naming `create statement`: PostgreSQL's are `SECURITY INVOKER` unless told, so read as ours they would change who may do what -- the meaning the SQL-spellings rule keeps ([fenecql.md](fenecql.md#sql-spellings)).

**The SDKs.** `db.call('transfer', {from: 1, to: 2, amount: 300}, { idempotencyKey, wait, signal })` in JavaScript, answered as `run` is; Python's `db.call("transfer", {...}, idempotency_key=..., wait=...)`; Go's `db.Call(ctx, "transfer", fenec.Params{...})`; .NET's `CallAsync`; Swift's and Kotlin's `call`; Dart's `callStatement` -- a Dart instance method named `call` makes its object callable as a function and lets it be torn off where a `Function` is expected, which a database handle must not be, so Dart takes a name of its own, as it took `openSynced` beside `sync()`. Each sends `call <name> $1` with the arguments as `$1` -- the text a builder renders, held to `integrations/builder-golden.json` with a case for each parameter type, for `reason` and for `as` -- over `/query`, so the transport, the errors, the key and `wait` are what every SDK has. A `{ read: true }` call is marked for a read replica only once the read-only executor exists; until then the SDKs send none marked. `call` was chosen over `run`, which each SDK holds already for a text, and over `rpc`: FenecQL's word, SQL's `CALL`, the route, the grant and the method are one word. `fenec types` writes each statement's arguments, and its answer as far as it is typed, in every language it writes.

**MCP: a tool a statement.** With `--mcp`, each statement the token may call is a tool named `call_<name>`. MCP's own rule takes dots ([tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)), but the clients hand a tool's name on to a model's API, and Claude's takes `^[a-zA-Z0-9_-]{1,128}$` ([define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)) and OpenAI's function names `^[a-zA-Z0-9_-]{1,64}$`: no dot, and 64 characters at most, which `call_` and a 59-byte name fit. The tool's `description` is the statement's `comment`; its `inputSchema` the signature (`required` the parameters with no default, `additionalProperties: false`); its `outputSchema` the answer as `{"rows": [...]}`, its columns typed as `describe` types them; `readOnlyHint` and `destructiveHint` from what the body does. A writing statement is a tool only under `--mcp-write`, as every write tool is. A curated statement is the safest tool an operator can hand an agent: a model's arguments go in as values, never as text, the rule every tool keeps ([http.md](http.md#mcp)). The answer is held to `--mcp-max-rows` and `--mcp-max-bytes` before its block lands: past them a write is put back and the call refused (413), so a model is never told half an answer nor leaves a write it was not told of. `--mcp-calls-per-sec` holds them, and a writing one is a `mcp` audit line. fenecdb's MCP answers one JSON object and never streams, and declares `listChanged: false` as it does now: a client lists again.

**The studio** lists the statements in the schema view -- the server's token sees each definition, why one is broken, and its `/_schema/plan` as replaced; a scoped token the signatures it may call -- and a call form made from the signature, its inputs typed, answers in the grid; a call is sent under an `Idempotency-Key`, as the studio's writes are, written in `studio/statements*.js` under their rules: arguments as one parameter, the name as FenecQL writes one ([http.md](http.md#studio)). Two pieces of the studio read FenecQL's text themselves and must learn `begin ... end`: the editor's `splitStatements` (`statements-views.js` 26), which cuts at every `;` outside strings and comments and would send a definition's body as separate statements, and the highlighter, `site/highlight.js`, copied in by `make studio-highlight`, whose words gain `begin`, `end`, `call`, `statement`, `claims` and the markers.

**The shell** reads `call` as a write (`kind`: it waits for an empty line when typed over lines), `create`/`drop statement` as schema changes, `statements` and `describe statement` as reads. A body over lines needs no bracket of `lexer::Unclosed`: the parser refuses an unended `begin` at the text's end, which the shell reads as "go on". `call transfer` at a line's end is a mark in `Parser::cut` (its document may come on the next line) -- `require <n>`'s `else` needs none, read straight after the count; each form takes a line of `a_statement_written_over_lines_reads_as_one`'s corpus ([fenecql.md](fenecql.md#the-shell)).

## Replicas, sync, the router and upgrades

**A replica refuses a call until the read-only executor exists.** A call is a write at every site (above), so a follower, a read-only server and a marked read refuse it (403, `Error::ReadOnly`) before any of it runs. With the read-only executor, a follower answers a body of `get`s from the statements in its file, a marked read (`Fenec-Read: replica`) of one goes near through the router like any marked read ([read-replicas.md](read-replicas.md#marked-reads)), and a writing one is still 403.

**A sync replica refuses `call` and `create statement`, in both runners, from the slice that brings the syntax.** A sync replica holds its shapes, not its server's file, and none of its statements: its rows are a filtered part of the server's, so the transfer's credit would find no account the shape does not hold and its `require` would count the replica's rows -- the reason it already refuses a `get`'s `require` beside a synced write (`GUARDED`), a write reaching an unanswered insert's row (`REQUIRE_UNANSWERED`), a picked write (`PICKED`) and an upsert naming no key (`UPSERT_KEY`) ([writes.md](writes.md)). So in this first version a synced database refuses both by a code of their own, the native core and `FenecSync` alike, each a scenario of `integrations/sync-scenarios.json` before either runner changes ([native-and-sync.md](native-and-sync.md#sync-scenarios)); an app calls its server through its HTTP client, and what the call wrote reaches the replica through the shapes' streams as any server write does. Forwarding a call from the replica is [a follow-up](#forwarding-calls-from-a-sync-replica).

**The router forwards a call, and parses a tenant's schema.** `/t/<tenant>/_call/<name>` is a tenant path, forwarded as bytes; as a `POST` it is sent again only where `replayable` allows -- keyed ([router.md](router.md#pooled-connections)). The global entry passes it as any `/t/<tenant>/` path. But "the router parses no FenecQL" holds for requests, not for a tenant's creation: `PUT /_shard/tenants/<t> {schema}` reads the schema text before anything is placed (fenec-shard's `create`, through `fenec_http::admin::schema_description`, `lib.rs` 4716), so a schema holding `create statement` needs a router that knows the grammar, and a router from before refuses it as a schema that does not read (400) -- loudly, with nothing placed. A query across tenants is read-only on every node, so it refuses a call until the read-only executor, and a writing one after.

**Upgrades go one way, readers first.** A binary from before refuses record kind 13 and a block holding one, so the first `create statement` on a primary stops every reader of its file that is older: a replica following its stream, an archiver writing it, a node a tenant is moved or restored to, a standby a failover would promote. The order, written into RELEASING.md's notes for the release and `deploy/RUNBOOK.md`'s *Upgrading with no downtime*: archivers, then every node -- each replica and standby, each node a move or a restore may target -- then the routers (for the schema text), and only then may any primary define a statement. The runbook says already that files go one way and an older node may not follow a newer stream; this is the first feature whose first use, not its install, moves the format, so the release notes name the statement that does. A test drives the order: an archiver and a replica built without the kind meet the record and stop with a refusal in words, never a misread.

## The browser module and embedded

**The record is core in every build; defining and calling are measured, and refused in the shipped module unless they fit the budget.** A file a server wrote opens in a page (`openFile`) and in an app, and a build must open every file and keep what it holds through its compacts ([browser-module.md](browser-module.md#language-features)), so every build keeps the record -- reads it, writes it again in its images, applies it from a replica, lists its name, version and whether it is broken -- with no parser of its own needed: a build that cannot parse a statement keeps its text as it came, and a schema change touching what its `depends` names marks it broken, as an internal writer does (the holder of the file holds everything; the server that opens the file again refuses its calls until redefined). Defining and calling -- the signature's parse and typing, the checks, the dependency checks at commit, the plan's comparison, the call's typing and its refusal texts, `describe`'s JSON -- the review estimates at 6-9 KB brotli of the module, above the first draft's 3.5-5, which left out the refusal texts, the dependency checks, the plan and `describe`; for scale, upserts grew the module 1.3 KB brotli, picked writes 1.9, an `alter` 4.0 ([writes.md](writes.md), [fenecql.md](fenecql.md#alter-collection)). Measured in their slice (`make wasm-sizes`, `make size-report`), they ship in the module only within the budget [the owner sets](#decisions-for-the-owner); otherwise the module refuses `call` and `create statement` with words of their own ("named statements are a server's; this module is built without them"), and an embedder needing them uses the native library or a server.

**How the code leaves the module, not merely a feature inside `full`.** The module ships "with every feature" ([browser-module.md](browser-module.md#index-features)), and a crate using fenec-core names `full`, so a feature `full` turned on would still ship. Defining and calling are a fenec-core and fenec-ql feature, `statements`, that `full` does not include: `fenec-http`, `fenec-ffi`, `fenec-cli` and `fenec-server` name it, `fenec-wasm` and the module's `make wasm` do not, `fenec-abi` names it only in its dev-dependencies (its calls pass `Statement::Call` to the engine and hold no code of their own), and `off.rs` refuses a call by name in a build without it (`not_built`). `make wasm-sizes` reports it in its table beside the index features. A Durable Object running the module then has no calls -- the one use the first draft made the module's case on -- until the budget lets them in.

**The embedded API** is a statement, not an export: `call transfer $1` through `Database::execute_with` and `fenec_query`, so no C ABI, no JNI entry and no `fenec.h` line is new. `Database::call(name, args, claims)` is the engine's path the statement runs (arguments by name or place, claims the values of the declared claims). The native SDKs' local `call` (Swift's and Kotlin's `call`, Dart's `callStatement`) take `claims` -- the embedder's `as` -- since an app may call a statement reading `$jwt.sub` with its signed-in user, held to the declared types as a token's are. `Fenec-Wait` is a server's: `wait` on a local call is refused (`LOCAL_WAIT`), as on any local write.

## What it does not do

No user code: no JavaScript, WASM or Lua in the engine. Every crate but `fenec-bench` has zero dependencies ([crates.md](crates.md#zero-dependencies)), and an interpreter of its own would be the largest code and attack surface the server holds, under a write lock a single writer shares with every client. No loops or branches (above); no network calls -- a call holds the write lock, and a wait on a socket under it stalls every writer, which is why Convex's mutations "must be deterministic, and cannot call third party APIs" ([mutations](https://docs.convex.dev/functions/mutation-functions)); no variables carrying one statement's result into the next; no schedule. An API needing a statement's result in the next takes a key from its caller -- a `@unique` text the client makes, which the statements after the `insert` find the row by -- until a follow-up binds results to names. Four follow-ups would reuse the definition machinery -- the record, the checks, the authority as the text, the surfaces -- each a proposal of its own.

**F2, write-bound statements.** A statement bound to the writes of a collection, `after set orders where new.status = 'paid'`, run in the block of the write that matched it with that row as `new.` and `old.`: derived rows -- a counter, a ledger line, a denormalized field -- kept with the write that made them, PostgreSQL's trigger without its language and PocketBase's `onRecordAfterUpdateSuccess` without its JavaScript. It inherits the danger PostgreSQL's CVE-2020-25695 and CVE-2022-1552 are: code with one authority run by another's action -- there, functions and triggers a user created, run with a superuser's identity by `ANALYZE`, `REINDEX`, `CREATE INDEX`, `VACUUM FULL`, autovacuum or a restore, "an attacker having permission to create non-temp objects in at least one schema could execute arbitrary SQL functions under a superuser identity" ([CVE-2020-25695](https://www.postgresql.org/support/security/CVE-2020-25695/), [CVE-2022-1552](https://www.postgresql.org/support/security/CVE-2022-1552/)). Here a bound statement would run with its own authority when a scoped token writes, and when the server's own writers -- the sweeper, a migration, `--follow`'s mirror, a restore -- write. It owes: definition by the server's token alone, as every statement; never run by an internal writer (a replica's apply, a load, a restore, a compact, the sweeper replays nothing, since the record holds what the statement wrote); a depth of one (its writes bind nothing further); a bound on the rows one write may wake; the plugin `Hook` as the place it runs; and a sync replica that does not run it optimistically but receives what it wrote through its streams.

**F3, scheduled statements.** `create statement purge() public every 1h as del sessions where seen < now() - 86400000`, run by the primary alone as `@ttl`'s sweeper is -- never a replica, a following tenant or the browser ([indexes.md](indexes.md#ttl)) -- each run a block keyed by its slot, so a failover between a run and its answer runs it once; one behind its schedule runs once, not once a slot missed; held to the tenant's quota and `--call-max-rows`, its time out of the slow log as a held write's is. It owes the clock it reads (`now()` folded once a run), a last-run record that replicates, and the router knowing nothing of it.

**F4, webhook consumers.** An inbound endpoint, `POST /_hooks/<name>`, verified by a signature its sender makes -- an HMAC of the body under a secret, as Stripe and GitHub sign theirs -- and bound to a statement's parameters from the body, keyed by the event's id so a sender's retries land once. The secret is the policy's or a key file's, never the database's, so an archive holds no credential; the statement is a named statement with an authority of its own, its caller the sender, its claims none (`public`).

### Forwarding calls from a sync replica

A later version may let a synced database's `call` go to its server rather than refuse it. Three things the first draft passed over make it a proposal of its own. *When it settles*: the call's promise would settle once the replica holds what it wrote, but a call's writes are known by the collections its body writes, not by a seq a shape is sure to pass -- a body writing a collection no shape follows moves no stream -- so it settles by the shapes over the collections the definition says it writes, each past the answer's `Fenec-Seq`, and at once where none is followed. *Its place in the queue*: sent after the writes made before it, a call is a barrier in `_sync_queue` -- the writes after it wait for its answer, since one may read what it wrote -- which the queue, a line of independent writes each with its undo, does not have. *The native path*: `fenec_query` returns a native write once kept, where a call has nothing to keep and must wait for its server, so the native core needs an asynchronous action and answer it does not have (`fenec_sync_feed`'s actions are the binding's to perform, its writes answered at once). Each is a scenario first, both runners.

**Also left:** live calls -- a read-only call as a live query (`FenecHttp.live` polls a text by its content tag already, and `call board $1` is one) -- needs the read-only executor and the collections a call reads named to the client; `if absent else set` and `put` in a body, where the key or the id is the statement's own; `insert <c> $n` with the documents' fields fixed by the statement; a scoped `/batch` of several calls; a parameter's type named after a field (`$amount accounts.balance`, PostgreSQL's `%TYPE`); the answer's type inference.

## What is built

**Slice 1, the parser and the tree.** Every form of this proposal reads into its tree: `create [or replace] statement` with its signature, claims, markers, `comment` and `check`, a body of one statement or `begin ... end`; `drop statement [if exists]`, `statements`, `describe statement <name>`; `call` with a document, a parameter or SQL's list, and `as`. The tree is `fenec_core::named` -- `Definition`, `Param`, `Claim`, `Call`, `Args` -- and the body's refusals that need nothing but its text (`Definition::refused`: a `put`, a parameter's documents, `else set`, a `set` or `del` with neither `where` nor a pick, a schema change, `compact`, `call`, a `_` collection, an answer naming no fields, a writing body reading no claim and not `public`) are answered as the definition is read, each at the statement it is about. `$name` and `$jwt.<claim>` are `Tok::Named`, numbered by the definition's parser (`Parser::named`) and refused outside one; the rest of the language reads as on main.

*Nothing runs one.* `Statement::is_named` is asked before a block opens (`execute_block`, `execute_with`), so a `/batch` holding a `call` behind a `put` lands nothing; `query` refuses them too; `scoped()` refuses a `call` before it asks a rule of the token (a definition and a drop are schema changes, refused to a scoped token as ever); MCP's `write` refuses a `call`. Each answers `NOT_BUILT`, "named statements are not built yet", a query error (400), its words a client tells it by. `statements` answers no row and `describe statement` 404, for every token. A sync replica meets the same refusal -- the native core passes the statement to the engine, FenecSync runs on the module, which reads none -- until slice 3 gives each runner its own code and scenario.

*The module.* Named statements are a feature, `statements`, of fenec-core (the variants of `Statement` and `fenec_core::named`, and the engine's answers) and of fenec-ql (their parse, turning on fenec-core's), outside `full`. fenec-ql takes it by default, and the workspace's dependency without: fenec-http, fenec-cli and fenec-ffi name it (fenec-server and fenec-shard through fenec-http), fenec-abi in its dev-dependencies alone, and fenec-wasm does not. The module refuses `create [or replace] statement`, `drop statement`, `statements`, `call` and a `$` before a letter (`$a`) in words of their own, "named statements are a server's; this module is built without them", before anything of the text runs, and reads `describe statement x` and SQL's routines as main did (`web/fenec.test.js`). The tree's variants were core in the first cut and cost the module 1 807 bytes brotli (6 385 raw) refusing all of it -- `Statement`'s drop glue, the engine's arms, the parser's refusals of what only a server reads -- and gated 481 raw bytes, gzip and brotli within their noise (`make size-report BASE=origin/main`): the dispatch of the five refusals, the lexer's of `$from`, the parser's one field. Slice 2's record is core in every build, with the code that keeps it; defining and calling stay in the feature. Turned on in the module, slice 1's parse alone weighs 28.6 KB raw and 8 668 bytes brotli -- the parse of the signature and body, `Definition::refused`, the canonical encoder and their words -- against the 3 KB brotli budget suggested for all of defining and calling ([the owner's decision 5](#decisions-for-the-owner)): it stays out. The server pays for them: `fenec-server`'s code is 39.2 KB more, 3 076.6 KB to 3 115.8 (fenec-ql 16.9, fenec-core 13.5, `core`'s formatting 8.1), its build 62 KB of 5 298 (`make size-report BIN=fenec-server`, on main and the branch).

*Parse time.* The parse of the repository's texts that are no definition -- 8 909 of the corpus below, `parse` alone, 40 rounds, the median of nine runs -- took 1 305-1 310 ns a text on the branch against 1 303-1 306 on main, in turns, the feature off 1 306-1 312: as main's. The first cut measured 1.6% slower: the definition's paths inline in the lexer's loop, `primary`, `put`'s documents and a `get`'s collection weighed on texts holding none, and each went out of line, `#[cold]`.

*Size and stack.* Each variant past a select's size is boxed (`CreateStatement(Box<Definition>)`, `Call(Box<Call>)`): a `Statement` is 968 bytes on main and on the branch, a `Select`'s 960 and its tag, held by `a_statement_is_as_large_as_a_select`. 511 parentheses in a body or a `check` parse within the stack 511 take at the top -- 1 011 KiB in release, 7 282 KiB in a debug build against 7 266 -- a definition's frames above its body's statement a few; 512 are refused as at the top.

*The digest and the epoch.* `Definition::canonical` writes the tree as tagged fields, each written only where it holds something -- so a field added to the tree later leaves every stored digest as it was (`a_field_that_holds_nothing_is_not_written`) -- and `digest` hashes it; `replace` and `block`, how a definition was written rather than what it means, are left out, and so is every literal's spelling but its bits (`0.0` and `-0.0` apart). A guard's reason is a field of its own beside its count, and an operator, `CmpOp`'s and `ArithOp`'s, is a byte of its own (`cmp_byte`, `arith_byte`), never its variant's place, so an enum reordered or grown moves no digest. `fenec_ql::GRAMMAR_EPOCH` is 1; the transfer's digest is pinned in `the_digest_holds_the_tree_not_the_text`, so a change of the encoding fails there and raises the epoch with it.

*The corpus.* `make fenecql-corpus BASE=origin/main` (`tools/fenecql_corpus.py`, `crates/fenec-ql/examples/corpus.rs`) harvests every FenecQL text the repository tracks -- the docs' blocks and inline code, the golden files and the sync's scenarios, the string literals of every SDK's sources and the crates' -- and parses each with `parse` and `parse_exact` in this tree and in BASE's, comparing the trees' `Debug` forms. Against main: 9 122 texts, 18 244 parses, no tree changed and none that parsed refused; 68 parse that were refused (this branch's own texts and docs, the design's examples, and two that were never FenecQL, a .NET example's "Call mom" and the studio's label `Statements`), and 190 are refused in other words. The texts reworded are those `$` and a letter, `select f(...)` with no `from` and `call` reached: `$LIMIT` in a template is now refused as a named parameter rather than as no number, and `select count(*) where ...`, its collection left out, is told both readings, `select count(...) from <collection>` and `call count(...)`.

*The words.* `call` and `statements` begin statements and reserve no word: SQL reserves neither (PostgreSQL's `CALL` is a word any alias takes), so they are not in `COMMANDS`, the words no alias may be, but in `NAMED_COMMANDS`, the words no named statement's name may be. `select a from t call`, `select a call from t`, `select count(*) statements from t`, `select c.a, call.b from t c join calls call on call.id = c.id` and `select a from t statements` read as on main, in the module too. At the text's end a `call` with no name after it is not consumed, so `select a call` with `from t` to come is one statement, not a `get` and a `call`; a SQL statement followed by a `call` takes a `;` between them, as in PostgreSQL.

*The shell.* `call` is a write in fenec-cli's `kind`, `drop statement` and a `begin ... end` definition schema changes, `statements` and `describe statement` reads, a definition of one statement a write, since its `where` may come on the next line. An unended `begin` is refused at the text's end, which the shell reads as "go on", with no bracket of `lexer::Unclosed`; `call <name>` at a line's end is a mark in `Parser::cut`, its document on the next line, and so is `describe statement`, the collection `statement`'s description alone and a named statement's with a name after it: the reading says so (`Reading::open`), and the shell holds it for the next line where it would run a read at Enter. Not every mark holds a statement: most are left by a reading tried and dropped -- `get notes count` tries SQL's list first -- and a read the next line may go on with runs at Enter all the same; each form is a line of `a_statement_written_over_lines_reads_as_one`'s corpus, and `tests/shell.rs` types and pipes a definition over lines.

> **[A named statement is a record of its database, checked against its schema and marked broken rather than failing an open.](docs/design/named-statements.md#definitions)** `create statement` writes record kind 13, a write `writes_in` counts, undone in a block (`Undo::Statement`), kept by every image with its grammar epoch and its tree's digest, and applied by a replica; its version is `(history, change)`. >

## Decisions for the owner

1. **Where a definition lives.** *Recommended: in the database file*, a record of kind 13, replicated, archived, moved and restored with the data and checked against its schema; a tenant's statements are its own. The alternative, the server's policy file, is one API for every tenant of a node and goes unchecked when a schema changes.
2. **Whose authority a call runs under.** *Recommended: the statement's text, with typed declared claims* -- granted by name, no default grant, claims missing when null, empty or mistyped, the one statement outside `within()`. The alternatives -- the caller's rules (invoker), their intersection with the statement's, a role per statement -- each leave a transfer unable to do what it is for or put a second layer between the reader and what a statement may do.
3. **A replacement that changes the contract** -- whether it writes, the claims it reads, the fields it answers. *Recommended: refused, written as `drop` and `create`*, so no grant starts meaning more without a line of the policy changing, and the `drop` leaves every grant naming it logged. The alternative: allowed, logged as an audit event of its own, which keeps a statement's name and grants through such a change and asks operators to read the log.
4. **Sync replicas in the first version.** *Recommended: `call` and `create statement` refused in both runners*, from the slice that brings the syntax; the app calls its server over HTTP and the streams bring back what the call wrote. The alternative, forwarding from the replica, needs settling by the collections a body writes, a barrier in the queue and an asynchronous native path ([above](#forwarding-calls-from-a-sync-replica)), each a scenario of its own.
5. **The browser module.** *Recommended: the record in every build; defining and calling in a `statements` feature outside `full`, refused in the shipped module unless measured within a budget the owner sets* -- 3 KB brotli is suggested, against the review's 6-9 KB estimate, which would keep them out of the module for now. The alternatives: core in every build, which pays 6-9 KB for every page and gives a Durable Object calls; or never in the module.
