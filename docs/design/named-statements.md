# Named statements (proposal)

**Status: proposal.** Nothing here is built. No invariant in [CLAUDE.md](../../CLAUDE.md) holds it yet, and no code, test or bench exists for it; the figures below are quoted from the design notes they cite, and the ones this would owe are named with the bench that would take them. Once it is built, each section's rule moves into CLAUDE.md in a few sentences (the drafts are in [the plan](#the-plan-in-slices)) and this file becomes its long form, as the others are.

A named statement is a FenecQL statement, or a block of them, defined once in a database and called by name with typed arguments: `create statement transfer($from int, $to int, $amount int) as begin ... end`, then `POST /call/transfer` with `{"params": {...}}`, `call transfer {...}` in FenecQL or `db.call('transfer', {...})` in every SDK. Its authority is its own: a token may be granted `transfer call` with no write rule on the collections it touches. It is fenecdb's answer to PostgreSQL functions used as an API (`SECURITY DEFINER` and PostgREST's `/rpc/`, Supabase's `rpc()`), Convex's mutations and queries and Firebase's callable functions -- without running user code: the body is FenecQL, parsed once, bounded by the limits every statement has, and run as one block under the single writer.

What it answers. Under a scoped token today the policy is the API: a ledger's app token needs `update(balance)` on `accounts` to move money, and nothing in the policy can say "only as one debit and one credit of the same amount, from an account you own". `require <n>` made a transfer's `/batch` safe against the race ([writes.md](writes.md#require)), but a client holding the grant can still send the debit alone or the credit alone. Transitions ([access.md](access.md#scoped-tokens)) say which way a row may move, never which rows must move together. So an app that wants an operation rather than a grant runs a server of its own in front of fenecdb -- the code fenecdb exists to spare it. A named statement is that operation, kept in the database beside the data it moves.

## Definitions

**A named statement is a record of its database, defined by its text, parsed once and checked against the schema it reads.** `create statement` writes a record of its own kind (13, `REC_STATEMENT`), a write moving the change counter by one; it rides in a block, is undone by a variant of its own (`Undo::Statement`), is kept by every image and applied by a replica as a schema record is; its version is the change it was defined at. A schema change that would break a defined statement is refused, naming it.

```fenecql
create statement transfer($from int, $to int, $amount int)
  comment 'Moves an amount from an account the caller owns to another'
  check $amount > 0 and $from != $to
as begin
  get accounts select id where id = $from and owner = $jwt.sub
    limit 1 require 1 else 'not your account';
  set accounts {balance: balance - $amount} where id = $from and balance >= $amount
    require 1 else 'insufficient funds';
  set accounts {balance: balance + $amount} where id = $to
    require 1 else 'no such account';
  insert entries {from: $from, to: $to, amount: $amount, by: $jwt.sub, at: now()}
    returning id, at
end
```

Each statement of that body runs today through the shell as written, literals in place of the parameters, but for `else '<reason>'` (below).

**The signature.** A name as a collection's is written (a namespace of its own: a statement and a collection may share one), then its parameters, each `$name` and a type the schema's types name -- `bool`, `int`, `float`, `text`, `bytes`, `timestamp`, `json`, `geo`, `vector<N>`, `sparse<N>`, `[T]` -- read by the parser's `data_type`, so a parameter's type is a field's. A parameter is required and never null unless it is given a default, a literal (`$n int = 10`, `$note text = null`). `check <expr>` is a condition over the parameters, the caller's claims and `now()` alone -- a field named in it is refused at definition -- asked once before the call takes any lock: a negative amount is a 400 naming the check, never a debit that found the money. `comment '<text>'` is what `describe`, the MCP tool and generated types say of it. At most 32 parameters.

**The body** is one statement, or `begin` and statements cut by `;` to `end` -- PostgreSQL's SQL-standard `BEGIN ATOMIC ... END` body, which [its manual](https://www.postgresql.org/docs/current/sql-createfunction.html) says "is parsed at function definition time" and "tracks dependencies between the function and objects used in the function body". It holds `get` (and SQL's `select`), `put`, `insert`, `set` and `del` alone, at most 64 of them: no schema change (that authority is the server token's, and a statement granting it would hand it to every caller), no `compact`, no `call` (no recursion to bound, and a body is read whole where it is defined). A `set` or a `del` with neither `where` nor a pick is refused -- `where true` says it is meant, as REST's `PATCH /<name>/all` does -- since a call any granted token makes would otherwise empty a collection. A body names none of the server's own collections (`_idempotency`, the sync's `_sync_*`, `_migrations`), which would let a call forge a replayed answer. A name is never a parameter in FenecQL, so a call cannot be pointed at another collection: the trap PostgreSQL's dynamic SQL (`EXECUTE format(...)`) sets has no way in.

**Parameters are names in the text and places in the tree.** The lexer reads `$` followed by a letter as a name (`Tok::Named`) -- `$` and anything but a digit is refused today, so no text that parsed reads otherwise -- and the definition's parser numbers them: the declared parameters first in the signature's order, then each `$jwt.<claim>` the body reads in the order it first appears, so the body is the same `Expr::Param`s every statement holds and the engine's every path takes it unchanged. `$1` in a body is the first declared parameter, PostgreSQL's "older numeric approach" ([SQL functions](https://www.postgresql.org/docs/current/xfunc-sql.html)). A named parameter outside a definition is refused ("`$from` names a named statement's parameter; a statement sent alone numbers them, `$1`"); a policy keeps reading `$jwt.<claim>` as it does.

**The answer names its fields.** The body's last statement is what a call answers (below), and it names every field it answers: a `get` has a `select` list, `returning` names its fields, a `lookup` level its own, and `*`, or a `get` with no list, is refused at definition. Run with an authority of its own, a `select *` would start answering a field added to the collection after it was defined -- a `password_hash` -- through every call already granted; PostgreSQL's views expand `*` once, at creation: "columns added later to the table will not be part of the view" ([CREATE VIEW](https://www.postgresql.org/docs/current/sql-createview.html)). Refused rather than expanded, so the text shown is the answer given. The last statement's fields and their types are known at definition, which is what `describe`, MCP's `outputSchema` and `fenec types` read.

**Checked at definition, and at every schema change.** The body passes the checks every statement passes before it reads a row -- names against the schema (`Flat::names`, `path_of`), `check`, `check_counts`, `check_order`, `check_subquery`, a `lookup`'s child key indexed, `fits_block` -- against the schema as it stands under the write lock that defines it. Then wherever the schema changes -- `alter`, `drop collection`, a field dropped or renamed, an index a `lookup` reads taken off, `declared::plan`'s apply -- the statements naming that collection (each keeps the collections it reads and writes) are checked against the schema the change would leave, and the change is refused naming the first that would break ("statement `transfer` reads `accounts.balance`: replace or drop it first"), as PostgreSQL refuses `DROP` over a dependent view without `CASCADE`. A rename is refused too: a statement's text is never rewritten for it, as `declared::plan` never guesses one. In a block the checks run statement by statement, so `drop statement transfer; alter collection accounts drop field balance; create statement transfer ...` lands as one change. Late binding was the alternative -- PL/pgSQL's bodies are strings parsed at their first run -- and a deploy that renamed a field would have broken an API at its next call rather than at the deploy.

**Stored as its text.** The record is `[13][0][length][op][version][name][text]`, `op` a definition or a drop, the text the definition's own bytes from `create` to its end (`spans`), comments and all: FenecQL has no binary form of a tree, and its text is the stable form, held so by the corpus every grammar change is parsed against ([fenecql.md](fenecql.md#sql-spellings): 7 620 texts, none parsed to another tree). An open parses each definition against the schema the load left; one a later binary's parser refuses -- which the corpus rule exists to prevent -- or one whose body uses a feature the build was made without is kept, listed with its error, and a call is answered that error as its text would be: an open never fails on a statement, since an API's definition must not hold the data hostage. A binary from before refuses kind 13, as the file format requires of a new kind ([storage.md](storage.md#file-format)), and so a block holding one.

**Replicated, archived, compacted.** The record goes through `wal` and moves the counter by one (`writes_in`), so a replica's counter stays the primary's write for write ([replication.md](replication.md#replication)) and applies it as it applies an alter, checking nothing more than the parse; a promotion, a tenant's move, a restore and a read replica carry the statements in the file. An image writes the live definitions after the collections, each with its version, so a compact keeps them as they were. `/_changes` passes over the record as over a schema record that names no collection's rows -- the cursor moves past it and no row is told -- and a sync replica's stream does too: the server owns its statements, and remaking collections for it would reseed every shape.

**Versions.** `create statement` refuses a name held (409); `create or replace statement` replaces it, `drop statement [if exists]` drops it, each a schema change: refused to a scoped token, logged by the audit as every `create`/`drop` shape is ([http.md](http.md#audit)). A statement's version is the change it was defined at (`Fenec-Seq` of its definition): unique, rising, carried in its record through compaction, and the place an archive's restore names, so `version: 48213` says both which text ran and where the archive holds it -- a counter of its own would be a second number to keep. Every version is in the archive; the file holds the live one. A call runs the definition it finds under the lock it runs under, and a replacement lands under the write lock, so a call runs one version whole. Two versions callable side by side (`transfer@2`) were weighed and left: a change that breaks callers is a new name, `transfer_v2`, as an HTTP API's is.

**Listing and describing.** `statements` lists them, as `collections` lists collections; `describe statement transfer` answers its name, version, parameters with their types and defaults, the claims it reads, its `check`, `comment`, whether it writes and whether it can be held (`Fenec-Wait`, below), the fields and types it answers, and -- to the server's token alone -- its text and the collections it reads and writes. `describe statement` alone stays a collection named `statement`'s description, and `describe statement x` was refused before, so no text that parsed reads otherwise. `GET /_schema` lists them beside the collections, and `?as=fenecql` writes their definitions after the collections.

**Declared in code.** `schema.fenecql` may hold `create statement`s (`fenec_ql::schema_text` reads them after the collections they name), and `declared::plan` plans a statement the database lacks as its `create` and one whose text differs as its `create or replace` -- the one change it plans rather than refuses, since a statement holds no data and the code owns its API; one the database holds and the code does not is left alone, as a collection is. `Mode::Follow` holds them to be there and equal. `integrations/schema-golden.json` gains the cases.

**Limits error.** 64 statements a body, 32 parameters, 1 000 statements a database, a definition of 64 KB: each refused at definition, never cut ([crates.md](crates.md#limits)). The statements' own limits -- 512 levels of an expression, a `lookup` chain of 8, `in (get ...)` at 100 000 values and 4 levels, `near` and `match` at 10 000 rows -- hold in a body as anywhere.

## Calls

**A call is one block, its arguments values bound by place.** The arguments are checked against the signature where they arrive -- a missing or extra one, a null where none is taken, a value its type refuses: 400, naming it -- and read by each parameter's type as a document's field of that type reads a body's value (`parse_documents_json`: a `json` argument exact, a `vector<N>` its `f32`s, a timestamp from its text or milliseconds); then `check`, then the body runs as `execute_block` runs a `/batch`, every statement with the call's values: its writes land as one record, or none do, and a read in it sees the writes before it ([engine.md](engine.md#blocks)). Nothing is spliced: the body was parsed at definition, and a value is never text again.

**The answer is the last statement's**, as `/query` answers that statement -- the rows of a `get` or a `returning`, a write's count otherwise -- with `Fenec-Seq` and `Fenec-History`; the statements before it answer nothing. PostgreSQL's SQL functions return "the result of the last query in the list" ([SQL functions](https://www.postgresql.org/docs/current/xfunc-sql.html)); an answer of every statement, as `/batch` gives, would make each guard's rows part of the API.

**Guards, not branches.** FenecQL has no `if` and no loop, and a body gets none: a call holds the write lock for its whole block (a read-only one the read lock, or a pin), so a body whose cost a value could make unbounded would stall every writer behind the single writer ([engine.md](engine.md#single-writer)). What branching an API needs is the block's all-or-nothing over guards: `require <n>` makes a statement's count a condition and puts the block back otherwise ([writes.md](writes.md#require)); a `get ... limit 1 require 1` is "this row exists", a `get` with `require 0` "it does not"; `check` holds the arguments; `put ... if absent require 1` is "only the first time"; `if absent else set` is the upsert; a `where` picks the rows a write applies to and `order ... limit` the one a claim takes. A `like` that counts each user once, over `create index on likes (post, user) @unique`:

```fenecql
create statement like($post int)
as begin
  insert likes {post: $post, user: $jwt.sub} if absent require 1 else 'already liked';
  set posts {likes: likes + 1} where id = $post require 1 else 'no such post'
    returning id, likes
end
```

**A guard may say why.** `require <n> else '<reason>'` -- a text literal, never a parameter, as `n` is never one -- puts the reason in the 412 beside `at`: `{"error": ..., "status": 412, "at": 1, "reason": "insufficient funds"}`. An API's caller must tell "insufficient funds" from "no such account", and `at` alone made the body's order part of the API, which a statement added in front would shift. It is FenecQL's, not a call's: a `/batch` takes it too, every builder's `require` option a `reason` beside it, held to the golden file. `require 1 else` is refused today ("unknown command `else`"), so no text that parsed reads otherwise; the shell owes a mark in `Parser::cut` after `require <n>`, since an `else` on the next line goes on with it.

**Read-only calls read.** A body of `get`s alone is a read: it runs under the read lock as a read-only `/batch` does, at one change, pinned when its statements read `PIN_AT` rows or more by their shape and declined otherwise ([engine.md](engine.md#pinned-reads)), and a replica, a read-only server and a marked read answer it. A body that writes takes the write lock, and its `put`s of `PREPARE_AT` documents or more are built beside the readers against the definition's schema `Arc`s ([engine.md](engine.md#prepared-blocks)). Whether it writes is the body's, shown by `describe`: a keyword saying so (Convex's `query` and `mutation`) would be a second statement of a fact the parser knows, and a replacement that starts writing is refused loudly wherever a read was asked for (403).

**Lookups beside the lock.** A server reads the definition (an `Arc`) under a short read lock -- for its claims, whether it writes, whether it can be held -- then takes the lock it needs and runs it only where the database holds that very definition (`Arc::ptr_eq`), reading it again otherwise, as a REST insert's early body is held to its schema ([engine.md](engine.md#prepared-blocks)).

**Held, keyed and after.** `Fenec-Wait` holds a call as it holds a `/batch` ([waits.md](waits.md#fenec-wait)): a body with no `put`, whose filters read the time only as `holdable` allows, can be held (`describe`'s `holdable`), its group planned from the body with the arguments and claims bound in (`waits::plan`), each look running `handle` whole, token, grant and definition again -- a replacement or a drop is a schema mark, which wakes every group (`wrote(None)`). A worker given `claim call` and nothing on `jobs` waits for a job with one held request:

```fenecql
create statement claim($queue text)
as set jobs {owner: $jwt.sub, run_at: now() + 30000, attempts: attempts + 1}
   where queue = $queue and run_at <= now() order run_at limit 1
   returning id, payload
```

An `Idempotency-Key` makes a call once as it makes a write once ([http.md](http.md#idempotency-keys)): its block and the key's `_idempotency` row land together, the key the subject's for a scoped token, the request's hash over the path and body, so a retry after a replacement is answered what the first try answered -- the call was made once. `Fenec-After` makes it wait for a change first, as any request.

**Parsed once.** `POST /call/<name>` parses nothing: the body's tree is the definition's, shared by every call, and run with the call's values where a scoped `/batch`'s statements are copied to have the scope ANDed in ([http.md](http.md#parse-cache)). `call transfer $1` over `/query` is a short text the parse cache keeps.

**Counted and traced by name.** `/_stats/statements` counts a call by the shape `call transfer $1`, whichever surface made it -- its arguments are one parameter -- never its body's statements apart: the call is the unit an operator tunes, and a body's statements counted under the API's traffic would double it ([http.md](http.md#statement-counts)). The slow log's `statement` is that shape, its line naming the version; the trace's `db.query.text` is the shape and `db.stored_procedure.name` the name, OpenTelemetry's stable attribute for "the name of a stored procedure within the database" ([registry](https://opentelemetry.io/docs/specs/semconv/registry/attributes/db/)). `/_metrics` counts the route as `call`, never its name: a statement's name is the tenant's API, as a collection's name is the tenant's, and no label names those ([http.md](http.md#metrics)).

## Authority

**A call runs its statement's text with the statement's own authority, and nothing else.** The authority is the text, not a role: there is no owner whose rights a call borrows, so what a statement can do is what it says, fixed when it is defined; a replacement is a schema change, the server token's, logged. A scoped token calls only what a `call` rule grants it; its collection rules hold nothing in the body; the caller reaches the body only as the claims it reads.

**Granted by the policy, by role, and to no one by default.** A policy line `<statement|*> call [for <role>]` grants calling, as every line grants by role:

```text
# statement    access   role
transfer       call     for customer
claim          call     for worker
*              call     for teller
```

`call` stands alone on its line -- beside `read` or a `where` it is refused at startup: a name is a collection's or a statement's on a line, and a grant is all or nothing, as PostgreSQL's `EXECUTE` privilege is. A statement a token is not granted is a 404 to it, the answer a statement no database holds gets, so a name tried says nothing -- as a collection no rule grants does not exist for a token ([access.md](access.md#scoped-tokens)). The server's token calls every one. `/_whoami` lists a token's `call` grants. A grant named in a JWT claim (`"calls": ["transfer"]`) was weighed and left: the policy is the one place that says what any token may do, and whoever mints tokens picks among its lines by `role` already. So was a `where` on a grant over the arguments (`transfer call where $from in $jwt.accounts`): two places to read what a statement allows, where the statement's own `check` and `where`s are one; two roles with two bounds are two statements.

**The caller is its claims.** `$jwt.<claim>` in a body is bound from the verified token -- read exact, a list claim spread after `in` and refused past `MAX_CLAIM_VALUES` as a policy's is -- and a token carrying none of a claim the statement reads is refused (403), not run with a null there: "a filter with a hole in it would match rows it was never meant to", as a policy rule naming a missing claim does not apply (`Access::scope`). The claims a statement reads are part of its signature, which `describe` shows. The server's token carries none: it calls a statement reading claims with `as {sub: 'alice'}`, which a scoped token is refused (403) -- the server's token reads and writes everything already, so a call as another user gives it nothing new, and the shell, the studio's admin and a test need it. Convex's functions read `ctx.auth.getUserIdentity()` and Firebase's callable functions get `request.auth` the same way, the authorization written in the function ([Convex](https://docs.convex.dev/auth/functions-auth), [Firebase](https://firebase.google.com/docs/functions/callable)); here it is written in the `where`s and `check`.

**The one statement run outside `within()`.** `scoped()` is where a token meets a statement, and a `call` passes there: the grant asked, the claims bound into the call, `as` refused, and the `append-only` collections held -- a scoped token's call whose body updates or deletes in one is refused (403), since `append-only` takes updates and deletes from every scoped token whatever its rules say ([access.md](access.md#scoped-tokens)), and the server's token keeps corrections there. Then the body runs with no scope installed: the `Check` hook finds none, `fields::hold` and `fields::write` hold nothing, `Hook::answering` passes the answer. CLAUDE.md's "a scoped write run outside `within()` goes unchecked" is this path's point and must stay its only instance. So a `/batch` holding a call holds calls alone for a scoped token (400 otherwise): the hook finds its scope through a thread-local set around the execution, and switching it statement by statement inside one block is code in the engine, which knows nothing of scopes, for a mix nothing needs -- two calls in one block, the composition that matters, stay one block. The server's token mixes freely.

**The answer is the statement's, not masked by the caller's rules.** A leaderboard over scores no player may read, a balance by an account the caller owns, a job's payload a worker has no `read` on: the statement answers what it names, which is why it must name it. Masking it by the caller's field lists (`Scope::shown`) would make a call's answer depend on who called it -- the property it replaces -- and a statement wanting the caller's rows writes `owner = $jwt.sub` where it reads. Supabase warns that a `security definer` function "can return rows the caller isn't allowed to read" ([database functions](https://supabase.com/docs/guides/database/functions)); here that is the purpose, made safe by the named answer, the default deny and the text being the whole authority.

**A refusal tells a scoped caller its kind, `at` and `reason` alone.** A body's error message names the collections, fields and values it met -- "document 3 holds `bob@x.io` already" -- which a token that may read none of them is told nothing of, as `access::told` keeps a `@unique` clash to the field. The status stays; the message is the server's, in the trace and, at `--slow-ms`, the slow line, under the request id.

**Bound to its tenant.** The policy and its `call` lines are the node's; the statements are the tenant's, in its file. A call reaches `/t/<t>/call/<name>` only past `route_tenant`'s check of the token's tenant claim ([access.md](access.md#tenant-binding)), and a tenant holding no `transfer` answers 404 to a token granted it.

**Audited where schemas are.** `create statement`, `create or replace statement` and `drop statement` are audit events by their shapes, as every `create` and `drop` is; a call is no event, as a write is none, but an MCP tool's (below) is a `mcp` line. Who called is the statement's to write -- `by: $jwt.sub` in the entry the transfer inserts -- which lands in the block, replicates and is restored with the money it moved, where a log line would be beside it.

**Against `SECURITY DEFINER`'s pitfalls.** PostgreSQL's manual and Supabase's guide name them; each has its answer here:

| PostgreSQL's pitfall | Here |
|---|---|
| `search_path`: "malicious users ... creating objects ... that mask objects intended to be used by the function", `pg_temp` searched first ([CREATE FUNCTION](https://www.postgresql.org/docs/current/sql-createfunction.html)) | One namespace a database, no schemas to search; names checked at definition and at every schema change; only the server's token changes the schema |
| "execute privilege is granted to `PUBLIC` for newly created functions"; Supabase: "any role can call it by default, including `anon`" | Granted to no scoped token until a `call` line names it, and a 404 until then |
| The owner's privileges, which change after the function is written | No owner: the authority is the text; a replacement is a logged schema change |
| Dynamic SQL built from arguments | None: parsed once; arguments are values by place; a name is never a parameter |
| String bodies parsed at their first run, "may leave dangling functions" | Parsed at definition; a schema change that would break one is refused |
| `SELECT *` gaining columns | The answer names its fields |
| Error messages from inside | A scoped caller is told the kind, `at` and `reason` |

**Models weighed.** *Invoker* -- the caller's rules applied to the body, PostgreSQL's and Supabase's default -- gives no statement an authority of its own, the one thing asked; what it adds over sending the text to `/query`, a name and a typed signature, does not pay for a second model whose answers mean different things by caller. *The caller's scope intersected with the definer's* has a customer unable to credit another's account, the one write a transfer is. *A role declared per statement* (`as role ledger`) runs the body under a role's rules: two layers to read for what it may do, where the `where`s and `check` are one. *Definer, as the text* is the least surprising: what the statement does is what is written, and every guard is in it.

## Surfaces

**`POST /call/<name>`**, a body `{"params": {...}}` (none for no arguments), answers as `/query` answers the call's last statement. A path of its own -- a proxy, a firewall's rule or the router in front tells one call from another without reading a body -- prefixed as PostgREST's `/rpc/` is, "to avoid route collisions with tables/views of the same name" ([PostgREST](https://docs.postgrest.org/en/stable/references/api/functions.html)): a collection named `call` loses `POST /call/near` over REST, as one named `query` or `batch` cannot be inserted into over it, and keeps it through FenecQL. It translates to the `call` statement and runs where FenecQL runs, as every REST route does (`api::route`), and asks `answered_under_lease` as every route answering a write must ([tenants.md](tenants.md#scaling-out-by-tenant)). CORS lets it in as `/query`. GET for a read-only call (PostgREST's "if the function doesn't modify the database, it will also run under the GET method") was left: typed arguments in a query string are texts, and a read already goes near by `Fenec-Read: replica`. HTTP stays the one protocol: a call is a request, never an RPC wire of its own.

| Answer | Status |
|---|---|
| answered | as `/query`: 200 |
| no such statement, or one not granted to a scoped token | 404 |
| an argument missing, extra, null or of another type; `check` false; a scoped `/batch` mixing a call with other statements | 400 |
| a claim the statement reads missing from the token; `as` from a scoped token; a scoped call updating or deleting in an `append-only` collection; a writing call on a replica, a read-only server or a marked read | 403 |
| `insert` over a held id, a `@unique` value taken | 409 |
| `require` unmet: `at`, `reason` | 412 |
| the `Idempotency-Key` with another request | 422 |
| an MCP answer past `--mcp-max-rows` or `--mcp-max-bytes`, put back | 413 |
| the tenant's quota | 507 |
| a lease lapsed | 500, `outcome: unknown` |
| a tenant closed, a ceiling: `retry_after` | 503 |
| `Fenec-After` not reached | 504 |

**FenecQL: `call`.** `call transfer {from: 1, to: 2, amount: 300}` takes its arguments as a document, named; `call transfer $1` from a parameter's object, as `put <c> $n` takes documents; `as {sub: 'alice'}` after either, for the server's token. A command word that begins no statement today (refused as "unknown command `call`"), and one more of `TAKEN`, the words no alias takes. `Statement::Call { name, args, claims }` -- `args` a document, a parameter or SQL's positional list, matched to the signature by the engine, since the parser reads no schema. `Database::exactly` walks a call's arguments by its signature, a `json` one read as written.

**SQL: `CALL`, where the meaning holds.** `CALL transfer(1, 2, 300)`, and `name => value` for an argument by name (PostgreSQL's form, [CALL](https://www.postgresql.org/docs/current/sql-call.html)), are `call`: a stored routine run by name, which may write -- its answer the last statement's rows where PostgreSQL's is the output parameters' row, the one difference, in a column list nobody reads by position. `SELECT transfer(...)` and `SELECT * FROM transfer(...)` are refused naming `call`, without consuming the word: in SQL the first is a function's value in a row and the second a table, and a FROM names a collection here. `CREATE FUNCTION` and `CREATE PROCEDURE` are refused naming `create statement`: PostgreSQL's are `SECURITY INVOKER` unless told, so read as ours they would change who may do what -- the meaning the SQL-spellings rule keeps ([fenecql.md](fenecql.md#sql-spellings)).

**The SDKs: `call`.** `db.call('transfer', {from: 1, to: 2, amount: 300}, { idempotencyKey, wait, signal, read })` in JavaScript, answered as `run` is; Python's `db.call("transfer", {...}, idempotency_key=..., wait=...)`; Go's `db.Call(ctx, "transfer", fenec.Params{...})`; .NET's `CallAsync`; Swift's, Kotlin's and Dart's `call`. Each sends `call <name> $1` with the arguments as `$1` -- the text a builder renders, held to `integrations/builder-golden.json` with a case for each parameter type, for `reason` and for `as` -- over `/query`, so the transport, the errors, the key, `wait` and `read` are what every SDK has. `{ read: true }` marks it for a read replica as `run`'s does; a writing statement so marked is refused (403), nothing run, since the client cannot know what the body does. `call` was chosen over `run`, which each SDK holds already for a text, and over `rpc`: FenecQL's word, SQL's `CALL`, the route, the grant and the method are one word. Dart's instance method named `call` makes a `Fenec` callable as a function, which the SDK slice weighs against a name of its own, as `openSynced` was weighed beside `sync()`. A builder's batch takes calls (`toCall`), held to the rule above. `fenec types` writes each statement's arguments and answer as types and a wrapper a statement in every language it writes.

**MCP: a tool a statement.** With `--mcp`, each statement the token may call is a tool, `call.<name>` -- MCP's names take "uppercase and lowercase ASCII letters ..., digits, underscore, hyphen, and dot" ([tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)), and the prefix keeps them from `schema`, `query` and `write` -- its `description` the statement's `comment`, its `inputSchema` the signature (`required` the parameters with no default, `additionalProperties: false`), its `outputSchema` the named answer as `{"rows": [...]}`, and `readOnlyHint` and `destructiveHint` from what the body does. A writing statement is a tool only under `--mcp-write`, as every write tool is. A curated statement is the safest tool an operator can hand an agent: a model's arguments go in as values, never as text, the rule every tool keeps ([http.md](http.md#mcp)). The answer is held to `--mcp-max-rows` and `--mcp-max-bytes` before its block lands: past them a write is put back and the call refused (413), so a model is never told half an answer nor leaves a write it was not told of. `--mcp-calls-per-sec` holds them, and a writing one is a `mcp` audit line. fenecdb's MCP answers one JSON object and never streams, and declares `listChanged: false` as it does now: a client lists again.

**The studio** lists the statements in the schema view -- the server's token sees each definition and its `/_schema/plan` as replaced, a scoped token the signatures it may call -- and a call form made from the signature, its inputs typed, answers in the grid; a write is the call under an `Idempotency-Key`, as the studio's writes are, written in `studio/statements*.js` under their rules: arguments as one parameter, the name as FenecQL writes one ([http.md](http.md#studio)).

**The shell** reads `call` as a write (`kind`: it waits for an empty line when typed over lines, since whether a body writes is the database's to say), `create`/`drop statement` as schema changes, `statements` and `describe statement` as reads. A body over lines needs no bracket of `lexer::Unclosed`: the parser refuses an unended `begin` at the text's end, which the shell reads as "go on". `call transfer` at a line's end is a mark in `Parser::cut` (its document may come on the next line), as is `require <n>` (its `else`); each form takes a line of `a_statement_written_over_lines_reads_as_one`'s corpus ([fenecql.md](fenecql.md#the-shell)).

## Replicas, sync and the router

**A read replica answers a read-only call; a sync replica sends a call to its server.** A follower holds the statements in its file and refuses writes (`Error::ReadOnly`), so a read-only call is answered there and a writing one is 403 before any of it runs; a marked read (`Fenec-Read: replica`) of a call goes near through the router like any marked read, run read-only on every route ([read-replicas.md](read-replicas.md#marked-reads)).

A sync replica holds its shapes, not its server's file, and none of its statements, and runs none: its rows are a filtered part of the server's, so the transfer's credit would find no account the shape does not hold and its `require` would count the replica's rows -- the reason it refuses a `get`'s `require` beside a synced write (`GUARDED`), a write's reaching an unanswered insert's row (`REQUIRE_UNANSWERED`), a picked write (`PICKED`) and an upsert naming no key (`UPSERT_KEY`) ([writes.md](writes.md)). So `call` on a synced database goes to the server, behind the writes queued before it -- sent once each was answered, so it reads what the app wrote -- applies nothing locally and stores nothing: its promise settles with the server's answer once the shapes' streams have passed the answer's `Fenec-Seq`, so a read of the replica after it sees what the call wrote, as an unshaped insert's temporary row waits for that seq. Offline it fails at once (status 0) rather than queue: a call is asked for its answer, and one replayed after a restart with no caller left to tell would move the server's state unseen. A synced database refuses `create statement` (its server's statements are the server's). A queued call -- an outbox, kept in `_sync_queue` and answered when sent -- is a follow-up, not this. Each behaviour is a scenario of `integrations/sync-scenarios.json` first: a call answered and its writes streamed back, a call behind a queued write, a call offline, a call refused with its `reason`, `create statement` refused; both runners run them ([native-and-sync.md](native-and-sync.md#sync-scenarios)).

**The router forwards it.** `/t/<tenant>/call/<name>` is a tenant path, forwarded as bytes, its FenecQL never parsed ([tenants.md](tenants.md#scaling-out-by-tenant)); as a `POST` it is sent again only where `replayable` allows -- keyed, or marked read ([router.md](router.md#pooled-connections)). The global entry passes it as any `/t/<tenant>/` path. A query across tenants, read-only on every node, holds a read-only call as any read and refuses a writing one there. A tenant created through the router takes `create statement`s in its schema text, applied on the node as the rest is.

## The browser module and embedded

**Core, in every build, the call path behind a feature if it costs more than it was estimated at.** A file a server wrote opens in a page (`openFile`) and in an app, and a build must open every file and keep what it holds through its compacts ([browser-module.md](browser-module.md#language-features)): the record, its image and its undo are needed in every build whatever else is. Defining and calling are core too. PostgreSQL's functions, MySQL's procedures and SQL Server's are what an app moving off one looks for (SQLite, the nearest embedded database, has none, and a page could call its own JavaScript), but the reason that decides it is that the module serves too: a Durable Object running it is a server, and a Worker that verified its user's token calls `db.call('transfer', params, { claims: { sub } })` in the module as a node runs it, the same statement and the same answer. The authority -- grants, verification, `scoped()` -- is fenec-http's and none of it reaches the module, which has no tokens: the page holding the file holds everything.

**What it costs.** Estimated from the features nearest it in the design notes, to be measured by `make wasm-sizes` and `make size-report`: upserts grew the module 5.0 KB, 1.3 brotli, picked writes 5.2 and 1.9, an `alter`'s reading and writing 12.2 and 4.0, `limit $n` 2.3 and 0.8 ([writes.md](writes.md), [fenecql.md](fenecql.md)). The parser's forms -- the signature, `$name`, `begin ... end`, `check`, `comment`, `call` in three spellings, `require ... else`, the refusals -- are about upserts' and `limit $n`'s together; the record, the image, the undo, the checks at a schema change and the call's typing about an `alter`'s writing half: some 11-16 KB, 3.5-5 KB brotli. Past 5 KB brotli measured, defining and calling go behind a feature (`statements`), the record kept in every build (`off.rs` refusing a call by name, `not_built`). Natively `fenec-server`, `fenec-shard` (which parses nothing new and grows by nothing but the route's name) and the shell are measured as each feature is.

**The embedded API** is a statement, not an export: `call transfer $1` through `Database::execute_with`, `fenec_query` and the module's `run`, so no C ABI, no JNI entry and no `fenec.h` line is new. `Database::call(name, args, claims)` is the engine's path the statement runs (args by name or place, claims the values of the `$jwt` places). JS `Fenec.call`, Swift's, Kotlin's and Dart's local `call` take `{ claims }` -- the embedder's `as` -- since an app may call a statement reading `$jwt.sub` with its signed-in user. `Fenec-Wait` is a server's: `wait` on a local call is refused (`LOCAL_WAIT`), as on any local write.

## What it does not do

No user code: no JavaScript, WASM or Lua in the engine. Every crate but `fenec-bench` has zero dependencies ([crates.md](crates.md#zero-dependencies)), and an interpreter of its own would be the largest code and attack surface the server holds, under a write lock a single writer shares with every client. No loops or branches (above), no network calls -- a call holds the write lock, and a wait on a socket under it stalls every writer, which is why Convex's mutations "must be deterministic, and cannot call third party APIs" ([mutations](https://docs.convex.dev/functions/mutation-functions)) -- no variables carrying one statement's result into the next, and no schedule. An API needing a statement's result in the next takes a key from its caller (a `@unique` text the client makes, `put <c> $docs` and an `in (get ...)` over it), until a follow-up binds results to names. Three follow-ups, F2 to F4, would reuse the definition machinery -- the record, the checks, the authority as the text, the surfaces -- each a proposal of its own:

**F2, write-bound statements.** A statement bound to the writes of a collection, `after set orders where new.status = 'paid'`, run in the block of the write that matched it with that row as `new.` and `old.`: derived rows -- a counter, a ledger line, a denormalized field -- kept with the write that made them, PostgreSQL's trigger without its language and PocketBase's `onRecordAfterUpdateSuccess` without its JavaScript. It owes a depth of one (its writes bind nothing further), a bound on the rows one write may wake, the plugin `Hook` as the place it runs, and a sync replica that does not run it optimistically but receives what it wrote through its streams.

**F3, scheduled statements.** `create statement purge() every 1h as del sessions where seen < now() - 86400000`, run by the primary alone as `@ttl`'s sweeper is -- never a replica, a following tenant or the browser ([indexes.md](indexes.md#ttl)) -- each run a block keyed by its slot, so a failover between a run and its answer runs it once; one behind its schedule runs once, not once a slot missed; held to the tenant's quota, its time out of the slow log as a held write's is. It owes the clock it reads (`now()` folded once a run), a last-run record that replicates, and the router knowing nothing of it.

**F4, webhook consumers.** An inbound endpoint, `POST /hooks/<name>`, verified by a signature its sender makes -- an HMAC of the body under a secret, as Stripe and GitHub sign theirs -- and bound to a statement's parameters from the body, keyed by the event's id so a sender's retries land once. The secret is the policy's or a key file's, never the database's, so an archive holds no credential; the statement is a named statement with an authority of its own, its caller the sender.

**Also left:** live calls -- a read-only call as a live query (`FenecHttp.live` polls a text by its content tag already, and `call board $1` is one) -- needs the collections a call reads named to the client for its streams; an outbox of calls on a sync replica (above); a parameter's type named after a field (`$amount accounts.balance`, PostgreSQL's `%TYPE`).

## The plan in slices

Each slice is a pull request of its own, green and measured, its docs in it ([CLAUDE.md](../../CLAUDE.md)'s conventions). A slice that adds a statement form or a status says so where a user looks in the same pull request.

**1. The parser and the tree** (fenec-ql, fenec-core's `query`). `create [or replace] statement`, the signature, `$name` and `$jwt.<claim>` numbered inside a definition and refused outside, `check`, `comment`, `begin ... end`, `drop statement`, `statements`, `describe statement`, `call` in its three forms with `as`, `require <n> else '<reason>'`, SQL's `CALL` and the three refusals; the boxed `Statement::CreateStatement`, `DropStatement`, `ListStatements`, `DescribeStatement` and `Call` (a `Statement` is as large as its largest variant). Owes: the corpus of every FenecQL text the repository holds parsed on main and the branch, no tree changed ([fenecql.md](fenecql.md#sql-spellings)); fenec-cli's `kind`, `Parser::cut`'s two marks, the shell corpus' lines; the refusals not consuming their word; `TAKEN`; the stack of 511 parentheses measured; `make wasm-sizes`.

**2. Storage and replication** (fenec-core). The statements' table in `Database`, record kind 13 alone and inside a block, `Undo::Statement`, the image, the load's parse with an error kept, `apply` on a replica, `writes_in`, `changes_in` passing over it, the checks at definition and at every schema change, `declared::plan` and `schema_text`. Tests: a torn tail, a block put back with a definition in it, a compact keeping versions, a replica's counter equal to its primary's, a restore to a change between two versions, a binary refusing kind 13 (a fixture), `tests/language.fenec` with a statement (`FENEC_WRITE_FIXTURE=1`), every schema change refused over a statement that would break, `schema-golden.json`'s cases. Owes the file format, blocks, replication and declared-schema invariants their new sentences; `make opens-bench` with 1 000 statements.

**3. Calls and authority** (fenec-core's call, fenec-http's `access`). `Database::call`, the arguments' typing, `check`, the last statement's answer, `reason` in `Unmet` and in `render_batch_stop`; `scoped()` taking a `Call` -- the grant, the claims, `as`, `append-only` -- the run outside `within()`, a scoped `/batch` of calls alone, `told` for a call's errors, the policy's `call` lines refused beside anything else, `/_whoami`. Tests in a file of their own (`tests/calls.rs`): a token holding `transfer call` alone moves money it could not move with `/batch` (403 there); eight clients' transfers keep the sum as `tests/require.rs` does; an ungranted statement's 404 the same as a missing one's; a missing claim 403; `as` from a scoped token 403; an `append-only` delete 403; an unfiltered `del` and `select *` refused at definition; field lists not masking a call's answer; a scoped caller's error told; each attack failing with its part taken out. Benches: `make policy-bench` gains a call beside the scoped `/batch` of the same writes; `make requests-bench` unchanged for everything else.

**4. HTTP and the router** (fenec-http, fenec-shard). `POST /call/<name>`, its statuses, `answered_under_lease`, CORS, the `Idempotency-Key`, `Fenec-Wait` (`holdable` and `waits::plan` over a body), a marked read, `/_metrics`' route, the statement shape, `db.stored_procedure.name`, the slow line. The router changes no code: a test sends a keyed call through it once after a dropped connection and an unkeyed one never twice, and a marked read-only call near. Owes `make shard-bench ARGS=latency` inside its spread.

**5. The SDKs and the golden files** (`web/`, `integrations/`). `call` in seven SDKs, the builder's `call` and `toCall` and `require`'s `reason` held to `builder-golden.json` (`make builder-golden`), `fenec.d.ts` (`make types-check`), `fenec types`' wrappers in `types-golden/`, and the sync's scenarios in the scenario file first, both runners (`make sync-scenarios-check`).

**6. The studio, MCP and the shell.** The schema view's statements and the call form (`transport.test.mjs` holding a call's answers to a server's), the `call.<name>` tools (`integrations/mcp` against the official client in both eras, the bound checked before the block lands), the shell's `.help`. Owes `make studio-test` and `make mcp-test`.

**7. The docs.** A reference page, `site/content/docs/named-statements.html`, linked from `fenecql-writing.html`, `http-access.html` (the `call` lines), `http-reference.html` (the route and its statuses), `sql.html` (`CALL` and the refusals), `mcp.html` and `sync.html`; README's feature table; the SDK lists of `languages.html`, `mobile.html`, `sharding.html` and `integrations.html`; the home page, since a visitor choosing between fenecdb and Supabase or Convex picks by it; the site search cache's vectors.

**What CLAUDE.md would gain**, a section *Named statements* after *Writes*, each rule linking here:

> **[A named statement is a record of its database, parsed once and checked against its schema.](docs/design/named-statements.md#definitions)** `create statement` writes record kind 13, a write moving the counter by one (`writes_in`), undone in a block (`Undo::Statement`), kept by every image and applied by a replica as a schema record is; its version is the change it was defined at. A body holds `get`, `put`, `set` and `del` alone -- no schema change, no `call`, no unfiltered write -- and its last statement names the fields it answers; a schema change that would break a statement is refused naming it, and an open never fails on one.
>
> **[A call runs its statement's text with the statement's own authority.](docs/design/named-statements.md#authority)** `scoped()` passes a `call` only where a policy's `call` line grants it (404 otherwise, as a statement no database holds), binds its `$jwt.<claim>`s from the token (403 where one is missing) and refuses `as` and an `append-only` update or delete; it is the one statement run outside `within()`, never in a block beside a scoped token's own statements, and a scoped caller is told a refusal's kind, `at` and `reason` alone.
>
> **[A call is one block, its arguments values.](docs/design/named-statements.md#calls)** Arguments are checked against the signature where they arrive (400) and bound by place, never spliced; `check` runs before any lock; the answer is the last statement's; `Fenec-Wait`, an `Idempotency-Key` and a marked read take a call as they take a `/batch`. A sync replica sends a call to its server behind its queue and applies none of it.
>
> **[Every surface names a call alike.](docs/design/named-statements.md#surfaces)** `POST /call/<name>`, FenecQL's `call`, SQL's `CALL` and every SDK's `call`, held to the golden file; MCP's `call.<name>` tools, a writing one under `--mcp-write` and an answer past the bounds put back; counted as the shape `call <name> $1`, traced with `db.stored_procedure.name`, and no metric label names one.

And *Declared schemas*' "plans additions alone" becomes "plans additions, and a statement's replacement".

## What it would measure

No figure above is this feature's own.
